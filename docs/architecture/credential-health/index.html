How a key earns a bench

A provider holding several keys has to answer two independent questions about one failure: should another key be tried, and does this failure cost the credential anything? MCC answers each from its own allow-list, rather than from one deny-list that defaults to blaming the key.

Question one: try another key?

Only three failures justify a different credential: an auth rejection, a 429 and a transport fault. A different credential means a different account or a different connection, so one of them might help. Nothing else does. Every key in the pool reaches the same model and would meet the same timeout, 5xx, 410 or 400, so those raise out of the rotating loop and the fallback chain moves on to the next model instead.

Credentials already tried in a request are passed to the pool as an avoid set, so rotation cannot end with keys untried. The timeout class is excluded by name, because a model that never answered is not a broken socket and spending the whole pool on it would be a self-inflicted outage.

Question two: what does it cost the credential?

Only the three signals that describe the credential charge it. A 401 or 403 walks an escalating lockout ladder: five minutes, one hour, one day by default, one step per consecutive rejection, staying at the last entry. A 429 is benched for exactly the wait the provider published, or for the configured cooldown when it published none, under the operator's ceiling. That bench is scoped to the (key, model) pair, and it leaves the slot healthy, because a gateway that limits one model has made no statement about the key's other models.

An exhausted-credit refusal is different. Where the provider says in words that the account behind the key has no balance left, the whole key is benched for the cooldown window, because a wallet is not per model. The matcher reads only the provider's own structured words, through an echo-safe reader, so a prompt that happens to contain a billing phrase cannot bench a key. A bare 402 that names no phrase rotates and falls through but charges nothing.

The key itself is benched only once a configured number of distinct models hold a live bench on it at the same time, for the longest window already published and never less than the triggering 429 asked for. No ladder and no escalation beyond that one step are invented.

Rotate the pool, or route around the model?

Not every 429 should rotate. When route-around is on, the pool reports the failure, decides health as usual, and then raises a typed model-rate-limited signal. The executor moves to the next chain model on that same provider, because that is where the evidence points: on one measured request all three keys refused one model inside 0.2 seconds each while another model answered on the first key in the same second. With no such model on the chain, one bounded diagnostic probe on a model the operator already configured there decides whether to keep the scoped bench or promote it to the whole key.

The probe's clock belongs to the executor; the pool holds none of its own. That deliberate cost is that a key failing 5xx or transport on every request is retried once per request rather than benched, because the failure classes that could identify a dead key were the same ones emptying healthy pools.

One mechanism, two tunings

The rotation engine exists once, in core, and each frontend parameterises it. The provider tuning reaches neither the generic cooldown ladder nor the circuit breaker, because a provider adapter never classifies a failure as transient. The web-search tuning keeps both, because a search key that keeps erroring is worth resting. No half-open probe state remains: a slot reserved on acquire used to outlive a request that reported neither success nor failure, leaving the key unselectable until reset by hand, so a credential now wakes straight to healthy at the cost of at most one extra failed request.

Per-key attribution

Every request records which key answered, and the key is shown by name where a name exists and by a mask where it does not. The Analytics key filter still matches a renamed key's history by its mask, and the exports carry both the mask and the name. A masked label two keys share resolves to no name at all rather than to a guess.

Limits and behaviour

  • A country refusal is about the address, not the key: it never locks a key out on any route.
  • The pool never invents a ceiling: a wait comes from the provider's own headers or the configured window.
  • A key's health is decided before the response is committed and is visible in the request log afterwards.
  • Rotation changes which key is tried, never which model a route points at.
