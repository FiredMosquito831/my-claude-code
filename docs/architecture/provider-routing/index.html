From a tier name to one real model

The router answers one question: which concrete provider model serves this request, with which reasoning preference, and what happens if it cannot. It is deliberately small, and the rules it follows are the product's contract.

Three ways to name a model

Resolution takes three forms. A direct provider model ref names the provider and the exact model. A gateway model ID is decoded by the gateway-ID codec. The five tier aliases are intercepted ahead of both, and are pointers rather than models. If the incoming name is not direct, the router maps it by Claude tier: a name containing fable, opus, sonnet or haiku uses the matching tier override when set, and otherwise falls back to the default model.

The router also selects the reasoning preference. A direct ref uses the root policy; a Claude tier route uses a non-inherited tier override or the root fallback; the no-thinking gateway variant forces off. The application layer combines that preference with the concrete client request exactly once, and the resulting plan owns both the selected route and the final request-scoped policy.

What the picker is told

The model-listing route advertises configured provider refs, cached provider-discovered models, no-thinking variants where appropriate, and built-in Claude model IDs for compatibility. A discovered model's thinking support is used for presentation only; it never selects request behaviour. A per-client picker is shaped outside the route: the composition bridge builds catalogue records from the same ladder, using the same visibility filter and projection, so a model cannot appear in one surface and not the other, and it writes each harness's catalogue without making a loopback HTTP request.

One consequence is worth stating because it is visible: a catalogue is a snapshot. The Codex App reads its catalogue at startup, so it must restart to see a later publication, and the Codex launcher remains a launch-time synchroniser for the same reason. An existing last-known-good catalogue is preserved when a projection resolves no routable models.

Aliases are pointers

The protocol names mcc/cyber, mcc/best, mcc/good, mcc/medium, mcc/cheap and mcc/vision serve harnesses that have no Claude vocabulary of their own. Each names one of the router's global routes, together with that route's fallback chain and pause list, and an unset route collapses onto the default model exactly as the Claude tier does. The provider ID mcc is reserved so a custom provider cannot make an alias ambiguous.

The tier segment is matched exactly, not by substring. The router takes an optional harness name from the request header or the user-agent fingerprint; an unidentified request resolves against the global chain rather than failing. The resolved tier route is recorded on the plan, which is what lets the request log name the tier, its source and its harness without adding a column to the log.

Walking the chain

Each route has a model and an ordered chain of stand-ins. The executor attempts the route's model first, then each entry in order. A model listed twice is tried twice, and each listing is judged when it is reached. A paused entry keeps its place and is never tried: no attempt is spent, no deadline is consumed, and the log records the reason.

The chain's decision rules come from the failure, not from a general retry count. An auth rejection, a 429 and a transport fault can all be helped by a different key, so the pool rotates. A timeout, a 5xx, a 410 or a plain 400 cannot: every key talks to the same model and would hear the same answer, so those raise out of the rotating loop and the chain moves to the next model. A timeout is explicitly excluded from the transport-fault class, because a model that never answered is not a broken socket.

Media rails are not chat tiers

The image, speech, transcription and video rails walk their chains under the same rules through a separate copy of the engine, and a contract test holds the two copies to the same decisions. They keep their own key, model and proxy health, so a media failure never benches anything for chat. Nothing on a media rail is listed in the model catalogue or offered to a coding agent.

Limits and behaviour

  • The router never inspects an upstream model name or version to choose reasoning behaviour.
  • A route whose every model is paused fails with an error naming the key rather than silently falling through.
  • A failure after the first streamed chunk is not retried; the response is already committed.
  • An unknown harness is served, not refused.
  • A catalogue write that resolves no routable models preserves the last good file.
