From a door to a committed reply

A request is authenticated once, correlated once, routed once and executed against one provider at a time. The hard part is not the happy path; it is deciding when a failure is still an HTTP error and when it is already part of a stream. This page is the LLM request path, from the door the client entered by to the point the reply is committed.

The routes

The proxy exposes POST /v1/messages for Anthropic Messages, POST /v1/responses for OpenAI Responses, POST /v1/chat/completions for Chat Completions, POST /v1/messages/count_tokens for Anthropic token counting, GET /v1/models for the gateway and Claude-compatible model list, GET /health, POST /stop, and HEAD and OPTIONS probes on the supported endpoints. Google's surface lives in its own module because its path shape is unlike every other route: POST /v1beta/models/{model}:generateContent and its streaming, token-count and list siblings.

Authentication and correlation

Proxy authentication is one function. If ANTHROPIC_AUTH_TOKEN is blank, proxy authentication is disabled. Otherwise the proxy accepts exactly a bearer token, and other credential headers are ignored, so a stale provider key cannot mask valid proxy authorization. The complete token is compared in constant time, and no model suffix or other token mutation is accepted.

A pure ASGI boundary creates one opaque request ID before routing, places it in the log context and request state, and adds it to the response while forwarding the real response-start message. The Responses surface and the shared model catalogue expose the same value as a request-id header. Provider execution receives that existing ID; it never creates a second one. Keeping the context around the whole inner call is what preserves correlation during streaming.

Routing and shaping

The product handler validates the request, resolves the model and the reasoning intent, applies Claude-only safety-classifier and local-optimization policy, handles local server tools, and then asks the executor to stream the routed request. The Responses handler is streaming-only and delegates its protocol work to an adapter that converts the payload into an Anthropic Messages request before execution and converts the streamed events back afterwards.

The commit boundary

The executor resolves a provider from the current generation, synchronously preflights the upstream request, emits trace events, counts input tokens and returns an iterator of protocol events. The response layer then waits for the first protocol chunk before it returns a successful streaming response. That wait is the commit boundary. A provider failure before it stays a typed non-2xx JSON response, and that response carries a retry header set to false, because MCC retains ownership of upstream retry rather than causing a second client retry loop.

After the first chunk has escaped, HTTP status is committed. The Messages surface then emits an Anthropic error event and closes without a synthetic message-stop; the Responses surface emits a failed response with its original ID. Non-streaming Messages requests aggregate internally and return a non-2xx JSON for any terminal stream error, discarding incomplete content rather than presenting a partial success.

Close ownership

The public response chain follows a transitive close-ownership rule. A response owns its replay iterator; replay owns the active protocol adapter; each adapter owns its direct input; tracing owns the executor body; the executor body owns the provider iterator; and the provider runner owns its upstream stream. Each owner closes its direct input on normal completion, failure, cancellation and early consumer close. A generation lease is released only after the body chain has finished closing.

Failures that are not provider failures

Ingress authentication, request validation, model routing and deterministic preflight failures are ordinary HTTP errors and do not receive the terminal retry header. Missing provider configuration and a shutting-down request runtime are application-readiness errors: the Messages surface serialises them as Anthropic JSON and the Responses surface as OpenAI JSON, and neither is misclassified as an already-finalised provider failure.

The Gemini difference

The Gemini door keeps Google's error envelope, because Gemini CLI branches on the status string when it decides whether to retry. Its prompt token count includes the cached prompt, unlike Anthropic's, because Google's field includes it and reports the served part separately; a straight rename would under-report every cached request. Its stream has no done sentinel, because that is OpenAI's convention and Google's client would try to parse it as JSON.

Limits and behaviour

  • One request ID, created at ingress, is reused by every stage. There is no second identifier.
  • A failure after the first chunk cannot change the HTTP status; it is an in-band event.
  • A non-streaming request discards an incomplete reply rather than returning partial content as success.
  • The executor depends on a provider port, not on a provider implementation, which is why four doors can share one executor.
