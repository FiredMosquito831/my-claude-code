How the system is put together

MCC is a local proxy, a set of launchers and an optional messaging bridge, built from eight packages with one dependency rule. This page is the map; the six pages after it go into the machinery a request actually touches.

The repository documents its own architecture in a long, maintained file. This page condenses the parts that explain the behaviour you can see: why one address can serve four protocols, why a credential can be judged without judging the model, and why a request is priced once rather than reconstructed later.

Three runtime surfaces

  • The HTTP proxy. A FastAPI application exposes the Anthropic Messages, OpenAI Responses, Chat Completions and Gemini routes, the health and model-listing routes, and the admin surface.
  • The CLI launchers. Wrapper entrypoints prepare a coding agent, or a managed session, to target the local proxy.
  • The messaging bridge. Optional Discord or Telegram adapters turn chat messages into managed client sessions.

All three surfaces end at the same proxy. A chat-driven request and a terminal-driven one are the same kind of request once they reach the router, which is why routing, keys, cost and health behave identically whichever surface sent them.

Eight packages, one dependency rule

The installable wheel is eight packages. config and core are dependency leaves and import nothing first-party. application depends on those two. messaging depends on core. providers depends on application, config and core. The api depends on the same three. The cli depends on config and core. The runtime is the composition root and depends on everything else. There is one deliberate exception: the CLI delegates server construction to the runtime's bootstrap.

An import-boundary contract derives every static production edge with one AST scanner and checks the package matrix, the exact exception, facade ownership and lazy optional imports. The resulting graph must stay acyclic. The same contract rejects untyped provider collaborators and private provider access from helper modules. This is the structural reason the boundaries hold: they are tested, not merely documented.

One request, from door to log

A request enters a route, passes proxy authentication, acquires the current provider generation, is validated and routed, is shaped by reasoning and budget settings, and is executed against one provider at a time. The reply is translated back into the client's protocol. The whole exchange is priced and logged once. The next pages take that apart.

Where the state lives

One configuration directory holds one .env and the documents beside it. The request log is a local SQLite database, with a search index and a prompt chunk store beside it. Catalogue snapshots, OAuth stores, proxy chains and learned facts are separate documents, so a settings save does not rewrite a credential and a credential refresh does not rewrite a setting.

Testing and CI

Deterministic tests cover API routes, configuration, provider conversion, upstream adapters, streaming contracts, messaging, CLI adapters, import boundaries and provider-catalogue contracts. Local and live smoke tests live apart, so a test that launches a subprocess or touches a real service cannot be mistaken for a unit test. The repository holds 905 test files, and the CI workflows name the checks that must pass before a change lands.

What this architecture does not claim

  • It does not claim a provider is available. Availability is the provider's, and the chain exists because it varies.
  • It does not claim a price is correct. It records the source that stated it and says when none did.
  • It does not claim a model can reason. It records the fields the host parses and sends only what both sides can express.
  • It does not claim the proxy is an authenticator. The subscription client gate reads an attribution field; it does not verify a claim.
