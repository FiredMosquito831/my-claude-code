Coding-agent sessions over Discord and Telegram

Messaging is optional. When it is on, a chat message becomes an inbound turn to a managed coding-agent session, and the reply comes back to the chat. It is the same proxy underneath, with the same routing, keys and log. It is optional and off by default. It is LLM messaging in its narrowest sense: a chat surface for a coding-agent session, over Discord or Telegram.

The messaging bridge is skipped entirely when the platform is none or when the selected platform's token is missing. Nothing else in MCC depends on it. When it is configured, an inbound message is normalised by the platform adapter, handed to one platform-agnostic workflow, and answered through an outbound messenger that queues sends, edits and deletes.

Discord

  1. Create a bot in the Discord Developer Portal.
  2. Enable Message Content Intent and invite it with read, send, message-history and Manage Messages permissions, so clear can remove user prompts.
  3. Set Messaging Platform to discord.
  4. Enter the Discord bot token, the allowed channels and an absolute allowed directory.
  5. Apply the settings and restart the server if the page asks for it.

Telegram

  1. Create a bot with BotFather.
  2. Get your numeric user ID from userinfobot. In groups, grant the bot permission to delete messages.
  3. Set Messaging Platform to telegram.
  4. Enter the Telegram bot token, the allowed user ID and an absolute allowed directory.
  5. Apply the settings and restart the server if the page asks for it.

An allowed directory is required and absolute, so a chat cannot be pointed at an arbitrary path by a message. The bot is the only ingress, and a chat that is not allowed is not served.

Commands

UsageBehaviour
/statsshow session state
standalone /stopcancel all work
reply with /stopcancel only the selected request while other queued requests continue
standalone /clearreset all MCC state and remove every tracked message in that chat, including user prompts, voice notes, MCC replies, Telegram's online notice and the clear command itself
reply with /cleardelete the selected message and its literal platform reply subtree, preserving its ancestors and siblings

The workflow keeps a per-chat generation and a global stop generation. A standalone stop invalidates every older provisional turn; a standalone clear invalidates only the invoking chat. Reply-scoped commands apply an exact reference transition, so a voice cancellation or an admitted tree wins without double-counting.

Voice notes

A voice note is downloaded, size-checked, transcribed and handed to the same inbound path as text. The transcription backend is chosen at install time: NVIDIA NIM, local Whisper on CPU or CUDA, or both. Local gated models need a Hugging Face key; NIM transcription needs the NVIDIA NIM key. Changing the credential an active voice backend uses requires a restart, while the same provider credential stays hot-replaceable when voice does not use it.

Install a voice backend (Linux, macOS or WSL)
curl -fsSL "https://raw.githubusercontent.com/FiredMosquito831/my-claude-code/main/scripts/install.sh" | sh -s -- --voice-local

Pending voice notes have their own registry, which owns an optional status binding, cancellation by either message ID, and the exclusive handoff lease. A voice-transcribed stop or clear cannot cancel itself, and a stale flow cannot bind or remove a newer generation that reuses the same ID.

What you see

The Messaging page holds the platform, its token fields, the allowed channels or user ID, the allowed directory and the voice controls. The optional messaging step also appears in the Get Started checklist, so a new install is told it exists without being forced through it.

Requests made through a messaging session are ordinary proxied requests and appear in Analytics like any other. The harness attribution names the agent behind them, so a chat-driven session can be told apart from a terminal one. A chat-driven request is not a special kind of request; it is the same proxy with a different ingress.

Configuration

The names are MESSAGING_PLATFORM, the platform token variables, MESSAGING_RATE_LIMIT and MESSAGING_RATE_WINDOW, and the voice settings for backend, device and model. A Telegram proxy URL is optional and used only for that transport. Values are configured on the Messaging page and written to the same .env the server reads; this site publishes no values.

Limits and behaviour

  • Messaging is off by default and skipped cleanly when it is not configured.
  • An allowed directory is required; a chat cannot widen it.
  • A voice note that fails transcription gets an error reply and is cleaned up; it does not leave a temp file behind.
  • A reply-scoped clear deletes only the selected subtree, never its ancestors.
  • The bridge is optional, but a request it makes is an ordinary request for routing, keys, cost and health.
