Providers, keys and credential health

Every provider MCC can route to is a card on one page. A card holds a key or a pool of keys, its rotation policy, its model list and its health. The rest of this page is what happens when a provider answers, refuses, or says nothing at all.

The provider table in the repository lists 60 cards across cloud APIs, subscription and OAuth sign-ins, gateways, local servers and marketplaces. MCC builds each model slug as <provider-id>/<exact-provider-model-id>, and free-text entry stays available when a provider cannot list its models.

One key, or a pool

Put multiple API keys in one variable, comma-separated, and choose a policy with {ENV}_ROTATION. Every key in a pool gets its own upstream client and its own rate-limit window, so one key saturating or stalling never throttles the others. The order in the pool is the order the policies read.

PolicyBehaviour
singlealways the first key; the default when one key is set
round_robinspread requests across healthy keys in turn
least_usedthe healthy key with the fewest requests goes first
failover / on_errorstick to the first healthy key until it fails, then move to the next; the default when several keys are set

Keys can be reordered without retyping the variable, and each key can carry a name. Names live in credential_names.json, keyed by a hash of the key and never by the key itself; they never reach an upstream request or the request log. A renamed key keeps its history, and two keys given one name read as the name plus their masked label.

Health is judged on the key, not on the weather

A key is only ever judged on signals about the credential. There are exactly three. A 401 or 403 walks an escalating lockout ladder of five minutes, one hour and one day, on its own counter. A 429 benches the (key, model) pair for exactly the wait the provider published, or a configured cooldown when it published none, and the key stays healthy for its other models. An exhausted-credit refusal, where the provider says in words that the account has no balance left, benches the whole key, because a wallet is not per model.

Everything else, including timeouts, 5xx, a 410 model-gone, other 4xx and transport faults, leaves every key untouched. A model that will not answer is the model's problem: the fallback chain moves to the next model instead of spending the pool on it. A timeout is explicitly not read as a broken socket, so a model that never answered is not charged against the rest of the pool.

Custom providers and the model catalogue

Any other OpenAI-compatible endpoint can be added as a custom provider from the same page. A custom provider is not a second kind of provider: it is an ordinary descriptor injected from a different source. Its definition lives in custom_providers.json, never in the .env, because its static credential travels on the descriptor rather than through a settings field. Deleting a custom provider removes its refs from every route; disabling it leaves the refs and pauses them.

A custom provider cannot inherit its host's reasoning_effort vocabulary, so MCC measures it. At most two 16-token chat completions are sent, the first with a deliberately invalid effort value, and the enum is read out of the 400 the host answers with. The learned words are persisted and bound to a reasoning encoder exactly as a static provider declaration would be.

The Models page is the catalogue behind that: every model every configured provider publishes, with bulk visibility, capability probes, learned facts and an hourly background refresh. Each row names where its entry came from. Hiding a model changes what is listed, never what is routed.

OAuth sign-ins

An OAuth provider sits in the same grid and carries the same badges, but its credential is a sign-in rather than a string you paste. MCC supports a Claude subscription, ChatGPT and Kimi For Coding. The Claude subscription route is not permitted by Anthropic: Anthropic's published terms forbid routing Free, Pro or Max plan credentials on behalf of third-party users, and the risk is to your account. MCC limits it by admitting only Anthropic's own clients, using an attribution line that travels in the request body, and it documents the position rather than hiding it. Read docs/ANTHROPIC-SUBSCRIPTION.md before enabling it. The ChatGPT subscription has its own caveats and is documented in the same place.

Proxy chains

A provider can go out through a named chain of proxy exits. A chain whose provider limits per address moves a refused or dropped request to another exit on the same model, within your switch limit, and remembers the refused exits across saves. A country refusal is about the address, not the key: it never locks a key out, on any route. Three ways to fill a chain are built in: a scan for a proxy you already run on this machine, a bring-your-own-tor card where each SOCKS port becomes one named identity, and VPN accounts, gateways and provider proxy lists. WireGuard files your VPN exports can be run by MCC as named loopback exits.

Configuration

The provider credential settings are the environment variables named on the provider's card, for example ANTHROPIC_API_KEY, OPENROUTER_API_KEY or GEMINI_API_KEY. Rotation is {ENV}_ROTATION. The health knobs are CREDENTIAL_LOCKOUT_TIERS, RATE_LIMIT_COOLDOWN_SECONDS, RATE_LIMIT_COOLDOWN_MAX_SECONDS, RATE_LIMIT_COOLDOWN_MODE and CREDENTIAL_MODEL_BENCH_ESCALATION. Variables are named, never given example values.

Limits and behaviour

  • No bench duration is invented at the rotation layer: it comes from the provider's own Retry-After or the configured window.
  • A bare 402 that names no billing phrase rotates and falls through but charges nothing.
  • A key that fails 5xx or transport on every request is retried once per request rather than benched. That is the deliberate trade that stopped healthy keys being benched for faults they did not cause.
  • A custom provider's URL is called as typed; the generic profile deliberately does not normalise it.
  • Local providers (LM Studio, llama.cpp, Ollama) need a base URL rather than a key.
