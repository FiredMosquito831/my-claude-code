Platform, desktop app and updates

MCC runs on Windows, macOS and Linux, as a server, as a native desktop app, or both. There is one update path, one configuration directory and one set of commands, whichever route you took in. This page is the LLM gateway update path, and the platform support behind it: what the installer does on each system, and what it deliberately does not touch.

The server is the product; the desktop app is a window onto it. Every install route ends at the same server, the same dashboard and the same configuration directory. The server one-liners are the right choice on a headless box, a VPS, over SSH or inside WSL, where there is no tray to draw into.

What the installer does

  • Installs uv if it is missing, and replaces one below the required floor.
  • Installs Python 3.14 through uv, so no system Python is needed and none is used.
  • Downloads the latest release wheel and verifies the SHA-256 GitHub publishes for it.
  • Installs MCC into an isolated tool environment and puts every mcc-* command on your PATH.
  • Creates the configuration home, and with the desktop flag, installs the desktop app too.

The installer needs no Node, no Python and no git. It cannot install curl on Linux, macOS or WSL: it names the exact package-manager line for your machine and stops. On Windows it uses the built-in PowerShell, and the Command Prompt route passes the execution-policy flag a saved script would otherwise need.

After it finishes, close and reopen your terminal. The installer adds ~/.local/bin to your PATH, and a shell that was already open cannot see it. That is the single most common reason mcc-server looks missing straight after a successful install.

The desktop app and tray

The desktop app is a real window with its own icon and tray, not a second copy of the server. It has three server modes: spawn, where it starts the server; attach, where it connects to one already running; and off, where it does neither. It can start at login, and its preferences persist in the configuration home. The tray menu covers Open Admin, Check Server Status, Restart Server, the server mode, Start at Login, Tray Enabled, a Token optimizer submenu and Quit.

Its own prerequisites travel with its packages: the Windows installer bootstraps WebView2, the .deb declares its webkit dependency, and macOS needs nothing extra. WSL has no tray, and the app says so and refuses rather than pretending.

One update path

The dashboard shows the running version, announces releases and installs them with checksum verification. The installer is the same path: re-running it always fetches the newest release. An update is atomic. The new version is built beside the running one, run once to prove it works, and swapped in by two directory renames; if it never answers the health endpoint, the previous version is put back and started. The server is down for the stop, the rename and the start, not for the download and the dependency resolve.

During an update the desktop window shows a stage timeline with timestamps, elapsed time and the installer's log tailed live. The progress document and the install log are written into the configuration home, so a failed update can be read afterwards.

Packaging

MCC ships as a Python wheel on PyPI, as an npm package that wraps the same digest-verified installer, and as native desktop installers for each platform. The npm route reads the machine before it installs anything: where there is a desktop session it also installs the native app, each verified against the release's checksum manifest; over SSH, in CI, on a headless box or in WSL without a display it installs the server alone and says why. The PyPI route is the one that assumes something: it requires Python 3.14 and provisions nothing for you.

Update and uninstall

Uninstall is one line, and it verifies every MCC command is gone before it reports success. The desktop app is removed separately, by the platform's own mechanism. A pre-6.40.0 install that lives in the legacy configuration home is migrated on first start by one atomic rename, nothing copied or merged, provided nothing is holding the directory open; mcc-migrate runs the same move by hand and refuses while it can see a live server.

Uninstall (Linux, macOS or WSL)
curl -fsSL "https://raw.githubusercontent.com/FiredMosquito831/my-claude-code/main/scripts/uninstall.sh" | sh

Configuration

The install-time switches are flags, not settings: --dry-run, --version, --desktop, --no-restart, --no-start, --no-desktop and --yes-sudo. MCC_INSTALL_REF points the installer at a branch, and MCC_INSTALL_NO_START and MCC_INSTALL_NO_DESKTOP carry the same intent as environment variables. The server's own host and port are HOST and PORT.

Limits and behaviour

  • The Windows installer is unsigned, so SmartScreen asks for More info then Run anyway. Machines with Smart App Control on cannot run it; use the PowerShell one-liner there.
  • The macOS disk image is unsigned and quarantined, so moving the app across needs one quarantine-removal command. The server one-liner is never quarantined.
  • The installer cannot install curl, and it does not install Claude Code or any other agent.
  • Every other MCC server on the machine is listed and left running. A port held by something that is not MCC is reported rather than touched.
