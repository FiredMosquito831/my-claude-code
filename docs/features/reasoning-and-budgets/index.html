Reasoning control and output budgets

Every provider spells reasoning differently. MCC keeps one neutral policy, then lets each provider adapter translate only the subset its wire API can express. The same page also decides how long a model may think, how many tokens it may spend, and how long the router waits before it calls a silent model a failure. This page is LLM reasoning control and the output token budget that goes with it.

Reasoning is not one setting. It is three independent facts: whether the client wants reasoning on, off or by default; the named effort it asked for, when it named one; and an exact token budget, when it supplied one. MCC resolves those facts once, at the application boundary, and passes one immutable policy to the provider. Provider adapters alone decide how to spell it.

One scale, many dialects

When a numeric-budget provider needs a number, MCC expresses named effort through one product scale: minimal and low are 512 tokens, medium is 1,024, high is 2,048, xhigh is 4,096 and max is 8,192. An exact client budget takes precedence over the scale.

Each host declares a reasoning dialect: which fields it parses, the words it accepts in an effort field, whether it has an on/off channel, a numeric budget, an OFF spelling and an adaptive channel. A control is emitted only where the model has that knob and the host has a field to spell it in. Where one of the two is missing, the nearest thing both can express goes instead: an effort outside the host's vocabulary clamps to the nearest rung that host spells, and a toggle-only model on an effort-only host is sent the rung the client asked for, clamped to that host's enum. Where nothing can be expressed, nothing is sent, the model's own default applies, and the request log records that rather than implying an instruction was honoured.

Adaptive reasoning on every door

ADAPTIVE is not an effort level and not a budget. It asks the host to think as much as it decides it needs, and each door says that in the host's own words: Anthropic's thinking: {"type":"adaptive"} verbatim; an on/off field switched on where that is a different field from its effort one; the highest rung the host publishes where effort is all it has, recorded as a substitution; and nothing at all where the host parses no reasoning field. Every request that does not ask for adaptive is byte-for-byte unchanged.

Learned rejections

A host that answers a 400 naming a reasoning field is retried once without that field, and on success the (provider, model) pair is remembered for the life of the process. The narrowing is instance-scoped: a configuration reload rebuilds the provider and forgets it. A complaint naming a sampling field is never treated as a reasoning rejection, and an unrecognised 400 still fails visibly.

Reasoning replay across turns

A coding conversation spans many turns, and each turn has to decide what to carry forward. MCC keeps that decision explicit per provider: native reasoning content, a native reasoning field, think tags, provider-specific chunks, or no replay. Turning computation off for the next generation does not silently erase prior assistant state a valid continuation needs.

The provenance guard is the safety net. An envelope is host-bound: it is replayed only to the exact provider, endpoint, account and model that produced it. A request that carries an envelope into a door that cannot have minted it is refused and counted as history_carrier_foreign. Readable reasoning is untouched and still crosses models and providers.

Prompt-cache lifetime

Prompt caching is off by default: the client's own lifetimes go untouched. Set minutes per tier and MCC sends the host's nearest lifetime at least that long: 5 minutes or 1 hour on Anthropic and on Claude models through OpenRouter, in_memory or 24-hour retention on Azure OpenAI. Hosts that cache automatically, including ChatGPT, Gemini, DeepSeek, Nous and NIM, get nothing. A per-provider or per-model row can override the lifetime, or force From client, for gateways that speak Anthropic's protocol.

Output budgets and deadlines

The output allowance is resolved separately from reasoning, and the order matters. When the resolved policy will ask the model to think, the ask is first raised to the model's own published output limit, because thinking and answer tokens are spent from one allowance the client sized for the answer alone. Then the model limit applies, then the unknown-default, then the floor, then the ceiling, then context headroom. The floor is the only step that raises, and it sits after the model limit so it can never ask for more than the model published, and before context headroom so it can never re-inflate a budget the remaining context cannot hold.

Deadlines are the other half of a budget. A first-token deadline and a total deadline per route turn a silent model into a failure instead of a hang. The calculator shows what each model on your chains actually gets, which is rarely the number in the box, because the model limit, the floor, the ceiling and context headroom all interact.

Configuration

The reasoning policy and its per-tier overrides live on Model Config. The budgets and deadlines live on Limits and Resilience. The settings are named REASONING_*, MAX_OUTPUT_TOKENS_*, REQUEST_*_DEADLINE* and PROMPT_CACHE_*; the exact names and their purposes are on the configuration page. No example values are published for any secret-like setting.

Limits and behaviour

  • The router never uses the output-token limit as a reasoning budget. A named or numeric reasoning budget travels only through documented fields.
  • A provider-default intent emits no compute-control field at all.
  • An exact client token budget takes precedence over MCC's named-effort scale.
  • A reasoning control the host cannot express is not invented: nothing is sent and the request log says so.
  • Learned rejections are per process. A reload forgets them, deliberately.
