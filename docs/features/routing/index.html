Model tiers and fallback chains

A coding agent asks for a model by a name it knows. MCC turns that name into a real provider model, applies your reasoning and budget settings, and walks an ordered chain of stand-ins when the first model cannot serve the request. The chain is yours, and every step it took is in the log.

Routing is the reason a proxy can be useful at all. Without it, every coding tool carries its own model list, its own keys and its own idea of what to do when a provider says no. With it, one tier map serves every tool, and swapping a model is one edit on one page.

What a request can name

The router accepts three forms. A direct provider model ref such as nvidia_nim/nvidia/model-name names the provider and the exact model. A gateway model ID is decoded by MCC's own ID codec. And the five coding-agent tier aliases are intercepted ahead of both: mcc/cyber, mcc/best, mcc/good, mcc/medium and mcc/cheap. They are pointers, not models. Each names one of the router's own global routes, together with that route's fallback chain and pause list.

A name that is not a direct ref or a tier alias is mapped by Claude tier. Names containing fable, opus, sonnet or haiku use the matching tier override when one is set, and otherwise fall back to MODEL. A blank MODEL_HAIKU follows MODEL, which is what a fresh install ships.

The tier map

Each tier has three settings: the model it routes to, an ordered comma-separated fallback chain, and a pause list. The dashboard renders them as one rail per tier, in the order the router walks them.

How a fallback chain behaves

  1. The router resolves the requested tier to its primary model and records the route on the request.
  2. The executor attempts the primary model with a healthy credential.
  3. If the model rate-limits, errors or refuses, the next entry in that tier's chain is tried, then the next.
  4. The first attempt that succeeds ends the walk. Every later entry is recorded as not reached.

The chain does not retry the same model forever. A 429 benches the (key, model) pair for the wait the provider published, and the key keeps serving its other models. An auth rejection locks that key out on an escalating ladder. A timeout, a 5xx, a 410 or a plain 400 is treated as the model's answer, and the chain moves to the next model instead of spending the rest of the key pool on it.

Pausing one entry

Each row on a rail has a Pause button. A paused model keeps its place and stays fully on screen, but the router never tries it: no attempt is spent, no deadline is consumed, and the request log lists it as not tried with the reason paused. Unlike most of the page, a pause is written the moment you click it, with no Apply, and the status panel offers an Undo. Pausing is per route: the same model paused on Opus keeps serving Sonnet.

Pausing is not hiding. Visibility changes on the Models page change what appears in /v1/models and never change routing; a pause changes routing and never changes listings. A route whose every model is paused fails with an error naming the key rather than quietly falling through to another route.

Per-agent tiers

A different agent can have a different tier map. MCC identifies the harness from the x-mcc-harness header or from the request's user-agent fingerprint, and resolves against that agent's override when one exists. The overrides live in harness_tiers.json, are parsed defensively and are cached on the file's own timestamp, so a dashboard write lands without a restart.

The vision adapter

An image request can be diverted to a model that can see, with its own chain. VISION_ADAPTER_MODE=describe adds a third behaviour for a blind tier: instead of dropping the image, MCC builds one ordinary routed plan per image over the vision chain, has a sighted model describe it, and sends the description onward. The description is cached on the image's content address, so a screenshot re-sent every turn is described once. Every failure returns to the behaviour the request would have had without the adapter: divert, or send the substitute image.

Two image behaviours are automatic. Outbound pictures are resized to a 1568-pixel long edge on the router's own copy, never the client's. And an image a tool returns reaches the model as a picture rather than as base64 text: one walk finds an image or document inside a tool result, and the token estimator and the outbound converters call the same walk, so they cannot disagree about whether it is an image or 680,000 characters of text.

Where you see it

The tier map is on Model Config. The chain a request actually walked is on Analytics: the Failover panel counts every primary-to-stand-in pair that fired, and one request's detail shows each attempt with its key, timings and the reason it was or was not tried. The Models page lists what /v1/models advertises to clients.

Configuration

Routing is configured by names, not values. The tier models are MODEL, MODEL_MYTHOS, MODEL_FABLE, MODEL_OPUS, MODEL_SONNET, MODEL_HAIKU and MODEL_VISION. Each has a _FALLBACKS list and a _PAUSED list. The media rails use MODEL_IMAGE, MODEL_TTS, MODEL_ASR and MODEL_VIDEO, and are not chat tiers: nothing on them is listed in /v1/models or offered to a coding agent.

SettingWhat it decides
MODELthe model used when nothing more specific matches
MODEL_MYTHOSMythos-tier traffic, alias mcc/cyber

Limits and behaviour

  • Failover happens before the first streamed chunk. Once output has started, switching models would corrupt the response, so a mid-stream failure is surfaced to the client.
  • A request that carries no identifying harness resolves against the global chain. It is never failed for being unidentified.
