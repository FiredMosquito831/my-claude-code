The commands MCC puts on your PATH

The dashboard is optional. Everything the page can do has a command, and the launchers are how most people start an agent. This page is the reference for the commands, with the flags that exist and the ones that do not.

An install puts mcc-server and the mcc-* launchers on your PATH, and adds the headless tools beside them. A launcher whose agent is missing prints that agent's own install command and exits; it does not try to install the agent itself.

The launcher set is generated from one registry, so a new agent is a registry entry rather than a new script. A launcher whose agent is missing prints that agent's own install command and exits, which is why the CLI never installs an agent on its own.

The server and the launchers

Start the server
mcc-server

mcc-server --version prints the running release. The server listens on loopback port 8082 by default, serves the dashboard at /admin and answers /health. Every other MCC server on the machine is left alone.

mcc-claudelaunch Claude Code against the proxy; --discover-models wires the native model picker, and mcc-claude-old keeps the older launch shape
mcc-codexlaunch Codex CLI over the OpenAI Responses surface

Headless app control

mcc-apps does what the Desktop apps cards do, which matters on a headless machine or over SSH. Its subcommands are list, status, configure (with --preview to show the change without writing it) and undo (with --restore to put back the exact values MCC replaced).

Preview a desktop-app change
mcc-apps configure --preview

Sign-in, migration and the token optimizer

  • mcc-anthropic-oauth-login signs in from a terminal. It takes --paste, --no-browser, --list and --remove <id>, and answers --help without starting anything.
  • mcc-migrate runs the legacy-home move by hand. It refuses while it can see a live server.
  • mcc-rtk status|enable|disable|uninstall|apply controls the opt-in token optimizer per agent, the same control the dashboard's Token optimizer card writes.
  • mcc-desktop fetches and verifies the desktop app, and refuses rather than pretending on a machine with no tray.

The installer's flags

The one-liners accept --dry-run to see the plan without changing anything, --version to pin a release, --desktop to install the app too, --no-restart to leave a running server alone, --no-start to stop and start nothing, --no-desktop to leave the app alone and --yes-sudo to answer the sudo prompt for the Linux package step. The npm wrapper accepts --server-only, --desktop-only, --no-desktop and --yes-sudo, and reads MCC_NPM_INSTALL=server|desktop|both|none.

See what an install would do
curl -fsSL "https://raw.githubusercontent.com/FiredMosquito831/my-claude-code/main/scripts/install.sh" | sh -s -- --dry-run

A first run, in order

  1. Install with the one-liner for your platform, then reopen the terminal so the PATH change is visible.
  2. Run mcc-server; on first start it writes the configuration home and generates the proxy token.
  3. Add one provider key on the Providers page, then set the tiers on Model Config.
  4. Launch the agent with its own command, for example mcc-claude. The launcher passes the proxy address, the token and the generated catalogue, and the agent itself looks unchanged.

Where the CLI and the dashboard meet

The command line and the dashboard are two front doors to one configuration. A command does not keep a private copy of a setting, and a page does not write somewhere the server will not read. mcc-apps configure shows the same diff preview the card shows, and mcc-apps undo performs the same two undo modes.

The exceptions are the things that must be decided before the settings file exists. MCC_CONFIG_DIR is a shell variable, not a setting, and the install-time switches are flags rather than values. Everything else has one name and one place, which is what makes a command and a page safe to use interchangeably.

A command that needs a provider key reads it from the same configuration home the server reads, through the same settings resolution. There is no separate credential path for the CLI, and no command that writes a key the dashboard would not show.

What the commands do not do

  • A launcher does not install its agent. It prints the agent's own install line and exits.
  • The installer does not install curl, and it does not upgrade your system Python. It uses Python 3.14 through uv.
  • The CLI does not write a file the dashboard does not also write; both go through the same configuration.
  • No command changes repository settings, DNS or a hosting account.
