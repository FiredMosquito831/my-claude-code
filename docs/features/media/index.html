Image, speech and video over the same engine

Media is not bolted on. The image, speech, transcription and video endpoints run over their own rails, but they share the chat engine's retry, key rotation, 429 handling and proxy rules, with health records of their own so a media failure never benches a model for chat.

A media request names a model on a media rail. MCC walks that rail's chain exactly as it walks a chat chain: the same deadlines, pauses, skip kinds and retry rules, through a separate copy of the engine that a contract test holds to chat's decisions. The rails keep their own key, model and proxy health, so a failed image request does not bench anything for a chat.

A provider serves only what it declares

A provider serves a media operation only when it declares that endpoint. MCC never guesses from a model name. A model on a provider that declares nothing for the operation is skipped and not charged a failure; the request log shows it as unsupported. An edit therefore skips every model whose provider declares no edit endpoint, uncharged, and is served by the first one that does.

Most image providers are passed through field for field: the body the client sent is forwarded with the model replaced by the rail's model, so a parameter only one host understands still reaches it, and the host's answer is returned as it came. Gemini's native speech and transcription surfaces and Mistral's image surface are translated instead. MCC builds those requests itself, lists any field it has no place for under not_forwarded on the request row rather than guessing, and turns the host's answer back into what an OpenAI client reads.

Mistral images are the unusual wire: Mistral does not document an image-generation endpoint. MCC asks for the picture on chat/completions with the image_generation built-in tool, then fetches the result with a second call on the same key and the same proxy exit. Only the prompt is forwarded; the rest is recorded as not forwarded, and the image is recorded as unpriced because no source publishes a per-image rate.

Uploads, edits and streaming

An edit is forwarded in the client's own encoding. A multipart upload goes out as multipart, streamed from the server's spooled copy of each file, and re-read from the start if the rail falls back to the next model. The JSON variant goes out as JSON. MEDIA_UPLOAD_MAX_MB sets an optional upload limit: above zero, a file larger than that many megabytes is refused with a 413 before any provider is asked, so nothing is spent on it.

A request that asks to stream is routed to a surface documented to stream it. When a rail has no such surface, a streamed image or speech request is answered as one event rather than a stalled stream.

What you see and what it costs

The Models page lists every media-rail model with its declared endpoints and media health, and each model publishes the fields its request takes as a JSON Schema per operation, each with who said so. That schema is shown only; nothing sent changes. Clients can read it from GET /v1/media/models. Analytics has a separate Media card, and every row is labelled by its own API, so a generated image reads as such in the requests table.

Media requests are priced like chat ones: a provider figure first, then models.dev, then LiteLLM when it is on, else unpriced. Generated media can optionally be stored, controlled by MEDIA_STORE_ENABLED.

Media tools for coding agents

MCC's media server, mcc-mcp, exposes one tool per filled rail plus a free status tool over MCP. It can be added to an agent from the Coding agents page, or written into Codex's config.toml, OpenCode's opencode.json and Command Code's mcp.json from the Desktop apps cards. The change is shown first, written only on confirmation, backed up once, and removable back to the same bytes. An entry MCC did not add is left alone. The server is off for every agent by default.

Configuration

The rails are MODEL_IMAGE, MODEL_TTS, MODEL_ASR and MODEL_VIDEO, each with a _FALLBACKS and _PAUSED list. The upload cap is MEDIA_UPLOAD_MAX_MB, optional storage is MEDIA_STORE_ENABLED, and the agent tools are gated by MCP_MEDIA_APPS. None of the rails is a chat tier: nothing on them is listed in /v1/models or offered to a coding agent.

Limits and behaviour

  • A model whose provider declares no endpoint for the operation is skipped uncharged and logged as unsupported.
  • A Mistral image fetch that fails after the host billed the picture fails the attempt, because the host has already charged it.
  • A media failure never benches a chat model; the rails keep their own health records.
  • An upload over the configured cap is refused before any provider is asked.
  • A field MCC cannot place on a translated surface is listed as not forwarded rather than silently dropped.
