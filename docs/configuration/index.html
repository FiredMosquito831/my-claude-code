How settings are provided

MCC has one configuration home, one .env and one set of documents beside it. The dashboard writes the file, the server reads it, and the launchers resolve the same directory. There is no second configuration system to reconcile. This page is the LLM gateway configuration map: the home, the file, the documents beside it and the variables that are read before the file is.

The configuration home

A new install keeps everything in ~/.mcc. That directory holds the .env, the request log under logs/, the per-agent documents the launchers write, and the JSON documents that do not belong in a settings file: custom provider definitions, per-agent tier overrides, credential names, OAuth stores, model overrides, learned facts, proxy chains and marketplace profiles. An install from before 6.40.0 is migrated from its legacy directory on its first start by one atomic rename, nothing copied or merged, and the startup log always names the directory in use.

One variable resolves before the file does. MCC_CONFIG_DIR pins the configuration home to an absolute path and overrides every default. It must be set in your shell, not written into the .env, because the directory has to be known before there is a file to read. Set it for the mcc-* launchers too, or they will read a different directory than the server.

The .env

The .env is the settings file. Every setting lives there with the same name it has in the documentation, and the dashboard writes the same file, so a value set on a page and a value set by hand are the same value. On a new install the server writes the file on first start and generates the proxy token for that machine.

The repository ships an annotated example file, .env.example, with inline comments and cost notes. Its variable names are public; its values are not, and this site never publishes one. For a secret-like setting the configuration page on this site gives the name and the purpose only.

Environment variables that are not settings

A settings save and a credential refresh write different files. That split is what lets a provider be re-keyed without rewriting the routing map, and a tier change without touching an OAuth store. It is also why the dashboard can show a key round-trip and a tier change as two independent actions rather than one save that rewrites everything.

A few variables are read before or outside the settings file. MCC_CONFIG_DIR chooses the directory. MCC_ENV_FILE names an explicit dotenv file to load instead of the default one. The install scripts read MCC_INSTALL_NO_START and MCC_INSTALL_NO_DESKTOP, and the npm wrapper reads MCC_NPM_INSTALL. HTTPS_PROXY, HTTP_PROXY and NO_PROXY are honoured by the installers and by outbound requests.

Editing rules

  • A blank value means unset. Removing a value from the page writes a blank, and the default applies.
  • A restart-required setting is labelled on the page; Apply does not pretend it took effect.
  • A managed write backs the file up before it changes it.
  • A leftover setting from a removed feature is ignored at startup and dropped on the next save.
  • The launchers read the same directory as the server; a mismatch is the one configuration mistake the product cannot fix for you.
