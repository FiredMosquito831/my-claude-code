## Description

The dashboard update button **corrupted the install on Windows**. PATCH `4.21.1` → `4.21.2`.

## Root cause

`uv tool install --force` removes the existing tool environment before reinstalling. But `fcc-server` *runs from that environment* — on this machine, `…\uv\tools\free-claude-code\Scripts\python.exe`.

Windows holds a running executable and its loaded DLLs open. The removal fails partway with the access-denied error you saw, leaving a **half-deleted environment** — hence the corruption. WSL and Linux were unaffected because POSIX unlinks open files without complaint, which is exactly why it worked for you there.

## Fix

Windows now **stages** instead of installing in place:

1. Download the wheel and verify its SHA-256 — unchanged, same checks as before.
2. Write it to `~/.fcc/updates/`.
3. Spawn a **detached PowerShell helper** that waits for this process to exit, pauses for Windows to release the handles, runs `uv`, and records the outcome.
4. The banner reads *"Update staged — stop the server to finish installing"*.

You stop `fcc-server`, the update applies by itself, you start it again on the new version.

**The existing install is never touched while it's running**, so a failed update can no longer strand you mid-way — the old version stays fully working until the moment it isn't running.

## Why PowerShell, not Python

The only interpreter we can rely on is the one **inside the environment being replaced**. Using it would hold open the very directory `uv` needs to delete — reintroducing the bug in a new place. PowerShell is always present on Windows and is external to the target.

Arguments are passed as a fixed argv, quoted for PowerShell, so release metadata reaching the wheel name can't inject commands. Spawned `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` so it survives both this process and the console the server was started from, and it gives up after an hour rather than sitting resident forever.

## Reporting a failure you can't see happen

The helper only reports *after* the server that staged it is gone. `ReleaseStatus` now carries the recorded outcome, so a failed deferred install surfaces in the dashboard on the next start rather than vanishing silently.

## Residual risks

The helper is fire-and-forget: if the machine is powered off between staging and shutdown, the staged wheel simply sits in `~/.fcc/updates/` and the install never runs. Harmless, but it does mean "staged" isn't a guarantee — the next status check will still show an update available.

If someone stops the server and immediately restarts it within the helper's 2-second settle window, the install could still race the restart. Unlikely by hand; worth knowing if you script it.
