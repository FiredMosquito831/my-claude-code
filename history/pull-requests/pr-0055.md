## Description

The 4.39.0 Providers page was rejected, and correctly. It put every provider behind a collapsed category group, so reaching one meant **section → closed group → card → closed "Advanced"**: four levels, two shut by default, and a page that opened showing mostly headings. It solved "too much scrolling" by *hiding things*, which is a worse problem.

## Categories are gone

"Inference platform" vs "Gateway" is a way of thinking about the vendor landscape, not information anyone needs in order to paste a key. Grouping by it made finding a provider harder. The dot rail went with it — it was an abstraction you had to learn before it told you anything.

## What comes back, and what actually gets fixed

The original **240px card grid** and the original **status pill** return unchanged.

The one structural change is the thing that was genuinely wrong before: a provider's **status** and its **key fields** lived in two different places on the page. They are now the same card. Press **Configure** → the card expands across the row to hold the whole provider form. Press **Done** → it collapses.

**Refresh models now sits on the card face next to Configure**, reachable without opening anything. It was buried inside the expanded form. Local providers show "Test connection" in the same slot.

## The form is the whole provider

This is what earlier iterations of this work misrepresented. A provider is not a name and a key — it is a small form:

- the **multi-key pool**, each key with health, plus add and remove
- the **rotation policy** select (single / round robin / least used / failover)
- proxy and base URL
- the model refresh

None of this was ever broken — `renderField()` attaches the key manager for a credential field, so it came along — but no version of the design *acknowledged* it, which is why the flat-grid ideas kept failing. All 35 forms cannot be open at once. That is the real constraint the layout has to respect.

## New payload field

`provider_status[].key_count` carries the size of each key pool so a card face can read **"3 keys · Round robin"** without one HTTP request per provider on load. It cannot be derived client-side: secrets are masked to a constant before they leave the server. The rotation label comes from the `_ROTATION` field already in the payload.

## Residual risks

- **Still not rendered in a browser.** No browser tooling is reachable in this session. jsdom proves structure and wiring, not appearance.
- An expanded card takes the full grid row (`grid-column: 1 / -1`), so opening one reflows the cards after it. Deliberate — the key pool needs the width — but it is the most likely thing to feel wrong in practice.
