## Description

Follow-up to #273, fixing a real failure rather than a hypothetical one.

The first dispatch against the existing release, `gh workflow run shell-release.yml -f tag=v6.43.0`, **failed on all four legs in under a minute** ([run 33868330910](https://github.com/FiredMosquito831/my-claude-code/actions/runs/33868330910)):

```
##[error]An error occurred trying to start process '/usr/bin/bash' with working
directory '.../desktop-shell/src-tauri'. No such file or directory
```

`v6.43.0` predates #272. The workflow checked out the tag it was uploading to, and there is no shell in that tree to build.

## What changes

On `release: published`, building the tag is right and stays: the tag carries the source that release is made of, so the shell attached to it is built from it. A dispatch is the case where the two questions genuinely differ — backfilling assets onto a release published *before* the shell existed, or before a fix to this workflow landed, means uploading **to** that tag while building something newer.

So the dispatch now takes two inputs:

- **`tag`** — where the assets go (required, unchanged).
- **`ref`** — what to build: a branch, tag or SHA. Empty means `tag`, so the ordinary case is untouched.

Plus a guard step that reports a checkout with no `desktop-shell/` in it **once**, naming the ref and the fix, instead of letting four legs fail on a working directory that does not exist. `The directory name is invalid` names neither the cause nor the remedy.

Docs updated in both places that describe the dispatch: `desktop-shell/README.md` and `docs/RELEASE-CHECKLIST.md` §7 now show the backfill form, `-f tag=v6.43.0 -f ref=main`.

No Python change at all in this PR, so no version bump and no release.

The proof dispatch is re-run against `v6.43.0` with `-f ref=main` once this merges.
