## What and why

A desktop shell (S2) renders `http://127.0.0.1:<port>/admin` in a second process. That process must never decide where the config lives, which port to use, or how long to wait for a restart. `resolve_config_dir()` (`config/paths.py:295`) is a *policy*, not a lookup — `MCC_CONFIG_DIR`, then `~/.mcc`, then `~/.fcc` only if it passes four checks, two of which open the SQLite request log and construct a whole `Settings`. Reimplementing any of that in Rust is the single most likely way this design decays.

So the shell asks Python. `mcc-desktop --print-status` (and the `fcc-desktop` alias) prints **one JSON document** on stdout and exits `0`.

**No new logic.** `cli/desktop_status.py` only spells existing answers as JSON.

Three keys are additions to the spec's §2.1 sketch, each because a shell provably needs it: `config_dir_is_legacy` (the spec's "legacy flag"), `minimize_to_tray` and `health_poll_seconds` (C9's debounce is *threshold × poll interval*, and the threshold alone does not give a duration), plus `window_width`/`window_height` for §2.4's first-run geometry. `version` is emitted; **`latest` is deliberately omitted** — it needs a GitHub call or an in-process cache that a fresh `--print-status` subprocess cannot see, and the spec's own rule is that this command makes no network call off the machine. The shell reads `latest` from `/admin/api/version` once it is attached, like the dashboard does.
