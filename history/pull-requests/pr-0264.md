## Description

# feat(config): ~/.mcc default for new installs; ~/.fcc stays legacy, opt-in migrate

Target: MINOR bump `6.39.2` → `6.40.0` (precedent: the `fcc-*`→`mcc-*` command rename shipped as MINOR 4.55.0). Fork `FiredMosquito831/my-claude-code`; never `origin`.

## What was wrong

- New installs and existing installs shared the same default config dir (`~/.fcc`), so a user who started on an older build could not benefit from newer conventions without manual work.
- There was no guided path to move to a cleaner default, and no way to detect a legacy install and prompt the migration.
- Rotated server logs were unbounded — the live install's `logs/` holds **17 GB** of rotated 50 MB `server.*.log` files despite `retention=5` in code.

## What changed

### Config-dir resolution (one function, `config/paths.py::config_dir_path`, cached per process; every consumer routes through it)

Order, in one function (`resolve_config_dir`):
1. `MCC_CONFIG_DIR` env override (NEW — there was no `FCC_CONFIG_DIR`, so no alias).
2. `~/.mcc` if it exists → use it. If `~/.fcc` also exists, log **one** warning naming both; `.mcc` wins.
3. Else `~/.fcc` if it exists **and passes a health check** → use it as the legacy home, with a one-line log and a Get Started banner ("Your data lives in the legacy `~/.fcc`. Run `mcc-migrate` to move it to `~/.mcc`.").
4. Else `~/.mcc`, created fresh. If `~/.fcc` existed but **failed** the health check, log exactly which check failed and leave it untouched (never delete, never rename); the banner names the failure.

**Health check** (measurable, in order, nothing else): dir lists; `.env` present and `Settings()` builds from it (loads the legacy `custom_providers.json` first so custom-provider model refs validate); `logs/requests.db` absent or opens `mode=ro` with the columns the store requires (reuses the store's own `required_request_columns()`); `custom_providers.json` absent or parses as the `{"providers": [...]}` wrapper.

### Opt-in migration

New `mcc-migrate` (+ `fcc-migrate` alias) and `POST /admin/api/migrate-config-dir` behind `require_loopback_admin`. Behaviour:
- Refuse unless `~/.mcc` is absent (raises `MigrationError` → HTTP 409).
- Single atomic `os.replace(~/.fcc, ~/.mcc)`. On Windows the rename **fails with `PermissionError` if any file inside is open** — which is the safety check (the spec agent proved it): on failure, report the likely holders (the tray via `~/.fcc/desktop.lock`, the server, `mcc-*` launcher sessions, the deferred updater — PID/command-line scan on Windows via `tasklist`, `lsof`-free reasoning on POSIX), move nothing, and tell the user to close them and re-run.
- On success create an **empty** `~/.fcc-old/` holding only `RESTORE.txt` (the literal one-line `Move-Item`/`mv` command + the date). If `~/.fcc-old` already exists, leave it and say so. The user restarts the server themselves (the command prints it; nothing is restarted for them).

### Legacy compatibility — all kept

The 12 `fcc-*` console scripts, `fcc-desktop`, the `free_claude_code` compatibility package, and `FCC_*` env vars are **untouched**. Where a `FCC_*` var exists today it is accepted as an alias of the new `MCC_*` name (pydantic `AliasChoices`, `MCC_*` first), with one deprecation log line per process. The admin persistence prefix (`config/admin/persistence.py`) now accepts **both** `MCC_` and `FCC_` prefixes (was `_FCC_OWNED_ENV_PREFIX = "FCC_"`, now `_OWNED_ENV_PREFIXES = ("MCC_", "FCC_")`).

Alias table (`MCC_*` ↔ `FCC_*`, canonical first):
- `MCC_CONFIG_DIR` — NEW, no legacy form.
- `MCC_ENV_FILE` / `FCC_ENV_FILE` (explicit dotenv override).
- `MCC_OPEN_BROWSER` / `FCC_OPEN_BROWSER`.
- `MCC_CODEX_API_KEY` — process-local, freely renamed.
- `MCC_PI_API_KEY` / `FCC_PI_API_KEY`, `MCC_PI_BASE_URL` / `FCC_PI_BASE_URL` — private protocol.
- Admin-owned prefix: `MCC_*` and `FCC_*` both persist.

Not renamed (no `FCC_` prefix today): `FCC_TEMP_SUFFIX = ".fcc-tmp"`, `.fcc-backup`, the Codex provider id literal `fcc`, `FCC_SMOKE_*`/`FCC_COMMANDS` (cosmetic).

### Server-log retention cap

New `SERVER_LOG_RETAIN_FILES` setting, default **10** (dashboard field on the Diagnostics card, which owns log rotation). The existing rotation parameter was `retention=5` yet the live install had ~340 rotated files, so the cap is applied by a **startup sweep** in `configure_logging` that deletes the oldest rotated `server.*.log` beyond the cap (never the current file, logs what it deleted). `0` = keep all.

### Docs + drift guard

README, USAGE, the in-dashboard Guide and Get Started now say `~/.mcc` everywhere with a "Legacy `~/.fcc`" subsection and the `mcc-migrate` walkthrough. `tests/contracts/test_docs_reference_drift.py` gains a **fifth check** for config-dir paths (`~/.mcc` allowed; `~/.fcc` allowed only inside the legacy subsections).

## Residual risks

- The live migration is opt-in and refuses while anything holds files — no data should move without the user running `mcc-migrate`.
- The `~/.fcc` → `~/.mcc` rename is atomic only on the same volume (always the case here, both under the user's home).
- `~/.fcc-old` does not let an older build run (it reads `~/.fcc`); `RESTORE.txt` is the rollback.
- `FCC_*` deprecation fires once per process.
- The health check loads a fresh `ProviderRegistry` pointed at the legacy `custom_providers.json` for the duration of the `.env` build, then **restores the previous global registry** so the probe never pollutes the provider ids the rest of the process sees (this was a measured regression — it broke `test_custom_providers`/`test_routing` until restored).
- **UNVERIFIED:** browser drive of the Get Started banner + migrate button (jsdom can't render layout); a real-browser pass is recommended before release.
- AGPL relicensing of inherited MIT code: the inherited MIT portions stay MIT; the user's own additions are AGPL-3.0-or-later. Not legal advice — the user should have counsel review.
