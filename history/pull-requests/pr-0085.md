## What changed

The 5.0.2 running-launcher guard over-corrected: it hard-blocked any install while a launcher was running, but that is the normal flow on POSIX (uv unlinks open files, so the running app keeps old code in memory and picks up the new version on restart). On Windows, uv cannot replace the tool environment while a process runs from it, so the fix is to **defer**, not refuse.

### 1. `install.sh` — removed the running-launcher guard entirely

POSIX install-while-running is native and must keep working.

### 2. `install.ps1` — detects running launchers and defers instead of refusing

When any launcher is live, the installer stages the verified wheel and hands the install to a **detached PowerShell helper** that:
- waits for those launchers to exit (bounded);
- then runs `uv tool install --force` with backoff retry (same as the dashboard updater's deferred helper);
- does **not** start the app — the user restarts it and picks up the new version.

When no launcher is running, it installs directly as before.

## Residual risks

- The deferred helper waits up to 6 hours for the launchers to exit; if they never stop, the install is not applied and the user is told to re-run the installer. The staged wheel is cleaned up after a successful install.
- `Get-Process -Name` matches process names globally (not per bin-dir), which is the right scope — a running proxy child is what blocks uv regardless of which dir it launched from.
