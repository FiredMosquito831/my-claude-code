## Description

## The problem

The Windows installer deferred whenever any launcher was running: it staged the wheel and a detached helper waited (up to 6h) for every launcher pid to exit before running `uv tool install --force`. The user explicitly wants the install to **complete immediately** even with `mcc-claude`/`fcc-claude` windows open — open windows keep old code, new sessions/servers get the new version.

## Why deferring existed

Windows refuses to **delete** a uv tool directory a process runs from (interpreter + loaded `.pyd` held open), so `uv tool install --force` fails partway. But Windows **allows renaming** a directory a process runs from, and a running process keeps already-loaded modules in memory. Verified live: a loaded `.pyd` and the entire tool dir can be renamed while a real session runs from it.

## The fix

`Install-FreeClaudeCode` now, when launchers are running:
1. Renames the old tool env aside → `my-claude-code.old-<ts>`.
2. Runs `uv tool install --force` into the fresh canonical path.
3. Best-effort removes the `.old-*` dir (kept open by live windows → becomes orphaned garbage swept on next install).
4. **Rename failure** (rare hard lock) → falls back to the previous detached-helper deferral.
5. **Failed fresh install** → renames the old dir back, so the user is never left with no working tool.
