## Description

The dashboard's **Update** button stopped halfway: it downloaded, verified and installed/staged the release, then told the operator to restart manually. This closes that lifecycle.

## Why the existing restart callback was not enough

FCC already had an automatic restart callback for config changes. It rebuilds the ASGI application inside the **same Python interpreter**. That is correct for a port/config change and wrong for a package update: `sys.modules` still holds the old bytecode, so it would look like a restart while continuing to run the old release.

This PR adds a separate **process replacement** path and leaves config restart semantics unchanged.

## What happens now

### Linux, macOS and normal WSL/ext4

1. Download and SHA-256 verify the GitHub release wheel.
2. Preserve the uv receipt's Python pin and extras.
3. Install through fixed argv (`uv tool install --force`).
4. Return the successful HTTP response to the dashboard.
5. Gracefully close the complete runtime ownership graph.
6. Flush Loguru's `enqueue=True` queue and clean up registered children.
7. `execv()` the stable `fcc-server` launcher outside the replaced uv tool environment, preserving argv, environment, cwd and PID.

### Native Windows

Windows cannot replace a running tool environment: the interpreter and loaded DLLs hold it open. The existing detached PowerShell helper remains the owner of installation:

1. The server stages the verified wheel and helper.
2. The upgrade response is returned.
3. The server gracefully closes and exits.
4. The helper pins the parent by PID **and creation time**, waits for handle release, and retries uv with the existing backoff.
5. It records success/failure and starts `fcc-server.exe` **only after success**.

A failed or partial install is never relaunched.

### WSL tool directory under `/mnt`

Refused before install. DrvFs may expose Windows file-lock semantics even though Python reports POSIX; attempting in-place replacement can corrupt the environment. The error tells the operator to move `UV_TOOL_DIR` to WSL's filesystem or update after stopping.

## Adjacent bug fixed

The uv receipt path was hardcoded to `~/.local/share/uv/tools/...`. On Windows the real path is under `%APPDATA%\uv\tools`, so dashboard updates silently dropped installed extras and pinned the wrong interpreter. Receipt and launcher roots now come from:

```text
uv tool dir
uv tool dir --bin
```

That honors platform defaults and `UV_TOOL_DIR`.

## Dashboard behavior

The button now moves through:

```text
Updating… → Restarting — reconnecting… → Updated and restarted on vX.Y.Z
```

Reconnect polling:

- tolerates the expected connection refusal while the port is unbound;
- ignores a response from the old process;
- resolves only when the installed version answers;
- times out with a concrete error after two minutes.

Deferred helper outcomes render exactly once after relaunch, including successful Windows installs, then the receipt is consumed.

## Residual risks

- Native Windows helper relaunch is pinned structurally and by the existing helper contract tests, but this PR has not yet been exercised as a published N-1 → N dashboard update against an isolated Windows uv installation. That must be the release acceptance test before the live WSL install.
- A streaming request still active after Uvicorn's five-second graceful-shutdown budget may be cut. The server does not splice or replay committed output during an update.
- WSL installations deliberately configured under `/mnt` require moving the uv tool root or a stopped-server install; this release refuses rather than risk corruption.
