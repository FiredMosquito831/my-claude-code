## The problem

Reasoning is translated **per provider**, with no per-**model** knowledge. `ReasoningEncoder.encode(body, policy)` receives no model information at all and fires unconditionally.

That is how a numeric budget reached a model that only accepts an effort enum (see v5.31.1, Fireworks), and how `xhigh` reaches a model whose vocabulary stops at `high`.

## The find

models.dev publishes exactly the missing data — and **this project already fetches and disk-caches that index** for cost, context limit and vision, then discards every reasoning field.

```json
"reasoning": true,
"reasoning_options": [{"type":"toggle"},
                      {"type":"effort","values":["low","medium","high"]},
                      {"type":"budget_tokens"}]
```

Measured against the live 4 MB index:

```
192 providers, 6838 models, 4718 reasoning-capable
reasoning_options: effort 2515 | toggle 1081 | budget_tokens 587
effort values: none, minimal, low, medium, high, xhigh, max
```

The effort vocabulary is **identical** to this project's `ReasoningEffort` enum, and the three option types map **one-to-one** onto the encoder families already in the code (`NamedEffortReasoning` / `ThinkingObjectReasoning` / the budget path).

Coverage for this project's 56 providers: **42 resolve** (with an alias map), covering 2,569 models of which 1,276 carry `reasoning_options`. The 14 with no entry — `agnes`, `commandcode`, `featherless`, `llamacpp`, `mistral_codestral`, `nararoute`, `nous_portal`, `ollama`, `opencode_go`, `qwencloud`, `qwencloud_coding`, `sambanova`, `tokenrouter`, `wafer` — resolve to unknown, never an error.

## What this adds

- **`ModelReasoningCapability`** beside `ProviderModelInfo`. Three independent control-style booleans rather than one enum, because a model can advertise several at once and callers ask about each separately. Every field's `None` means **unknown**, deliberately distinct from a known `False` — the consumer must only change behaviour for capabilities it can confirm.
- **Parsing** of `reasoning`/`reasoning_options`, tolerating malformed entries and dropping value strings that are not `ReasoningEffort` members (the stray `"default"`) rather than raising.
- **A lookup**, layered `provider-reported → models.dev → None`.

## The trap this deliberately avoids

The lookup reads the **disk** cache, never the in-memory `ProviderModelCache`.

That cache is populated *only* by the admin `/admin/api/models/refresh` endpoint and is **empty on a fresh server**. A lookup gated on it would leave this entire feature silently never firing — the exact failure mode this project has hit four separate times. There is a test named for that specific trap, and it is mutation-verified.

## Residual risks

**models.dev is hand-curated and externally maintained**, so we inherit its update lag; a brand-new model may be absent for a while. That degrades to unknown, which the next PR treats as "behave exactly as today", so the failure mode is *no improvement*, never a regression.

**Model-id matching is string normalisation**, reusing the existing `_normalize_candidates`. A provider whose model ids diverge from models.dev's spelling will resolve to unknown rather than mismatch — verified for the 14 uncovered providers.
