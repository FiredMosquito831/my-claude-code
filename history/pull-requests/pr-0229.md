## Description

## What was wrong

An attempt row in `request_attempts` carried **one** status, **one** credential and **one** duration — however many times the provider had actually knocked.

Request `req_f3b018…` (2026-08-30 09:12:18Z) spent 107 seconds making **fifteen** upstream tries across **three** credentials, met **twelve 429s before a 502**, and slept **96 of those 107 seconds** in MCC's own exponential backoff. The database recorded exactly this:

| column | value |
|---|---|
| `outcome` | `failed` |
| `error_kind` | `upstream` |
| `error_message` | `Upstream provider NIM returned HTTP 502.` |
| `duration_ms` | 107534.16 |
| `key_index` | `0` |

None of the fifteen tries, the twelve 429s, the three keys, the twelve sleeps or the three health decisions existed anywhere in the database. The 502 was the last thing that happened, not the thing that went wrong.

Measured against the live install, read-only (`sqlite3.connect("file:…?mode=ro", uri=True)`), over the one hour where the retained server log overlaps the database:

```
attempts of kind unavailable/timeout/upstream/rate_limit in the log window: 16
distinct requests:                                                         14
requests with >= 2 upstream statuses behind the ONE recorded:              14  (100%)
requests with >= 2 DISTINCT status codes behind it:                        13  ( 93%)
upstream status observations in the log for those requests:               178  (429x147, 502x19, 503x12)
DB attempt rows carrying them:                                             16
=> 162 of 178 upstream statuses (91%) unrecorded
MCC backoff seconds slept inside those 14 requests:                        720
limiter reactive-wait seconds inside them:                                 143
```

A second request was stored as `timeout` / *"Provider 'x' produced no output within 120s."* — which is **false in the way that matters**: the model never received an accepted request at all. Its whole deadline went on 429 retries and limiter waits. The row sent the reader to the wrong setting.

### The mechanism

The retry ladder lives in `ProviderRateLimiter.execute_with_retry` (`providers/rate_limit.py`) and the limiter's reactive block. The only thing that had ever seen it was `trace_event`, which writes to the logger at **DEBUG** — off at the shipped `INFO` level. `RequestCapture` had no holder for it, so nothing survived to the commit boundary.

Separately: `RequestCapture.record_attempt_result` read the shared credential-attribution slot at observer time, and `_AttemptLedger.publish()` fires the observer for **every** attempt in one loop at the end of the chain. So the chain's *last* key was stamped onto every row — including skipped attempts and attempts against a different provider's pool entirely.

## What this does

**It records and renders. It decides nothing.** Retry counts, backoff delays, credential health, rotation and deadlines are unchanged.

- **`core/upstream_ladder.py`** (new) mirrors `core/wire_capture.py` exactly: a mutable dataclass in a `ContextVar`, installed once per request by `RequestCapture`, written by `providers/` through module-level functions that are a no-op outside a tracked request and take only primitives — so `core/` stays SDK-free and providers keep sole ownership of classifying their own failures.
- **Producers** sit *after* the decisions they describe: every try and every backoff sleep in the retry loop; every reactive wait in the limiter; the fully-benched pool in the rotating loop; and every credential-health verdict in `report_failure` — whose bench duration is **read back out of the rotation engine that just set it** (`max(slot.cooldown_until, slot.lockout_until) - clock()`), never recomputed from tuning.
- **Storage**: the ladder goes in `params.ladder`, beside `params.wire`. One new column, `ladder_tries INTEGER`, added through the guarded `_ATTEMPT_ADDED_COLUMNS` / `_ensure_attempt_columns` pattern, denormalised so the new Analytics aggregate can restrict its `json_each` scan to rows that have a ladder at all. The INSERT column list and its placeholders are still generated from one tuple, and a new test asserts every named column round-trips.
- **The root-cause sentence is stored, not composed in the browser**, so the modal and all four export formats say the same string and a test can pin it verbatim.
- **The `key_index` regression is fixed**: each attempt's credential now comes from that attempt's last upstream try, falling back to the attribution slot only when it recorded none.

### What it looks like

Regression test, replaying the real `req_f3b018…` ladder from server.log (anonymised) — asserted **verbatim**:

```
3 keys × 5 tries: 12×429, 3×502 — 96s of the 107s were MCC backoff sleeps; keys 0 and 1 benched 60s on 429 (no Retry-After); key 2 not charged (502 is not credential-shaped)
```

A timeout whose duration went on backoff gets a different sentence:

```
deadline reached after 148s of backoff — the model never received an accepted request: 2×429, 1×502
```

The stored `error_message` is deliberately **not** changed — it is the executor's true statement about its own deadline. The ladder is what explains it.

In the request-detail modal (`createElement` + `textContent` only; no `innerHTML`, no `insertAdjacentHTML`):

- an attempt headline — `15 tries · 12×429, 3×502 · 3 keys · 96s sleeping`
- the stored root-cause line
- `Show 15 upstream tries` → one row per try: `#7 · key 1 nvap…8f21 · 429 · 410ms · waited 4900ms · retry-after 12s`, with a redacted excerpt of the upstream's own body under each try that had one
- one line per credential: `key 0 nvap…8f21 — benched 60s (rate_limit): 429, no Retry-After -- operator cooldown 60s` / `key 2 — health unchanged: 502 is not credential-shaped`

Plus **Analytics → Upstream statuses**, counting by the status the upstream actually returned rather than the one mapped kind that survived the ladder, and three request-level export columns (`Upstream tries`, `Upstream statuses`, `Root cause`) in all four formats.

### One deliberate deviation from the spec

`extend_reactive_block` is **not** recorded as a wait. It is called with the same delay that is slept immediately afterwards, so recording both would double-count the same seconds and make `time_sleeping_ms` — the number the root-cause sentence is built on — a lie. Time is recorded where it is actually spent: the backoff sleep and the limiter's own wait.

## Residual risks

- **`json_each` aggregate cost on a large window.** The Analytics "Upstream statuses" block scans `params` JSON for rows where `ladder_tries > 1`. The guard is what the denormalised column exists for — the measured share of attempt rows that ever retry is ~4.6% — and the result rides the existing 5-second stats cache. On a very large window it is still the most expensive aggregate on the page; it is wrapped in the same `try/except sqlite3.Error` as the recovery aggregate, so one unreadable `params` value degrades the block rather than the page.
- **The 800-char per-try body cap loses detail on verbose upstreams.** Truncation is marked (`body_truncated`), and the status, credential, timing and wait are recorded regardless of the body. `REQUEST_LOG_LADDER_BODY_MAX_CHARS` raises it.
- **`params` blob growth.** Worst case 60 tries × 800 chars = 48 KB per attempt, against the 8,000-char wire body already stored per attempt. Typical is 3–5 tries with short bodies. `MAX_TRIES_PER_ATTEMPT = 60` bounds the array and `summary.tries_dropped` records what was dropped, so the count stays truthful.
- **A provider not routed through `execute_with_retry` would record a shorter ladder than reality.** Every current commit boundary does go through it (`openai_chat:378`, `anthropic_messages:191`, `chatgpt_oauth:303`/`:325`, `vertex/client:125`), and the native `anthropic` provider delegates its streaming to `AnthropicMessagesProvider`, which does — but a future provider that opens its own stream would need its own producer.
- **`error_kind` on a try is the SDK exception class name when the provider had not yet classified the failure** (the retry frame runs before the classifier). The *status* is always the observed one. Documented on the field.
- **Old rows show no ladder.** That is **"not measured"**, not "there were no retries" — stated in the README, USAGE and the in-dashboard guide.
- **The pre-existing local baseline is 15 failures**, listed above, unchanged by this PR.
- **Not done deliberately:** per-attempt rows are still absent from every export (the three columns are a request-level rollup); no new index was added to `request_attempts`; `.env.example` was not edited (writes to it are denied in this environment) — the README, `docs/USAGE.md` and the admin manifest carry the `REQUEST_LOG_LADDER_BODY_MAX_CHARS` documentation instead.
