## Description

Found by probing the values rather than reading the code. Two things were wrong with the settings promoted in 4.50.0.

## A blank value refused to start the server

```
case              outcome    result
absent            loads      120.0
blank             REFUSES    "Input should be a valid number"
```

The admin UI writes `KEY=` for a cleared field, and a hand-edited file can hold the same — so "stop specifying this" was indistinguishable from "this is broken". Blank now means the default, which is what clearing a field is asking for.

## Nothing was bounded

```
compression 42     loads     REQUEST_LOG_COMPRESSION_LEVEL = 42
retries -4         loads     PROVIDER_RETRY_ATTEMPTS = -4
holdback -1        loads     STREAM_COMMIT_HOLDBACK_SECONDS = -1.0
deadline 99999999  loads     FALLBACK_FIRST_TOKEN_TIMEOUT = 99999999.0
```

Level 42 validated as **valid** and then failed on every body write — zstd's real ceiling is 22, so request logging would have broken silently.

## One table, three readers

`config/limits.py` holds the ranges. Settings clamps to it so the server always starts, the manifest publishes it so the number input carries `min`/`max` and the help says *"Accepts 1 to 22."*, and the admin validator quotes it back rather than silently clamping what someone typed.

The two answers to a bad value are deliberately different: a **form** can reject it while the user is looking at it; a **file** edited by hand is only discovered at boot, where refusing to start is worse than running a sane value and logging the change.

Bounds are wide on purpose — they rule out values that cannot work, not values someone might reasonably want. A provider always gets at least one attempt; a holdback above 30s is latency rather than a recovery window; `0` keeps its documented meaning wherever it had one.
