## What this adds

**Detection.** The card now enumerates every user-level `settings.json` that could apply on this machine, most likely first, and reports for each whether it exists and whether it already points at this proxy.

Under **WSL that is two genuinely different files** — your Linux home and your Windows home — which different Claude Code installs read. That is the failure mode most likely to waste an afternoon: configure one, launch the other, conclude the proxy is broken. Now both are listed and selectable.

**Precedence warnings.** Enterprise `managed-settings.json` and its drop-in fragments are located per platform and surfaced as warnings, because they outrank the file being configured:

| OS | managed path |
| --- | --- |
| macOS | `/Library/Application Support/ClaudeCode/managed-settings.json` |
| Linux / WSL | `/etc/claude-code/managed-settings.json` |
| Windows | `C:\Program Files\ClaudeCode\managed-settings.json` |

Drop-in `*.json` fragments in the sibling `managed-settings.d/` directory are included. Windows registry policies are out of scope and not read.

## A warning we shipped that could never fire

4.26.0 warned about a sibling `~/.claude/settings.local.json`. **Claude Code does not read that file.** Measured against 2.1.223 in a controlled home directory with identical content in each:

| file in `~/.claude/` | requests reaching the proxy |
| --- | --- |
| `settings.json` | **4** |
| `settings.local.json` | **0** |

The `settings.json` row is the positive control — it proves the method works, so the zero is real. `local` scope is repository-root only, exactly as the docs say; our code assumed a sibling of the user file.

So the check is **deleted rather than extended**, `claude_local_settings_path()` goes with it as dead code, and the two tests that asserted the old behaviour now assert the measured one with the evidence recorded in a comment.

Project-level files *do* outrank the user file, but the server cannot know which repository you are in — so that is a one-line static caveat in the card, not a filesystem scan.

## API change

`ClaudeSettingsStatus.local_override` → `overrides`, a list of `{path, scope, variables}`. It carries only variable **names**, so an override file's secrets cannot leak through it. `GET /admin/api/claude-settings` returns `targets` in place of `suggested_paths`. No compatibility shim — every consumer updated.
