## Description

Answering "does the Analytics search box actually work?" — it worked, but it was looking at a minority of what it had stored.

## The gap, measured on real data

Search matched only `input_text` and `output_text`. On the reporter's live log:

```
rows                50,059
with thinking_text  27,745  (55.4%)
with tool_calls     38,934  (77.8%)
```

Proven by probing 600 of their real requests — a phrase occurring **only** in reasoning and one occurring **only** in a tool call:

| | before | after |
| --- | --- | --- |
| `"understand what keys"` (reasoning only) | **0 rows** | 308 |
| `"backend start command"` (tool call only) | **0 rows** | 422 |
| control: phrase from the prompt | 600 | 600 |

## What changed

- Search covers **prompt, reply, reasoning, and tool calls**.
- Tool calls match on their **string values**, not their JSON encoding — the encoding both misses (`C:\Users` is stored escaped) and misleads (every row contains the key name `command`).
- **Multi-word queries require every word somewhere in the request**, not an adjacent phrase. `proxy 8082` now finds a request whose prompt says "restart the proxy" and whose reasoning says "port 8082 is busy". A single word is unchanged, and since a phrase match implies every word is present, this only ever adds results.

## Performance

Searching two more fields costs less than the version that searched two:

| 600 real rows | first working version | this PR |
| --- | --- | --- |
| three words | 991 ms | **518 ms** |
| tool path | 1,116 ms | **436 ms** |

Case folding moved from Python text to bytes: 7× cheaper on a 43 KB body (0.533 → 0.073 ms), found by profiling the per-row cost. It is also **more correct** — SQLite's `LIKE` is case-insensitive for ASCII only, so folding in text would have made compressed rows match things the inline rows beside them did not.

## Verification
