## Description

7.113.5 (#317) taught OpenCode Go to read its own registry bucket, so a Go
model resolves to the door the vendor publishes. This release lets a model have
more than one door.

`muse-spark-1.3-contributor` was measured on 2026-10-29 answering HTTP 200 on
both `/v1/messages` and `/v1/responses`; the resolver could still only answer
with one of them. A wrong door also cost the request, and a model the vendor
places on an API this build cannot speak (`@ai-sdk/google`) was refused before
any call.

- The inbound client family (`/v1/messages` -> Anthropic; `/v1/chat/completions`
  and `/v1/responses` -> OpenAI; nothing in flight -> unknown) orders the doors
  a model is *known* to answer on. The order is a sort key, never a filter.
- The known set is the first non-empty rung of: operator override, learned,
  **measured** (new: a dated measurement shipped with the build), vendor
  registry, marketplace upstream, profile floor.
- A known door that answers wrong-door evidence is pruned from the learned set
  (a list, `source=probe`, seven-day TTL, same row identity,
  `DOCUMENT_VERSION` still 2) and the client's request continues on the next
  known door inside the same attempt. `429`/`401`/timeouts/region refusals and
  a `404` on a vouched-for door never teach; a `404` on a *guessed* door does.
- On the two OpenCode profiles (`optimistic_first_try`) an unservable
  declaration is a reason to probe once (~16 tokens), not to refuse; the
  vendor's statement and reason stay on the Models page until a probe answers.

The client family reaches the resolver through a per-request `ContextVar`
installed by `ProviderExecutor.stream` -- the one funnel every door shares and
the only file of the frozen boundary this PR touches, by design.
