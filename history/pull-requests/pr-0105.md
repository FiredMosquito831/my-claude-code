## Description

## What

Site persistence previously remembered only the active view, auto-refresh toggle/interval, and web-search period. An F5 on the Analytics page lost every filter. Now:

- **Persist the analytics filters + page** — provider, model, key, search, status, endpoint, window, page size, and the page offset are saved to `mcc-dashboard-state` and restored on refresh.
- **New "Clear filters" button** in the requests toolbar resets every filter to its default and reloads the view in place.

## Why

The user asked: "when i refresh remember what page i was on before and let me continue from there and also remember my analytics options (like auto-refresh and its time) also add a button to clear filters for analytics."

## Two real bugs found and fixed while verifying in a live browser

1. **Early-load localStorage race** — `restoreDashboardState()` returned an empty object when called at the very start of `load()`, because the browser settles localStorage during the initial synchronous script execution. Reading it after the first `await` makes it reliable. Reproduced in **both** jsdom and a live browser before the fix (this is why the existing v5.2.0 persistence looked flaky).
2. **Initial-load state clobber** — navigation during `load()` persisted half-restored state (empty filters) over the saved state. A `state.loading` guard blocks persistence during load, cleared in a `finally` so an error can never leave persistence disabled.

## Verification (real browser, throwaway server on :8163, fake home)

- Set filters → Apply → reload → activeView + all 6 filters + pageSize restore correctly.
- Clear filters → every input resets, view reloads, cleared state persists.
- 100 admin + docs-label tests pass.

## Residual risks

- Restore is deferred until after the onboarding fetch completes; if that endpoint hangs, filters restore late. Acceptable (onboarding is a fast local call).
- The page offset restores only when > 0 (page 1 always starts at 0).
