## Description

Second of four from the fallback audit.

## The gap

The provider holds a brief window of SSE so an early cutoff can be retried invisibly. That window was anchored to **the first frame of any kind** — so a model that emitted `message_start` and then stalled had already committed the route. Nothing had reached the reader, and yet no fallback was possible, because a second attempt would put a second `message_start` into a stream the client was already reading.

Measured on 21 days of live traffic, the 500 requests that ran the full 600s budget *with a chain configured* split cleanly:

```
393  non-streaming, scaffolding only    reader saw nothing
106  streaming, real content produced   reader saw output
  1  streaming, scaffolding only
```

Only the first and last groups are recoverable at all, and both were lost to this anchor. The 106 have genuinely shown the reader something and are beyond any fallback — they need a stall guard, which is not this change.

## What changed

The window now starts at the **first non-scaffolding frame**. `message_start`, `message_delta`, `message_stop`, `content_block_start`, `content_block_stop` and `ping` never start it, so a stream producing only envelope stays uncommitted however long it takes.

**The window itself is kept**, rather than committing on content's first byte. That distinction is the entire point of the buffer: bytes still held have not reached the client, which is what lets the provider retry an immediate cutoff with no visible seam. Committing on first content removed that grace and broke two existing provider tests — which is how the trade-off was found, and why the final change is much smaller than the first draft.

## Two things mutation testing changed about the design

**1. Three classes collapsed to two.** The first draft returned `content | scaffolding | unknown`. Mutating "thinking and tool deltas are content" failed *nothing* — because with a window, content and unknown behave identically (both start the clock). Only "is this scaffolding" ever mattered. The third class read as precision while changing nothing any caller did.

**2. A redundant check was actively wrong.** The predicate also required `not isinstance(data["delta"], dict)`. Mutating it away failed nothing either: `content_block_delta` is already outside the scaffolding set by type. Worse, the clause **misclassified `message_delta`**, which legitimately carries a `delta` holding a stop reason and usage — not any part of the answer. Classifying on frame type rather than on the presence of a `delta` field is what keeps that right, and there is now a test pinning it.

## Verification

Guards mutation-tested, each failing **by name**:

| mutation | caught by |
| --- | --- |
| M1 scaffolding starts the window again | `scaffolding_never_commits_however_long_it_takes` |
| M2 content commits instantly | 12 tests, including both provider invisible-retry contracts |
| M3 `content_block_delta` treated as envelope | 5 tests |
| M5 byte cap removed | `the_byte_cap_still_bounds_what_is_held` |

Three existing tests were **updated, not silenced** — the behaviour they pinned changed deliberately, and each now states the new anchor in its docstring.

Local CI: `ruff format --check`, `ruff check`, `ty` clean; pytest **4,811 passed** with the documented 6 `test_install_ps1_*` baseline failures.

## Residual risks

- **This is NOT demonstrated to fix the 393 production hangs, and I am not claiming it does.** I built two stub upstreams — one emitting a role-only delta, one emitting empty content deltas — and *both fell back correctly on unmodified `main` as well*. Neither reproduces whatever frame flushed the buffer in production, so the fix cannot be credited with them on this evidence. What bounds those regardless of cause is the per-attempt deadline, which is next in the series.
- **Slightly later commit for normal streams.** A stream now commits 0.75s after its first *content* frame rather than 0.75s after `message_start`. In practice `message_start` is immediately followed by content, so the shift is small — but it is a real change to when invisible retry stops being possible.
- **The 106 committed-then-stalled requests are untouched** and will keep hitting the total budget. They are the case a stall guard would cover; that was offered and not selected.
