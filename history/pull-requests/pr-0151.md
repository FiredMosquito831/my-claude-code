## Description

## What was broken

A client thinking budget was written into `reasoning_effort`, a field Fireworks defines as a **string enum**. Measured against the real profile before the fix:

```
fireworks   budget_only -> {'reasoning_effort': 8192}
```

An integer in an enum field. Any client asking for a specific thinking budget on Fireworks sent an invalid request. The profile also emitted `"xhigh"`, `"max"` and `"none"` — none of which appear in Fireworks' own API reference — and it held the only `budget_field="reasoning_effort"` wiring in the codebase, with **zero tests** covering it.

## Mechanism

`NamedEffortReasoning.budget_field` writes the numeric budget into the named field. That is correct for LM Studio (`reasoning_tokens` is a real numeric field) and wrong for Fireworks, whose numeric path is a separate top-level object.

Per [docs.fireworks.ai/guides/reasoning](https://docs.fireworks.ai/guides/reasoning), verified against the primary source:

> "You cannot specify both `thinking` and `reasoning_effort` in the same request. If both are provided, a validation error will be raised."

```python
thinking = {"type": "enabled", "budget_tokens": 4096}   # must be >= 1024
```

## The fix

Adds `EffortOrThinkingBudgetReasoning`, a general encoder for gateways where a named-effort field and a numeric `thinking` object are mutually exclusive on the wire, and rewires Fireworks onto it:

| Input | Emitted |
| --- | --- |
| effort | `reasoning_effort`, narrowed to `low\|medium\|high` (xhigh/max clamp to high) |
| explicit budget | `thinking {type: enabled, budget_tokens: N}`, clamped up to 1024; `reasoning_effort` omitted |
| reasoning off | `thinking {type: disabled}`; `reasoning_effort` omitted (was `"none"`) |

The two fields can never coexist **by construction** — each branch returns.

Narrowing rather than widening is deliberate: an unsent reasoning field costs thinking on one provider, a wrongly-sent one fails every request, and Fireworks does not document what an unrecognised value does. Clamping up to the vendor's documented floor (rather than refusing) follows the existing clamp-non-interactively rule — our internal table maps MINIMAL/LOW to 512, which Fireworks would reject.

`budget_field` is **kept** — `lmstudio/client.py:52` is a real user of it.

## Not done

**Per-model gating.** Fireworks does not document whether a non-reasoning model rejects or ignores `reasoning_effort`, and the codebase has no per-model capability data. Tracked separately.

**No live key.** Every assertion here is against the emitted request body and the vendor's published contract — not a real Fireworks call. That distinction is deliberate and stated.

## Residual risks

The `thinking {type: "disabled"}` form for turning reasoning off follows Fireworks' Anthropic-compatible `thinking` object, but the docs page shows only the `enabled` example — the disabled spelling is inferred from that convention. It replaces `reasoning_effort: "none"`, which was undocumented in the same way, so this is not a regression in confidence. Everything else is quoted from the vendor's own reference.
