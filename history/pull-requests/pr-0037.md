## What this adds

**Detection.** The card enumerates every user-level `settings.json` that could apply on this machine, most likely first, and reports for each whether it exists and whether it already points at this proxy.

Under **WSL that is two genuinely different files** — your Linux home and your Windows home — which different Claude Code installs read. That is the failure mode most likely to waste an afternoon: configure one, launch the other, conclude the proxy is broken. Both are now listed and selectable.

**Precedence warnings.** Enterprise `managed-settings.json` and its drop-in fragments are located per platform and surfaced as warnings, because they outrank the file being configured:

| OS | managed path |
| --- | --- |
| macOS | `/Library/Application Support/ClaudeCode/managed-settings.json` |
| Linux / WSL | `/etc/claude-code/managed-settings.json` |
| Windows | `C:\Program Files\ClaudeCode\managed-settings.json` |

Drop-in `*.json` fragments in the sibling `managed-settings.d/` directory are included. Windows registry policies are out of scope and not read.

## A warning we shipped that could never fire

4.26.0 warned about a sibling `~/.claude/settings.local.json`. **Claude Code does not read that file.** Measured against 2.1.223 in a controlled home directory with identical content in each:

| file in `~/.claude/` | requests reaching the proxy |
| --- | --- |
| `settings.json` | **4** |
| `settings.local.json` | **0** |

The `settings.json` row is the positive control — it proves the method works, so the zero means something. `local` scope is repository-root only, exactly as the docs say; our code assumed a sibling of the user file.

The check is **deleted rather than extended**, `claude_local_settings_path()` goes with it as dead code, and the two tests that asserted the old behaviour now assert the measured one with the evidence recorded in a comment.

Project-level files *do* outrank the user file, but the server cannot know which repository you are in — so that is a one-line static caveat in the card, explicitly labelled as not a detection result, rather than a filesystem scan.

## API change

`ClaudeSettingsStatus.local_override` → `overrides`, a list of `{path, scope, variables}` carrying only variable **names**, so an override file's secrets cannot leak through it. `GET /admin/api/claude-settings` returns `targets` in place of `suggested_paths`. No compatibility shim — every consumer updated.

## Verification

Per-platform detection, probed by monkeypatching `sys.platform` and the path constants:

```
macOS    -> ['managed-settings.json', 'a.json']     drop-in *.json included
linux    -> ['managed-settings.json', 'a.json']     .txt ignored
windows  -> ['managed-settings.json', 'a.json']
malformed managed file -> no override, state unchanged, no exception
this machine (win32)   -> 1 candidate, 0 managed
```

Live against a 4.28.0 server:

```json
"targets": [{"path": "C:\Users\...\.claude\settings.json",
             "exists": true, "state": "unset", "is_default": true}]
"overrides": []
```

`suggested_paths` is gone from the codebase entirely; `/admin` and both assets serve 200.

**Full suite after the rebase: 3182 passed, 14 failed** — the documented pre-existing baseline, unchanged on unmodified `main`.

> Note for anyone running this locally: an `ENABLE_WEB_SERVER_TOOLS` value in your shell environment defeats `Settings()` isolation and inflates that count to ~43. Unmodified `main` fails identically with it set. Run with `env -u ENABLE_WEB_SERVER_TOOLS` to see the true baseline. CI has no such variable.

**One flake, fixed:** a new API test failed once in a full run while passing in isolation. It monkeypatched `ANTHROPIC_AUTH_TOKEN` and so depended on whether settings had already been cached in that xdist worker. The dependency is removed; the affected selection then ran clean three times.
