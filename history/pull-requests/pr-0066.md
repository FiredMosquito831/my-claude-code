## Description

Reported twice as *"analytics resets after 50,070 requests"*. Checked against the reporter's live server:

```
windowed total     : 50,080     <- oscillates 50,000 -> 50,099 -> back
retained_rows_max  : 50,000
retention notice   : SHOWN
lifetime requests  : 50,620     <- climbing correctly
compressed bodies  :    573     <- 4.46.0 running
```

Nothing resets, and nothing was broken. Prune runs every 100 inserts, so stored rows climb just past the cap and drop back to it, forever. **A card labelled "Total requests" made that look like a counter resetting.**

## The label was the bug

- **"Total requests" → "Stored requests"**, with `at the storage cap — older ones deleted` underneath once the cap is reached. The number was always right for what it counted; the label promised something it could not deliver.
- The retention note now leads with the consequence nobody had stated: **pruned requests are deleted**. They cannot be listed, opened or searched. All-time keeps counting, but those are *counts* — a rollup does not bring rows back. Raising `REQUEST_LOG_MAX_ROWS` is the only way to browse further back, and the note now quotes the real cost (~7 KB a request compressed, against 41 KB before) so the disk trade is concrete rather than abstract.
- Page size gains **250** and **500**, matching the limit the API already allowed.
