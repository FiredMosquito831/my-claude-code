## Description

## Why

A new install landed on the Providers tab with no indication of what to do first, in what order, or when setup was actually finished.

## What this adds

A **Get Started** view, first in the nav and the landing view on first run. Seven steps, each with a button that switches to the page where the work actually happens — it walks you through the dashboard rather than duplicating it.

| Step | Opens | Green when |
| --- | --- | --- |
| Connect a model provider | Providers | a provider credential exists |
| Set your fallback model | Model Config | the fallback can actually serve a request |
| Point Claude Code at FCC | Providers → settings card | that file really says so |
| Enable web search *(optional)* | Web Search | a search credential exists |
| Connect messaging *(optional)* | Messaging | the selected platform has its token |
| Send your first request *(optional)* | Analytics | the request log has a row |
| Take the tour *(optional)* | Guide | you have opened it |

## Done-ness is derived, not ticked

Every step's state comes from **actual configuration, server-side**. A step is green because a credential exists — not because someone clicked something. The checklist therefore cannot drift from reality, stays correct when you configure something outside the flow, and goes back to red if you later remove a key. The Claude Code step reuses the same `read_status` the 4.28.0 settings card uses.

Steps derive from `PROVIDER_CATALOG` and `WEBSEARCH_CATALOG`, not a hardcoded list of env var names, so a new provider is picked up automatically.

## A required step that was green for everyone

`MODEL` ships with a template value, so an "is it non-empty" check reported **Set your fallback model** as already done on a machine where nothing was configured — a required step pre-satisfied on a fresh install.

It now asks whether the fallback **can actually serve a request**: the model ref's provider prefix resolves to a provider that has a credential. Keeping the shipped default is still legitimately done once its provider has a key, which is more useful than nagging about a model that already works.

## Residual risks

- `analytics` is done once the request log has any row, so it stays done forever after your first request. That is the intended reading of "you've seen traffic", not a live health check.
- The messaging check knows Telegram and Discord specifically; a future platform needs adding there, unlike the provider checks which are catalog-driven.
- Auto-open triggers whenever the checklist is incomplete and undismissed, so a user who deliberately skips an essential step keeps landing on it until they dismiss.
