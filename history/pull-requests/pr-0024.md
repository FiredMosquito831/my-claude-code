## Description

Third and final defect in the Windows update path. PATCH `4.21.3` → `4.21.4`.

## What was wrong

The deferred helper was spawned with `DETACHED_PROCESS`, which denies the child a console. `powershell.exe` then **exits immediately without running the script** — so the staged update silently never installed, and no result was recorded either. From the outside the update just appeared to do nothing.

Measured across creation-flag variants, everything else held constant:

```
DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP   ran=False
CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP   ran=True
CREATE_NO_WINDOW                              ran=True
CREATE_NEW_PROCESS_GROUP                      ran=True
(no flags)                                    ran=True
```

`CREATE_NO_WINDOW` keeps a console the child can use while hiding it. The new process group is retained so the helper isn't signalled along with the console the server was started from. Survival across parent exit was confirmed separately.

## Verified unattended, nothing stubbed

In an isolated `UV_TOOL_DIR`:

```
env before : 4.21.4
staged     : True  | 4.21.3 is verified and staged…
parent exited — helper running unattended
helper     : ok=True exit=0 | Deferred install completed.
env after  : 4.21.3
entrypoint : free-claude-code 4.21.3
```

The install genuinely happens with no manual step.

## Why this took three attempts

Worth stating plainly: 4.21.2 and 4.21.3 were both tested with the spawn stubbed or the helper script run by hand. Both defects — the `NativeCommandError` and this one — live precisely in the gap those stubs left. The end-to-end path is the only test that would have caught either.

The regression test now asserts `CREATE_NO_WINDOW` is set **and** `DETACHED_PROCESS` is not.

## Still true

An install running 4.21.3 or earlier cannot fix itself — the upgrade is performed by the code already loaded. Windows users below 4.21.4 should update once from the install script; after that the button works.
