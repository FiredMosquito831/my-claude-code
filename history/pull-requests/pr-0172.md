## Description

## The report

> `API Error: 400 Upstream provider OPENROUTER returned HTTP 400.` … `This endpoint's maximum context length is 256000 tokens. However, you requested about 256487 tokens (151032 of text input, 41455 of tool input, 64000 in the output).`

That request had a **seven-model fallback chain configured and used none of it.**

## Cause

Every 400 was classified `FailureKind.INVALID_REQUEST`, and `INVALID_REQUEST` is the single kind on the default skip list, so `_ends_the_route()` aborted the chain. Its docstring gave the rationale:

> *"the same body fails identically on every model, so a chain turns one fast 400 into three slow ones"*

True of a malformed body. **False of a context overflow** — a body that exceeds model A's window succeeds on model B with a larger one. It is the one 400 a chain can actually fix, and it was the one 400 guaranteed not to get a chance.

Measured on a 153,198-request production log: **11 of 22 `invalid_request` failures — exactly half — are context overflows**, across `nous_portal` (7), `nvidia_nim` (2), `open_router` (2).

## Fix

A distinct `FailureKind.CONTEXT_LENGTH`, classified at the **provider boundary** (where SDK/HTTP classification belongs in this codebase), matched at both 400 sites. It is deliberately *absent* from the default `skip_kinds`, so the chain proceeds. Nothing else about a 400 changes.

The matcher covers all three real vendor wordings — `This model's …`, `This endpoint's …`, and Nous's, which hides it after `Additional info:`. Anything unrecognised stays `INVALID_REQUEST` and still ends the route: a false positive would retry a genuinely broken body on every model, so the conservative direction is the cheap one.

`retryable` stays `False` — in this codebase that means "safe to retry the **same** credential", which it is not. That flag governs credential rotation, not the chain.

## The part that wasn't in the plan

My brief said clearing the skip list was "the entire fix". **It wasn't.** `_FAILURE_ERROR_TYPES` in both `core/anthropic/errors.py` and `core/openai_responses/errors.py` is a bare subscript with no default:

```python
return _FAILURE_ERROR_TYPES[kind]
```

Adding a `FailureKind` without adding it to both raises `KeyError` at the commit boundary — turning a clean 400 into a **500** — and only once a chain is exhausted, which is exactly the path this bug takes. No existing test covered it. Both maps now carry `CONTEXT_LENGTH → "invalid_request_error"`, so the client-visible wire shape is byte-identical to today; the new kind steers routing and nothing else.

## Numbers in the message

Reported only when both regexes match, otherwise the bare upstream sentence is kept:

```
Request exceeds this model's context window.
Needed about 256487 tokens; this model holds 256000.
```

## Opting out

`FALLBACK_SKIP_KINDS=context_length` restores today's behaviour. Covered end to end including the settings validator.

## Cost when a chain can't help

These are **rejections, not timeouts** — the upstream validates the token count before scheduling inference. A seven-model chain of context 400s costs ~7 round trips, and `_attempt_deadline` gives each attempt only its share of the remaining budget, which a fast rejection barely touches. Worst case: the same 400 a few hundred ms later, with N extra log rows.

## Deliberately not done

- **No models.dev pre-emptive window selection.** Skipping straight to a model that fits is the better long-term fix; this is its prerequisite, since `CONTEXT_LENGTH` is now an observable signal.
- **No new setting** — `FALLBACK_SKIP_KINDS` already covers the opt-out.

## Residual risks

- **The matcher is substring-based and English-only.** A provider phrasing overflow differently (`"input too long"`, a localised message) still classifies as `INVALID_REQUEST` and still ends the route. This fixes the three vendors we have measured, not all vendors. Adding markers later is cheap.
- **The native-Anthropic SSE path is untouched.** `core/anthropic/upstream_errors.py` maps a mid-stream `invalid_request_error` without inspecting the message, so a native-protocol provider reporting an overflow mid-stream would still end the route. None of the 11 production cases came through that path (all three vendors are OpenAI-compatible). Left alone rather than widening the change — recorded as the most likely place this fix looks incomplete later.
- **No single end-to-end test spans provider classification → executor.** The two halves are each covered and meet at `FailureKind`; that seam is untested by design, consistent with how the suite is layered.
