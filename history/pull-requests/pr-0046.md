## Description

## What was wrong

Reported directly: *"the apply button doesn't light up after setting fallbacks so that i can save them in the .env file."*

The chain editor built its hidden input, wrote every edit into it, and **never put it in the document**:

```js
this.element.append(this.rowsEl, this.addButton);   // this.input is missing
```

`changedValues()` collects fields by walking `[data-key]` across the page, so an input that stays detached is invisible to it. Adding, editing or reordering a fallback updated a node nothing could see: Apply stayed dark and the chain was never written to `.env`.

**The feature has been unusable from the dashboard since it shipped in 4.31.0.**

## The fix

Two places. The editor appends its own input, so the intent is local to the thing that owns it. And `buildFieldControl` enforces the invariant for every control type:

```js
if (!control.contains(input)) control.appendChild(input);
```

That is deliberately not left to each wrapper. It costs nothing when the wrapper already did the right thing, and the failure mode is invisible until someone tries to save — which is exactly how this shipped.

## Why it was not caught

4.31.0 was verified by POSTing to `/admin/api/config/apply` with curl and reading `.env` back. That proved the **server** persists a chain correctly, which was never in doubt, and skipped the only layer that was broken.

Verifying the layer you suspect instead of the layer the bug lives in is a documented trap in this project, and I walked into it again.

## Guard

A static assertion over `admin.js` for both the invariant and the editor's append. The suite has no DOM harness, so this follows the same approach the installer tests use for behaviour CI cannot execute. It is a weaker test than rendering the page — **and it would have caught this exact bug.**

`node --check` clean. The value path is now complete by inspection: input is inside control, control is appended to the rail, the rail is inside the card, the card is in the section container — so `querySelectorAll("[data-key]")` reaches it.

## Residual risks

- **Still no browser in this environment**, so the dirty state was not observed lighting up. That is the same gap that let the bug ship, and it will keep being a gap until this suite gets a DOM harness. Worth doing as its own change.
- The static guard asserts exact source strings. If those lines are legitimately reworded the test fails and must be updated with them — deliberate, since the alternative is a test that quietly stops checking anything.
