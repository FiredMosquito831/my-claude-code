## Description

## What was broken

A caller that demanded a specific tool got a request that no longer demanded it.

`_downgrade_forced_tool_choice` (`compat.py:420-433`) rewrote **every** Anthropic `tool_choice: {type:"tool", name:X}` to `{"type":"auto"}` while building the request body, logging only at `logger.debug`. The model was then free to answer in prose and call nothing — exactly the failure a forced tool choice exists to prevent — and nothing surfaced that the demand had been dropped.

## Mechanism

The downgrade was **unconditional and up front**, applied to every DeepSeek request.

But [DeepSeek's API reference](https://api-docs.deepseek.com/api/create-chat-completion/) documents `tool_choice` accepting `"none"` | `"auto"` | `"required"` | a named function object — forced choice is a supported part of the general model surface. Only the *reasoning* models reject it, at request time with an HTTP 400 ([R1 #836](https://github.com/deepseek-ai/DeepSeek-R1/issues/836), [R1 #813](https://github.com/deepseek-ai/DeepSeek-R1/issues/813), [V3 #1376](https://github.com/deepseek-ai/DeepSeek-V3/issues/1376)).

Downgrading everything to protect one model class removed a documented capability from all of them.

## The fix

Removes the up-front rewrite; handles rejection **reactively**, mirroring the existing sibling pattern in `mistral/client.py:58-68` — a narrow error predicate, a body clone, wired through the provider's `_get_retry_request_body` hook, logged at **WARNING**.

```
forced named choice  -> sent to DeepSeek unmodified
   |
   +-- rejected (400 mentioning tool_choice) -> retry once with tool_choice: "required"
```

`"required"` rather than `"auto"`: the caller demanded a tool call, so the must-call-*something* half survives even when the *which tool* half cannot be honoured.

**Detection is on the returned error, never the model id.** DeepSeek's names have already shifted once (`deepseek-reasoner` → `deepseek-v4-pro/flash`), and branching on upstream model names is banned by CLAUDE.md. This also **self-heals** the day DeepSeek lifts the restriction — no list to maintain.

The predicate requires **both** an HTTP 400 **and** text mentioning `tool_choice` together with a rejection word, so unrelated 400s (context length, bad schema, invalid model) never trigger a downgrade. There is a test for exactly that.

## Known limitation — documented, not hidden

The retry hook fires **at most once per request**. `_next_create_retry_body` adds `"provider_specific"` to `used_retry_kinds` and every later iteration skips the branch:

```python
# openai_chat/provider.py:340-345
if "provider_specific" not in used_retry_kinds:
    retry_body = self._get_retry_request_body(error, body)
    if retry_body is not None:
        used_retry_kinds.add("provider_specific")
        return retry_body
return None
```

So a model that *also* rejects `"required"` is not recovered — the failure propagates. A `named → required → auto` ladder is impossible without changing that shared gating, which would affect Mistral and every other provider using the hook. Out of scope for a bugfix; recorded in a code comment and in a test whose docstring cites the mechanism.

## Residual risks

**No live DeepSeek key.** The rejection path is exercised against simulated 400s, not a real reasoning model. The predicate's word list is therefore a best match against reported error text (`"deepseek-reasoner does not support this tool_choice"`), not against a response I have observed. If DeepSeek's wording differs, the symptom is the old behaviour minus the silence — the 400 surfaces instead of being silently swallowed, which is still an improvement on debug-level masking.

**One extra round trip** on affected models, by design — that is the cost of not branching on model names.
