## Description

## The report

> the DB or analytics page seems to not like show more than 50040 requests? I left it running overnight doing a ton of api requests and I didn't see requests number or token usage increase lifetime for hy3

Both symptoms, one mechanism. Nothing was broken.

`REQUEST_LOG_MAX_ROWS` defaults to **50,000**; prune runs every 100 inserts, so the count oscillates between 50,000 and 50,099. Every figure in `stats()` is a `COUNT(*)`/`SUM()` over that same table, so **at the cap the totals converge to a constant** — one row leaves for each one that arrives.

Evidence from the reporter's live database (1.7 GB, read-only):

```
rows now   : 50,073
oldest row : 2026-07-31 12:10 UTC    <- mid-day cut, i.e. actively deleting
2026-07-31 :  1,638 rows             <- partial day, being eaten
2026-08-08 :  9,266 rows
```

~9,000 requests/day ⇒ a **5.5-day window**. There was no cumulative counter anywhere in the codebase, so "lifetime" meant "the last 50,000 requests" — and neither the UI nor the docs said so.

## What this adds

- **`request_totals`** — one row per `(day, provider, model)`, incremented at flush, never pruned. Only ids not already stored are folded in, since the insert is `INSERT OR REPLACE` and the counters are add-only.
- **Backfill**, once, *before the writer accepts its first flush* so no request is counted by both the rollup and the aggregate. **1.0 s on the real 1.7 GB / 50k-row database**, no measurable file growth. Rows already pruned are gone and are not invented.
- **`server_sessions`** — the writer records when a server was actually running. The same report asked about a 9-hour overnight hole; a flat chart cannot distinguish *no traffic* from *no server*, and now it can.
- **UI** — an `All time` section, an explicit notice when stored rows are at the cap, and an uptime line under the series chart whose gap threshold scales with the selected range so a restart does not cry wolf.
- **`clear()` erases the counters too** — "Clear log" is an explicit erase, and millions of all-time requests over an empty table reads as a bug.
