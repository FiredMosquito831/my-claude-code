## The report

From a real machine:

```
error: failed to remove directory
  `...\uv\tools\my-claude-code\Scripts`: Access is denied. (os error 5)
```

It left the tool environment **half-removed** — `Scripts` and `pyvenv.cfg` with no `site-packages` and no dist-info — so every shim survived while pointing at nothing:

```
mcc-server --version  →  error: uv trampoline failed to canonicalize script path
```

Two independent defects, both Windows-only.

## 1. The launcher detection drifted four features behind pyproject

`Get-LauncherCommands` is a hand-maintained list that `install.ps1` checks before deciding whether to defer. It listed **18** names; pyproject publishes **26**. Missing: `mcc-desktop`, `mcc-rtk`, `mcc-help`, `mcc-anthropic-oauth-login` and their `fcc-` aliases.

`mcc-desktop` is the one that bites. It's a `[project.gui-scripts]` entry, so the running app is a `pythonw.exe` executing **out of the uv tool environment**, holding that directory open. Invisible to the detection, the installer took the direct path and uv tried to delete a live environment.

Measured against the user's actually-running app:

```
OLD (published)  knows 18 names, detects running: NOTHING
NEW (fixed)      knows 26 names, detects running: mcc-desktop
```

## 2. uv colours its output, and PowerShell's capture isn't a pipe

`uv tool dir --bin` came back as `ESC[36m` + path + `ESC[39m` — **35 characters where the directory name is 25**:

```
bytes: 1b 5b 33 36 6d │ C:\Users\...\.local\bin │ 1b 5b 33 39 6d
```

So `Test-Path` returned False for a directory that plainly exists, and the "did this command resolve inside the tool bin?" check could never pass.

uv suppresses colour when stdout is a pipe. POSIX `$(...)` looks like one to it; **PowerShell's capture does not** — which is exactly why Linux was unaffected and this was reported as Windows-only. `Invoke-NativeCapture` now strips ANSI before returning, and `NO_COLOR` is set so uv shouldn't emit it at all. Both, because a future uv could colour some other command.

## Verified in the exact failure case

Ran the fixed installer with the user's `mcc-desktop` live and its `pythonw.exe` holding the tool directory. It:

1. **detected** the running launcher
2. took the rename-aside hybrid path
3. installed successfully
4. **verified `mcc-server --version`** — which defect 2 had made impossible
5. failed only on copying the running `mcc-desktop.exe` shim with `os error 32` — the expected, handled case that defers one shim

Final state: dist-info present, **all 13 shims present**, `my-claude-code 5.30.0` reported, install healthy.

## The durable half

A list that must mirror another file is a list that drifts. A contract test now compares `Get-LauncherCommands` against `[project.scripts]` + `[project.gui-scripts]` **in both directions**, and asserts the ANSI stripping is wired into `Invoke-NativeCapture`. Mutation-tested: removing `mcc-desktop` again fails it by name.
