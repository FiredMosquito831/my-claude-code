## Description

Follow-up to #6. A delayed audit report surfaced a defect that #6 missed, and it is the most severe one in the rotation engine. 4.14.0 -> 4.14.1 (PATCH).

## The bug

Sub-providers classify their own SDK/HTTP failures **before** `RotatingProvider` sees them, so an upstream 401/403 arrives as `ExecutionFailure(retryable=False)` — not a raw `openai.AuthenticationError` or `httpx.HTTPStatusError`. `error_justifies_rotation` recognized only the raw shapes, and `retryable=False` made both fallback checks decline:

- not `openai.AuthenticationError`, not `httpx.HTTPStatusError` → first two checks fail
- `retryable_transient_status`: `exc.retryable and ...` → `None`
- `retryable_upstream_transport_error`: `exc.retryable and ...` → `False`

So it returned `False` for the exact failure rotation exists to handle. **A revoked, expired, or exhausted key failed the in-flight request outright instead of failing over to a healthy credential.**

Verified against the real classifier (`classify_provider_failure`) before the fix:

```
401 invalid key    kind=upstream     retryable=False  ROTATE=False   <-- bug
403 forbidden      kind=upstream     retryable=False  ROTATE=False   <-- bug
429 rate limit     kind=rate_limit   retryable=True   ROTATE=True
503 overload       kind=upstream     retryable=True   ROTATE=True
```

Note 401 classifies to `kind=upstream`, not `AUTHENTICATION` — so keying off `FailureKind` would not have caught it either. The fix keys off the status code.

## Scope of impact

Not total breakage: `report_failure` still ran, so the key was benched `LOCKED_OUT` and *subsequent* requests routed around it. But every credential death cost one user-visible request failure — precisely what failover is meant to prevent, and worse under `failover` policy where the whole point is transparent recovery.

## The fix

`retryable` encodes "safe to retry the **same** credential", which a 401 never is. It says nothing about whether a *different* credential would succeed. Rotation now keys off the auth status directly.

After:

```
401 invalid key    ROTATE=True
403 forbidden      ROTATE=True
429 rate limit     ROTATE=True
503 overload       ROTATE=True
400 bad request    ROTATE=False   <-- still correct, fails identically on every key
```

## Verification

- Parametrized regression test over 401/403 asserting `retryable is False` **and** rotation is allowed, so the discrepancy that caused this can't silently return.
- `test_classified_bad_request_still_does_not_rotate` guards against over-rotating.
- End-to-end: a 401 on key 0 is served by key 1, key 0 ends `LOCKED_OUT`.
- Full `./scripts/ci.sh`: **3017 passed, 14 failed** — exactly the known pre-existing set (websearch tests reading the real `~/.fcc/.env`, PowerShell installer checksum). **Zero new failures.**
