## Description

Analytics and request-log storage fixes for the request log. Every number below
was measured, and the ones that turned out to be measurement artifacts are
called out rather than quietly dropped.

## What was wrong

1. **All 8 analytics endpoints blocked the event loop.** They are `async def`
   calling synchronous SQLite inline. FastAPI only offloads plain `def`
   handlers, so a slow aggregate stalled *every* concurrent request, including
   `/health` and proxy traffic.
2. **Connections were never closed.** `sqlite3.Connection.__exit__` only
   commits or rolls back. Connections are GC-tracked rather than
   reference-counted, so `with self._connect() as conn:` leaked file
   descriptors until the next collection — measured 1 → 61 live connections
   across 60 reads with GC disabled. This fired on the background writer's
   flush path too, so it happened on ordinary proxy traffic, not just when the
   dashboard was open.
3. **Bodies were capped at flush, not at enqueue.** Queued records held
   uncapped `input_text`, so a backlog could retain far more than the persisted
   50k-char per-row limit.
4. **The database file could only grow.** No `auto_vacuum`, so `prune()` freed
   pages onto the freelist and never returned them to the filesystem.
5. **Aggregates read the bodies they never referenced.** SQLite stores all
   columns of a row together, so each of `stats()`'s seven scans walked
   overflow pages holding up to 100k characters of text per row.

## Changes

- `request_log`: a closing `_connection()` helper used on every read and
  maintenance path; the writer thread keeps one persistent connection instead
  of reconnecting per batch.
- `request_log`: cap bodies in `enqueue()` rather than at flush.
- `request_log`: `auto_vacuum=INCREMENTAL` plus `incremental_vacuum` after a
  prune that removed rows.
- `request_log`: `idx_requests_stats`, covering the columns the aggregates read
  so they run index-only.
- `request_log`: list queries project explicit metadata columns with SQL-side
  `substr` previews instead of `SELECT *`; `stats()` memoized for 5s.
- `admin_routes`, `admin_websearch_routes`: all 8 endpoints run their SQLite
  work via `asyncio.to_thread`.

Both migrations run on the writer thread. An earlier revision of this branch put
the conversion VACUUM in `RequestLogStore.__init__`, which is reached lazily from
a request handler — benchmarking caught construction regressing from 8 ms to
17,304 ms, i.e. trading a ~3 s stall for a 17 s one. That is fixed and covered by
a test asserting construction stays under a second on a database still needing
conversion.

## Measured

Live install, WSL/ext4, 4,946 rows / 149.5 MB. A/B by dropping and restoring the
index on a copy, unique filters per call to defeat the stats cache:

| uncached | without index | with index |
| --- | --- | --- |
| `stats()` unfiltered | 242.6 ms | **23.1 ms** |
| `stats(q=...)` | ~2.2-3.2 s | ~2.2-3.2 s |

`stats(q=...)` is unchanged by design: a leading-wildcard `%LIKE%` over the body
columns cannot use any index. That needs FTS5 and is deliberately out of scope.

Event-loop starvation, on the running server — 6 concurrent uncached queries at
2.2-2.6 s each (all HTTP 200, full payloads):

| | result |
| --- | --- |
| `/health` probes completed | 80 / 80 |
| probes over 500 ms | 0 |
| worst `/health` latency | 18 ms |

Connection hygiene: 1 → 61 live connections across 60 reads with GC disabled
becomes 3 → 3. Process footprint flat across 75 s idle after load (RSS, fds and
thread count unchanged).

### Correction to earlier figures

Initial benchmarks ran against copies on NTFS and overstated the absolute
numbers by roughly 10x for the unfiltered case — the real ext4 baseline is
~240 ms, not ~2,415 ms. The relative win is 10.5x, not 45x. The multi-second
figures are real only for the `q=`-filtered shape.

### Costs

- Threads 10 → 16 (`asyncio.to_thread` grows the default executor).
- A one-time conversion VACUUM on an existing large log takes ~8-14 s on the
  writer thread, and is logged.
