## Description

Audit of the credential rotation mechanisms, the five defects it found, and per-key request analytics. Version bumped 4.13.1 -> 4.14.0 (MINOR: new analytics capability).

## Defects fixed

Each was reproduced against the real engine before the fix and is covered by a regression test.

| | Defect | Impact |
|---|---|---|
| B1 | `acquire()` returned early for the `single` policy and one-key pools, skipping usage bookkeeping | `single` is the **default** policy, so every default install reported **zero** requests per credential |
| B2 | Client disconnect mid-stream reported neither success nor failure, leaving a half-open credential's `is_probing` reservation set forever | The credential was **never selectable again** |
| B3 | Failures after the first chunk were never reported | A credential that consistently died mid-stream accrued no failures and never cooled down |
| B4 | Auth lockout tiers were indexed by `consecutive_failures`, which non-auth errors also increment | Two 5xx plus one 401 jumped straight to the **24-hour** tier, benching a healthy key for a day after one blip |
| B6 | The already-attempted fallback reached past the pool for an untried index, bypassing health checks | Could dispatch to a `LOCKED_OUT` credential (latent) |

B5 (429 never opens the circuit) was reviewed and kept — a rate limit means throttled, not broken — but is now explicitly documented rather than implicit.

`release_probe` is deliberately synchronous: it runs from a `finally` block that can execute while `GeneratorExit` propagates, where awaiting is unsafe.

## Per-key analytics

Mirrors the pattern `websearch/analytics.py` already uses.

- `requests` gains nullable `key_index` / `key_label`, added via explicit `ALTER TABLE` — `CREATE TABLE IF NOT EXISTS` is a no-op on an existing database. Verified against a real old-schema DB: legacy rows survive and show as `(unknown)`.
- The stats covering index is **versioned** (`idx_requests_stats_v2`), since `CREATE INDEX IF NOT EXISTS` would otherwise silently keep the old index built without `key_label`.
- `stats()` returns `by_key`; both request endpoints accept a `key` filter.
- Requests tab gains a Key column, a key filter, and a Key performance panel.

**Propagation:** the credential is chosen deep in the provider stack but the record is finalized at the API boundary. Rather than widening every provider signature, the API layer installs a mutable per-request slot that the rotating provider writes into. The slot is mutable on purpose — a plain `ContextVar` value would be invisible to the installer if the provider runs in a child task, since that task mutates its own copy of the context.

**Safety:** only the index and a masked `first4…last4` label are stored. The raw key never reaches the database, a log line, or an HTTP body. `mask_key_label` moved to its neutral owner beside `parse_credential_keys`.

## Also

- `.env.example` now documents provider-side multi-key rotation, which previously covered only the websearch equivalents.
- Noted for a follow-up PR: the provider and websearch rotation engines have diverged (async+lock vs no lock, 5 states vs 4, threshold 3 vs 4, 24h vs 1h lockout cap). Consolidating them is deliberately **not** in this PR.
