## Description

Second bug found by running the **published** command rather than the file.

```
+ irm  -OutFile C:\Users\...\fcc-wheel-f26a0339Invoke-RestMethod : Invalid URI: The hostname could not be parsed.
```

The published Windows command runs the script as a **scriptblock** (`irm ... | iex`). Under that form a function's `$script:` writes are not visible to the rest of the script, so `Resolve-Release`'s `$script:FccWheelUrl` / `FccWheelName` never reached `Get-VerifiedReleaseWheel` — it called `Invoke-RestMethod` with an empty URI.

**Why nothing caught it:** the file parses fine, and `-File` execution works, because *that* form does give functions the script scope. Only the published invocation fails. My earlier dry-run used `-File`, which is why it looked correct.

`Resolve-Release` now returns the resolved release and callers take it as a parameter, so behaviour no longer depends on how the script was invoked. `Configure-AndConfirmFreeClaudeCode` takes the expected version explicitly for the same reason.

Verified by running the real, non-dry install through the scriptblock form:

```
Free Claude Code 4.18.1 is installed and verified.
```

Adds `test_install_ps1_does_not_rely_on_script_scope_for_release_state`, which runs on any platform.
