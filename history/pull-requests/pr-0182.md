## Description

Found by auditing #181 against the project's own working notes after it merged. Two defects in what I shipped, one of them serious.

## The serious one: the deadline is sized for the wrong thing

5.50.0 stopped reasoning from committing the route — correct — but a held-reasoning attempt then looks **silent** to routing, so it inherits the first-token share: `FALLBACK_TOTAL_TIMEOUT ÷ chain length`. On the reporter's **eleven-model** sonnet route that is **54 seconds**, which is not enough time for a model to think.

Measured against the same 161,812-row log:

```
successful requests that produced reasoning        105,078
  slower than a 54.5s answer-deadline, with
  little or no answer  -> would be diverted           1,387
  same, against a 300s answer-deadline                   27
budget exhaustions that were reasoning-only              44
```

**~1,387 diversions to rescue ~44 failures** — and the tightness buys nothing, because every one of the 499 budget exhaustions ran the **full** 600s, so any allowance below that rescues all of them. On a chain of similarly slow models those diversions can cascade into outright failures.

### The fix

`FALLBACK_REASONING_ANSWER_TIMEOUT`, default **300s**, a flat allowance instead of a share.

The provider emits an empty heartbeat while its holdback buffer is withholding thought frames. Routing consumes it, keeps the attempt uncommitted, and starts the allowance from the **first** held thought — deliberately not re-armed per thought, because a model looping forever produces reasoning indefinitely and a stall-style clock would never fire on the exact failure this bounds.

A stream that produces **nothing at all** sends no heartbeat and keeps the tight share, so the fix that took hangs from 150/day to roughly one is untouched. There is a test pinning that.

The sentinel lives in `core/anthropic/stream_contracts.py`, not the provider package — `application` may not import `providers`, and `test_import_boundaries.py` said so. Moved, not shimmed.

## The other one: a number I published was wrong

5.50.0 claimed "**479 of 499** budget exhaustions" were this mechanism. 479 is how many ran on one **model** — I grouped by `resolved_model` and read the top row as a mechanism count. Grouped by mechanism:

```
nothing at all   401   (the older scaffolding shape)
some answer       54
reasoning only    44
```

Overstated ~11x. The mechanism and the reported failure are unchanged. Corrected here, in the v5.50.0 release notes, and on #181.

## Residual risks

- At the 300s default, ~27 slow reasoning requests in 105,078 would still divert to a fallback rather than complete on the primary. `0` disables the allowance entirely and lets a thinking model run to the whole request budget.
- The heartbeat is a new provider→routing signal. It is empty, is not valid SSE, and is consumed before any client-facing branch; a test asserts it never reaches the client.
