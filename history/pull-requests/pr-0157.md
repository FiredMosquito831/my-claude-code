## Description

## The problem it fixes as well as the one it solves

v5.33.0 gated reasoning per model — and in doing so **silently changed what the `reasoning` column means**.

`_route_for` stores the *gated* policy on `RoutedMessagesRequest` (`routing.py:443`), and `request_capture.py:144` reads exactly that. So rows written **before** v5.33.0 record what was **requested**; rows written **since** record what was **applied**. They agree whenever nothing was clamped and diverge precisely when the interesting thing happened — with nothing marking the boundary.

That is the same trap as the 4.25.1 and 5.13.0 steps: a trend line that breaks for a reason nobody remembers. Better caught the same day than in six months.

## What this records

`reasoning` **keeps** its current meaning — the applied value. Every downstream consumer already treats it as what was sent, and flipping that meaning twice would be worse than leaving it. `requested_reasoning` carries the pre-gating intent. `_route_for` already computed the ungated policy before gating it; this stops throwing it away.

**NULL means unknown, never "unchanged."** Rows written before this column existed genuinely have no requested value. They are not backfilled and not inferred, and the documented query excludes them from the denominator rather than counting them as unchanged.

The field is **required with no default** on `RoutedMessagesRequest`, so a future construction cannot silently regress the recording to `requested == applied` — it surfaces as a type error instead.

## Migration

Follows the file's existing `_ADDED_COLUMNS` + `_ensure_added_columns` pattern: `PRAGMA table_info` guard, then `ALTER TABLE`, with the existing `OperationalError` re-check covering a cross-process race. The column is in `_SCHEMA` too so fresh databases get it in order.

It runs in `_init_db` rather than on the writer thread because SQLite's `ADD COLUMN` is **metadata-only** — unlike the totals backfill and the auto-vacuum conversion, which are on the writer thread for good reason.

**No index, deliberately.** `requested_reasoning <> reasoning` is a non-sargable two-column expression that an index on either column cannot serve — SQLite scans regardless. The write path is an INSERT on every request while the query is an occasional aggregate, and a new index would also perturb the planner's existing choice of `idx_requests_stats_v3`. Revisit if someone reports the aggregate being slow.

## An export bug found on the way

`reasoning` appeared in `_REQUEST_COLUMN_ORDER` and `_REQUEST_COLUMN_LABELS` but belonged to **no** `_REQUEST_FIELD_COLUMNS` entry — so `request_detail_columns` could never select it and **the reasoning policy has never been exportable**. Both columns now hang off the `thinking` field, with a standing guard that every exportable column exists in the schema.

## The query this unlocks

```sql
SELECT resolved_model, requested_reasoning, reasoning AS applied, COUNT(*) AS n
FROM requests
WHERE requested_reasoning IS NOT NULL      -- exclude pre-v5.34 rows: unknown, not unchanged
  AND requested_reasoning <> reasoning
GROUP BY resolved_model, requested_reasoning, reasoning
ORDER BY n DESC;
```

## Residual risks

**Old rows stay unknown forever.** No backfill is possible — the requested value was never stored. Any rate calculated across the boundary must use `COUNT(requested_reasoning)` as its denominator, which the documented query does.

**The detail view hides the requested row when it equals the applied one.** Deliberate (an identical row on every request is noise), but it means "absent" reads as either *unchanged* or *legacy row* — the export and SQL distinguish them; the modal does not.
