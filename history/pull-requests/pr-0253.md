## Description

## The failure

Two real installs, three days apart, same shape:

```
04:06  failed to copy ... Scripts\mcc-claude.exe  -> ~\.local\bin\mcc-claude.exe:
       The process cannot access the file because it is being used by another process. (os error 32)

16:30  failed to copy ... Scripts\mcc-desktop.exe -> ~\.local\bin\mcc-desktop.exe:
       The process cannot access the file because it is being used by another process. (os error 32)
       My Claude Code install failed: Command failed with exit code 2
       At line:709 char:9   throw "My Claude Code install failed: $installError"
```

## Root cause

Line 709 of the shipped v6.32.0 `install.ps1` is the `throw` inside `Invoke-RenameThenReinstall`'s rollback, so the rename path **did** run and the tool-directory rename **had** succeeded. `mcc-desktop` **is** in `Get-LauncherCommands` — the stale-list hypothesis is refuted. The rename of that one shim was refused, and `Rename-LauncherShimsAside` swallowed the refusal:

```powershell
catch {
    # Leave it: uv will fail on this one shim and we report it as a
    # missing command rather than silently shipping a broken set.
}
```

uv does not fail on *one* shim. It aborts the whole entrypoint pass on the first file it cannot write, writes no receipt, and the rollback then throws.

And Windows really does refuse those renames. Measured on a scratch install with `mcc-server`, the `mcc-desktop` tray and an `mcc-claude` session live: **all three** of their shims were refused, the other 35 moved aside without complaint. uv writes entrypoints in ASCII order, so the first refused shim it reached was `mcc-desktop.exe` — the file in the 16:30 error — and `mcc-claude.exe` in the 04:06 one.

*(Which handle holds the file is not identified; it is not needed. The design no longer assumes the rename can always be done.)*

## What changed

**`scripts/install.ps1`**

- `Get-ManagedShimName` (new) — the shim set is a union of three independent sources: the `^(mcc|fcc)-.*\.exe$` family pattern plus `my-claude-code.exe` / `free-claude-code.exe`, every `install-path` in uv's own `uv-receipt.toml`, and the `Get-LauncherCommands` contract list. A new command cannot be missed by all three. The contract test pinning the list to `pyproject.toml` stays, but the rename no longer depends on it.
- `Rename-LauncherShimsAside` — returns one record per shim including `Renamed = $false` and the OS error, instead of an empty `catch`.
- `Invoke-StagedInstall` (new) — the fallback. Re-runs uv with `UV_TOOL_BIN_DIR` at a fresh staging directory, so uv writes all 38 shims and a complete receipt somewhere nothing can be holding, then places them into the real bin directory one file at a time (rename aside with retries, then copy). A destination that still cannot be replaced keeps the old file — restored if it had already been moved aside — and is returned as "kept", never as a failure.
- `Update-UvReceiptEntrypoint` (new) — repoints the receipt's `install-path` entries at the real bin directory through a temp file and an atomic move.
- `Invoke-RenameThenReinstall` — routes to the staged install when any rename was refused **or** when the direct install failed for any other reason; only a failure of *that* rolls back and throws.
- `Install-FreeClaudeCode` — the plain path (nothing detected as running) now also retries through the rename/staged path when uv fails. Process detection is a name match, and a name match can miss.
- Closing summary lists kept shims by name with "these keep working and will refresh on the next install". Still exits non-zero, and still refuses to print "verified", for a command that is genuinely absent.

**`src/my_claude_code/application/release_updates.py`** — the tray/dashboard updater's detached helper gets the same mechanism: family-wide discovery, refusals recorded, staged fallback, receipt repointed, and a result carrying `kept_shims` as refreshing-next-time rather than as errors.

**Docs** — README install-troubleshooting rows and `docs/USAGE.md` §15 now state that installing while MCC is running is supported, that running sessions keep the old version until restarted, and that a locked shim refreshes on the next install.

## The uv receipt finding

Measured with uv 0.11.21: an install run with `UV_TOOL_BIN_DIR` set records every `install-path` under **that** directory:

```toml
{ name = "mccprobe-claude", install-path = ".../installer-fix2/stage/mccprobe-claude.exe", from = "mccprobe" },
```

Left as written, a later `uv tool uninstall` or `uv tool upgrade` would chase a temp path that no longer exists. Rewriting the receipt was chosen over a second full `uv tool install` pass: it is deterministic, costs no second 87-package install, and cannot hit the same lock again. After the staged path the receipt reads:

```toml
{ name = "fcc-anthropic-oauth-login", install-path = ".../rt/bin/fcc-anthropic-oauth-login.exe", from = "my-claude-code" },
```

The direct rename path was kept as the fast path rather than always staging: it is the behaviour already proven in v6.30.1, it is one uv invocation, and uv writes a correct receipt itself.

## Residual risks

- **Which handle refuses the rename is not identified.** The design does not depend on it, and the staged fallback covers any holder — but it also means the refusal rate on other machines is unknown.
- **The renamed-aside tool directory can survive as `my-claude-code.old-<stamp>`** while processes still run from it, and `uv tool list` prints `warning: Ignoring malformed tool ...` until the next install sweeps it. Pre-existing since v6.30.1; a leading-dot name was tried and makes uv error harder, so the naming was left alone.
- **A command *added* by the release whose shim is locked would be reported missing and exit non-zero.** That is deliberate — it is genuinely absent — but it is the one case where a locked file still costs a re-run.
- **The staging directory lives under `%TEMP%`** and is removed on both branches; a hard kill mid-install could leave one `mcc-stage-bin-*` directory behind.
- **PowerShell installer tests never run on Linux CI**, so a PS-only regression can ship green; the runtime tests above were executed locally on Windows against both shells.
