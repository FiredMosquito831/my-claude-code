## Description

# Reasoning gets the model's whole output allowance, and the ceiling becomes your head

A thinking request is now sized from what the routed model can actually emit, not from a number the client picked for an answer. `MAX_OUTPUT_TOKENS_CEILING` ships set at **131,072** as the head on that. A model that publishes no reasoning control keeps the rung it was asked for. `thinking_chars` records a measured **0** instead of NULL. And the request-detail wire pane now names every parameter the body carried, widening included.

## What was wrong

**Reasoning could only ever narrow `max_tokens`, never widen it.** All four steps in `resolve_max_output_tokens` clamp down, and the number they clamp is `routed.request.max_tokens` — the client's own ask. Nothing in the chain knew the request was a thinking request. Thinking tokens and answer tokens come out of that one allowance (WORKING-NOTES §54), so a client that sized `max_tokens` for an answer had unknowingly sized the thinking too.

Measured: on Command Code at effort `max` with `max_tokens 8000`, the host produced **9,024 tokens of thinking and a one-character answer**. The rung was right; the allowance it was spent from was the client's, and the client had no way to know the route was a thinking route.

On a 262,144-output model with a 64,000 ask at `max`:

| | before | after |
| --- | --- | --- |
| wire `max_tokens` | 64,000 | 131,072 |
| answer reserve `min(16384, output // 2)` | 16,384 | 16,384 |
| thinking budget at ratio 0.95 | `min(60,800, 47,616)` = **47,616** | `min(124,518, 114,688)` = **114,688** |
| answer room left | 16,384 | 16,384 |

**`_drop_controls` read the wrong boolean.** A model publishing `reasoning_options: []` — about 23% of models.dev's reasoning catalogue — reached `_drop_controls`, which decided on `dialect.toggle` raw. On Command Code, whose only on-channel is `reasoning_effort` with `enabled_value="max"`, an explicit `low` came back as a bare ON and the encoder spelled it as the host's own `max`. That is byte-for-byte the regression PR G removed for toggle-only models; `_drop_controls` never got the memo — it read `_Channels.default_rung` where it needed `_Channels.on_signal_is_the_effort_field`.

**`thinking_chars` was `self._thinking_chars or None`**, folding "this stream returned no reasoning" into "nobody was counting" — precisely the distinction `reasoning_by_model` exists to report.

**And when the allowance did move, nothing said so.**

## What to expect now

A 64,000-token ask, wire `max_tokens`, at the shipped 131,072 ceiling:

| model output limit | `max` | `high` | `low` | reasoning off |
| --- | --- | --- | --- | --- |
| 16,384 | 16,384 | 16,384 | 16,384 | 16,384 |
| 64,000 | 64,000 | 64,000 | 64,000 | 64,000 |
| 131,072 | 131,072 | 131,072 | 131,072 | 64,000 |
| 262,144 | 131,072 | 131,072 | 131,072 | 64,000 |

The rung does not change the allowance — the *presence* of reasoning does. The rung then decides how much of that allowance the thinking may take, on hosts that speak a numeric budget; on effort-only hosts the rung is untouched and only the answer stops starving. Reasoning off is byte-identical to 6.7.0 except for the new ceiling. A model publishing **less** than the ask is still clamped down to its own limit, as before. An **unknown** limit is never widened — a number nobody published has no standing to raise an explicit request, the same rule that stops it lowering one. `max_tokens: 0` stays 0.

## Also in this PR: the wire pane names every parameter

`wire_params_summary` kept a hand-picked subset, so the pane could only ever show a knob somebody had thought to list — `stream`, `stream_options`, `tool_choice`, `parallel_tool_calls`, `response_format`, `min_p` and a provider's own `extra_body` entries were invisible. Every non-content key is kept now: the named ones first in their existing order, then every remaining top-level key alphabetically, then every non-reasoning `extra_body` key as `extra_body.<name>`. Content fields stay out — they are content, not parameters, and they are what the body pane degrades when its size cap bites. **The parameter section is never truncated**, because a knob lost to a cap is not recoverable from anywhere else. Redaction is unchanged, and the new tail is redacted as a mapping so a top-level `authorization` is caught by name rather than only by value shape. `buildWireKnobs` renders all of it, above the body, so the pane reads knobs first and structure second.

## Action required

**The ceiling now defaults to 131,072.** Set `MAX_OUTPUT_TOKENS_CEILING=0` for no ceiling at all, or your own number.

It ships set because the widening asks for the model's maximum, and OpenAI/Azure-style limiters pre-reserve `max_tokens` against the TPM bucket before generating — so an unbounded thinking turn on a 262,144-output model can 429 a request that would have been served. It applies uniformly, reasoning or not, and it never raises a model above its own published limit.

**Blank no longer means "off".** `blank_limit_falls_back_to_its_default` makes an empty field resolve to the field's default, which is now a number. `0` is the sentinel — the idiom `config/limits.py` already uses for its other three budget keys — and the range widens to `LimitRange(0, 1_048_576)`. The sentinel is re-applied *after* the range clamp too, since that clamp's floor for this key is the sentinel and a literal ceiling of zero would cap every answer at nothing.

## Known and deliberate

- **OpenAI/Azure TPM pre-reservation** is accepted, with the ceiling as the mitigation and the knob.
- **Empty-answer rescue is deferred.** A stream that thinks and then ends cleanly with `finish_reason=length` and an empty visible answer is not rescued. `FALLBACK_ON_REASONING_ONLY` fires from the *deadline* path, and a stream that ended on time, with output, never reaches it — that needs a commit-boundary rule, not a timer. Documented as a known gap in the README, in `docs/USAGE.md` § Deadlines, and on the setting's own card in the admin UI.
- **`output_widened_from` is a per-attempt `params` key, not a `ReasoningAdaptation` kind.** A new kind would touch `core/reasoning.py`, the severity table, `combine_reasoning_adaptations`, the badge lists and four jsdom tests, to describe something that is not a reasoning adaptation at all — the reasoning is exactly what was asked for; only the allowance moved.

## Residual risks

1. **TPM pre-reservation.** A widened reasoning turn can 429 sooner on limiters that reserve `max_tokens` before generating. Mitigated by the 131,072 default; the escape hatch is lowering it.
2. **Longer thinking, more `FALLBACK_REASONING_ANSWER_TIMEOUT`.** A budget host given 114,688 thinking tokens instead of 47,616 can legitimately think past the 300s reasoning-answer deadline, which will now end more attempts. The timer is unchanged; the traffic under it is not.
3. **A behaviour change for operators who wanted no head.** Anyone relying on "the ceiling is unset" gets 131,072 on upgrade, silently, on non-reasoning requests too. Recoverable with `=0`. Blank no longer meaning "off" is the sharpest edge here.
4. **The learned output cap is still per-process.** Widening asks a larger number of an under-reporting provider, so the one 400 that teaches the cap is marginally more reachable on the first reasoning request after a restart. Pre-existing gap.
5. **A no-control model may be handed a rung its own vendor rejects.** The §0.4 fix writes the caller's rung into the host's effort field for a model that publishes no control. A forwarding host that refuses it pays one 400 and is remembered (`openai_chat/reasoning_reject.py`) — the same trade PR G took.
6. **`output_widened_from` is visible only in the wire pane.** Not in the reasoning badge, the severity table, or exports that read only the request row. Deliberate (see above).
7. **Nothing detects a widening that did not help.** A model that spends the whole widened allowance thinking and still answers nothing is the deferred gap above.
8. **The parameter block is now unbounded in key count.** A dialect that sends a very large number of top-level keys makes a longer list. It is bounded by what a real provider body carries, and no key is truncated by design.

## Deviations from the spec, and why

- **`_prepare_from` announces attempt 0 *before* the budgets run**, because preflight has to stay ahead of token counting (WORKING-NOTES §56, pinned by `test_executor_preflight_failure_stays_before_token_count_and_stream`). So `on_attempt` saw the pre-budget object and `output_widened_from` never reached the log. The spec asked this be verified rather than assumed; it is false, and the fix is a **narrow re-announcement** of the prepared attempt after the rebinding, taken only when `output_widened_from` is set. Re-announcing unconditionally doubles the chain's announcement sequence, which is itself a contract that four `test_execution.py` cases assert.
- **`config/settings.py` gained `_no_ceiling_when_zero`**, shared by the field validator and the range clamp. Not in the spec: the clamp's floor for this key *is* the sentinel, so a hand-typed negative resolved to a literal ceiling of 0 and would have capped every answer at nothing. Pinned by `test_a_negative_output_ceiling_lands_on_the_sentinel_not_on_zero`.
- **`tests/config/test_limit_bounds.py::test_a_value_below_the_range_is_clamped_not_fatal`** special-cases the ceiling for the same reason, as the spec anticipated.
- **The browser check ran against 8199's own admin directly** rather than through a static harness on 8099 proxying GETs to 8199. The 8199 server already serves this branch's `admin_static` *and* holds the rows, so the proxy would have added a layer without adding fidelity. Nothing was ever sent to port 8082.
