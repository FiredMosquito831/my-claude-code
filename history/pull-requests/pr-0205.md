## Description

## What was missing

5.65.0 added a hide-only model visibility filter and 5.66.0 added a per-provider
and per-model request-parameter override store. Both shipped with no surface: the
only way to use either was to hand-edit `MODEL_VISIBILITY_ALLOW`/`DENY` in `.env`
or `~/.fcc/model_overrides.json` by hand, against a catalogue of hundreds of
models the user could not see. And the capability metadata those overrides sit on
top of -- output limit, context length, reasoning controls -- was resolved from up
to four sources of very different quality with no way to tell which one answered.

## What this does

A new **Models** page in the dashboard, with three sections over one payload.

**Visibility.** A provider -> model tree of the whole catalogue with a per-model
tick, plus a free-text editor for both glob lists and a Preview button that says
what a pattern set would hide *before* it becomes the running configuration.
Ticking a model writes an exact-match pattern into the same two lists a glob goes
into -- there is no second store to keep in sync. The hide-only contract is
printed on the page, and any configured route ref that is currently hidden is
listed with the env keys that name it, because that is the one case where the
page would otherwise look like a model had vanished.

**Parameter overrides.** The nine allowed parameters, editable per provider and
per model, persisted through `save_model_overrides`. Each model row shows the
resolved effective value -- what would actually be sent -- beside the raw
override, and which level it came from. `max_tokens` and the reasoning fields are
listed by name with the reason they are not editable here, rather than being
silently absent.

**Capability inspector (read-only).** Per model: output limit, context length,
vision, the gateway's `default_parameters` and `supported_parameters`, and all
seven reasoning capability fields -- each with the tier that stated it.

## Non-obvious choices

**The three-state control is a mode select, not a text box.** Inherit /
Force unset / Force value, with the value box disabled in the first two. An empty
text box cannot distinguish "say nothing" from "remove this key even if the
provider set it", and that distinction is the entire point of the override file.
On the wire the three states are: a value, `null` for force-unset, and the string
`"inherit"` to delete the key. `null` could not double as "clear" because `null`
is already force-unset.

**Source tiers are derived from the resolution order, not from a new provenance
field.** `ProviderModelInfo.reasoning_capability` and `max_output_tokens` are the
provider's own `/models` answer -- models.dev enrichment never writes them -- so
"provider stated it" is knowable exactly. Below that, the page asks models.dev
directly and uses the new public `models_dev_describes_provider()` to tell an
authoritative models.dev row from the approximate cross-provider vote, which
returns the same type. `context_length` is the one field whose merge is lossy, so
it is labelled "provider /models or models.dev" with that stated in the row rather
than guessed at.

**The approximate tier is styled as a warning and carries its sample size.** It
renders as "guessed from 1 same-named row(s), 100% agreement" in the error colour,
because that is exactly what hands `commandcode/minimax/minimax-m3-free` an output
limit of 1,048,576. The matcher itself is untouched here.

**The page claims no manifest section.** `containerId` stays `null`, which is what
`renderSections()` skips on. That is the §36 trap -- a container-less view once made
`byId(view.containerId).innerHTML = ""` throw inside the shared loop and blanked
*every* tab, not just the new one -- so both guards are now asserted by a test.

**Visibility writes go through `apply_admin_config`, not the env file.** These are
two ordinary manifest settings; going around the manifest would skip validation,
the locked-source check and the restart bookkeeping every other field gets.

**Two import-boundary exceptions.** `api.model_admin` imports
`providers.runtime.models_dev` and `providers.reasoning_vocabulary` directly. The
page's whole purpose is to name which tier answered, and the tiers *are* those
lookups; reading them through an abstraction would erase the distinction the
section exists to show. Both are documented in `IMPORT_EXCEPTIONS`, read-only, and
admin-surface only, alongside the existing `admin_routes -> providers` entries.

## Endpoints (all loopback-restricted, following the existing route style)

- `GET  /admin/api/model-admin` -- tree, overrides and capabilities in one request
- `POST /admin/api/model-admin/visibility` -- persist both pattern lists
- `POST /admin/api/model-admin/visibility/preview` -- what a pattern set would hide, saving nothing
- `POST /admin/api/model-admin/visibility/toggle` -- tick one model, reporting whether a broader glob overruled it
- `POST /admin/api/model-admin/overrides` -- rewrite one provider or model row

## Deliberately not done

- Validating an override against the model's `supported_parameters` (deferred).
- Fixing the cross-provider matcher. This surfaces how weak it is; a separate PR
  fixes it.
- Any change to visibility or override *semantics*. This is the surface only.


## Residual risks

- **Source tiers are derived, not recorded.** The provider tier for the output
  limit and the reasoning fields is exact (enrichment never writes those fields),
  but `context_length` is a lossy merge and is labelled as such rather than
  attributed. If a future change makes models.dev enrichment write
  `max_output_tokens` or `reasoning_capability`, this page would start calling
  those values authoritative. The tests pin the current behaviour per tier.
- **No browser ran this page.** Coverage is endpoint tests plus static assertions
  on the shipped JS; the visual layout is unverified by machine.
- **A large catalogue renders as one tree.** `nous_portal` alone lists 343 models,
  and every model row builds an override editor and a capability table when its
  provider is unfolded. Providers are collapsed by default and there is a filter,
  but a user who expands a 343-model provider will feel it.
- **The visibility save is a settings apply**, so it inherits whatever restart
  semantics those two fields have.
