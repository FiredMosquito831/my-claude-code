## Description

## The bug

A stop had four waits and only the first of them was bounded:

| # | Wait | Bounded before? |
|---|---|---|
| 1 | uvicorn stops accepting, waits for connections and tasks | **yes** — `timeout_graceful_shutdown` |
| 2 | uvicorn cancels the surviving request tasks | n/a (instant) |
| 3 | MCC's response cleanup, which **swallowed that cancellation** | no |
| 4 | ASGI lifespan shutdown = `ApplicationRuntime.close()` | no |
| 4a | ↳ `ProviderRuntimeManager.close()` waiting on `drained` | no |

With every per-request deadline at `0` — the shipped default since 6.16.0, and the
right default for a *running* request — a request against a silent upstream meant a
server that never exited. uvicorn cancelled the request task at its bound; the
shielded loop in `api/response_streams.py::_wait_for_cleanup` re-awaited through
that cancellation; the provider lease the response held was never released; and
`ProviderRuntimeManager.close()`'s `await asyncio.gather(*(g.drained.wait() ...))`
had no timeout at all. A rotated log holds one such run still serving **98 minutes**
after its shutdown request.

The other half of the report — *"instead of waiting until current requests finish it
also allows new ones"* — is that the only refusal MCC had (`ApplicationUnavailableError`
from `ProviderRuntimeManager.acquire`) was armed by `self._closing = True` **inside
`close()`**, i.e. after the whole drain window had already passed. For its entire
duration, new requests on an already-established keep-alive connection were served
normally, each taking a lease, each lease re-clearing `drained`, each pushing the
finish line further out.

Reproduced on a scratch server with a stalled upstream: with a 5 s bound the server
was still alive **39.56 s** later and climbing. After this change, same setup, same
5 s bound: **exits at 5.2 s**.

## The contract

| # | Situation | Before | After |
|---|---|---|---|
| C1 | Stop requested, nothing in flight | exits promptly | unchanged |
| C2 | Stop requested, healthy in-flight request | drains, exits | unchanged |
| C3 | Stop requested, request against a stalled upstream | **never exits** | exits within the budget + a 3 s teardown margin |
| C4 | New TCP connection during the drain | refused by uvicorn | unchanged |
| C5 | New request on an existing keep-alive connection | **served, and extends the drain** | `503` + `Connection: close` + `Retry-After`, does not extend it |
| C6 | Stream cut at the bound | truncated / TCP close | plain close — no new wire frame; the harness's own retry finds the restarted server |
| C7 | `REPLACE_PROCESS` when the drain overran | unreachable code | reachable: refuses loudly, exits 1 |
| C8 | `RELOAD` when the drain overran | unreachable code | reachable: fresh generation, server stays up |
| C9 | Tray stop/restart | no graceful ask at all, hard-coded 5 s, then `TerminateProcess` | asks, waits the server's own budget + margin, then terminates the exact pid it launched |
| C10 | Updater's deferred helper | polls the parent for a flat **3600 s**, then gives up **without installing** | waits the same budget + margin, ends the exact parent pid it was given, then installs |
| C11 | Per-request deadlines all `0` | implied an unbounded stop | no effect on the stop bound |

## How

`src/my_claude_code/core/stop_deadline.py` is the single answer to "how long may a
stop take". At the instant a stop is requested, `SERVER_GRACEFUL_SHUTDOWN_SECONDS`
becomes **one wall-clock deadline**; every later stage reads the time it has *left*
against that same clock rather than starting a budget of its own, so nested bounds
compose instead of stacking. A fixed **3 s** teardown margin sits past it for the
forced close, and a watchdog thread `os._exit`s one beat after that — armed only for
a terminal stop, never for a `RELOAD`, whose overrun must keep the process alive (C8).

It lives in `core` because the supervisor (`cli`), the ASGI gate and lifespan
(`runtime`), the provider drain (`runtime`) and the response cleanup (`api`) all read
it, and `core` is the only package all four may import.

uvicorn owns the signal handlers — MCC installs none of its own — and they set
`should_exit` directly without going through the supervisor's `request()`. Its
`handle_exit` is wrapped so a Ctrl+C, a SIGTERM or the tray's CTRL_BREAK starts the
same clock; arming only on the in-process restart paths would have left every bound
here inert in exactly the case that was reported.

`ApplicationRuntime.close` still applies no generic timeout of its own — the reason
given at `runtime/application.py:64-67` is sound, and this release honours it by
bounding each *resource-specific* cleanup. The lifespan `wait_for` is a backstop that
only fires when one of those is not enough, and answering `lifespan.shutdown.failed`
is what hands the decision back to the supervisor, which before now could never take it.

## The default drops from 300 s to 20 s

As the bound on *one wait inside* a stop, a large value cost nothing. As the bound on
*the whole stop*, it is the time an operator spends watching a tray icon after pressing
Restart. The range stays 1 s – 600 s, and the Limits & Resilience help text, the
`.env.example` comment and `docs/USAGE.md` all now say so — including the note to
lower an inherited `300`.

## User decisions this PR implements

- **Q1** one wall-clock deadline computed once at "stop requested", shared by every stage; `SERVER_GRACEFUL_SHUTDOWN_SECONDS` stays the single user-owned setting, default now 20 s, plus a fixed 3 s teardown margin then hard-exit. Clamped to 1–600 s.
- **Q2** at the bound the client sees **nothing special** — a plain close, no terminal SSE frame, no new wire format.
- **Q3** every new request during the drain is refused: `503`, `Connection: close`, `Retry-After: 5`, from an ASGI-level gate. Health and admin included — the dashboard's reconnect loop already treats a failed poll as the expected mid-handoff disconnect and keeps polling.
- **Q4** the tray and the updater's deferred helper escalate: ask, wait the bound + margin, then terminate the **exact pid**. `Start-DeferredInstall` in `scripts/install.ps1` drops from 6 hours to 10 minutes and escalates the same way. C7/C8 are reachable and correct.
- **Q6** MINOR: **6.41.0**.

## Also in here

- `kill_pid_tree_best_effort`'s `taskkill` gets a `timeout=`. It runs at `atexit` and on the supervisor's way out, and was one more place a stop could hang forever.
- `install.ps1` computed `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP` into `$flags` and never used it — `Start-Process` has no creation-flags parameter — so the comment described a behaviour the helper did not have. The dead value is gone.
