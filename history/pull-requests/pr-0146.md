## Description

## Why

The dashboard persists its own state and restores it on reload. The desktop app persisted preferences but nothing about **the window itself** — and one line actively destroyed the memory the platform was already keeping.

## The bug

Chromium stores window geometry per profile. A real profile this feature created holds:

```
browser.window_placement = {'left': 10, 'top': 10, 'right': 1410, 'bottom': 910, ...}
```

`AppModeWindow` passed `--window-size` on **every** launch, overwriting it. Resize or move the window, and the next launch discarded it.

The configured size is now the **initial** size: passed when the profile has no remembered placement, or when the configured value differs from the size last applied (recorded in `desktop.json`). So a manual resize survives indefinitely, and changing the setting is still honoured — **once** — rather than silently ignored.

The alternative considered was "pass it unless the setting is at its default", rejected because it compares against a *constant* rather than *history*: anyone running a non-default size would have it forced on every launch forever, permanently defeating the platform's memory.

Reading the placement is best-effort by construction — missing file, unreadable file, malformed JSON, or an unexpected shape all mean "no memory yet, pass the size". Never an exception on a launch path.

## A defect caught in review

`minimize_to_tray` is **off by default**, so closing the window *ends* the app — and the first implementation recorded `window_open=False` on that path too. The ordinary act of closing the app would have stopped it ever opening a window again:

```
launch → close → quit → relaunch → tray icon and nothing else
```

which looks exactly like a broken start. Now only a close the app **survives** records "no window"; a close that quits leaves the state alone, because the user's last intent was an app with a window. Guard added and mutation-tested — it fails by name against the original code.

## The other half needed no code

app-mode already launches with a dedicated `--user-data-dir`, so the dashboard's own `localStorage` — active view, filters, theme, auto-refresh — is keyed to a stable origin inside a profile that persists across launches. That half of "persistency like the dashboard has" was **already satisfied**; it's recorded rather than reimplemented.

## Residual risks

- **No real browser window was launched.** No real profile and none of the user's `~/.fcc` was touched — every test runs against a fake profile under `tmp_path` with `HOME` redirected. That Chromium honours the *omission* of `--window-size` the way its `Preferences` file implies is documented behaviour read out of a real profile, not exercised against a live binary here.
- **Migration nuance:** on a profile upgraded from the always-forcing code, `last_applied_*` starts unset, so the first post-upgrade launch applies the configured size once more before going hands-off. Unavoidable — the old code never recorded what it applied.
- **Pre-existing and unchanged:** `handle_window_closed` is still not wired to an OS-level window-close event, so it is reached through the tray rather than by clicking the window's own close button.
