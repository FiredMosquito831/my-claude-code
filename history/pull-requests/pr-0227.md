## Description

## What was wrong

A live route logged this against a configuration that set 120, 600 and 300:

```
MODEL DEADLINE: 'nvidia_nim/moonshotai/kimi-k3' produced no first token after 74.9494s
```

Nothing anywhere was set to 75. An operator could read every deadline on
**Limits & Resilience** and still not find the one that ended their request.

## The mechanism

`application/execution.py::_attempt_deadline` gives each attempt
`remaining_total / attempts_remaining`, and `_chunk_timeout` then applies
`min(first_token_timeout, that share)` before the first chunk. On the user's
eight-model chain that share is `600 / 8 = 75 s`, so it was always the smaller
term and the configured `120` never applied to that route at all.

The equal share earns its place — 393 requests on 21 days of traffic ran the
whole 600 s budget producing only scaffolding while a configured chain sat
unused — so it stays. What it must not do is silently replace a number the
operator set. 6.0.0 (#216) removed the further per-CREDENTIAL subdivision of
this same share; the per-MODEL share survived and is what this fixes.

## What this does

New setting **`FALLBACK_ATTEMPT_SHARE_FLOOR`** (seconds, default `180`), the
smallest slice the division may return:

```
share     = remaining_total / attempts_remaining     (unchanged)
share     = max(share, floor)                        (if floor > 0)
share     = min(share, remaining_total)              (a floor cannot extend the budget)
allowance = min(first_token_timeout, share)          (unchanged)
```

Because the first-token deadline still caps the result, the floor can only
restore the operator's number, never invent a longer one. It ships equal to the
first-token default, so the pair honours itself at any chain length. `0`
restores the pure equal share exactly.

**The cost, stated rather than hidden:** N silent models can spend up to
`N × floor` before the total budget clamps them, and the models after that get
less than the floor, or nothing. The Deadlines calculator names the floor in its
formula when the floor is what decides, and warns with the arithmetic.

### Shipped deadlines raised 1.5× (requested)

| Setting | was | now |
| --- | --- | --- |
| `FALLBACK_FIRST_TOKEN_TIMEOUT` | 120 | **180** |
| `FALLBACK_STALL_TIMEOUT` | 120 | **180** |
| `FALLBACK_REASONING_ANSWER_TIMEOUT` | 300 | **450** |
| `FALLBACK_ATTEMPT_SHARE_FLOOR` | — | **180** |

`FALLBACK_TOTAL_TIMEOUT` stays 600. 120 sat just under the measured p99.9
first-token latency of 181.7 s, which mattered little while a long chain cut it
down anyway; now that the floor makes it the number that actually fires, cutting
off a merely slow model costs a real answer. **Only the shipped defaults move** —
an existing managed `.env` keeps whatever it holds.

## A defect the browser drive found

The calculator read a blank field as `0`. A field nobody has saved — which is
every install's state for a brand-new setting — would therefore have shown the
floor switched off while the server was applying its default. `calcNumber()` now
falls back to the payload's `effective` value, which is what the server uses.
Covered by a jsdom test that clears the first-token deadline and asserts the
formula still names 120 s.

## Residual risks

- **An operator who already runs a long chain gets longer worst-case waits.**
  That is the point of the setting, but it is a behaviour change on upgrade for
  anyone whose chain was longer than `total ÷ floor`. The floor is one number in
  the box away from the old behaviour (`0`), and the calculator states the trade
  before they hit it.
- **The three raised defaults only affect installs that have never saved those
  fields.** Anything in a managed `.env` is untouched, so most existing installs
  see no change from that half.
- **The calculator mirrors `_attempt_deadline` in JavaScript.** Two
  implementations of one rule can drift. The jsdom suite pins the arithmetic on
  both the floored and the pure-share paths, which is what catches drift.
- **`N × floor` exhaustion is a warning, not a refusal.** A budget that cannot
  fit the floor is a legitimate configuration; the page explains it rather than
  blocking the save.

## Deliberately not done

No live upstream was made to stall. The deadline is proved through the real
executor and the real settings-to-policy path with providers that genuinely
produce nothing, not against a real provider that goes quiet. The 8082 server was
read from and never written to or restarted, so it still runs the released build.
No release was cut.
