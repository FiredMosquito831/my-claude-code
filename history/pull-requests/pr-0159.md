## Description

## What was broken

Per-model reasoning capability is keyed by `(provider id, model id)` against models.dev, whose provider ids do not always match ours. **Four of our providers exist there under a different name and simply had no alias**, so every model behind them resolved to unknown and kept today's behaviour — while better data sat in the index.

Found by auditing all 56 of our providers against the live 192-provider index. Coverage was **40/56**; these four take it to **44**:

| ours | models.dev | models | how it was resolved |
| --- | --- | --- | --- |
| `opencode_go` | `opencode-go` | 26 | exact product match |
| `wafer` | `wafer.ai` | 5 | exact product match |
| `kimi` | `moonshotai` | 10 | `KIMI_DEFAULT_BASE` is `api.moonshot.ai/v1` |
| `cloudflare` | `cloudflare-workers-ai` | 25 | `CLOUDFLARE_AI_REST_ROOT` is `api.cloudflare.com/client/v4` — the Workers AI REST root, **not** the AI Gateway host |

The last two were resolved from **base URLs, not name similarity** — that distinction matters, because name similarity is exactly what produces the false matches below.

## The `:free` fallback, kept narrow

After an exact match fails, the lookup retries **within the same provider bucket** with a routing/pricing tag stripped — allow-list `free`, `nitro`, `floor` only.

**`:thinking` and numeric tags are never stripped.** models.dev carries `claude-opus-4-thinking:32000` *and* `:32768`, plus `gemini-2.5-flash-preview:thinking`. For those the tag **is** the reasoning difference, so conflating them would be wrong in precisely the dimension this data configures. An exact hit always beats a tag-stripped one, so `x` and `x:free` keep distinct entries.

**It lives at the lookup layer, not in `_normalize_candidates`** — a genuinely good call by the implementation. That helper runs on both the query *and* the index-building side; widening it would make an `x:free` row register the bare key `x` at build time, colliding with a real `x` row and destroying the ordering, and would leak into the cross-provider-flattened cost/context/vision enrichment where no bucket boundary exists.

## What was deliberately NOT matched, and why it's recorded in-file

Six pairings were considered and **rejected as different products**. A wrong match is *strictly worse* than none, because unknown means "behave exactly as today":

`llamacpp`→`llama` (Meta's hosted API vs a local server) · `ollama`→`ollama-cloud` · `nararoute`→`orcarouter` · `tokenrouter`→`openrouter` · `qwencloud`→`ebcloud` · `mistral_codestral`→`mistral` (deferred — different endpoint)

Six more have no entry at all and correctly stay unknown: `agnes`, `commandcode`, `featherless`, `nous_portal`, `qwencloud_coding`, `sambanova`.

There is a test asserting `llamacpp` resolves to `None` **even when a `llama` provider exists in the fixture** — so a future contributor cannot silently "fix" this into a bug.

**Cross-provider matching by model id alone is deliberately not built**, and the measurement is in the file: `deepseek/deepseek-v4-flash` appears under **81 providers with 16 distinct effort vocabularies and contradictory `can_reason` values**. Reasoning capability is a property of the deployment, not the model.

## Drift guard

`PROVIDER_ID_ALIASES` is a hand-maintained list mirroring another source — the exact shape that broke the Windows installer. A guard now asserts every key is a real `PROVIDER_CATALOG` id, none maps to itself, and none is duplicated in the source text (parsed from text, since a dict literal silently dedupes).

## Residual risks

**The fallback is one-directional** — a tagged id in the index is not reachable from an untagged query. Intentional; only the query direction was in scope.

**The alias map still needs a human when models.dev renames a provider.** The drift guard catches keys that stop being ours; it cannot catch a target that disappears upstream without a network call, which is deliberately not in the test suite.
