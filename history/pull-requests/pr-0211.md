## Description

## What was latent

Not an active failure. The live server log shows only sane values today — `MAX TOKENS BOUNDED BY CONTEXT` producing 42,992–46,128 on `opencode/hy3-free` against 142–146k prompts, and 42,992 is the smallest value produced anywhere. Nothing shipped a tiny `max_tokens`. The defect is that **nothing prevented one**.

## Mechanism

`_apply_context_headroom`, shipped in 5.63.0, computes

```python
headroom = context_length - input_tokens - context_margin   # margin = 1024
if headroom <= 0 or headroom >= resolved: return resolved
return headroom
```

That expression is bounded below by **1**, not by anything useful. When a catalogue `context_length` is wrong, or simply small against a long prompt, it emits an arbitrarily small budget — **3 is reachable**. A request carrying `max_tokens: 3` does not fail; it succeeds and returns a one-token answer, which reads as *"the model had nothing to say"* rather than *"the published context length is wrong"*. That is strictly worse than failing.

**1,117 of 7,440 models.dev entries (15%) report `limit.output == limit.context`**, so this path is not exotic. It is safe today only by the luck of catalogue quality.

## Fix

A new `MAX_OUTPUT_TOKENS_CONTEXT_FLOOR = 4096`, declared the way its three 5.63.0 neighbours are: `config/constants.py` default, `config/settings.py` with `validation_alias`, `.env.example`, the README table, a `LIMIT_RANGES` bound, and the `limits` admin manifest section.

When headroom is positive but below the floor the request is **left unmodified** and a WARNING names the model, the context length, the input tokens, the computed headroom and the floor — the same honest outcome the `headroom <= 0` branch already takes and documents, so the provider reports the real context error instead of MCC inventing a useless budget. `0` restores the pre-floor behaviour.

```
MAX TOKENS BOUNDED BY CONTEXT: 'nvidia_nim/minimaxai/minimax-m3' has a 131072-token
context and the prompt uses 131069, leaving only 3 output tokens -- below
MAX_OUTPUT_TOKENS_CONTEXT_FLOOR=4096. Sending the request unchanged so the provider
reports the real context error; the published context length for this model is
probably wrong
```

### Why 4,096

- **Large enough that a surviving request is useful:** it is the entire output limit many catalogue entries publish, and it is the smallest context window in the catalogue. A model handed 4,096 output tokens is asked for no less than a real small model can do — a tool call plus a genuine answer fits.
- **Small enough not to reject workable requests:** it is a quarter of `REASONING_ANSWER_FLOOR_MAX` (16,384), which is the *most* the reasoning split ever holds back for the visible answer, applied as `min(that, output // 2)`. A floor at or near 16,384 would reject prompts the reasoning path itself is content to run at 2,048 answer tokens. A quarter leaves that split its full working range while still refusing the arbitrarily small budgets the floor exists to stop.

Behaviour at `headroom <= 0` and `headroom >= resolved` is untouched, and the four decision steps stay separately named as 5.63.0 left them (`_apply_model_limit`, `_fall_back_when_unknown`, `_apply_ceiling`, `_apply_context_headroom`).

## Residual risks

- **The floor value is a judgement, not a measurement.** 4,096 is argued from catalogue statistics and from `REASONING_ANSWER_FLOOR_MAX`, not from observed truncations — there are none to observe, because the path has never produced a small budget in the live log. An operator on a genuinely tight small-context model now gets a provider error where they previously got a small-but-nonzero answer; `MAX_OUTPUT_TOKENS_CONTEXT_FLOOR=0` restores the old behaviour exactly.
- **The change is only reachable on models that publish a `context_length`.** Models with no catalogue context are unaffected, as before.
- The WARNING fires once per affected request. On a systematically wrong catalogue entry that is one line per request, which is the intent — the operator needs to see it — but it is not rate-limited.
