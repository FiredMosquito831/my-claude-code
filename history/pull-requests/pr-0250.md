## What this adds

Four coding agents that could not reach this proxy before `POST /v1/chat/completions` shipped in 6.30.0. Three of them use it. The fourth turned out not to need it.

| Harness | id | Command | Protocol | How it is pointed here | Where the model facts go |
| --- | --- | --- | --- | --- | --- |
| **Cline** 3.0.61 | `cline_cli` | `mcc-cline` | OpenAI Chat Completions | `--config <dir>` -> `~/.fcc/cline/` | `providers.json`, `openai-compatible` provider, `contextWindow` / `maxTokens` |
| **Goose** 1.48.0 | `goose` | `mcc-goose` | OpenAI Chat Completions | six environment variables, **no file anywhere** | `GOOSE_CONTEXT_LIMIT` |
| **Aider** 0.86.2 | `aider` | `mcc-aider` | OpenAI Chat Completions | `--model-metadata-file` + `--model-settings-file` | LiteLLM `model_cost` map, plus a `ModelSettings` list |
| **Droid** 0.210.0 | `droid` | `mcc-droid` | **Anthropic Messages** | `--settings <path>` runtime overlay | `customModels[]` with `maxContextLimit` / `maxOutputTokens` / `enableThinking` / `noImageSupport` |

Every fact below was read out of an installed copy of the CLI — each installed into a scratch prefix under the scratchpad, never a global package manager — and then confirmed on the wire against a scratch proxy on 8199. The spec this work came from was wrong about all four in ways that change the design.

## Per CLI: what the spec said, what the CLI does

### Cline — `openai-compatible`, not `openai-native`, and a document with no room for MCC

The spec proposed running `cline auth --provider openai-native --baseurl … --apikey …` against the user's own `~/.cline`. Reading 3.0.61:

- `cline --config <dir>` moves the **whole configuration directory**, and Cline derives its data directory from the settings file inside it. Passing only `--config` produced the full `data/{cache,logs,settings}` tree there. So MCC owns `~/.fcc/cline/` and `~/.cline` is never read for a provider or written.
- `openai-native` is OpenAI's **own hosted** entry. `openai` is an alias that normalises to `openai-compatible`. Only `openai-compatible` both takes an arbitrary `baseUrl` and carries no `modelsSourceUrl`, so it makes no discovery call to a route this proxy does not serve under that id.
- Writing the provider block is **not enough**. With it written but not selected, Cline fell back to its own hosted `cline` provider and failed `Unauthorized: … re-authenticate your Cline account`. `-P openai-compatible` is passed on every session launch.
- **`updatedAt` is required.** An entry with `settings` and `tokenSource` but no `updatedAt` had its whole settings object discarded and rewritten as `{"provider": …, "model": "gpt-4o"}` — base URL and key gone, and the next run reached `api.openai.com`.
- **Any unrecognised root key does the same.** `_mcc_models`, or even `_mcc_defaulted` on its own, triggered the identical reset. So `config/harness_cline.strip_mcc_keys` removes MCC's bookkeeping immediately before the write, and the defaulted record is reported on stderr and by `GET /admin/api/catalogue-models` instead.
- **The key is literal, and that is measured.** With `apiKey` absent and `OPENAI_API_KEY` exported, the run neither authenticated nor terminated. With the key in the document the same run answered in 885 ms. It lands in MCC's own `0600` file under `~/.fcc/cline/`, beside the `.env` that already holds the identical value — the Kimi Code precedent, and nothing is written into a file the user owns.
- Cline's schema has **no per-model array**: the provider entry holds the numbers for the one model it names. So every routable model's resolved limits are recorded in an inert block and `-m`/`--model` promotes the one asked for.

### Goose — the one harness with no generated file at all

Goose 1.48.0 *does* have a declared-model mechanism: `<config dir>/custom_providers/<id>.json`, whose `models[]` carry `context_limit` and per-token costs. It is not used, and the reason is a rule this project already had: that directory is Goose's own (`%APPDATA%\Block\goose\config` on Windows), it holds the user's settings, and Goose publishes no variable or flag moving the config file alone. Writing there would put an MCC-owned document inside a directory MCC does not own.

Everything comes from the environment instead, set in the launched process only: `OPENAI_HOST` + `OPENAI_BASE_PATH=v1/chat/completions` (Goose joins them with RFC 3986 rules and its own default path carries no leading slash), `OPENAI_API_KEY`, `GOOSE_PROVIDER`, `GOOSE_MODEL`, `GOOSE_CONTEXT_LIMIT` and `GOOSE_DISABLE_KEYRING`. Model discovery still works — Goose fetches `<host>/v1/models`, a route this proxy serves.

### Aider — two documents, two flags, and a dataclass that raises

Aider searches for both of its model files in the working directory, the git root **and** `~`, so writing them would mean writing into the user's home. Both have a flag. `HarnessCatalogue` grew `sidecar_filename` / `sidecar_config_flag` for it, and `application/catalogues/__init__.py` grew `SIDECAR_SERIALISERS` beside `SERIALISERS`.

The split is not arbitrary. The metadata JSON is *what the model is*; the settings YAML is *what it accepts* — `accepts_settings: [reasoning_effort, thinking_tokens]` from the ladder's own control flags, `use_temperature: false` only when the provider is known to pin `temperature`. That second file is loaded with `ModelSettings(**entry)`, so an unrecognised key raises: the `_mcc_defaulted` record lives only in the metadata file, which is a plain `dict.update`. The sidecar is written as JSON, which `yaml.safe_load` parses identically, so there is one atomic writer rather than two encoders.

The metadata file is keyed by the whole `openai/<gateway id>` string, because that is the exact argument `Model.get_model_info` looks up; prices are converted from the ladder's USD-per-million to LiteLLM's per-token; and an exact hit short-circuits LiteLLM's price-table fetch from GitHub.

### Droid — Anthropic Messages, and it was worth trying first

The spec grouped Droid with the OpenAI-only CLIs and said to declare a `generic-chat-completion-api` custom model, with "try `anthropic` first" as an aside. Trying it settled it: `provider: "anthropic"` accepts an arbitrary `baseUrl`, instantiates the bundled `@anthropic-ai/sdk` against it and reaches `POST <baseUrl>/v1/messages`. So `mcc-droid` speaks this proxy's own native protocol with no translation layer, and its `HarnessProtocol` is `ANTHROPIC_MESSAGES`.

`--settings <path>` is a runtime overlay merged into Droid's settings hierarchy for that process only — on a machine with no `~/.factory` at all, a file containing nothing but `customModels` was enough for the model to appear and dispatch. So MCC owns `~/.fcc/droid-settings.json` and neither `~/.factory/settings.json` nor its legacy `config.json` is read, merged into or backed up. The key is Droid's own documented `${VAR}` reference; `authMode: "bearer"` moves the SDK off its default `x-api-key`. No Factory account is required: a custom model is classified `isByok` and the login check does not gate it.

## Base-URL shape is now a registry field

An Anthropic SDK appends `/v1/messages` to whatever base URL it is given; an OpenAI SDK appends `chat/completions` and nothing else. `HarnessCatalogue.base_url_shape` selects between `config/harness_base_url.with_root_base_url` and the new `with_v1_base_url`, so a wrong shape fails `test_base_url_shape_is_declared_per_sdk_not_guessed` instead of producing `/v1/v1/…` after a launch.

## One demonstrated defect fixed, because all four expose it

A request that streamed **to completion** through `/v1/chat/completions` or `/v1/responses` was logged as `cancelled`, while the identical request to `/v1/messages` was logged as `success`. Reproducible with plain `curl` on both OpenAI surfaces:

```
$ curl -sN .../v1/chat/completions -d '{"model":"…","stream":true,"messages":[…]}' | tail -1
data: [DONE]
$ # request log row, before:
{'endpoint': '/v1/chat/completions', 'protocol': 'openai_chat', 'status': 'cancelled'}
$ # after:
{'endpoint': '/v1/chat/completions', 'protocol': 'openai_chat', 'status': 'success', 'tokens_out': 7}
```

Cause: both OpenAI adapters `return` the moment their assembler goes terminal, which closes the capture wrapper while it is suspended on its last `yield`; `RequestCapture._observe` recorded `GeneratorExit` as a cancellation unconditionally. It now asks whether the stream had already reached `message_stop` — a reader that stops **after** the answer finished is not a cancellation; one that stops before it still is, and a mid-stream error is still an error. Two tests pin both halves. This is the only change outside the harness layer, and it is not in the chat-completions adapter: the adapters are untouched.

## Residual risks

- **Cline's card reports one provider block rather than a model count, and no defaulted badge.** Cline's document has no room for MCC's own bookkeeping — any unrecognised root key resets it — so the record reaches the launcher's stderr and `GET /admin/api/catalogue-models` but not the file the card reads. Stated in the launcher docstring and in USAGE.
- **Cline's `updatedAt` is written as the epoch**, because a serialiser is a pure function and a real clock would defeat the content-compare skip. Cline replaces it with a real timestamp the first time it saves, and with one provider entry nothing is ordered by it — but a future Cline that *does* order by it would see MCC's file as oldest.
- **Cline's proxy token is literal on disk**, in MCC's own `0600` file. Justified by measurement rather than by schema, so a future Cline release that fixes its `OPENAI_API_KEY` fallback would make this unnecessary.
- **Goose gets no per-model catalogue.** `GOOSE_CONTEXT_LIMIT` carries one model's context window and nothing carries output ceilings, prices or vision. The declared-provider file that would is inside Goose's own config directory; if Goose ever publishes an override for it, that is the follow-up.
- **Aider's `--model-settings-file` is all-or-nothing.** An unknown key makes Aider report an error and continue with the file unapplied; only fields present on 0.86.2's `ModelSettings` are emitted, and a version that removes one would silently drop the whole file's settings.
- **`_mcc_defaulted` in Aider's metadata file is an inert pseudo-model.** It has no `mode: "chat"`, so Aider's own listing skips it, and `model_entries` skips it too — but a future Aider that iterates the map without filtering would see it.
- **Droid's `modelPolicy.allowedBaseUrls` exists** and defaults to unrestricted; an org-managed Factory account could refuse this proxy's base URL. Not reproducible here.
- **The `cancelled` -> `success` fix changes historic-looking behaviour on `/v1/responses` too.** That is the point — the same bug produced the same wrong row there — but anyone who had learned to read `cancelled` as "an OpenAI-surface request" will see the label change.
- **`~/.cline/cli-node-extra-ca-certs.pem` was created on this machine** by the very first `cline --version` probe, before the scratch-home redirection was in place. It is a CA bundle Cline's own Node wrapper writes on startup, holds no user data, and no configuration was written; nothing in the shipped code touches that directory.
