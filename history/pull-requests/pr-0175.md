## Description

## Why

The three rules removed in 5.44.0 had fired **zero** times in 153,198 requests. The deeper problem was never those three: **the rule set mirrors somebody else's product by hand, and nothing could notice drift in either direction.** While they rotted, a *new* housekeeping family appeared and is being paid for with no rule for it — 11 requests of `"Generate a short kebab-case name (2-4 words)"`. This is the thing that notices.

## What

An **on-demand** scan that clusters requests into prompt families and reports each with its measured cost — request count, tokens in/out, tokens per request, first/last seen, char stats, how many carried tools, and a representative request id so a human can open it in the existing detail view.

**Signature:** strip a leading `x-anthropic-billing-header:` line, then the first two non-empty lines truncated to 160 chars. Every part is load-bearing and mutation-covered — the header strip most of all, since it carries `cc_version` and leaving it in splits one family across every Claude Code release that sent it.

**No scoring formula, deliberately.** Invented constants are banned here and no defensible one could be derived, so ranking is by *tokens actually spent* — a measurement — and every input a human might weigh is in the row.

**Families a live rule already answers are excluded** from candidates, keyed on the `optimization` column added in 5.42.0. A solved family is not a discovery.

**Bounded, on-demand, never scheduled and never during a page load.** Default `row_limit` 2,000; above the ceiling the route returns **422 rather than clamping**, because a silently clamped bound makes a sample look like a full scan. The response always states what was actually covered.

## Measured

20,000 rows written through the real store, ~40 KB prompts, unique payloads so blob dedup doesn't flatter it:

```
 1,000 rows (cold)   0.82 s    1,220 rows/s
 5,000 rows          1.55 s    3,218 rows/s
20,000 rows          3.87 s    5,164 rows/s
```

Throughput tracks **prompt bytes, not row count** — the same fixture with 2.3 KB prompts ran at 26,400 rows/s.

**The agent's one unmeasured caveat, now measured.** It flagged that `matching_rows` costs a `COUNT(*)` it worried might dominate. On the real 157,906-row database:

```
COUNT(*) unfiltered    rows= 157,906   best of 3:  2.0 ms
COUNT(*) last 7d       rows=  33,685   best of 3:  0.7 ms
```

0.1% of the default scan. It stays.

## Architecture

`core/optimization_discovery.py`. The policy declares `"core": set()`, and the module imports only stdlib plus `core.request_log`, so no cross-package edge is created. It reads through `iter_export_rows` rather than touching `body_blobs` directly — a checker that encodes its own assumptions about the storage layout is as likely to be wrong as the thing it checks.

One annotation change in `request_log.py`: `iter_export_rows` retyped `Iterator` → `Generator`, because `close()` is part of its contract and a bounded scan that stops early must run the `finally` that closes the connection. `ty` rejected calling `.close()` on an `Iterator`, and no-ignores meant fixing the type rather than hiding it. **Annotation only** — verified, and `admin_export_routes.py` also consumes this generator and is unaffected.

## Deliberately not done

- **No UI, no rule creation, no settings, no scheduling.** A candidate is a suggestion a human approves later; nothing here can cause a request to be answered locally.

## Residual risks

- **The scan is newest-first, so a bounded scan is a recency sample, not a random one.** A family that stopped firing months ago will not appear at the default bound — right for drift detection, a real blind spot for proving a rule has rotted. Widening `row_limit` or setting `since`/`until` is the workaround.
- **`requests_with_tools` reads `params.tools_count`**, written only by messages-path capture. Older rows read as `0` tools rather than *unknown*, unlike `rows_without_prompt_text` which is counted explicitly. Worth fixing if the page leans on the tools signal.
- **`min_requests` floors at 2.** Arguably as invented as any threshold; the defence is only that a set of one is not a recurrence.
