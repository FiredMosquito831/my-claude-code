## Description

Closes the reasoning half of the per-model capability arc (#199, #200, #201). Four defects in one path, all measured on `fork/main`.

## What was broken

**1. `reasoning_options: []` forwarded a raw effort.** models.dev's authoring rules define the empty options list as *"reasoning is on, but the caller has no control"* — **1,223 of its 5,230 reasoning models (23%)** carry it. The parser already represented it correctly (`can_reason=True`, all three `supports_*_control` explicitly `False`, as against `None` for unknown), but `_adapt_effort` ended in an unconditional `return policy, UNCHANGED`: with all three flags `False` every branch was skipped and the effort fell through into a field the model does not have.

```
nvidia_nim/thinkingmachines/inkling   models.dev reasoning_options: []
  parsed  -> effort=False toggle=False budget=False efforts=None can_reason=True
  req minimal -> control=DEFAULT effort=minimal  UNCHANGED
  req max     -> control=DEFAULT effort=max      UNCHANGED
```

**2. Effort → budget was model-independent.** Two tables existed and disagreed. The flat one in `core/reasoning.py` — the one that actually reached the Anthropic, Vertex, NIM and llama.cpp encoders via `numeric_budget_tokens` — priced "high" at **2,048 tokens on a 230,400-output model and 2,048 on a 16,384-output one**. The capability-aware ratio table was reachable only from one narrow branch of `_adapt_effort`.

**3. Thinking and the answer were never reconciled.** `_clamp_budget` capped a budget *at* the output limit, so it could consume 100% of the allowance and leave nothing to reply with; and `providers/anthropic_messages/request.py` **raised** `max_tokens` to `budget + 1` whenever it collided, without consulting the model's real limit at all. A client asking for 4,096 output tokens at the `max` tier was silently sent asking for 8,193.

**4. A client `thinking.budget_tokens` passed through unclamped** whenever `supports_budget_control` was unknown — which is most models — even where `limit.output` was perfectly well known.

## What this does

**New `application/reasoning_budget.py`** owns effort pricing and the split:

```
answer_floor = min(REASONING_ANSWER_FLOOR_MAX, effective_output // 2)
budget       = min(requested, effective_output - answer_floor)
invariant:   budget < max_tokens
```

The floor is **proportional on purpose**: a flat 16,384 on a 16,384-output model (`nvidia_nim/minimaxai/minimax-m3`) gives a budget of zero and silently disables reasoning. Three bounds in increasing hardness — the floor, then Anthropic's 1,024 minimum (a 2,000-token allowance splits 1,024/976, not 1,000/1,000, because 1,000 is a budget the API rejects outright), then the invariant, applied last.

**`ReasoningPolicy` gains `effort_budget_tokens`**, read only by `numeric_budget_tokens`. Deliberately *not* `budget_tokens`: every encoder that can send both checks that field first, so writing a derived value there would have flipped every effort-capable provider onto its budget channel. The flat table survives as the documented last resort for a model nothing publishes a limit for.

**`apply_reasoning_budget` runs per attempt in `ProviderExecutor`**, immediately after `apply_output_token_budget`, so the reasoning budget is reconciled against the exact number that becomes `max_tokens` rather than a recomputed one. It cannot run at gating time: `max_tokens` is not final until the output budget has been resolved against the prompt's token count.

**The invariant is also asserted at the serialisation boundary** in `anthropic_messages/request.py` — user configuration and the per-model output budget are applied after gating, and a violation there is what 400s. The budget yields now, not `max_tokens`; the single exception is a `max_tokens` too small to admit any legal budget at all.

**Also:**

- `_publishes_no_control` drops effort *and* budget for the empty-options case and records `DROPPED` (the existing kind — "level discarded, thinking stays on", which the toggle-only case already reports; a new synonym would split one meaning across two values). Guarded on all three flags being `False`, never `None`, so unknown still passes through untouched.
- `_adapt_budget` clamps whenever the output limit is known, not only when budget *control* is known.
- New `providers/reasoning_vocabulary.py` declares the two endpoints that document a **single** accepted effort value: Mistral (`reasoning_effort: enum [high, none]` in [its own OpenAPI](https://github.com/mistralai/platform-docs-public/blob/main/openapi.yaml)) and Cohere ([documents](https://docs.cohere.com/docs/reasoning) `thinking.type` / `thinking.token_budget` and no effort scale at all). Both were flattening minimal/low/medium to `"high"` inside the request encoder, where nothing records it. Sending `"high"` is correct — mapping to `"none"` would disable the thinking that was asked for — so **the wire shape is unchanged**; declaring the vocabulary as a *lowest-priority* capability tier moves the clamp into gating, which returns an adaptation the request log shows. Only `supports_effort_control`/`supported_efforts` are stated: `can_reason` stays unknown, or every non-reasoning model behind those endpoints would look like a reasoning model.
- `capability.mandatory` is live for the first time (#200 sources it from the gateway; models.dev publishes no such key on any of its 7,483 rows), so `_mandatory_off_rewrite` is now tested end to end: an OFF request against a model that cannot disable thinking becomes its lowest supported effort, or adaptive when it publishes no vocabulary — never left OFF, never dropped.
- New setting `REASONING_ANSWER_FLOOR_MAX=16384` wired through `config/constants.py`, `config/settings.py`, `config/limits.py`, the admin `limits` manifest section, `.env.example` and the README table.

`default_enabled` is **deliberately left unconsumed**, documented at the field: every decision that could read it is answered better by a field that states the thing directly (`can_reason`, `mandatory`, the three `supports_*_control`), and the only remaining use would be emitting a reasoning block because a model defaults to thinking on — reasoning nobody asked for.

## Residual risks

- **The empty-options branch now returns `ReasoningPolicy.on()`**, so encoders with an `enabled_value` (e.g. `reasoning_effort: "high"` on a bare "on") still send that one field. That is the pre-existing toggle-case behaviour and is intentional — the request did ask for reasoning — but on a model that publishes *no* knob at all it is one field more than strictly necessary. It only affects models whose capability record states all three flags `False`.
- **Preflight sees the un-reconciled policy.** Preflight deliberately runs before token counting (pinned by `test_executor_preflight_failure_stays_before_token_count_and_stream`), so `effort_budget_tokens` is not filled in yet. Immaterial to a capability probe, but the two now differ by that field and a test asserts it explicitly.
- **The provider-vocabulary tier makes `resolve_model_reasoning_capability` return non-`None` for every Mistral and Cohere model**, so those two providers now take the full gating path instead of the identity early-return. `can_reason` is left unknown so a models.dev `can_reason=False` still suppresses first, and the encoders' wire output is unchanged — but the blast radius is the whole of those two providers rather than one model.
- **`REASONING_ANSWER_FLOOR_MAX` binds on small models.** On a 16,384-output model a `max` request now gets 8,192 thinking tokens instead of the whole allowance. That is the intended trade (the answer needs room), but it is a real reduction in thinking budget on small models versus `fork/main`.

## Deliberately not done

- Making the learned output cap (`providers/openai_chat/output_cap.py` `_model_output_caps`) durable across restarts.
- Reading `limit.context` from models.dev (#201 sources context only from the provider's own `/models`).
- **`ReasoningControl.ADAPTIVE` no-ops on 55 of 56 providers.** Confirmed by grep: only `providers/anthropic_messages/request.py` emits `{"type": "adaptive"}`, and `requests_reasoning` answers `False` for ADAPTIVE, so every OpenAI-dialect and Google encoder writes nothing at all. Choosing the `adaptive` tier in the admin UI therefore does nothing visible on almost every route, and nothing says so. **A warning is warranted** — but as a routing-time `ReasoningAdaptation` (one record per request, in the request log) rather than a log line, which needs the provider's encoder capability at routing time, and the router does not currently have it. Reported, not redesigned here.
