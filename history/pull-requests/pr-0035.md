## Description

## Why

4.26.0 reduced `fcc-claude` to the two proxy variables, which dropped `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY`. Measured against a live proxy, that variable is exactly what makes Claude Code fetch the catalog:

```
fcc-claude       GET /health,                          POST /v1/messages
fcc-claude-old   GET /health, GET /v1/models?limit=1000, POST /v1/messages
```

So the native `/model` picker stopped listing FCC's models under the default launcher. Requests still routed correctly — only the picker was affected.

## What this does

Adds an FCC-only `--discover-models` flag to `fcc-claude`:

```bash
fcc-claude --discover-models
```

- Stripped from argv **before Claude Code sees it**, and only when it appears before a bare `--` separator, so a literal occurrence inside a passed-through prompt survives.
- The minimal default is **unchanged**. The catalog fetch is an extra request to the proxy on every launch, which is why this is opt-in rather than simply restored.
- `build_minimal_claude_proxy_env` grows a keyword-only `enable_model_discovery` parameter rather than a third builder. `fcc-claude-old` is untouched.

## The documentation half — arguably the more important one

The README feature table claimed *"each agent's native model picker works against the FCC catalog"*. That became **false for `fcc-claude`** the moment 4.26.0 shipped. The same claim appeared in five more places. All corrected to state which launcher they apply to:

| File | Claim fixed |
| --- | --- |
| `README.md` | feature table, screenshot caption, "Connect Claude Code" intro, launcher section |
| `docs/USAGE.md` | "three consequences" list, Step 4 + caption, Shortcut section |
| `admin_static/index.html` | guide "how it works" list, Claude Code step 4, hand-edit fallback |

**Codex and Pi are genuinely unaffected**, and the docs still say so — verified against the code, not assumed: `codex.py` fetches the proxy model list and builds a catalog of its own, and `pi.py` passes `--models`.

The **settings.json route has the same gap**, so the manual instructions and the guide's hand-edit fallback now mention adding `"CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY": "1"` to the same `env` block.

## Verification

Live measurement against a 4.27.0 server, requests attributed by log-line boundaries:

```
=== fcc-claude (no flag) ===
"GET /health"
"POST /v1/messages?beta=true"

=== fcc-claude --discover-models ===
"GET /health"
"GET /v1/models?limit=1000"
"POST /v1/messages?beta=true"
```

Both runs completed a real prompt, which also proves the flag never reaches the `claude` binary — an unknown argument would have aborted it.

**Full suite: 3169 passed, 14 failed** — the documented pre-existing baseline (8 defeated by real API keys in the shell environment, 6 PowerShell installer tests), unchanged on unmodified `main`.

## Residual risks

- **The 4.26.0 dashboard card still writes only the two keys**, so configuring through the button leaves the picker empty as well. Documented, not fixed — whether that card should offer the discovery key is a product decision rather than part of this change.
- The argv rule means a bare `--discover-models` in the leading section is always treated as our flag. Documented in the helper's docstring. A prompt needing that literal text can put it after `--`.
- The picker itself was confirmed only through the proxy's access log, not by eye in an interactive session.
