## Description

## What this is

Custom providers are meant to behave like built-in ones once they are added. Four places where they did not, and one measurement that made the first of them diagnosable after the fact.

The starting evidence was one real request on the user's install: `custom_b_ai/glm-5.3-flash`, `REASONING_*` pinned to `max`, and a wire body carrying `reasoning_effort: "high"` with the adaptation *"…does not accept effort 'max'; sending 'high'"* — while the host accepts `max` and says so in its own 400.

## The dialect defect, measured against the real host

Two requests to `https://api.b.ai/v1`, key read from `~/.fcc/custom_providers.json` and never printed:

```
probe#1  reasoning_effort=bogus_value  -> 400
body: {"error":{"message":"The request is invalid: 该模型始终思考，不支持关闭思考；请使用 low、high 或 max。.
                          Please check the request body, required fields, and request format.", ...}}
parsed enum: ('low', 'high', 'max')

probe#2  reasoning_effort=max          -> 200   (reasoning_content deltas, usage present)
```

So the host takes `max`, names its enum in prose, and MCC was sending `high`. Not a gating bug: gating correctly emitted `model ∩ host`, and the host's half was the standard OpenAI enum because nothing had ever asked the host. A built-in provider states its vocabulary by *writing a profile*; a custom provider has no profile to write.

## The seam

The learned words become a `NamedEffortReasoning` and enter through the declaration a static profile already makes — one `dataclasses.replace` of the profile's `reasoning` field, in `providers/runtime/factory.py`:

```python
if descriptor.reasoning_effort_enum:
    profile = profile_with_learned_dialect(profile, descriptor.reasoning_effort_enum)
```

Nothing downstream can tell a learned dialect from a declared one, and the gating code is untouched:

Layering: the parse is pure text→words in `config/reasoning_enum.py` (stdlib only, no provider imports); the encoder binding is `providers/openai_chat/learned_dialect.py`; the HTTP probe is `providers/runtime/reasoning_probe.py`.

## The probe

At most **two** 16-token chat completions, against a model the catalogue already discovered. Run on create, on **Refresh models**, and from a **Probe reasoning dialect** button on the card.

| Outcome | Meaning | Stored |
| --- | --- | --- |
| 400 naming an enum | that enum is the host's vocabulary | `reasoning_effort_enum`, status `learned` |
| 200 | the host does not read the field | `reasoning_field_ignored: true` |
| 401/402/403/5xx/timeout | nothing measured | status only; behaviour unchanged |
| 400 naming nothing | one extra request tells "field rejected" from "request wrong"; still claims nothing | status only |

The parser accepts English enumerations (`'low', 'medium', 'high'`) and prose lists (`low、high 或 max`, `low, high or max`), and **refuses** to read a vocabulary out of ordinary prose — a candidate list wins only when ≥2 of its items are words an effort scale is actually spelled with. `"Please check the request body, required fields, and request format."` parses to `()`.

The card shows `learned {low, high, max} on 2026-09-01` / `ignored` / `unknown (401)`, never the key and never the response body. A comma-list field beside it edits the vocabulary by hand; clearing it forgets what was learned.

## The other three

**Per-key health on a custom pool.** `key_health()` had exactly one caller, behind a frozenset built from `PROVIDER_CATALOG` credential env keys — and a custom entry has no `credential_env` by design (its keys never reach `.env`). `GET /admin/api/custom-providers/{id}/keys` returns the identical payload, addressed by provider id, so the existing badges render unchanged including 6.19.0's `(key, model)` benches. `credential_rotation` now travels on the custom status entry so custom pools appear in "Rotation, per pool".

**Disable / delete no longer take the process down.** Either gesture on a provider a `MODEL*` setting named made the next `Settings()` raise `ValidationError`.

- **Delete** removes the refs from every `MODEL*` key through the managed-`.env` write path and lists what it removed. A primary route whose model was the deleted provider is unset back to its default.
- **Disable** leaves the refs and **pauses** them via 6.21.0's `MODEL_<TIER>_PAUSED`, recording the `(paused_key, ref)` pairs it added so re-enabling lifts its own pauses and not a hand-made one.
- Settings validation resolves ids through a new `configurable_ids()` — static catalog plus *every* custom entry — while `all_descriptors()`, the runtime's question, still drops the disabled ones.

**Onboarding** counts an enabled custom provider with a key, which its sibling `_fallback_model_configured()` already did. The two no longer disagree about one install.

## Response shape

"reasoning requested 1, returned 0" was two measurements of two different things — outbound bodies carrying a reasoning field, versus requests whose client saw a thinking block — with nothing recorded about the reply, so the ambiguity was unresolvable afterwards.

Each attempt now carries a bounded, content-free tally in `params.response_shape` (no column, no migration, so no `_ATTEMPT_ADDED_COLUMNS` placeholder risk):

```json
{"fields": {"reasoning_content": {"deltas": 1, "chars": 27},
            "content": {"deltas": 1, "chars": 20}},
 "chunks": 5, "finish_reason": "stop", "usage": true,
 "usage_keys": ["completion_tokens", "completion_tokens_details", "prompt_tokens",
                "prompt_tokens_details", "total_tokens"],
 "first_chunk_ms": 0}
```

Capped at 2 KB. **Never any text** — not a sample, not a first line. Absent means *not measured*, which is not the same as nothing arriving. Applied at the same three commit boundaries as `record_wire_request` (openai_chat, anthropic_messages, chatgpt_oauth); Vertex stays NULL as today. Rendered in the request-detail modal under the wire pane as "Response shape". Storage plus one modal block — no analytics rollup.

## Residual risks

- **The probe spends two upstream requests per create/refresh.** Bounded at `max_tokens: 16` and only ever against one discovered model, but a host that bills for a 400 will see a cent of traffic it did not before. It is skippable only by not pressing Refresh models; there is no opt-out setting.
- **A learned vocabulary is a claim about the host, applied to every model on it.** The probe asks one model. A gateway whose models disagree about their effort enums would get the first model's answer applied to all of them. The 6.5.0 reject-and-remember net still catches the per-model 400 that results, and the card's hand-edit is the escape hatch, but the claim is host-wide by construction.
- **Positional mapping for a non-FCC vocabulary is an ordering guess.** When a host's words are its own (`brief`, `detailed`), the six FCC rungs are spread across the list in the order the host named them. Every 400 seen so far lists low-to-high; a host that lists high-to-low would invert the scale. FCC-word vocabularies — the overwhelming majority, and every case measured — use the ordinary nearest-at-or-below rule instead and are unaffected.
- **Delete clears a primary route rather than replacing it.** `MODEL=custom_x/m` becomes unset, so the route falls back to the shipped default. That is deliberate (there is no honest replacement) and it is reported in the banner, but an operator who deletes a provider their primary route used will find their primary route changed.
- **The response shape is recorded on the success path.** An attempt whose stream raised mid-way records nothing, so a truncated stream still reads as "not measured". Widening it to the failure paths is a separate change.
- **`_route_updates_needed` was removed during review of this branch's own test failures.** It read `services.admin.settings` outside the config lock as a dry run, which is a second source of truth; every route write now goes through `apply_admin_config_with` unconditionally. The cost is that a delete or disable touching no routes still rewrites the managed `.env` with identical content.
- Q5, Q6, Q12, Q15, Q16 (context provenance) and Q17 (the five static families outside `_remember_reasoning_rejection` / `_apply_learned_output_cap`) are **out of scope by decision** and unchanged here.
