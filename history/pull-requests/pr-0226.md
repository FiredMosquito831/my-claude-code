## Description

## What was wrong

Agent harnesses verify their endpoint before every run with one tiny non-streaming request and read `response["model"]` back, to catch a proxy that quietly serves a different model than the one asked for:

```json
{"model": "sonnet", "max_tokens": 16, "messages": [{"role": "user", "content": "Say OK"}]}
```

The live request log holds **1,563 of them over four days**. Every one was a real upstream call — some over two minutes — spent to learn a fact MCC knows before it opens a socket.

## The mechanism

Two parts.

**Detecting the probe.** `is_model_routing_probe_request` is deliberately narrow in every dimension a real conversation differs in: no tools, no system text, not streaming, `max_tokens` present and `<= 32`, exactly one `user` turn whose text is `say ok` or `say ok.` after casefolding and stripping. A user who types "Say OK" into a chat carries a real output budget and usually history, so they are never caught.

**Naming the right model.** This is the part that is easy to get subtly wrong. The optimization intercept fires on `plan.primary`, but the executor tries the first attempt the route health registry has *not* benched (`application/execution.py`, `usable_indexes(...)`). So with the primary ejected, real traffic goes to a fallback while a naive local reply still names the primary — reporting the exact substitution the probe exists to detect as a clean bill of health.

`ProviderExecutor.first_usable_attempt(plan)` now exposes the executor's own ordering (same `usable_indexes`, same `provider_lookup`), and the probe's reply carries that attempt's `provider_model`. Other optimization rules are untouched.

### Which identity the normal reply echoes (verified, not assumed)

The probe must compare like with like, so this was grepped rather than guessed:

- `application/routing.py:598-599` — `routed = request.model_copy(deep=True); routed.model = resolved.provider_model`
- `application/execution.py` hands that same `routed.request` to the provider
- `providers/openai_chat/provider.py:1165-1171` — `AnthropicStreamLedger(self._message_id, self._request.model, ...)`
- `core/anthropic/streaming/ledger.py:172` (`self.model = model`) and `:196` (`"model": self.model` inside `message_start`)

So a normal streamed reply echoes the **bare upstream model id** (`minimax/minimax-m3-free`), never the `provider/model` ref (`commandcode/minimax/minimax-m3-free`). The probe reply now carries the same kind of identity.

## Residual risks

- A client that sends exactly `Say OK` with `max_tokens <= 32`, no system text, no tools and no history gets a local `OK`. That shape is a probe by construction, but if one ever is not, `ENABLE_PROBE_AUTO_RESPONSE=false` restores the previous behaviour exactly.
- The probe no longer proves upstream *liveness* — only routing. The run's first real request proves liveness anyway, and fails visibly where a synthetic `OK` would not. This is stated in the code and in the docs.
- `first_usable_attempt` consults `provider_lookup` in `rate_based` mode, which resolves a provider object to read its throttle. No network call, no request; the integration test asserts `preflight_stream` and `stream_response` were never called rather than that the resolver was never touched.
- The reply names the model the executor *would* try first. If the route's health changes between the probe and the run's first request, the two can disagree — the same window the real request already lives with.
