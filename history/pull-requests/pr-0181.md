## Description

Two independent reasons a configured chain sits unused. Both found from the reporter's own request log — 161,812 rows, server on 5.49.0.

---

## 1. A model that only thinks commits the route

This is the reported failure: `Provider 'nous_portal/tencent/hy3:free' exceeded the 600s request budget`, on a route with **eight models** configured behind it.

```
budget failures by model   tencent/hy3:free 479, upstage/solar-pro4:free 9
route_attempt on those     0 -> 490,  1 -> 7,  2 -> 2
the reported request       ttft 49.4s, thinking 5,518 chars, answer 0 chars, 600.1s
```

Reasoning deltas count as answer content, so **the first thought commits the route**. From then on no other model may take over, the stall guard never fires because thoughts keep arriving, and the request runs until the whole budget ends it. 490 of 499 exhaustions never left attempt 0.

**Nothing the reader has seen is nothing the reader would lose.** With `FALLBACK_ON_REASONING_ONLY` on, reasoning is held in the existing holdback buffer like an envelope frame — the executor sees no chunk, so the attempt keeps its first-token deadline and its share of the budget, expires there, and the next model answers.

The answer itself still commits exactly as before, and tool arguments are an answer: a tool call is the model acting, not deliberating. `signature_delta` travels with `thinking_delta` — it is the cryptographic tail of a thinking block.

**The cost is real, which is why it is a setting.** Reasoning no longer streams live; it arrives with the answer, or when the buffer's 64 KB cap forces a commit. Default on, because that is what the reporter is hitting. Off restores today's behaviour, on the model config page with the trade stated in the field description.

## 2. A provider in rate-limit cooldown is waited on instead of stepped over

A provider serving a 429 cooldown does not refuse the next request — it accepts it and **sleeps inside its own limiter** until the cooldown expires (up to an hour on `Retry-After`) or the attempt deadline does, then hands the chain a timeout.

`throttle_remaining()` already reported this on every provider; nothing above the provider layer looked. Routing now asks — **only while another candidate remains**, so the last model is tried cooldown or not (Part IV §3: skipping a bad model is an optimisation, refusing to try anything is an outage). A stepped-over model records `skipped` / `cooldown`, not `failed`, and is not counted toward ejection.

`RotatingProvider` inherited `BaseProvider`'s unconditional `0.0`, so a multi-credential provider claimed to be free with every key limited. It now reports the shortest cooldown across its credentials.

**Scope note (§168):** this half was written from the code path *before* the log was consulted, and is **not** credited with the reported failure. Their 429s are rare and last occurred 2026-08-14. It is a real gap on its own.

**Correction to the numbers in this PR, and a follow-up fix.**

Two errors found by auditing this work against the project's own notes after it merged.

**1. The "479 of 499" figure is wrong.** 479 is how many of those budget exhaustions ran on one *model* (`tencent/hy3:free`) — not how many had this *mechanism*. I grouped by model and reported it as a mechanism count. The real split of the 499:

```
nothing at all   401   (the older scaffolding shape, already fixed)
some answer       54
reasoning only    44   <- what this PR addresses
```

The reported failure is still a reasoning one, and the mechanism is still real. The prevalence claim was overstated by ~11x. Corrected in the release notes, `.env.example`, the README and the source comments.

**2. The deadline this PR gives a held-reasoning attempt is far too tight.** Holding reasoning makes the attempt look silent to routing, so it inherits the first-token share — `FALLBACK_TOTAL_TIMEOUT` divided by the chain length. On an 11-model chain that is **54 seconds**, which is not enough time for a model to think.

Measured against the same log:

```
successful requests that produced reasoning      105,078
  slower than a 54.5s answer-deadline, with
  little or no answer (i.e. would be diverted)     1,387
  same, against a 300s answer-deadline                27
```

So as merged this diverts ~1,387 successful requests to rescue ~44 failures. Every one of the 499 exhaustions ran the **full** 600s, so any allowance below that rescues all of them — the tight share buys nothing and costs a lot.

A follow-up adds `FALLBACK_REASONING_ANSWER_TIMEOUT` (default 300s) as a flat allowance, so a thinking attempt is judged by how long it has been thinking rather than by a share sized for a model that has shown nothing.
