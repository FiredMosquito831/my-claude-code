## Description

## What this adds

Three coding agents MCC could already serve had no launcher: **OpenCode**, the
**OpenCode 2** preview (a separate `opencode2` binary that installs beside v1)
and **Kilo CLI**, which documents itself as a fork of OpenCode with the same
configuration. All three speak Anthropic Messages, so they reach MCC's existing
`POST /v1/messages` and need no new inbound surface.

`mcc-opencode`, `mcc-opencode2` and `mcc-kilo` are generated from the registry
added in #241 — console scripts, both installers' verification and summary
lists, both uninstallers' cleanup lists, `mcc-help`, and the Coding agents page.
No `fcc-` aliases: no installed copy of MCC ever published one, so inventing
them would ship commands that never had users.

## Zero-clobber: MCC owns a file, the user keeps theirs

These are the first harnesses that read provider configuration from a **file**
rather than from argv or env. Merging a block into
`~/.config/opencode/opencode.json` would make MCC a co-owner of a hand-written
document and leave a provider behind for anyone who stops using it. Each CLI
publishes a way out — an environment variable naming an *extra* config file
that joins the precedence chain rather than replacing it:

| Command | File MCC owns | Variable it is handed with | Documented at |
| --- | --- | --- | --- |
| `mcc-opencode` | `~/.fcc/opencode-config.json` | `OPENCODE_CONFIG` | https://opencode.ai/docs/config/ — "Custom config is loaded between global and project configs in the precedence order", "Configuration files are merged together, not replaced" |
| `mcc-opencode2` | `~/.fcc/opencode2-config.json` | `OPENCODE_CONFIG` | same (verified against the v2 binary, below) |
| `mcc-kilo` | `~/.fcc/kilo-config.json` | `KILO_CONFIG` | https://kilo.ai/docs/code-with-ai/platforms/cli — "The Kilo CLI is a fork of OpenCode and supports the same configuration options" |

The user's own file is never read, written, merged or backed up. The file MCC
owns is created by the first `mcc-<id>` run — never at startup, so nothing is
scattered for a CLI you do not use — and refreshed by the existing fan-out
publisher afterwards.

**The token stays off disk.** The document writes `baseURL`, `apiKey` and an
`Authorization` header as OpenCode's own `{env:VARIABLE}` substitutions; the
launcher sets those two variables in the child process only.

The explicit `Authorization` header is not belt-and-braces. MCC authenticates
on `Authorization: Bearer` — the header Claude Code's `ANTHROPIC_AUTH_TOKEN`
produces (`api/dependencies.py:56`) — while `@ai-sdk/anthropic` sends
`x-api-key`, which MCC does not read. **Measured on OpenCode 1.18.25**: with
`apiKey` alone every request arrived at `POST /v1/messages` with no credential
and came back 401; adding the header made the same request 200.

## The serialiser

`application/catalogues/opencode.py`, one pure function shared by all three
harnesses (`format_id: "opencode"`), covered by the existing AST guard
`test_no_serialiser_hard_codes_a_limit`.

| Ladder field | OpenCode key |
| --- | --- |
| `context_length` | `limit.context` |
| `max_output_tokens` | `limit.output` |
| `reasoning.can_reason` | `reasoning` |
| `supports_tool_calls` | `tool_call` |
| `supports_vision` | `attachment` + `modalities.input` |
| `input_price` / `output_price` | `cost.input` / `cost.output` |
| `reasoning.supported_efforts` | `variants.<rung>`, clamped to OpenCode's own rungs |
| `default_parameters` | `options` |
| `provider_model_ref` (or the gateway id, for the no-thinking variant) | the model key, addressed as `mcc/<provider>/<model>` |

**Unknown stays unknown, in OpenCode's own idiom.** Every per-model key is
optional, and OpenCode's own fallback for an absent one is `0` — measured
against `opencode models --verbose` with a model declaring only a name. `0` is
exactly how models.dev, OpenCode's own model database, spells "not applicable
or unknown", and how MCC's own models.dev parser already reads it
(`providers/runtime/models_dev.py`). So an unknown limit is **omitted** rather
than invented, and every omission is recorded in `_mcc_defaulted`, on the
launcher's stderr and on the dashboard card.

## CONFIRMED vs UNVERIFIED

**CONFIRMED (a command was run, or the vendor's own doc was fetched)**

- `OPENCODE_CONFIG` points OpenCode at an MCC-owned file and merges rather than
  replaces — documented, and exercised on v1 `1.18.25` and v2 `0.0.0-beta-18743`.
- The per-model schema (`limit`, `cost`, `reasoning`, `tool_call`,
  `attachment`, `modalities`, `options`, `variants`) — read from the live
  `https://opencode.ai/config.json` schema and round-tripped through
  `opencode models --verbose`.
- OpenCode's fallback for an absent optional key is `0` for limits and costs,
  `true` for `tool_call`, `false` for `reasoning`/`attachment` — measured.
- `apiKey` alone does not authenticate against MCC; the `Authorization` header
  does — measured, 401 then 200.
- OpenCode 2 reads the same document and lists the same models; it needs
  `--standalone` because its background service keeps the config it started
  with — measured.
- `opencode` v1 `1.18.25` and `codex` are installed here; `opencode2` only in a
  scratch prefix; `kilo` is absent.

**UNVERIFIED**

- **Kilo's config was never loaded by a Kilo binary.** Its schema and
  `KILO_CONFIG` rest entirely on Kilo's own documentation, which states it is
  an OpenCode fork supporting the same options. Nobody ran `kilo` here.
- Whether `@ai-sdk/anthropic` honours a `variants.<rung>.reasoningEffort` body
  on the wire. MCC names only rungs the ladder published and invents no token
  budget, but the effect of selecting one was not measured.
- Whether OpenCode's own synthesised `high` / `max` thinking variants can be
  suppressed. For a reasoning model on `@ai-sdk/anthropic` OpenCode adds them
  itself from `limit.output`; MCC can decline to add rungs a model never
  claimed, but cannot remove OpenCode's two.
- RTK: all three ship `rtk_agent=False`. Whether RTK's shell-tool wrapper
  applies to OpenCode is unverified, and the registry's rule is that the flag
  is only set for an agent someone has confirmed.

## Deviations from the plan

- **`options.headers.Authorization` was added to the generated document.** The
  plan said auth would be MCC's `ANTHROPIC_AUTH_TOKEN` through `options.apiKey`;
  measurement showed that alone produces a 401 every time.
- **`mcc-opencode2 run` is documented and offered as `run --standalone`.** v2's
  background service caches the config it started with.
- **Unknown limits are omitted rather than filled from a CLI default.** The
  base rule says use the CLI's documented default where a field is required;
  OpenCode makes them all optional and its own fallback is `0`, which is
  models.dev's spelling of "unknown". Writing a made-up number would have been
  the invention the rule exists to prevent. Every omission is still recorded in
  `_mcc_defaulted`.

## Residual risks

- **Kilo is unverified end to end.** If its fork has diverged, `mcc-kilo` will
  produce a config Kilo ignores. It degrades to launching with no MCC provider
  rather than failing, and no user file is touched either way.
- **A `limit` MCC omits reads as `0` inside OpenCode**, which its context
  readout and compaction will treat as unknown. That is the honest state for a
  model nobody published a window for, but it is not a working ceiling.
- **Reasoning clamping is additive only.** OpenCode synthesises its own `high`
  and `max` variants for a reasoning model on `@ai-sdk/anthropic`; MCC cannot
  remove them, so a model whose ladder published only `low`/`medium` will still
  show OpenCode's two.
- **OpenCode 2 is a beta.** Its version string moves every build
  (`0.0.0-beta-18743` here) and its schema could diverge from v1 without notice;
  they share one serialiser today.
- **`opencode` on PATH is not proof it is OpenCode.** Unlike Pi, these three
  carry no `identity_help_markers`, so a same-named binary would be launched.
- The scratch verification used a local fake gateway for upstream metadata, not
  a paid provider; the numbers in the fragment above are models.dev's real
  answers for those model ids, resolved through MCC's own ladder.
