## Description

## What was wrong

A model that was **actively streaming a tool call** could be killed as a stall.

`req_e49840e712434d85ba85f0c4734b1e68` (`nvidia_nim/moonshotai/kimi-k3`, streaming client, 66 tools) produced 1,333 chars of text and 3,625 chars of thinking, then died at `MODEL DEADLINE: stalled after 120s` with `tool_call_count` NULL — no tool call ever completed, and `ladder_tries=1`.

## Mechanism

The stall clock in `application/execution.py` resets `last_progress` only on a chunk for which `sse_carries_content()` is true — i.e. one containing a `content_block_delta`.

The openai_chat translator holds tool arguments back until the JSON parses:

- `Task` arguments accumulate in `ledger.blocks.buffer_task_args`;
- any tool whose argument names were **aliased for the wire** accumulates in `tool_argument_alias_buffers` until `_restore_aliased_tool_arguments` succeeds.

While buffering, `_emit_tool_arg_delta` yielded **nothing at all**. So the executor saw no content and measured the buffer instead of the model: a stream delivering a fragment every 100 ms was judged silent.

## Fix

The two buffering paths now yield `REASONING_HEARTBEAT` — the existing *"I consumed an upstream delta and have nothing to forward yet"* signal, already used by the reasoning holdback in `providers/stream_recovery.py:234-237`. The openai_chat stream loop forwards it **directly rather than through `hold_event`**, so it can never enter the holdback and commit the route on nothing. In `execution.py` the heartbeat branch now resets `last_progress` in addition to setting `reasoning_since`.

No new setting, no `.env.example` change, no `_chunk_timeout` change.

## Residual risks

- A provider that emits heartbeats indefinitely while genuinely making no progress would now hold an attempt until the **total** budget rather than the stall limit. That requires the translator to keep consuming upstream fragments, which is upstream liveness by definition; `total_timeout` still bounds it.
- The heartbeat is the empty string and is shared with the reasoning holdback, so the two are indistinguishable at runtime. That is deliberate — every forwarder writes nothing for either, and giving them separate but equal constants would add a name without adding behaviour.
- A `Task` fragment arriving after the arguments already emitted also produces a heartbeat. It is still "upstream delivered a fragment", so the semantics hold.

## Known and deliberate (not in this PR)

Once content has been committed, a mid-stream stall still **ends** the request rather than following the fallback chain. Resuming a committed Anthropic SSE message on another model is separate work.
