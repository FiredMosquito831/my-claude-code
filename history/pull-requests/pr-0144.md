## What this changes

Nine values deciding how `mcc-desktop` behaves were literals in the source, and a Chromium installed anywhere unusual was **undiscoverable** because a hardcoded candidate list was the only way a browser could be found.

All nine become settings, riding the machinery that already exists for the fallback and retention limits rather than a parallel one — a `LimitRange` in the shared table, a `Settings` field, a manifest entry, an `.env.example` block.

| Setting | Default | Range | Why the bound |
|---|---|---|---|
| `DESKTOP_HEALTH_CHECK_INTERVAL` | 0.25 | 0.05–5 | floor stops a busy loop |
| `DESKTOP_SERVER_START_TIMEOUT` | 15 | 1–300 | |
| `DESKTOP_ADMIN_REQUEST_TIMEOUT` | 5 | 0.5–60 | loopback, so both ends stay short |
| `DESKTOP_ACTIVATION_POLL_SECONDS` | 1 | 0.1–3600 | floor stops a busy loop |
| `DESKTOP_HEALTH_POLL_SECONDS` | 5 | 0.5–3600 | floor stops a busy loop |
| `DESKTOP_HEALTH_FAILURE_THRESHOLD` | 3 | 1–1000 | this is what debounces a self-update restart |
| `DESKTOP_WINDOW_WIDTH` | 1400 | 640–7680 | 640 keeps the dashboard usable |
| `DESKTOP_WINDOW_HEIGHT` | 900 | 480–4320 | |
| `DESKTOP_BROWSER_PATH` | `""` | — | explicit Chromium path |

The shared table is the point: the form **rejects** out-of-range input and quotes the range, `Settings` **clamps** at load with a warning, and both read the same entry — so the form cannot accept a value the runtime will quietly change.

`"1400,900"` split into width and height because a single string cannot be range-validated. `DESKTOP_BROWSER_PATH` removes an assumption rather than a constant: set it and it wins; point it at nothing and it logs and falls through to the search.

**Deliberately left hardcoded**, with the reason: `desktop.lock` / `desktop.activate` (internal file names), `LINUX_WM_CLASS` (window-manager identity), the profile directory name, the server module import path. "As little hardcoded as possible" needs a boundary or it ends with a configurable application name.

Every field description states that `mcc-desktop` reads these **once at launch**, so a change applies to the next tray start. A setting that appears to do nothing is worse than one that is absent.

## A defect caught in review

The fields were registered as a `desktop` manifest section that **no dashboard view claimed** — so all nine would have been served by the API and **rendered nowhere**. Schema, persistence and serialization all working while the page stayed blank. This project shipped that exact gap once before, as a settings page with no page.

Fixed, and then made impossible to repeat: a new contract test asserts every manifest section is claimed by some view, and every key a view claims exists. It parses the shipped `admin.js` rather than a Python mirror — **a mirror would agree with itself while the page stayed blank**. It immediately found a second, pre-existing orphan (`smoke`), recorded in a documented allow-list rather than hidden by weakening the assertion.

Mutation-tested: unclaiming `desktop` fails it by name.

## Residual risks

- The desktop process reads these at launch, so a change needs a tray restart. Stated in every description, but it is a real ergonomic wrinkle.
- The window size feeds `--window-size` for app-mode; a value the OS rejects is the OS's business, not ours.
- `smoke` remains unrendered by design and is now explicitly recorded rather than silently orphaned.
