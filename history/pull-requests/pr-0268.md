Desktop PR **S0** of the webview arc (`specs/PR-DESKTOP-WEBVIEW-SPEC.md` §6.5) — contract **C7**. Version **6.41.3, PATCH**: a pure bug fix, no new surface, no new dependency, no shell.

## The bug

`uv tool uninstall` removes shims and nothing else. The config purge reaches only what is *inside* `~/.mcc` / `~/.fcc`. Every artefact the desktop half of an install writes lives outside both, so all of it survived an uninstall:

* the Start Menu shortcut kept pointing at a deleted `mcc-desktop.exe` and did nothing when clicked;
* the HKCU `Run` value — and on the other platforms the LaunchAgent, the systemd user unit and the XDG autostart entry — kept trying to launch a package that was no longer installed, at every login;
* the `.desktop` entry, its icon and the macOS `.app` bundle stayed in the launcher forever.

## What is deliberately kept

Purge semantics are untouched: `~/.mcc` and `~/.fcc` go, **`~/.fcc-old` stays** (it holds the user's rollback note), `~/.claude` is never touched, and uv, the uv-managed Python, Claude Code, Codex, Pi and shared `PATH` entries are left installed. `test_neither_uninstaller_touches_the_retired_rollback_directory` pins exactly that, so the new removals cannot drift into it. The shared XDG directories (`~/.local/share/applications`, `~/.config/autostart`) are left in place — they are not ours.

## Safety properties preserved

* **Ordering.** Desktop artefacts are removed only *after* every shim is verified gone, in the same gate that protects the config purge. An unverified tool removal now leaves config **and** shortcut exactly as they were (`test_uninstall_sh_keeps_desktop_artefacts_when_removal_is_unconfirmed`, `test_uninstall_ps1_keeps_the_shortcut_when_removal_is_unconfirmed`).
* **`--dry-run` / `-DryRun`** prints each removal and performs none (two new scenarios).
* **Best effort where it must be.** A `.lnk` the shell has open, or a locked `Run` key, warns rather than aborting — the tool and the config are already gone, so failing there would strand the user with nothing to retry (`test_uninstall_ps1_survives_a_registry_removal_failure`).
* **Absence is normal.** The launcher is opt-in and autostart is off by default; a missing artefact is never an error, and `systemctl` is invoked only when the unit file we wrote is actually present, so a machine with no user bus is untouched.

## Test-harness hardening (worth reviewing)

The PowerShell uninstaller fixture previously inherited the **real** `APPDATA` and had no registry stub. Adding shortcut and `Run`-value removal to the script without fixing that would have made a passing test delete the developer's own Start Menu entry and autostart value. The fixture now redirects `APPDATA`/`LOCALAPPDATA` into `tmp_path` (asserted in the fixture itself) and stubs `Get-ItemProperty` / `Remove-ItemProperty` in the wrapper, so no scenario in this suite can reach the real Start Menu or the real `Run` key.
