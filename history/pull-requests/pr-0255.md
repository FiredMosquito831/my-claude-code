## Description

# Catalogues that carry what the ladder already knows, and that every CLI will actually load

The user ran the shipped launcher and got this:

```
$ mcc-opencode models mcc
My Claude Code: 142 model(s) publish no value for one or more fields, so OpenCode falls back to its own default:
  chatgpt_oauth/gpt-5.5: limit.context, tool_call, attachment, cost
  commandcode/z-ai/glm-5.3-flash: tool_call, attachment, cost
  custom_b_ai/glm-5.3-flash: limit.context, tool_call, attachment, cost
  ... 139 more ...
Error: Configuration is invalid at C:\Users\...\.fcc\opencode-config.json
↳ Missing key provider.mcc.models.custom_b_ai/glm-5.3-flash.limit.context
↳ ... 53 more ...
```

Exit 1. Zero models listed. The 142 lines were not a warning about the failure —
they were noise in front of it.

Two causes, and the second is the interesting one.

---

## 1. The refusal: a `limit` object may not ship half-populated

`application/catalogues/opencode.py::_limit` built whichever half it knew and
`_entry` shipped it because it was truthy. Read out of the schema OpenCode
publishes (vendored at `tests/fixtures/schemas/opencode-config.schema.json`) and
reproduced against the real 1.18.26 binary:

```json
"limit": { "properties": {"context": …, "input": …, "output": …},
           "required": ["context","output"], "additionalProperties": false }
```

`limit` is **optional**; a *present* one must carry both. So the document was
rejected whole — not the entry, the document. The all-or-nothing rule was
already implemented one function down for `cost`; `_limit` simply never got it.

`_limit` now emits both keys or neither, filling an unknown half with `0` —
OpenCode's own documented unknown marker, the same value its coercion reads for
an absent `limit.context`. That keeps a known ceiling instead of discarding it
to satisfy a schema; a model with neither half known gets no `limit` at all,
which loads fine.

`cost` deliberately keeps the opposite rule and does **not** fill: a half-known
price is no price, and OpenCode publishes no spelling for an unknown *price*
the way it does for an unknown window.

## 2. The cause behind the cause: one field walked the ladder, four did not

`max_output_tokens` walked ten rungs — the routed deployment's own `/models`,
then models.dev's bucket for that provider, then the OpenRouter reference
catalogue, then a quorum-guarded cross-provider vote — and answered 124 of 128
models on this install.

`context_length`, `supports_vision`, `supports_tool_calls` and the prices
reached the same records through `enrich_model_infos`: a **flat, provider-blind,
un-tiered** name match that consults no reference bucket, strips no routing tag
and records no rung. It lands hardest on exactly the models a gateway resells.

Four siblings of `model_output_limit_tiered` now exist in
`providers/runtime/models_dev.py` — `model_context_length_tiered`,
`model_vision_tiered`, `model_tool_call_tiered`, `model_prices_tiered` — walking
the same rungs in the same order under the same minimum-sample guards, each
reporting the rung that answered.

**No rung's logic, order or quorum changed.** The diff of that file is **320
insertions and 0 deletions**:

```
$ git diff -U0 fork/main -- src/my_claude_code/providers/runtime/models_dev.py | grep '^-' | grep -v '^---' | wc -l
0
```

`capability_payload` (the Models page) and `catalogue_model._resolve` (every
generated catalogue, `/admin/api/catalogue-models`, `GET /v1beta/models`) both
consult them, with the routed deployment's own `ProviderModelInfo` winning
outright in both, so the two surfaces cannot disagree about a value or about its
provenance.

`ProviderManager.model_context_length` is deliberately **not** one of them and
stays provider-only. It feeds `application/output_tokens.py`, where an output
budget derived from a resold model's *originating* window would not fit the
deployment actually serving it. That file is unchanged.

### Kilo: two failures, one root cause

Kilo runs an excess-key check against the **root** of its config before
decoding:

```
Error: Configuration is invalid at …\kilo\kilo.json
↳ Unrecognized key: _mcc_defaulted
```

Through `KILO_CONFIG` it is worse, not better: that load path wraps the parse in
`catchDefect` and swallows the failure into an empty object, so the provider
simply vanishes — `kilo models` lists 300 built-ins, none of them MCC's, exit 0,
no error. That is what a user actually saw, and it is why `KILO_CONFIG` looked
broken. It is not: it works, and the marker key was the whole problem.

## Residual risks

1. **The cross-provider vote now decides more fields.** `tool_call` and the
   cache rates can be answered at tiers 7-10 — a modal value across rows that
   merely share a name. The same three-reporter quorum applies and the rung is
   reported and badged `approximate`, but a wrong `tool_call: true` for a model
   that cannot call tools would surface as a tool-use failure rather than as an
   absent capability. **Accepted:** the alternative is what shipped, which was
   63 of 142 models defaulting to `tool_call: true` anyway, unrecorded.
2. **Price tie-breaks resolve toward the lower number**, unlike limits and
   booleans which resolve toward the more capable reading. That is a judgement
   call written down in `_LadderField`, not a measurement.
3. **Codex's `availability_nux` and `upgrade`** appear in the binary's
   `ModelInfo` field list without an obvious `#[serde(default)]`. MCC does not
   emit them and Codex loads the catalogue anyway, so they are treated as not
   required — **UNVERIFIED** by direct probe.
4. **Six serialisers' unknown policies still rest on their own docstrings.**
   Crush and Cline were confirmed against binaries this round; Pi and Droid were
   not, and Command Code's `--list-models` shortfall (116 of 142) reported by
   the tester remains unexplained.
5. **`GET /v1beta/models` now lists fewer models than `/v1/models`.** That is
   the intended shape — a picker versus a protocol surface — but it is a
   user-visible change to a published route and is documented in ARCHITECTURE
   and USAGE rather than versioned as breaking, because no id changed meaning.
6. **The live 8082 was not restarted**, so none of this is running there yet.
   Everything measured against it is the *old* build's output used as input.
7. **A re-projected no-thinking twin loses its server-side reasoning
   suppression.** The `claude-3-freecc-no-thinking/` id decodes to
   `force_reasoning_off=True` in `application/routing.py`; the plain id takes
   the configured `reasoning_policy` instead. For the models this affects that
   is inert — they are re-projected *because* their provider reported they
   cannot think, and the record states `can_reason=False` — but it stops being
   inert if a provider's `supports_thinking` is wrong. On this install all 14
   such refs are `:batch` and are excluded anyway, so the path is dormant here:
   **CONFIRMED dormant, UNVERIFIED against a non-batch example.**
8. **`cline` and `qwen` config loading is UNVERIFIED.** Neither CLI has a
   non-interactive command that provably validates the document MCC writes —
   both exit 0 on a deliberately corrupt one, so their rows in the matrix are
   reported as weak passes rather than passes.
