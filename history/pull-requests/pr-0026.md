## Description

Two gaps in the model request analytics. MINOR `4.21.5` → `4.22.0`.

## 1. Per-provider token usage was unreadable

The provider and key tables collapsed input and output into one **Tokens** number — even though the store already returned `tokens_in`/`tokens_out` separately, and the *model* table already showed them as `in / out`. Same data, two different presentations, and per-provider usage couldn't actually be read off the page.

Both tables now report input and output separately.

## 2. Prompt caching wasn't tracked at all

For cache-heavy workloads this is most of the input bill, and nothing surfaced it.

`Usage` already carried `cache_creation_input_tokens` / `cache_read_input_tokens` (DeepSeek populates them), and the streaming capture read `input_tokens` out of *exactly the dict those sit in* — then discarded them.

Now captured, stored, aggregated, and surfaced as:

| Metric | Meaning |
|---|---|
| **Input (uncached)** | `tokens_in` — the uncached portion |
| **Cached input** | tokens served from cache |
| **Cache hit rate** | reads ÷ (uncached + reads + writes) |
| **Cache writes** | tokens written into the cache |

`tokens_in` deliberately stays the *uncached* portion, matching Anthropic's semantics — so total prompt input is uncached + reads + writes. The hit rate divides by that total, not by `tokens_in` alone, which would otherwise read well above 100%.

## Storage and migration

Columns arrive through the existing `_ADDED_COLUMNS` path, so databases created by earlier versions migrate in place rather than losing history.

The covering index gains both columns and is renamed **v3** — `CREATE INDEX IF NOT EXISTS` would otherwise keep the v2 index and silently drop index-only coverage. That's the exact trap its own comment documents, and it would have cost a slow full scan on every stats load.

## Verification

Against a copy of a real request log: existing rows survive the migration, a recorded request reports 900 cached against 100 uncached, and the provider breakdown yields **90.0%**. The rate helper was exercised directly:

```
nvidia_nim   -> 90.0%
no cache     -> 0.0%
with writes  -> 60.0%
no data      -> —
missing keys -> —
```

New tests cover the aggregation, the uncached-vs-cached semantics, and migration from a pre-cache schema. `ruff`, `ty` clean; full suite passes except the 14 failures that also fail on unmodified `main`.

## Residual risks

Only providers that actually report cache counters populate these — Anthropic-shaped upstreams and DeepSeek today. Everything else shows 0 cached and a 0.0% hit rate, which is accurate but could read as "caching is broken" rather than "this provider doesn't report it". Worth a follow-up to distinguish *unsupported* from *zero* if it causes confusion.

Historical rows keep `NULL` and are counted as 0 — your existing 8,614 requests will show no cache data until new traffic arrives.
