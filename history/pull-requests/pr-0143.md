## Description

## What this changes

v5.27.0 added a `window` preference to `desktop.json` and a `--window` flag, but **the dashboard could not set it**. The endpoint carried the value through every save without ever accepting one, so the CLI was the only way to change it.

The Deployment section already existed, so this adds a control to it rather than building a second home for desktop settings.

Beside the select, a read-only line reports what `auto` actually resolves to on this machine — `auto → app-mode (Microsoft Edge)` — because a preference of "auto" otherwise tells you nothing about what you will get.

Each option states its real consequence, and the embedded-webview option says plainly that **OAuth login, downloads and copy buttons may not work in it**. That is the whole reason app-mode is the default, so burying it is the one thing that hint must not do.

## The import boundary, resolved by moving

Resolution had to be readable from the API, and `api` may not import `cli` (`tests/contracts/test_import_boundaries.py`). Rather than crossing the edge or keeping a second copy, the Chromium lookup and availability logic **moved** from `cli/desktop_window.py` to `config/desktop.py`, which both may import — a complete migration, not a shim. Import-boundary contract: **19 passed**.

## One defect fixed on review

`_desktop_state_response` called `resolve_auto_window()` inline on an `async def` handler. Measured **43 ms median, 75 ms max**, and it does not get cheaper on repeat because `shutil.which` is the cost rather than the import — so every desktop request stalled the event loop for that long. All three call sites now hand it to a thread, with the measurement recorded beside it so nobody simplifies it back.

## A false bug worth recording

A live reproduction "showed" the preference resetting on every unrelated save, and the suite showed a matching **seventh** failure — three signals agreeing. All three were artifacts of starting a server from the worktree venv while `uv run pytest` was reinstalling the package into that same venv. Run with nothing else touching the venv, the behaviour is correct and the suite sits at baseline. Two concurrent `uv run` invocations against one worktree fight over its `.venv`; anything measured during the overlap is measuring a half-installed package.

## Residual risks

- **No DOM was executed.** The dashboard was exercised over real HTTP against a running server and the select's presence is asserted in the served markup — but `admin.js` was not run, so the wiring is verified by reading plus the API round trip, not by clicking.
- `resolve_auto_window()` is uncached. It is called once per page load and once per save, now off the event loop, so caching would add invalidation risk for no measurable gain.
