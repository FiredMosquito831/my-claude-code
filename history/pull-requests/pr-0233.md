## Description

## What was wrong


A model that fails *after* it has started answering cannot be replaced: the
reader has already seen its words, so no second model can take the turn over.
Until now that meant every failure past the commit point -- the stall
deadline, the total budget, a mid-stream 5xx, a dropped transport -- was
re-raised (execution.py:689-696 at 6.14.0) and reached Claude Code as an SSE `error`
frame printed underneath a half-written answer. The turn was dead. One real
incident streamed 1,333 characters, went quiet, and was reported as
"API Error ... stopped producing output for Ns", with seven healthy fallback
models recorded as `not tried: a timeout failure ends the route`.

The mechanism is that the executor had only one ending available for a
committed stream. The protocol has a better one. Every block left open can be
closed, and one `message_delta`/`message_stop` pair turns the partial answer
into a short but structurally complete message, so the session continues
instead of dying.

What this does, and only this:

- `core/anthropic/streaming/truncation.py` (new) follows the frames already
  forwarded -- which blocks are open, how much text the reader saw, whether
  the model already chose a stop reason -- and builds the closing frames.
  Pure protocol bookkeeping; it decides nothing.
- The committed branch in `application/execution.py` asks it for those frames
  and, when it gets them, emits them *after* the upstream stream is closed,
  then records and returns. When it gets none, today's four lines run verbatim.
- `stop_reason` is `max_tokens`. It is the only protocol-native value meaning
  "cut short rather than finished". `end_turn` would tell Claude Code a
  half-written plan was complete, which is the one outcome worse than an
  error. The real cause is recorded on the attempt row and in the modal.
- The attempt row keeps `outcome=failed` and its real `error_kind`, and gains
  `params.truncated_after_commit = {chars, blocks, reason, stop_reason_sent,
  ended_cleanly}` -- the same shape `params.bench` uses since 6.14.0. The
  request row stays `status=success`, because what the client received *is* a
  valid message; the attempt row is where the failure lives.
- The stalled model is now charged one `_health.record_failure`, the same call
  the uncommitted path has always made after a failed attempt. The committed
  branch never reached that line, because it raised first.
- `FALLBACK_END_CLEANLY_AFTER_COMMIT` (bool, default true, Limits &
  Resilience -> Deadlines) restores the old error.

Two cases deliberately keep the error, both because a valid message cannot be
built honestly:

- A `tool_use` block whose arguments stopped mid-JSON. Closing it would let
  `sse_aggregation.py:106-112` substitute `input={}`, and Claude Code *runs*
  tool calls. The truncation is still recorded so the modal can say "stalled
  inside a tool call -- cannot be completed".
- The Responses wire API. Its assembler has only `response.completed` and
  `response.failed` (`core/openai_responses/streaming/event_builders.py`);
  there is no `response.incomplete`, so a truncated message would translate
  into "the answer finished".

No retry layer, no deadline subdivision, no credential code. The moment the
stream stops is unchanged -- only what the client is handed.

## Decisions worth arguing with

- **`status=success` on the request row.** The client received a valid
  message, and every existing consumer reads `status` as "did the caller get an
  answer". The failure lives on the attempt row, where a truncation is
  countable without double-counting an error the client never saw. One line to
  change if you disagree.
- **No export column.** `_REQUEST_DETAIL_DERIVED` carries only ladder rollups
  and no export path joins attempt rows; adding one would touch the DDL and six
  export lists for information the attempt row already holds.
- **No `fallback` content block.** `_ALLOWED_BLOCK_START_TYPES` does not
  contain it, so emitting it would mean widening the contract validator every
  other stream test relies on.
- **`.env.example` untouched, deliberately.** `FALLBACK_ON_REASONING_ONLY` is
  absent from it for the same reason: a key there makes the template the owner
  of the default (`tests/config/test_admin_limits.py:224`).

## Residual risks

1. **The answer really is incomplete.** Claude Code is told `max_tokens`,
   which is the honest signal, but a client that auto-continues on
   `max_tokens` will ask for a continuation -- which is the wanted behaviour
   here rather than a bug. **UNVERIFIED against a real Claude Code client:**
   what the installed client does with `max_tokens` was read from the protocol,
   not observed. The live proof below is `curl`, not Claude Code.
2. **A closed `thinking` block carries no `signature`.** If a client sends that
   block back on the next turn, a strict Anthropic-protocol upstream may reject
   it. `sse_aggregation` already defaults the signature to `""` on the
   non-streaming path, so the shape is not new, but this change makes it
   reachable on the streaming path too.
3. **The tracker parses every forwarded frame.** `sse_carries_content` is a
   substring scan specifically to avoid a JSON parse per frame, and this adds
   one -- bounded by the same work `request_capture._consume_buffer` already
   does on the same stream whenever the request log is on. Not measured under
   load.
4. **`output_tokens` is estimated** when the stream died before its own
   `message_delta`, using the same `cl100k_base` count the provider ledger
   would have published. Reporting zero for text already on the reader's screen
   is the worse lie, but it is an estimate and nothing labels it as one.
5. **A committed stall now benches the model** -- one `record_failure` where
   there were none. With `FALLBACK_BENCH_ENABLED=false`, the shipped default
   since 6.14.0, this changes nothing at all; with benching on, a mid-answer
   stall now counts towards the model's rate. Timeouts are not model-shaped so
   they still do not bench, but the call is now made.
6. **The Responses path is unimproved.** A committed failure there still
   reaches the client as `response.failed` after partial output. Fixing it
   needs a `response.incomplete` builder and is out of scope.
7. **Not done here:** resuming onto the next model (Option A) is the next PR;
   the `input={}` substitution in `sse_aggregation.py:106-112` is left as a
   follow-up, because fixing it changes the non-streaming aggregator's
   behaviour and is not one line.
