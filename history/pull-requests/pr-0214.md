## Description

**Broken.** A multi-key provider behaved as though rotation were switched off:
one model burned the whole attempt, then every request was refused with
`All API keys for this provider are in cooldown. Retry in 119s.` -- 119s is
tier 4 of the 10/30/60/120s ladder, i.e. all three live NVIDIA keys pinned at
maximum. 1,887 `unavailable` attempt rows in the live DB.

**Not a 5.57 regression.** `RotatingProvider._stream_with_rotation` is
unchanged since v5.56.0 and #194 never touched the file: the loop does retry
each credential in-request. Three separate mechanisms preempted it.

**Mechanism A (predates 5.57).** `_attempt_deadline` divides the request
budget by the models still in the chain, and the executor applies that share
to the *whole* rotating generator as one unit. One slow key spent the entire
~60s share and keys 2..N were never tried:
`MODEL DEADLINE: 'nvidia_nim/moonshotai/kimi-k3' produced no first token after
66.661s` (x5).

**Mechanism B (introduced by #209).** `failure_implicates_credential` returned
True for `FailureKind.TIMEOUT`, so every first-token timeout escalated a key's
cooldown ladder and tripped its breaker at three. This is exactly the bug #209
fixed for 400s, one failure class over.

**Mechanism C.** `RotatingProvider.throttle_remaining()` was a `min()` over the
sub-providers' rate limiters only. With every key health-benched but none
rate-limited it still answered 0, so routing skipped its 5s step-over,
committed the attempt, and the request paid a full `ApplicationUnavailableError`
round trip.

**Fix.**

1. A third failure class, `ROUTE_SHAPED_KINDS = {TIMEOUT}`, beside the existing
   `REQUEST_SHAPED_KINDS`. Rotation and health accounting are now independent
   axes: a timeout still returns `rotate=True` (a different key may reach a
   faster replica) while charging the credential's health nothing. Chosen over
   simply widening the request-shaped set because a timeout is not
   request-shaped -- a 400 must *not* rotate, a timeout must. Deliberately
   narrow: only the canonical `TIMEOUT` kind. A dead socket classifies
   `UNAVAILABLE` and keeps charging health, as does any timeout reaching the
   layer without a provider classification.

2. A per-credential first-token budget. The executor publishes the attempt
   deadline in `core/attempt_budget.py` (a plain parent-to-child ContextVar,
   rather than widening `stream_response` for a value one provider reads), and
   `_stream_with_rotation` divides what is left by the credentials this request
   has not tried yet, floored at 5s and clamped to the remaining time. The
   executor keeps the outer bound; this only subdivides it, so the total
   attempt can never grow. With no deadline configured the wait stays exactly
   as unbounded as before.

3. `throttle_remaining()` is health-aware: 0 whenever any credential can serve,
   otherwise the shortest bench remaining. Selectability comes from the new
   `RotationEngine.selectable_indexes()` rather than per-slot `selectable()`,
   so the forced-single policies agree with what `acquire` would actually hand
   out -- a single-key provider serves slot 0 regardless of health and keeps
   reporting itself free.

**Residual risks.**

- The per-key budget is derived from the executor's attempt deadline. An
  operator running with no deadline configured gets no per-credential bound --
  behaviour identical to today, but mechanism A is not fixed for them. Fixing
  that needs a standalone setting, which this PR deliberately does not add.
- The 5s floor means a pool large enough to divide the share below it tries
  fewer credentials per attempt than it has keys. The executor's outer bound is
  still respected; the chain simply moves on.
- `selectable_indexes()` reads slot state and expires elapsed benches without
  the asyncio lock, because `throttle_remaining()` is synchronous on the
  provider interface. This matches what `get_metrics()` already does; the
  refresh is idempotent and only moves an expired bench to its wake state.
- The attempt deadline travels in a ContextVar. It is written per attempt by
  the executor and read in the same task, and providers used outside the
  executor see `None`. A future caller that consumed a provider stream from an
  unrelated task would read a stale value rather than a wrong one, and the
  clamp to the remaining time keeps that safe.
