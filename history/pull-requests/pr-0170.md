## Description

The last item left open by the reasoning arc.

## The gap

Model metadata — vision support, context length, prices — was matched against **every provider's models flattened into one namespace**, first writer wins, and the winner was decided by whichever order models.dev happened to serialise its JSON.

Measured against the live 2026-08 index (193 providers):

```
model ids claimed by >1 provider     3,757
  ...disagreeing about vision          234
```

So a model could be told it was blind because an unrelated provider hosts something with the same name — and vision routing then diverts a request that never needed diverting.

## What changed

**1. The model's own provider is consulted first**, via the same alias map the reasoning-capability lookup already uses (`open_router` → `openrouter`, `fireworks` → `fireworks-ai`). The cross-provider index stays as a *fallback*, because most of what a gateway resells is not published under that gateway.

**2. The fallback index accumulates field by field** instead of first-writer-wins, so whether a field is populated at all no longer depends on upstream serialisation order.

## The correction that mattered

Both are **merges, not replacements**. My first version chose the scoped match wholesale — it looked more correct and **cost 11 models metadata they have today**, which I only found by running it against the real index rather than a fixture. That's a regression however much more authoritative the source is.

So per field: the model's own provider wins where it says anything, and a namesake elsewhere fills only the gaps.

**M3 survived a first pass** — the test asserted an answer the flat fallback happened to give anyway. It now uses a competing provider that answers differently *and* is reached first, so the alias is the only thing that can produce the expected result.

Local CI: `ruff format --check`, `ruff check`, `ty` clean; pytest **4,840 passed** with the documented 6 `test_install_ps1_*` baseline failures.

## Residual risks

- **1,936 models change what MCC believes about them.** That is the point, but it is a large behavioural surface: some models will newly be considered vision-capable (or not), which changes when the vision adapter fires. The direction is toward the provider's own answer.
- **Two providers that both describe a model and disagree still resolve by iteration order** in the fallback — which now only matters when the model's own provider says nothing about that field. Making it deterministic needs a rule for which provider to believe, and there is no evidence yet for what that rule should be.
- Enrichment still only fills fields the provider itself left null, unchanged.
