## Description

## The report

```
PS> mcc-opencode
My Claude Code warning: could not prepare the OpenCode config (timed out); launching without an MCC provider.
```

OpenCode started with no MCC models in the picker. On the machine that reported
it, it would have done that on every launch, forever.

## What was actually wrong

Three defects compounded into a deadlock, none of them in the generated document
(OpenCode 1.18.26 loads it and lists every MCC model with zero errors).

**Wrong budget.** `cli/harnesses/catalogue_client.py` imported
`PROXY_PREFLIGHT_TIMEOUT_SECONDS = 1.5` from `cli/launchers/common.py` and used
it as the socket timeout for `GET /admin/api/catalogue-models`. That constant is
sized for `GET /health`, which answers in milliseconds. The route it was applied
to serialises **all thirteen** registered harness documents out of the resolution
ladder and measured **1.8–4.0 s** on the reporting install (1.41 MB response,
reproduced 3/3 through the launcher's own code path). The name is where the bug
lived: nothing about `PROXY_PREFLIGHT_TIMEOUT_SECONDS` says it is also the budget
for a multi-second serialisation.

**Wrong shape.** Most of that time was provenance. `capability_payload` walked
the ladder once per field per model — 2.74 ms/model warm × 292 models, so ~0.8 s
warm and ~5 s on a cold models.dev index — computed for the Models page and read
by nobody on this route. The launchers consume `document`, `model_count` and
`defaulted`; `defaulted` comes from the serialiser, not from provenance. The
whole walk was bought and thrown away on every launch.

**Wrong recovery.** `runtime/harness_catalogues.py` refreshed a document only
where `path.exists()`, creating one only for a spec declaring
`created_at_startup` — which only Codex did. So the launcher was the sole thing
that could create `~/.fcc/opencode-config.json`. The fetch timed out → the file
was never created → the publisher had nothing to refresh → the next launch
failed identically. The one failure mode that mattered was also the only one the
fallback ("launch without it") could not recover from.

## What changed

**The server owns the files; the launcher reads them.** `mcc-server` now
materialises every MCC-owned harness document at startup and rewrites it on every
catalogue publish. A launcher opens the file it needs and starts the agent with
**no HTTP at all**; it fetches only to create a document that is not there.

The concern the old rule answered was real but misplaced: these documents live
under `~/.fcc`, MCC's own directory, not inside any CLI's configuration folder,
so materialising them leaves nothing behind in a tool's own space.

**Command Code is unchanged and stays merge-on-launch.** Its provider block is
one key inside `~/.commandcode/providers.json`, a file the user wrote. A
`provider.mcc` block must never appear there because a key rotated on a server
they left running, so the fan-out still tests for MCC's own key rather than the
file, and the merge still happens on `mcc-commandcode` only.

**A separate, named budget.** `CATALOGUE_FETCH_TIMEOUT_SECONDS = 20.0`, its own
constant, a `Settings` field, a `LIMIT_RANGES` bound and a control on **Limits &
Resilience → Deadlines**. The floor is **1 s, not 0**: every other deadline in
this product reads 0 as "no limit", but `urlopen(timeout=0)` fails before it
connects, so a 0 here would mean "never build a missing document" — the deadlock
again, spelled differently.

**Provenance is opt-in.** `?provenance=1` for a caller that wants the per-field
ladder record; off by default for the launchers and the publisher.

**The warning is honest.** It names the file it expected, the request it tried,
the budget it had, the variable that sets it, and the two things a user can do:

```
My Claude Code warning: no OpenCode model list at C:\...\slowhome\.fcc\opencode-config.json, and building one failed: timed out.
  Tried GET http://127.0.0.1:8399/admin/api/catalogue-models with a 3s budget (CATALOGUE_FETCH_TIMEOUT_SECONDS).
  Start the server with mcc-server, or run mcc-opencode again once the dashboard's Coding agents page shows this agent's catalogue. Launching without an MCC provider.
```

**Dropped the `options.headers.Authorization` override** from the OpenCode
family's document (shared by OpenCode, OpenCode 2 and Kilo, which reuse the same
serialiser). Its comment said `@ai-sdk/anthropic` sends `x-api-key`, "which MCC
does not read" — true when it was written, wrong since 6.27.0, where
`api/dependencies.py::_presented_proxy_token` reads exactly that header. One
credential now, in one place, spelled the way the SDK spells it.

## Residual risks

- **The route is still uncached and still serialises thirteen documents to
  answer for one.** With provenance off it is 0.80–0.87 s for 292 models rather
  than 1.8–4.0 s, and it is now paid at most once per agent per machine, so this
  is a real but much smaller cost. `?harness=<id>` and a generation-keyed cache
  belong to a change about the route, with its own measurements — the second also
  touches the Models page's separate 9–13 s problem.
- **No staleness check on the file.** The launcher uses whatever is on disk and
  never asks whether the server has since resolved different capabilities. That
  is correct in the shape MCC actually runs — the launcher's preflight has
  already proved the server is up, and a running server has rewritten every
  document at startup and on every publish — but a document written by a server
  that has since been stopped, upgraded and not yet restarted will be used as-is.
  Deliberate: adding a conditional GET would put an HTTP round-trip back on every
  launch, which is the thing being removed.
- **Cline's per-launch `--model` is re-applied to the on-disk document** rather
  than to a freshly fetched one. That is one small write on a launch that names a
  model, and none otherwise. Cline is not installed on this machine, so that path
  is covered by unit tests only — **UNVERIFIED live**.
- **Aider, Crush, Droid, Kimi, Kilo and Cline were not launched for real** —
  their binaries are not installed here. Their file-first path is identical code
  and is covered by `test_every_catalogue_owning_launcher_reads_its_document_first`
  plus the fan-out materialisation test, and Gemini CLI and Codex exercise the
  same shape live.
- **The 292-model scratch install is a shaped approximation** of the reporting
  machine, not a copy of it: same model count and a real models.dev index, but
  one custom provider instead of theirs. The 1.8–4.0 s figure in this description
  is from the reporting install, measured with `curl`; the 0.80–0.87 s / 1.51–1.56 s
  pair is from the scratch server and is a before/after of provenance only.
- **`opencode2` and `kilo` share the OpenCode serialiser**, so dropping the
  Authorization header changes their documents too. OpenCode v1's live run proves
  the credential; v2 and Kilo are **UNVERIFIED live** (v2's background service did
  not start under a scratch HOME in the earlier investigation, and Kilo is not
  installed).
