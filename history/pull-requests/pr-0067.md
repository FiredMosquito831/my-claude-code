## Description

> *"didn't you do some compression techniques, what happened to them?"*

They shipped in 4.45.0 — but only for **newly written** requests. A database carried across the upgrade keeps paying the old price for its existing history. On the reporter's live log that meant 50,073 rows still stored inline and uncompressed, which is why the file was still 1.7 GB with only 573 compressed bodies.

## `fcc-compact-log`

Rewrites existing history in place. Measured on a **consistent copy of the real 1.7 GB database**:

```
converted   : 48,729 requests in 4.9 min
before      : 1.73 GB
after       : 0.29 GB
reduction   : 5.9x  (83.1% smaller)
```

Then verified: **49,934 bodies compared against the original, 0 mismatches.**

That verification caught a flaw in my first attempt — it reported 1,305 mismatches, exactly the number of rows 4.46.1 had already compressed. Their inline columns are NULL, so fingerprinting the raw columns compared real text against nothing. Re-exported through the decompression path: zero.

Safe to interrupt — batches commit individually, and a row is converted only after its body is stored, so a kill leaves a consistent database with the work merely unfinished. Running it again resumes (tested).

## Deduplication

Bodies are content-addressed by SHA-256 of their packed form: identical content is stored once, shared by every request pointing at it, and a repeat **skips compression entirely**. Blobs are collected only when the last referencing request is pruned — tested, including that deleting one request does not blank the others sharing its body.

**Honest note on the size of this win.** I predicted a lot from it: 62.7% of request *inputs* on a real log are byte-identical repeats. But whole *bodies* almost never repeat, because two requests sharing a prompt differ in their reply — measured dedup on the real database was **1.4%** (49,355 blobs for 50,034 requests). Splitting input from the rest into separate blobs would capture the input duplication; that is the obvious next step and is **not** in this PR.

## Also

- `page_size` widened to 16 KB during compaction, since a ~7 KB body always overflows a 4 KB page and the vacuum rewrites the file regardless.
- 4.45-era body rows are re-keyed to content addressing at startup (1,305 rows on the reporter's database, logged).
