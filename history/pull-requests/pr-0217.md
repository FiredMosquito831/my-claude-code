## Description

## The dashboard was writing settings you never chose

Pressing Save on one field wrote **every** setting in the manifest into
`~/.fcc/.env` as if you had picked it. That is why an install can be carrying
`FALLBACK_BENCH_ENABLED=false` without anyone having set it.

## What was wrong

Two mechanisms, both live until this PR.

**1. Every default was materialised as a user value.**
`target_values_with_updates` (`config/admin/persistence.py:68-98`) started from
`template_values()` — `.env.example` plus `field.default` for every field the
template does not name (`sources.py:63-69`) — overlaid the managed values,
applied the browser's updates, and then ran

```python
for field in FIELDS:
    values.setdefault(field.key, field.default)
```

`render_env_file` (`:256-294`) then wrote all of them as `KEY=value`. So the
first Save of *anything* between v5.58.0 and v5.60.0 wrote
`FALLBACK_BENCH_ENABLED=false`. v5.60.0 changed that default to `true`, but a
managed value outranks the template — so the file kept `false` forever, and
`load_value_state` reported the source as `managed_env`, indistinguishable from
a deliberate choice.

The general failure is bigger than the one setting: **no default could ever
change for an install that had pressed Save once.**

**2. An unset select displayed its first option and then saved it.**
`admin.js:1978-1984` did
`select.value = field.value || field.options[0]?.value || ""`, so a field with
options `("false","true")` and no value showed `false`, while `dataset.original`
stayed `""` (`:1605`). `readFieldValue` returned `"false"` against an original of
`""`, `changedValues()` submitted it, and the next Save persisted it.

**The measured consequence.** With `FALLBACK_BENCH_ENABLED=false`,
`RouteHealthRegistry.enabled` is False, so `FALLBACK_EJECT_AFTER_FAILURES`,
`FALLBACK_EJECT_SECONDS`, `FALLBACK_EJECT_WINDOW`,
`FALLBACK_EJECT_FAILURE_RATE`, `FALLBACK_EJECT_MIN_SAMPLES` and
`FALLBACK_BEHAVIOR=rate_based` are **all inert** — a model that fails half its
requests is retried at chain position 0 on every single request.

## What to expect now

The managed file records choices, never defaults.

| Situation | Managed file | Source | Settings uses |
|---|---|---|---|
| never touched | `# KEY= (default: true)` | `template` / `default` | the code default |
| you set it | `KEY=value` | `managed_env` | your value |
| you set it *to* the default | `KEY=value`, kept | `managed_env` | your value (an explicit choice survives a later default change) |
| you clear it, repo `.env` silent | line removed | `template` / `default` | the code default |
| you clear it, repo `.env` sets it | `KEY=` where the type accepts a blank | `managed_env` | the default, repo value masked |
| the manifest does not own the key | preserved verbatim | — | — |

Where a blank is *not* accepted (a plain `bool` or `int` with no blank
validator) the line is dropped and the save returns a warning naming the key,
shown in the dashboard.

In the UI:

- Every field prints its default underneath it.
- A value that came from the dashboard is badged **set here**, and gets a
  **Use default** button that removes the line.
- Selects have an explicit `Default (…)` option, so an unset field loads clean
  and the form reads "No changes".
- Booleans are three-state selects (`Default (On)` / `On` / `Off`) instead of
  checkboxes — a checkbox has two positions and a setting has three states.

## Action required

**If you never set `FALLBACK_BENCH_ENABLED` yourself, check the Limits page** —
a `false` written by an older dashboard disables chain benching and makes every
Eject setting below it inert. Press **Use default**.

## Known and deliberate

- **Existing managed files are not rewritten.** A value on disk is effective
  configuration; silently changing it would be a worse bug than the one being
  fixed. The fix is surfaced instead — source badge, printed default, one-click
  Use default — and named here.
- The Limits page redesign is PR E. This PR is correctness only.
- Eighteen manifest defaults legitimately differ from the bare code default
  (provider base URLs that name the endpoint an empty default resolves to, and
  fields showing the shipped `.env.example` recommendation). Each is now listed
  with its reason in a contract test that fails if a listed field starts
  matching, so the list cannot rot.

## Residual risks

1. **Existing installs keep their materialised defaults** until someone presses
   Use default. This PR stops new ones being written; it does not migrate the
   ones already on disk.
2. **A field whose Settings type rejects `""` cannot be blanked while the repo
   `.env` sets it.** The save drops the line and returns a warning saying to
   remove it there; it does not fail silently, but it also cannot do what was
   asked.
3. **Three-state booleans change the look of every boolean field** on the
   settings pages, including the Token Optimizer's proxied switch (which now
   reads the effective value rather than a checkbox's `checked`).
4. **The admin's prediction of Settings changed where a default was previously
   materialised.** Concretely, an install with no `VOICE_NOTE_ENABLED` line now
   reports the Hugging Face key as the live voice credential and asks for a
   restart when it changes. This matches what the running server already did;
   it is the admin that was wrong before.
