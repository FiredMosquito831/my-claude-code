**The icon is generated, not copied.** `sips -z` resamples the ten sizes

## The disk image

`hdiutil create -volname "My Claude Code" -srcfolder <staging> -fs HFS+ -format UDZO -ov`,
where staging is the `.app` and a symlink to `/Applications`. Two items, no
background image, no `.DS_Store` window layout: styling a dmg means mounting
read-write and driving Finder over AppleScript, which is three flaky steps on
a headless runner for an arrangement Finder overrides the first time anyone
opens the image.

`-fs HFS+` is explicit because newer macOS defaults `hdiutil` to APFS, which
older systems cannot mount at all — an image the app's own
`LSMinimumSystemVersion` could not open would make that claim false. The `.app`
is copied in with `ditto`, not `cp -R`: a signature lives partly in extended
attributes, and a broken seal presents as "the application is damaged".

## Universal, not per-arch — and why it is its own job

`build-app.sh` takes `--binary` more than once and runs `lipo -create`. One
image, both slices. A person downloading a Mac app should not have to know
which processor their Mac has.

That merge cannot happen on a matrix leg: the two macOS legs are two machines
running concurrently, and a leg has no way to wait for a sibling — it would
have to poll for an artifact that may never arrive, and a red Intel leg would
hang the aarch64 one for its full timeout instead of failing it. So
`macos-dmg` is a separate job with `needs: build`. It compiles nothing (it
downloads two binaries and runs two shell scripts), so it costs two or three
minutes of one macOS runner.

**The per-arch tarballs stay.** Delivery path A fetches exactly one per machine
and would gain nothing from downloading an architecture it cannot execute.

## Ad-hoc signed — a seal, not an identity

`codesign --force --deep --sign - --timestamp=none`. This is mandatory, not
decorative: on Apple silicon every Mach-O must carry at least an ad-hoc
signature, and `lipo` produces a fresh file whose inherited signature was
computed over something else. `--timestamp=none` because a trusted timestamp
needs Apple's server and is meaningless with no identity attached.

**It is not a Developer ID signature and it is not notarisation.** A contract
test forbids `notarytool`, `altool`, `stapler`, `--entitlements` and any
`--sign "<identity>"` in the script, and requires the script to say
`NOT Developer ID, NOT notarised` out loud in its own output.

### The Gatekeeper paragraph (same words in README, USAGE, release notes)

The app is not signed with an Apple Developer ID and is not notarised, because
this project has no Apple Developer account ($99/year). macOS quarantines
anything a browser downloads, and Gatekeeper refuses to launch a quarantined
app with no Developer ID. **There is no Control-click → Open workaround any
more** — Apple removed it in Sequoia, and on current macOS the dialog offers
little more than *Move to Trash*. The supported one-time fix, after dragging
the app across:

```bash
xattr -d com.apple.quarantine "/Applications/My Claude Code.app"
```

**The script install plus `mcc-desktop` remains the recommended zero-friction
macOS route**: it fetches the same binary over HTTPS from Python, quarantine is
applied by browsers, so Gatekeeper is never involved at all.

## The CI proof (`smoke/macos-dmg.sh`)

Same shape as the `.deb` proof in #279 — snapshot, exercise, assert, diff —
with one structural difference: **a `.dmg` is not an installer**, so there is
nothing to undo and the assertion is stronger. It mounts, asserts, and
`/Applications` and `~/Applications` must be byte-identical afterwards because
the smoke may not write to either.

In order:

1. the image mounts read-only and its root is *exactly* the `.app` and the
   `/Applications` symlink; `hdiutil imageinfo -format` says `UDZO`;
2. the bundle layout is the one `build-app.sh` declares, `PkgInfo` is
   `APPL????`, and `lipo -archs` shows **both** `arm64` and `x86_64`;
3. `plutil -lint`, then every key read back with `defaults read` —
   identifier, executable, name, package type, category, high-resolution,
   both version keys agreeing, a numeric minimum system version,
   `NSAllowsLocalNetworking` present and `NSAllowsArbitraryLoads` absent;
4. `codesign --verify --deep --strict` passes, and `codesign --display` shows
   **no signing authority** — so the day somebody quietly adds a certificate,
   the docs get updated with it rather than after it;
5. **`spctl --assess --type execute` is asserted to FAIL.** Its full output is
   printed. A green `spctl` fails the smoke with
   *"spctl ACCEPTED an unsigned app. Gatekeeper's behaviour, or this build,
   changed; the documented workaround may no longer be right."* This is the
   assertion the whole Gatekeeper paragraph rests on;
6. nothing in the image carries `com.apple.quarantine` (a CI-built file cannot
   have earned it), and `xattr -dr com.apple.quarantine` is then run on a copy
   anyway — the command the docs give users is a command this script proves
   works — and the seal is re-verified after `ditto`;
7. the program runs out of the image through `smoke/macos.sh` verbatim
   (`MCC_DESKTOP_SKIP_AUTOSTART=1`, foreign-status stub → port-conflict page,
   starts nothing);
8. detach;
9. `/Applications` and `~/Applications` diff clean.

## One name, two applications

`install.sh --desktop` writes a launcher bundle at
`~/Applications/My Claude Code.app` whose executable execs `mcc-desktop`. The
dmg's application has the same display name, and a user may drag it into
`~/Applications` — the same path. In `/Applications` a second bundle would be
a duplicate; in `~/Applications` it would be an **overwrite**: a working
application replaced by a shell wrapper.

The only thing that separates them is the `CFBundleIdentifier`. The launcher
already carried a different one (`com.my-claude-code.desktop`), so no change
of behaviour was needed there — only that both scripts start reading it:

| | |
| --- | --- |
| `install.sh --desktop` | Checks `/Applications` and `~/Applications` for `com.myclaudecode.desktop` and prints *"not adding a second launcher"* — the same sentence and the same behaviour as `create_linux_desktop_entry` stepping aside for the `.deb`'s menu entry (#279). |
| `uninstall.sh` | `remove_macos_launcher_bundle` removes `~/Applications/My Claude Code.app` **only** when it is not the app; `report_macos_desktop_app` prints the path, the bundle's contents and *"drag it to the Trash"* when it is. A bundle with no readable `Info.plist` is treated as the launcher, because `build-app.sh` always writes one. Same asymmetry as the `.deb`: detected and named, never removed. |

`tests/contracts/test_uninstaller_parity.py` gains a fourth section that pins
both identifiers, pins that they differ (and that neither contains the other,
since both scripts detect with `grep -F`), **parses `build-app.sh`'s bundle
layout out of the script** and asserts the uninstaller's message covers every
part of it, and asserts nothing in `uninstall.sh` removes from
`/Applications`.

## The two `.deb` follow-ups from #279

1. **`Depends` gains `libc6 (>= 2.35)`.** `lintian`'s
   `E: missing-dependency-on-libc` was right: the package is built on
   `ubuntu-22.04` (glibc 2.35), glibc is forward-compatible only, and without
   the field `apt` installs happily on Debian 11 (2.31) where the binary then
   dies at exec with `GLIBC_2.34 not found` — a message naming no package and
   suggesting no fix. Asserted in `smoke/linux-deb.sh` against the real
   package and in the contract.
2. **`chmod 0755` on the `mktemp -d` staging root.** `dpkg-deb --build`
   packages the staging root itself as `./`, and `mktemp -d` makes it 0700.

## Not proven here, and not claimed

- **Nothing macOS was run on a Mac.** There is no macOS machine on this
  profile. Every macOS claim in this PR is what `shell-release.yml` will
  assert, not what somebody saw. The release run is the first execution of
  `build-app.sh`, `build-dmg.sh` and `smoke/macos-dmg.sh` anywhere.
- **The Gatekeeper first-launch experience.** A runner is not a desktop, and
  quarantine is applied by browsers. `spctl` rejecting the app is asserted;
  what the dialog says to a human is not.
- **The Intel slice is not executed.** `macos-latest` is arm64 and Rosetta is
  not assumed present, so CI proves the `x86_64` slice exists (`lipo -archs`)
  and runs the `arm64` one.
