## Description

## The problem (discovered through live testing)

`uv tool install` fails (exit 2) when a launcher is open, because a running launcher holds its own `.exe` shim **without `FILE_SHARE_DELETE`** — it can't be overwritten (os error 32). This is the hard Windows limit: "running in memory" doesn't bypass it; the lock is on the open handle's share mode.

v5.3.3 tried renaming all shims aside, but that was too destructive — a failed install left canonical shims missing. **The user chose the hybrid approach.**

## The fix

1. Rename the tool dir aside, run `uv tool install`.
2. The tool env + all **non-running** shims update; only the running launcher's shim errors (expected).
3. Detect that expected failure **robustly**: check the fresh install actually landed in the tool dir (`uv-receipt.toml` names `$Version`). If so — keep the new install, report success, and launch the detached helper to finish the locked shim after the window closes.
4. Any **other** uv failure restores the previous install (never leaves the user with no working tool).
5. **No shims are renamed before install**, so a failure can never leave canonical shims missing.

Net result: new `mcc-claude`/`mcc-server` sessions get the new version immediately; the one open window keeps old code until it closes, then the helper finishes its shim. No waiting for anything else.
