## Workflow layout

`.github/workflows/shell-release.yml` has two jobs.

**`build`** — a four-leg matrix, `fail-fast: false`, `permissions: contents: read`, no `continue-on-error` anywhere. Each leg checks out the tag being released, installs Rust with the leg's target, `cargo test`, `cargo build`, runs its platform's real-binary smoke, packages one archive and one `sha256` line, and uploads them as an artifact.

**`release`** — `needs: build`, so a red leg means nothing is uploaded at all and the workflow fails. It is the only job granted `contents: write`, and it builds nothing: it downloads the four artifacts, assembles `SHA256SUMS-desktop-shell.txt`, verifies it with `sha256sum -c`, and runs `gh release upload <tag> … --clobber`.

Triggers: `release: published` — the Python release flow publishes the release with the wheel, this then attaches the shell to that same release — and `workflow_dispatch` with a `tag` input, so any existing release can be filled in and a red leg re-run without cutting a version. Concurrency is grouped per tag and **not** cancel-in-progress: a half-uploaded asset set is worse than a queued run.

## `cargo build`, not `cargo tauri build --no-bundle`

The build line is:

```
cargo build --release --locked --features custom-protocol --target <target>
```

The Tauri CLI's `build` does three things: run `beforeBuildCommand`, run cargo with `--features custom-protocol`, and bundle. This project has no `beforeBuildCommand` (`ui/` is one static HTML file; there is no frontend build) and `--no-bundle` switches the third off — so the CLI reduces to exactly the line above, at the cost of compiling `tauri-cli` on four runners.

**The feature is not optional**, and this is the part worth reviewing. `tauri::is_dev()` is `!cfg!(feature = "custom-protocol")` (`tauri-2.11.5/src/lib.rs:309`), and `tauri-macros` sets `dev: cfg!(not(feature = "custom-protocol"))` on the generated context — in a dev context the context reads `frontendDist` off the disk at run time instead of embedding it, so a binary built without the feature would look for a `ui/` directory the user does not have. That one flag is the whole difference between a release build and a development one.

Because of that, **`tests.yml`'s `desktop-shell (cargo)` gate now builds with the same feature** (one-line change) — otherwise the pull-request gate was passing on a configuration no release would ever make. The job is otherwise untouched and remains the PR gate for the shell.

## Smoke coverage

Three scripts under `desktop-shell/smoke/`, run on their own platform's leg after `cargo test`. They are the only tests in the tree that open a window. Each one:

1. asserts the artifact exists and is executable, and prints its sha256;
2. stands up a fake `mcc-desktop` and asserts **its exit codes** — `0` with a `schema: 1` document for `--print-status`, `3` for anything else — then parses the document and checks the keys the shell needs;
3. launches the real binary against that fake and waits (60 s budget) for the shell to have actually run it, failing with the shell's own output if it exits first;
4. asserts the window is still up five seconds later, and that **nothing was started**: the document says `server_presence: foreign`, so the port-conflict page is the whole of the ladder and the fake `mcc-server` must never run;
5. stops the shell **by its exact process id** and asserts it went.

Everything is pointed at a scratch directory through `MCC_SHELL_DESKTOP_COMMAND`, `MCC_SHELL_SERVER_COMMAND` and `MCC_SHELL_DATA_DIR`, so running a smoke on a machine with a real MCC install reads and writes nothing of it, contacts no port, and does not disturb the geometry of the window its owner actually uses. No process is ever stopped by name.

Per-platform differences, all of them for a stated reason:

- **Linux** starts `Xvfb` itself rather than through `xvfb-run`, so the pid the smoke signals is the shell's own and not a wrapper's, and exports `WEBKIT_DISABLE_COMPOSITING_MODE` / `WEBKIT_DISABLE_DMABUF_RENDERER` — without them WebKitGTK aborts on a virtual framebuffer and no window appears, *silently*, which is the exact failure this smoke exists to catch. It also fails early, naming the package, if webkit2gtk **4.1** is missing.
- **macOS** needs no display and adds `codesign --verify --strict`: on Apple silicon all code carries at least an ad-hoc signature, and a broken seal presents to the user as "damaged" rather than as anything a log explains. On x86_64 an absent signature is noted and permitted.
- **Windows** passes the fake through `cmd /c`, because `Command::new` cannot start a `.cmd` directly — which is also why the scratch path must contain no spaces (`MCC_SHELL_DESKTOP_COMMAND` is split on whitespace so it can carry arguments). The script ends with an explicit `exit 0`: a PowerShell script with no `exit` inherits `$LASTEXITCODE` from the last native command it ran, which here is the stub deliberately exiting 3, so a passing smoke reported failure until this was added. That was caught by running it, not by reading it.

## The updater-ignores-assets test

`tests/application/test_release_updates_ignores_shell_assets.py` pins that `_select_wheel_asset` filters on the `.whl` suffix and is blind to everything else on a release. This is what makes one release stream (Q6) provably safe.

The five shell assets all sort **before** the wheel by name (`MyClaudeCode-…` and `SHA256SUMS-…` precede `my_claude_code-…` in ASCII), so an implementation that took `assets[0]` — or the largest asset — would hand the dashboard's Update button a Windows zip. The test shuffles all six fifty ways and demands the wheel each time; a second test guards that the sort order it relies on is still true; others check that a shell-only release reads as "no wheel" rather than "wheel = the zip", that no single shell asset is ever mistaken for one, and that the check stays a suffix rather than becoming a substring.

**The only Python change in this PR is that test file. It is test-only, so there is no version bump and no release.**
