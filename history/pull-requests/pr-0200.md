## Description

## What was broken

MCC's reasoning gating (`application/reasoning_gating.py`) is well built and works. Running the user's real routed models through `adapt_reasoning_policy` confirms it clamps correctly whenever it has data. It usually has none: **6 of 10 routed models get no clamping at all.**

The failure is upstream of the gate, in three places.

**1. The `/models` payload was reduced to one boolean.** `providers/model_listing.py` computed `supports_thinking = "reasoning" in supported_parameters` and discarded everything else. It parsed no limit field of any kind — grepping the file for `context_length|limit|top_provider` returned zero hits. Here is the live `nous_portal` entry, all of which was being read and thrown away except one bit:

```json
{
  "id": "tencent/hy3:free",
  "context_length": 262144,
  "top_provider": {"context_length": 262144, "max_completion_tokens": 128000},
  "supported_parameters": ["frequency_penalty","include_reasoning","logit_bias",
      "max_completion_tokens","max_tokens","min_p","presence_penalty","reasoning",
      "reasoning_effort","repetition_penalty","response_format","seed","stop",
      "structured_outputs","temperature","tool_choice","tools","top_k","top_p"],
  "reasoning": {"mandatory": false, "default_enabled": true,
                "supported_efforts": ["high","low","none"]},
  "default_parameters": {"temperature": 1, "top_p": 0.95}
}
```

**2. `mandatory` was dead in two independent ways.** `resolve_model_reasoning_capability` took only `provider_supports_thinking: bool | None` and, when it was not None, rebuilt `ModelReasoningCapability` field by field while silently omitting `mandatory`. Separately, `_parse_reasoning_capability` sourced it from a models.dev key (`reasoning_mandatory`) that does not exist on any of the **7,483** rows in the live feed. So the v5.60.0 mandatory-model handling could never fire. The gateway is the only real source — `nous_portal` publishes `"reasoning": {"mandatory": true, ...}` on `z-ai/glm-5.3-flash` — and nothing read it.

**3. Two providers have no models.dev bucket at all.** `nous_portal` and `commandcode` return `None` from `model_reasoning_capability_from_models_dev`, so gating is a no-op for everything they serve.

## What this does

### A. Parse the full payload

`ProviderModelInfo` gains four fields, `ModelReasoningCapability` gains one. All default to `None`, and `None` means **not reported** — rigorously distinct from a reported "not supported".

| Field | Source | Semantics |
| --- | --- | --- |
| `max_output_tokens` | `top_provider.max_completion_tokens` | provider's own generated-token ceiling. `None` = unreported; a non-positive value reads as unreported, never as a ceiling of zero |
| `context_length` | `top_provider.context_length`, else top-level | routed deployment's window preferred over the nominal one |
| `supported_parameters` | the whole array | `None` = not published; empty frozenset = published empty |
| `default_parameters` | `default_parameters` | scalar pins only, sorted, as a hashable tuple of pairs. `None` = absent; `()` = the gateway published an empty object, i.e. it pins nothing |
| `reasoning_capability` | `reasoning{}` | `mandatory`, `default_enabled`, `supported_efforts`, `supports_max_tokens` → `supports_budget_control` |
| `ModelReasoningCapability.default_enabled` | `reasoning.default_enabled` | new; nothing consumed it before (zero occurrences in `src/`) |

The OpenRouter-dialect extractor and the generic tool-capable one now share one record builder, so both read the full payload.

**The gateway's `"none"` effort** is deliberately never mapped onto a `ReasoningEffort` member. It is not an effort level — it is the gateway saying reasoning can be switched off — and inventing a member would make "think as little as possible" and "do not think at all" the same request. It is read as toggle support instead, as is `mandatory: false`. A vocabulary of only `["none"]` therefore yields `supports_effort_control=False`, `supports_toggle_control=True`, `supported_efforts=frozenset()`.

### B. Gateway-first, field by field

`resolve_model_reasoning_capability` now takes the whole provider-reported capability and merges **per field**, not per source. The gateway wins each field it states; models.dev fills only what the gateway left `None`. A known `False` is an answer and is kept — only `None` defers. Merging per field is precisely what stops `mandatory` being dropped.

### C. Zero is a miss

`limit.output: 0` and `limit.context: 0` are treated as absent at every read site. models.dev's schema permits both despite an error message claiming they must be positive. Measured on the live feed: **195 rows publish `limit.output == 0`, 132 publish `limit.context == 0`** — mostly image/video models plus real holes on `vercel` (91) and `poe` (44). Zero means "not applicable / unknown", never "the limit is zero". `_build_output_limit_index` already skipped it; `_parse_models_dev_metadata`'s context read did not, and now routes through the same helper.

### D. Cross-provider fallback, modal, never outranking the gateway

For a provider models.dev does not describe at all, a new tier matches the model by name across every bucket, reusing the existing `_normalize_candidates` / `_lookup_in_bucket` normalisation rather than writing a second one.

Each field is the **mode** across matching rows. Not the minimum (under-uses a model, violating WORKING-NOTES §54) and not the maximum (hard 400s). Ties break toward the more capable option — `True` over `False`, the larger limit, the larger effort vocabulary — for the same reason. Effort vocabularies use the modal vocabulary rather than the intersection (which collapses to `['high']`) or the union (which spans seven efforts and invents capability).

Every resolution announces itself, memoized per cache generation so it is one line per model per refresh rather than one per request:

```
models.dev has no bucket for nous_portal; APPROXIMATE cross-provider match for
tencent/hy3:free: matches=2, output limit 64000 (100% agreement), efforts unknown
```

**Precedence is gateway → exact models.dev row → approximate tier → default.** `ProviderManager.model_output_limit` now prefers the routed target's own `max_output_tokens`, because for `nous_portal/tencent/hy3:free` the gateway reports **128,000** while the cross-provider mode is **64,000** — letting name matching win would halve the model's real capacity. A provider that *has* a bucket still never reads outside it.

### E. Conditional GET

models.dev serves a strong `ETag` and `Cache-Control: max-age=0, must-revalidate`, with no `Last-Modified`. The ETag is stored beside the payload and replayed as `If-None-Match`. A `304` leaves the 4.4 MB body byte-identical on disk and only stamps the file's mtime, which is now what freshness is measured from (`fetched_at` remains as the provenance of the bytes). Atomic temp+rename, the lock, corrupt-cache self-heal, silent failure and stale-cache-still-used are all preserved and covered by tests.

### Explicitly out of scope

No outbound request body changes, no `max_tokens` clamping, no effort→budget table edits. This PR only makes the data available and correct.

## Residual risks

- **The `llamacpp` / `ollama` guard is now softer.** Those providers have no models.dev bucket, so the approximate tier answers for them where nothing did before. Their catalogues are whatever the user pulled locally, so a same-named row elsewhere may describe a different quantisation. Mitigated by the tier being last, logged as APPROXIMATE, and never overriding the gateway; the deliberate **alias** rejection is untouched and still tested.
- **Freshness now reads the file mtime**, not the embedded `fetched_at`. A cache copied between machines with a newer mtime can look fresh for up to 24h. Self-healing on the next refresh; the alternative (rewriting 4.4 MB on every 304) defeats the point of the conditional GET.
- **A `304` invalidates the parsed-index memos**, which key on mtime, so the ~4 MB parse runs once per revalidation instead of once per download. Same order of magnitude, at most once per 24h.
- **`enrich_model_infos`' existing flat index is still first-writer-wins**, not modal. Only the new capability/limit tier votes. Unifying them was out of scope.
- **Cross-provider capability could suppress reasoning** if the modal `can_reason` were wrong. Measured unanimous on the user's models (50/51, 32/32, 28/28), and ties break toward `True`.

## Deliberately not done

Gating is untouched, as briefed. `reasoning_options: []` already parses correctly to "known, but no caller control" (`can_reason=True` with all three `supports_*_control` explicitly `False`) — verified, and now pinned by tests. What is still broken is downstream: `_adapt_effort` falls through to `UNCHANGED` for that state and forwards a raw effort to a model that accepts no control knob. That is a gating fix, not a parsing one.

`default_enabled` and `supports_max_tokens` are captured but not yet consumed. `supports_max_tokens` is the valuable one: it means models MCC currently treats as toggle-only may actually accept a numeric budget, and gating already prefers budget over toggle.
