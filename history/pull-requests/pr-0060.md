## Description

Three gaps, all found by looking at the running dashboard rather than the code.

## The routing page never mentioned images

Each tier draws its fallback rail, which answers *"what covers this model when it fails"*. It cannot answer *"what happens to a screenshot"* — the vision adapter fires on what a request **contains**, not on a failure. So the adapter sat in an isolated card at the bottom, disconnected from the tiers it affects, and a tier whose model is documented not to read images was silently sending them elsewhere.

A tier that needs the adapter now carries a hop under its rail:

```
IMAGES → chatgpt_oauth/gpt-5.6-luna
nous_portal/tencent/hy3:free cannot read them
```

It appears **only** on tiers that need it, so its presence is the signal. With no adapter configured it turns amber and says the images will fail there. The adapter's own card names the tiers it covers *today* rather than restating the rule.

## Most of the catalog had no vision metadata at all

Which means that hop could not have been drawn for anyone. models.dev enrichment was gated to Novita and custom providers; every other provider fell back to whatever it published itself — which for ~30 of them is nothing.

Enrichment now runs for **every** provider. It only fills fields the provider left null, so a gateway publishing its own modality data keeps it. Measured on this machine:

```
337 of 948 models now known to reject images
(previously: only what the OpenRouter-dialect providers reported)
```

`/admin/api/models` returns that as `blind_models` — **only reported refusals, never silence**. Claiming a tier "cannot read images" on the strength of missing metadata would be wrong for most of the catalog.

## The vision adapter had no fallbacks

One unreachable vision model lost every image on the machine. `MODEL_VISION_FALLBACKS` reuses the existing infrastructure rather than inventing a parallel one:

- same comma-separated form as the tier chains
- same `validate_model_fallback_chain` validators
- same `ModelChainEditor` rail on the card
- same `configured_chat_model_refs` walk, so its providers are warmed

A diverted request runs the adapter's chain first, then whatever on the original route can still see. An entry known to reject images is **dropped from a vision chain** — that is always a mistake, not a preference.

Tracking comes free: the diverted chain *is* a chain, so `route_chain`, `route_attempt` and the `vision` diversion pair from 4.42.0 already describe it end to end.

## Also fixed

A diverted request read as **"Primary model"** in the request detail — naming the wrong decision entirely, and contradicting the diversion note directly above it. Now: *"Vision adapter, instead of nous_portal/tencent/hy3:free"*.

## Verification — in a real browser, against a real config

- The hop renders on **Sonnet only**, the one tier whose model models.dev knows is text-only. The adapter card reads *"Currently covers Sonnet"*.
- Adding a vision fallback lights **Apply**, writes `MODEL_VISION_FALLBACKS` to `.env`, and survives a reload. The hidden chain input is confirmed in the document — that is the 4.34.1 failure mode that made chains silently unsaveable.
- **Caught a real ordering bug this way**: the routing section renders from the config payload *before* the model catalog loads, so the first paint had an empty blind-model set and drew nothing at all. The hops now update in place when the catalog arrives, which also preserves unsaved edits.
- Full suite: 3351 passed, 6 failed — the PowerShell installer baseline. `ruff format`, `ruff check`, `ty` clean.

## Residual risks

- models.dev matching is by normalized model id across the whole index, so a same-named model on a different provider inherits its metadata. Right for the common case (it *is* the same model); a mismatch would mark a model blind that is not, diverting images unnecessarily. The provider's own answer always wins where it has one.
- Enrichment now runs on every provider refresh instead of two. It reads a 24h-cached index, so the cost is a dictionary lookup per model.
- `blind_models` is only as good as the catalog. A model nobody reports on still gets no hop, which is the honest outcome.
