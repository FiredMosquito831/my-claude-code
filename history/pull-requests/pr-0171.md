## Description

## What was wrong

MCC has five local short-circuit rules that answer a request inside the proxy without contacting a provider. **Nothing recorded that this had happened**, so the entire layer was unmeasurable — the only way to find out whether it had ever fired was to decompress every stored prompt in a 153,198-row production log and replay the detectors by hand.

That measurement is what motivates this PR:

| rule | fires, lifetime | input tokens never sent |
| --- | ---: | ---: |
| `title_generation_skip` | 3,122 | ~14.3M |
| `suggestion_mode_skip` | 130 | ~1.0M |
| `quota_mock` | 0 | — |
| `prefix_detection` | 0 | — |
| `filepath_extraction_mock` | 0 | — |

Three defects, all invisible for the same reason.

**1. A locally-answered row named a provider.** `set_routing` runs before the intercepts, so the row recorded the provider the request *would* have gone to. In the production log that is **3,246 phantom requests spread across six real providers**, dragging their per-provider averages with them:

```
nous_portal   2,730     opencode  164     open_router     40
commandcode     214     nvidia_nim 58     chatgpt_oauth   40
```

**2. The reported usage was invented.** Every rule returned a hardcoded `input_tokens=100` / `output_tokens=5` regardless of the request, and those counts reach the client and feed its own accounting. Part IV §1 bans exactly this.

**3. The suggestion-mode trigger scanned the whole transcript.** Any user message containing `[SUGGESTION MODE:` *anywhere in history* answered the request with an empty string — the worst failure this module can produce, because the caller asked a real question and got nothing.

## What this does

- Adds `requests.optimization` (the rule that answered) and `requests.optimization_tokens_saved` (input tokens kept off the wire). Both NULL on an ordinary request.
- Clears `provider`/`resolved_model` on an optimized row. `requested_model` and `route_chain` still record what *would* have happened, so nothing is lost — only the false claim.
- Counts usage instead of inventing it. Measured cost of counting (cl100k, this hardware):

```
  1,500 chars ->     405 tokens     0.5 ms
 23,000 chars ->   6,241 tokens     7.1 ms   median title prompt
 76,000 chars ->  20,628 tokens    24.4 ms   typical suggestion prompt
560,000 chars -> 152,000 tokens   145.9 ms   largest observed
```

Against the multi-second round trip each match avoids, on a path that already calls this counter synchronously for web-tool requests.

- Narrows the suggestion trigger to the trailing user turn. Verified against **all 61** real suggestion requests: the marker is never earlier than **97.61%** into the prompt and is always followed by exactly the same **1,363-character** block, so narrowing loses nothing.
- Publishes `count_text_tokens`, because `get_token_count` bills fixed per-message framing — right for a request, wrong for a lone reply, which it scores at 4 for the empty string.

`tokens_in`/`tokens_out` stay **NULL, not 0**, on an optimized row: NULL is silence and no provider spoke (§13).

## Deliberately not done

- **No index on the new column.** The dashboard aggregate lands in a later PR, and adding an index changes every neighbouring query's plan (§59). It will be measured then, not guessed at now.
- **The three never-firing rules are untouched.** They are removed in their own change so this one stays about recording.
- **No backfill.** The 3,246 historical mis-attributed rows keep their wrong provider. Rewriting history would be worse than the ambiguity; the column marks the boundary from here.

## Residual risks

- The two live rules keep their current defaults (on), unchanged and user-confirmed. Behaviour of a matching request is identical apart from honest usage numbers.
- The narrowed suggestion trigger could in principle miss a future Claude Code variant that places the marker earlier. It fails *open* — the request goes upstream and is answered normally, which is the safe direction.
