## Description

## What this adds

Two related routing capabilities, both configurable from **Admin UI → Model Config**.

### Fallback chains

A single dead model took down a whole tier. If `MODEL_OPUS` pointed at a provider that was rate-limiting, out of credit, or had quietly retired the model id, every Opus request failed — even with three other providers configured and healthy.

Each tier now carries an ordered comma-separated list:

| Setting | Chain used |
| --- | --- |
| `MODEL_FALLBACKS` | after `MODEL`, for any tier with no override of its own |
| `MODEL_FABLE_FALLBACKS` | after `MODEL_FABLE` |
| `MODEL_OPUS_FALLBACKS` | after `MODEL_OPUS` |
| `MODEL_SONNET_FALLBACKS` | after `MODEL_SONNET` |
| `MODEL_HAIKU_FALLBACKS` | after `MODEL_HAIKU` |

A tier with its own primary override uses **only** its own chain; the two are never merged. So the models a route will try are exactly the primary plus the chain sitting next to it, with no hidden coupling to reason about.

### The commit boundary is the whole design

Attempts are tried in order until one produces its **first chunk**. Past that chunk the response is committed to the wire, so a later failure propagates rather than retrying on the next model — swapping models mid-stream would splice two different completions into one answer.

Preflight runs lazily, one attempt at a time, so a healthy primary never pays to validate a fallback it will not use. A plan with a single attempt behaves exactly as before, including raising synchronously when it fails, which preserves the caller's existing error surface.

Requests naming a provider and model directly (`open_router/…`) are never redirected — an explicit choice is answered as asked. A chain entry whose provider has left the registry is skipped with a warning rather than failing the route: a resilience feature must not become the outage.

### Vision adapter

`MODEL_VISION` serves image-carrying requests when the model a route picked is **known** not to accept images. Capability comes from what providers publish — OpenRouter-dialect `architecture.input_modalities`, models.dev `modalities.input`/`attachment` — threaded through `ProviderModelInfo.supports_vision`.

Unknown capability is deliberately left alone. Most providers publish no modality data at all, and diverting on silence would move traffic away from models that handle images perfectly well. Fallbacks known to be blind are dropped from a diverted chain: answering a question about an image it cannot see is worse than failing.

### Analytics follow the model that answered

The executor calls back into `RequestCapture.set_routing` on each attempt, so a request log row names the model that actually served it, not the one the route started from. Chain and vision entries also join `configured_chat_model_refs`, so their providers are discovered and warmed like any primary.

## A defect found by exercising the real API

Applying a chain persisted the raw submission verbatim, while `Settings` canonicalises on load. `.env` kept

```
MODEL_OPUS_FALLBACKS=" cerebras/qwen-3-coder-480b , groq/kimi-k2 ,cerebras/qwen-3-coder-480b "
```

while the value in effect was the trimmed, deduplicated one — two sources of truth with the visible one wrong. Normalization now happens per field type on the way in.

## Residual risks

- **No live request has been made through a chain against a real provider.** The failover logic is verified with provider doubles; a real 429-then-succeed round trip is not covered.
- **No model's vision metadata has been checked against a live `/models` payload.** The extractors are verified against the published response shapes and fixtures only. If a gateway spells `input_modalities` differently, that model reads as unknown and is simply left alone — the safe direction.
- **The chain editor has not been driven in a browser.** Rendering, reordering and the dirty-state hookup are verified by reading the apply path and by the API round-trip above, not by clicking it.
- Fallbacks multiply upstream attempts: each entry carries the provider's own retry behaviour, so a 4-long chain can quadruple worst-case attempts on a fully-broken configuration. Chains are opt-in and empty by default.
