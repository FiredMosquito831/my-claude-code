## Description

**This PR is observability-only.** It changes what a 429 *costs* a credential and what the dashboard and the request log can *say* about it. It does not change routing: the per-credential reactive block stays until `PR-LADDER-REDESIGN`. See **What this does not change** below before estimating its value.

## What was wrong

`req_cf646eed209a4c7f95064201d4a2a339`, 2026-08-31T14:10:35Z, read read-only from `~/.fcc/logs/requests.db` (`request_attempts.params.$.ladder`). Attempt 0 = `nvidia_nim/moonshotai/kimi-k3`, three-key `round_robin` pool:

```
summary     {"tries": 15, "statuses_by_code": {"429": 14, "502": 1}, "keys": 3,
             "time_upstream_ms": 6144.9, "time_sleeping_ms": 50967.6,
             "time_limiter_ms": 0.0, "tries_dropped": 0}
credentials all three keys, class "rate_limit", benched_for_s 60.0,
             retry_after null, reason "429, no Retry-After -- operator cooldown 60s"
root_cause  "3 keys x 5 tries: 14x429, 1x502 - 50s of the 57s were MCC backoff
             sleeps; keys 0, 1 and 2 benched 60s on 429 (no Retry-After)"
attempt 0   duration_ms 57284.3; the request took 81360.4 ms overall and was
             served by attempt 1 on a different provider entirely
attempt 7   nvidia/nemotron-3-ultra-550b-a55b -- recorded skipped
```

NVIDIA NIM publishes no `Retry-After` and no rate-limit headers, so the 60 s was the operator's `RATE_LIMIT_COOLDOWN_SECONDS`, not the provider's ask. Attempt 7 was skipped because every NIM key was health-benched — so every NIM *model* was off the route. At 14:13:07Z `nvidia/nemotron-3-ultra-550b` returned 200 on key 0, with nothing changed but the clock.

## The mechanism

Direct probes taken in the same minute: `moonshotai/kimi-k3` returns 429 on all three keys within 0.1 s, while `nvidia/nemotron-3-ultra` and a MiniMax model answer on those same keys in the same second. **The limit is the model's, and 6.18.0 charged the key.** Three keys times one model's limit removed every model on the provider for a full minute, and the cost landed on a request that had nothing to do with kimi.

## The fix

A fixed-mode 429 now benches the **(key, model)** pair.

- `PoolSlot.model_benches` — `model id -> deadline` on the engine's own clock, expired lazily by the same `refresh()` that expires `cooldown_until`. No timer, no new module.
- The slot stays **`HEALTHY`** while only that dict is populated: a per-model throttle is not a fault of the credential, and every other model on that key still serves.
- The whole key is benched only once `CREDENTIAL_MODEL_BENCH_ESCALATION` (**default 2**) distinct models hold a live bench on it simultaneously — which is what a genuinely key-wide limit looks like, one extra 429 later. The escalated window is the **longest bench already published, floored at what the triggering 429 asked for**: the engine may neither take back time it has promised nor invent time.
- `1` restores the 6.18.0 whole-key bench **exactly** — the no-redeploy rollback. `0` never escalates past the pair.
- A success, `restore()` or `restore_all()` clears every model bench on that key. A success on *any* model is evidence the credential is fine, and a narrower "clear only this model" would strand a key benched forever for a model that never recovers — the same trap the half-open probe state was removed for.
- Live benches are pruned on every read and hard-capped at 64 per slot, evicting soonest-to-expire.

Surfaces:

- `GET /admin/api/credentials/<KEY>/keys` gains `model_benches: [{model, remaining}]` per key. The key manager renders a sub-line under each key — capped at three with `+N more` — and the badge reads `HEALTHY (1 model)` rather than a bare `HEALTHY`, because "why is my key benched" is exactly the question a tooltip cannot answer on a row that looks healthy.
- The ladder's credential decision carries `model` and `model_benched_for_s` alongside `benched_for_s` — two different facts, and `benched_for_s` is absent for a scoped 429. The root-cause sentence now reads *"keys 0, 1 and 2 benched 60s for moonshotai/kimi-k3 on 429 (no Retry-After); no key charged"*. The unscoped wording is unchanged, byte for byte.
- A pool with no key for *this* model raises a distinct error — *"All API keys for this provider are rate-limited for `<model>`. Retry in Ns, or use another model on this provider."* — with ladder kind `pool_benched_model`. The existing whole-pool sentence and `pool_benched` kind are byte-identical, and the `(no key available)` sentinel is reused rather than a second one added.
- `ProviderPort.throttle_remaining()` gains an optional `model` keyword. Every non-rotating provider ignores it. `execution.py`'s cooldown step-over passes `routed.request.model` — the same string `report_failure` receives, pinned by a test rather than by a literal.

## What this does not change

Two independent things bench a credential on a 429, and both still fire. Only the **rotation-engine health bench** carries the model scope; the per-credential `ProviderRateLimiter` reactive block is untouched, because it also serves 5xx backoff, which genuinely is model-independent. `failure_policy` therefore still installs a key-wide window on a 429, `_unavailable_now()` still sees a 429'd key as unavailable, and `execution.py:1511` still steps the provider over.

**So: correct, observable pool health, and no routing change.** `PR-LADDER-REDESIGN` removes the duplicate reactive block and makes the (key, model) bench the single source of truth; that is the PR where the incident's routing behaviour changes.

Also out of scope, all belonging to that PR: the same-key backoff ladder that produced 51 of this request's 57 seconds, deadline accounting, the same-provider chain preference, the diagnostic probe, and the `.env.example` `PROVIDER_RETRY_BACKOFF_MAX_SECONDS=60` vs `constants.py` `10` divergence found while surveying.

**Websearch is byte-identical.** `websearch/rotation.py` reaches the engine only through `KeyPool.report_rate_limit` → `note_rate_limit()`, with no model, and `WEBSEARCH_TUNING` keeps `model_bench_escalation` at 1, so `_fixed_rate_window` takes its early return. `PoolSlot.model_benches` stays permanently empty for those pools and `snapshot()` does not read it, so `GET /admin/api/websearch/credentials/{env}/keys` is unchanged. A search API's quota has no per-model concept and none is invented for it.

## Residual risks

- **The routing win is not in this PR.** Anyone reading the incident and expecting nemotron to be served immediately will not see that until `PR-LADDER-REDESIGN` removes the duplicate reactive block. The engine state is correct now; the router is not asking the right question yet.
- **`get_metrics()` now reads `self._clock()` rather than `time.monotonic()` directly** and calls `refresh()` first. For the production pool these are the same clock, and it removes an implicit ordering dependency, but a test that injected a clock and asserted on `cooldown_remaining` would now get a different (correct) number. None does.
- **`restore_all()` now clears model benches on slots that are already `HEALTHY`.** Its return value — the count of restored *credentials* — is unchanged, but a reset that left a healthy key unroutable for a model would be lying to the operator.
- **`.key-manager-row` gained `flex-wrap: wrap`.** Nothing wrapped before because the content fitted; verified in the browser that the key, badge and Remove still share the first line.
- **One deliberate departure from the spec:** the escalation default constant is mirrored in `core/rate_limit.py` (beside the existing `DEFAULT_RATE_LIMIT_COOLDOWN_SECONDS`, which mirrors `RATE_LIMIT_COOLDOWN_SECONDS_DEFAULT` the same way) rather than imported into `core/` from `config/`. `core/` imports nothing from `config/` anywhere in this tree and this change is not the place to open that edge. The config layer still owns `CREDENTIAL_MODEL_BENCH_ESCALATION_DEFAULT`, and `test_every_manifest_default_matches_the_settings_default` pins the manifest against it.
- **`assets/admin-credential-health.png` was not retaken.** The in-app guide and docs now describe the model sub-line that the shipped screenshot predates. It needs a real 6.19.0 server with a live pool to retake honestly, which a scratch harness screenshot would not be.
- The 64-entry cap is a memory bound, not a behaviour: it can only bite a pool serving more than 64 distinct models inside one cooldown window, and it drops the entries closest to expiring anyway.
