## Description

## A toggle-only model on an effort-only host sends the level you asked for again

Since 6.3.0, a model whose only reasoning knob is an on/off switch, sitting behind a gateway whose only way of saying "reason" is one of its own effort words, has been sent **nothing at all**. This restores the instruction — as the level *you* asked for, clamped to that host's own scale — and stops the dashboard badging the correct "nothing was sent" case as a defect.

## What was wrong

**1. One host, two answers.** `_channels` narrows the toggle channel when a host's "on" value is written into its own effort field. That narrowing is right: `NamedEffortReasoning(enabled_value="max")` is a default rung, not a switch, and answering a request for `low` with the host's `max` was a real regression. But only one of the three consumers was taught what to do next. `_drop_controls` read the *unnarrowed* `dialect.toggle` and still emitted the on-value; `_adapt_budget` read `default_rung` and still emitted it; `_adapt_effort` read the narrowed `channels.toggle`, fell through, and returned "send nothing".

Measured on the running install since 6.4.0, route `commandcode/minimax/minimax-m3-free`:

```
38 requests, every one:  requested control=on, effort=max
                         reasoning_adaptation_kind = 'dropped'
                         reasoning_emitted        = 0
captured wire keys:      [max_tokens, messages, model, stream, stream_options, tools]
```

No reasoning key of any kind, where 5.73.0 sent `reasoning_effort: max`.

**2. One adaptation kind meant two incompatible things.** `DROPPED` was returned both where a reasoning key *is* sent (the level was discarded, thinking switched on through another field) and where nothing at all leaves. The dashboard's `wireContradicts` badges a row **"gating asked for reasoning; nothing was sent"** when `reasoning_emitted === 0` and the kind is `substituted|clamped|dropped` — so all 38 rows above, the correct and intended outcome, wore that badge falsely.

**3. The catalogue produced a record it forbids elsewhere.** `_cross_provider_capability` reconciles "this model has no effort knob" against a stated list of effort words, because the two are one statement. `_reference_then_vote_capability` merges the reference row and the vote *after* that reconciliation and never re-runs it, so `commandcode/openai/o3` resolved:

```
supports_effort_control = False                 (OpenRouter catalogue, tier 5)
supported_efforts       = {low, medium, high}   (cross-provider, tier 7)
```

`anthropic/claude-opus-4.5` was identical. Gating then read "no effort control" beside a vocabulary nothing would ever consult.

**4. A stated OpenRouter `False` beat a three-plus-row cross-provider `True`, always** — `merge_reasoning_capabilities` treats the primary's `False` as a real answer, which is correct for that function and wrong as the entire tie-break.

## Known and deliberate

- **Command Code still returns `reasoning_tokens=0` for `minimax/minimax-m3-free`.** It did so under every body shape probed before this change, including `reasoning:{enabled:true}` and `chat_template_kwargs`. This PR restores a correct *request*; whether that gateway forwards it to a model that acts on it is the gateway's business. The requested-vs-returned column added in 6.4.0 is what will say so. **Do not read this as a thinking improvement — it was not measured as one.**
- **Historic rows are not migrated.** A row written before this version means what it meant when it was written, so the dashboard will show both `dropped` and `nothing_sent` for the same pre-6.6.0 situation. That is intended, not a bug.
- **`"dropped"` was removed from the badge list rather than `"nothing_sent"` being added to it.** Because stored rows are not migrated, a stored `dropped` is ambiguous between the two senses, and on the live install the correct sense was the overwhelming majority. The cost is that a post-6.6.0 genuine `dropped` contradiction is no longer badged; a false alarm on working behaviour is worse than a missed one on a case the adaptation message already spells out. `substituted` and `clamped` are unambiguous in both versions and still badge.
- **`_drop_controls` deliberately keeps the host's on-value.** A toggle-only model asking for `low` now gets `low`; a model that publishes *no* control still gets the host's on-signal. The first told us it has a switch, so a rung is the nearest legal thing to the ask; the second told us it has neither a switch nor a scale. The asymmetry is intentional and has a test that says so.
- **The `_channels` narrowing is not reverted.** "Revert the narrowing" is the obvious wrong fix; this PR fixes its consequence.
- The tie-break is **not** extended to `can_reason` (inverting a curated "does not reason" would send reasoning to a model that has none) or to the provider-payload rungs 1-2 (a provider's own `/models` is a statement about *this deployment*, not about the model).

## Residual risks

1. **A host that forwards the rung to a model that rejects it pays one 400 per model, per provider generation.** The reject-and-remember net added in 6.5.0 is the backstop: it strips the field the host's own 400 names, retries once, and never sends it for that model again. Because the table is instance-scoped (exactly like the learned output cap), a config reload re-pays it once. Deliberate.
2. **The catalogue's "richer" record can overstate a deployment.** A model that genuinely has no effort control on *this* host, described by three other hosts that do, will now be sent the field. Three backstops: the reject-and-remember net; the requested-vs-returned column, where an operator can see the field went out and nothing came back; and the per-model parameter override, applied after every postprocessor, which can pin or null `reasoning_effort`.
3. **Fixing the wire is not the same as making a model think.** See "Known and deliberate".
4. **The new kind is a UI-visible enum change.** Any consumer keying on `dropped` that the grep did not find will silently stop matching the rows that became `nothing_sent`. The grep found exactly one — the badge list; the kind has no label map and is never rendered as a pill, only the adaptation *message* is shown.
5. **Tier reporting on the Models page moves for the affected routes.** A field that said "OpenRouter catalogue, exact id" may now say "cross-provider, exact id". That is more honest and less reassuring, and an operator who has learned to trust the tier-5 label will read it as a downgrade when the answer itself did not get worse.
6. **`_Channels` gains a third overlapping boolean.** `toggle`, `default_rung` and `on_signal_is_the_effort_field` now describe one host's on-signal, and reading the wrong one is precisely what shipped the defect this PR fixes. The docstring is the mitigation and was written with that in mind.
7. **`UNCHANGED` with no message hides a real pass-through from the request log.** A toggle-only model whose rung passes through unclamped produces no adaptation row; the operator learns what happened from the recorded wire value. Relaxing `ReasoningAdaptation`'s "`message is None` iff `UNCHANGED`" invariant to fix that would break every consumer's "a message means something changed" assumption, so it was not done.
