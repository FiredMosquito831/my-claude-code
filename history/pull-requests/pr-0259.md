## What the log actually said

was written.

**The OpenCode requests were never missing.** Four rows carry user-agent
`opencode/1.18.26 ai-sdk/provider-utils/4.0.46 runtime/bun/1.3.14`, `POST /v1/messages`,
`provider=nous_portal`, `meituan/longcat-2.0:free`, **all four `success`**, 2026-09-02T14:17:56 ..
22:17:13. They were indistinguishable from the 128,000+ Claude Code rows on the same models, because
nothing in the table, the cards or the detail dialog named the client.

**No `ling` request ever reached MCC.** `resolved_model LIKE '%ling%'` returns zero rows across the
whole log — not a failure, not an error, nothing. A model that appears nowhere in Analytics never
reached the proxy, which is a launcher/base-URL question and not an Analytics one. USAGE now says so
in as many words, because "I saw nothing" has two very different causes and only one of them is a bug
here.

## What this adds

`requests.harness`, filled at capture time from two signals, explicit first.

**1. `x-mcc-harness`**, written by MCC's own launchers into the configuration they generate. Eleven
of the sixteen agents can carry it; each was verified against that CLI's own bundle, vendored schema,
or the wire:

| how | agents |
| --- | --- |
| environment variable | Claude Code (`ANTHROPIC_CUSTOM_HEADERS`), Gemini CLI (`GEMINI_CLI_CUSTOM_HEADERS`) — appended, never assigned, so a value the user set survives |
| `-c` assignment | Codex (`model_providers.<id>.http_headers`) — verified on the wire against codex 0.151.0 |
| registered provider | Pi (`ProviderConfig.headers`) |
| generated provider document | OpenCode, OpenCode 2, Kilo, Command Code, Qwen Code, Crush, Cline |
| **nothing** | Kimi Code, Aider, Droid, Goose — no hook worth trusting; Antigravity is not launched by MCC |

Three of those documents come out of one serialiser (`format_id="opencode"` serves OpenCode,
OpenCode 2 and Kilo) which is a pure function of the model records and cannot know its own harness
id. Rather than change twelve signatures, it writes `MCC_HARNESS_ID_SENTINEL` and the caller resolves
it — the same shape `COMMANDCODE_BASE_URL_SENTINEL` already uses for the base URLs those serialisers
equally cannot know. Proven end to end: all seven document harnesses resolve to their own distinct
id, with no sentinel left on disk.

**2. The user-agent**, where no header arrived. Every non-SDK pattern was copied out of a real
request or the installed CLI's bundle, never invented — a rule written from a product name matches
nothing, and "no rows for this agent" is indistinguishable from "wrong rule for this agent" in a
breakdown.

The header is what makes the answer honest rather than merely plausible:

- **Qwen Code and Pi both send Claude Code's user-agent.** `@qwen-code/qwen-code@0.15.11` builds
  ``claude-cli/${version} (external, cli)`` on its Anthropic path and `@earendil-works/pi-ai` sends
  ``claude-cli/${claudeCodeVersion}``. Seven rows of this log are Qwen Code wearing Claude Code's
  name. No version rule separates them without breaking the day either ships a major, so
  fingerprinting answers `claude` for all three **on purpose** — recorded as `CLAUDE_CLI_COLLISION`
  and pinned by a test — and the header separates them from 6.37.0 on.
- **`claude_agent_sdk` is broken out from `claude`** for the opposite reason: it is a different
  program, and at 80,982 rows (30%) it is the busiest client on this machine.
- **`ai_sdk`, `anthropic_sdk`, `openai_sdk`, `script`** name libraries and one-liners, not agents.
  They are real answers to "who sent this" and can never be registry entries, so they live in a
  closed `NON_REGISTRY_HARNESS_IDS` set with display names, and a test proves nothing else escapes.

## Measured, with the shipped code

Not a prototype: the real `RequestLogStore` was pointed at a `VACUUM INTO` copy of the live log
(2.969 GB, 272,293 rows, no `harness` column) and its own writer thread did the migration.

| step | measured |
| --- | --- |
| `ALTER TABLE requests ADD COLUMN harness TEXT` | 0.002 s (metadata-only in SQLite) |
| backfill, 272,293 rows, 5,000 per committed chunk | **20.5 s** |
| `CREATE INDEX idx_requests_harness_v1 (harness, ts_epoch)` | 0.7 s |

| approach | all-time "requests by harness" |
| --- | --- |
| compute from stored headers at query time | 5.6 s — every Analytics load pays it |
| column + its own index | 756 ms |
| **+ tenth rollup dimension** | **103 ms**, in line with every other card |

## Two things found while proving it

- **The jsdom harness had been rendering nothing past the two charts in the requests view.**
  `getContext()` returns null there and `prepareCanvas()` called `setTransform()` on it, so
  `renderReqModelChart` threw and took the rest of `loadRequestsView` with it: the filter datalists,
  all six breakdown panels and the table body were dead in every existing test, and only
  `requestCards` was ever asserted. A no-op 2D context stub revives them; `consoleErrors` 5 → 0, no
  existing test changed outcome, and several previously vacuous areas are now genuinely exercised.
- **Inserting the column before Model moved the error-row colour off its cell.**
  `.req-status-error td:nth-child(5)` → `nth-child(6)`, confirmed in the real browser: `coloured
  cell 6 of 12 = "nvidia/nemotron-3-ultra-550b-a55b fallback"`.

## Residual risks

- The `claude` bucket over-counts by however many Qwen Code and Pi requests predate this release.
