## Description

The last case the fallback audit left open.

## The gap

A stream that has shown the reader part of an answer **cannot** fall back — switching models would splice two answers together. But nothing bounded it either: the first-token deadline stops applying the moment content appears, so the only limit left was the whole-request budget.

On 21 days of measured traffic, **106 requests held one open for the full 600s** after producing real output.

`FALLBACK_STALL_TIMEOUT`, default **120s**, `0` disables.

**Measured from the last chunk that moved the answer forward** — never from the last frame of any kind. A keepalive proves the connection is alive, not that the answer is advancing, and a guard that accepted one would never fire on the streams it exists for. A model producing steadily is therefore never cut, however long its answer runs.

## Both of the requested properties, demonstrated rather than argued

Live, against a real server and a real upstream:

```
answers then dies       10s, all 5 deltas delivered, clean terminal error
                        naming the stall limit
                        (121s before, on the provider read timeout;
                         600s in production, on the budget)

15s of steady output    16s, 60 content deltas, 0 errors, proper
under an 8s limit       message_stop — untouched
```

**No new failure mode.** The failure it raises is the one the total budget already raised on exactly these streams, via the same `anthropic_terminal_error_frame`. This is an earlier trigger for an existing outcome.

**It cannot introduce an unbounded wait, and removes one.** With the guard on, a committed stream is bounded even when `FALLBACK_TOTAL_TIMEOUT` is disabled. Proven by mutation: removing the limit makes the suite *hang*.

## Choosing 120s

Deliberately the same number as `FALLBACK_FIRST_TOKEN_TIMEOUT` rather than a new invented one. It answers the same question — how long may this model be silent — and mid-answer silence is if anything *more* suspicious than silence before the answer, which at least covers queueing and cold starts.

For scale: across **146,857 successful requests** the slowest averaged one output token every **2.27 seconds**, so the default sits ~50× beyond the worst rate ever observed here. An average cannot bound a single long pause, so this is a judgement rather than a proof — which is why `0` disables it and the setting is on the dashboard.

**M2 and M4 survived a first pass** and the tests were strengthened rather than the finding dropped: M2's keepalives were emitted back-to-back so the stream tripped either way, and M4 asserted only the error message, not the behaviour. An earlier run also reported three *false* survivals caused by a `-k` filter that excluded the very tests that catch them — the probe, not the code.

`test_no_limit_field_is_orphaned` caught the new field before I did; `LIMIT_KEYS` is updated.

Local CI: `ruff format --check`, `ruff check`, `ty` clean; pytest **4,836 passed** with the documented 6 `test_install_ps1_*` baseline failures.

## Found while testing, NOT fixed here

**The holdback buffer only checks its window when a new event arrives.** A stream that emits a burst of content and then stops never flushes — the content is discarded and the request is reported as *"produced no output"*, despite the model having produced some. Reproduced with a stub sending five deltas at once and stalling; it predates this change and needs a timer in the provider's read loop, which is its own PR. Say the word.

## Residual risks

- **The default is a judgement, not a proof.** If a provider legitimately pauses >120s mid-answer, its requests will now end. `FALLBACK_STALL_TIMEOUT=0` restores the old behaviour, and the setting is bounded 0–1h in the dashboard.
- **Silent extended thinking.** If a model reasons without streaming reasoning deltas, that silence counts against the limit. In the Anthropic shape thinking precedes content, so it is normally covered by the first-token deadline instead — but interleaved thinking mid-turn is the case to watch.
- The guard adds one substring scan per chunk. Exact for this protocol: only a `content_block_delta` can carry content.
