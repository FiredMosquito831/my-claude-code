## Description

Three gaps between what the web search stack fetches and what Claude actually receives. MINOR `4.18.3` → `4.19.0`.

## 1. Extracted page content was discarded

Seven adapters populate `WebSearchResultItem.content` (exa, tavily, firecrawl, jina, brave, ollama, parallel) and `_search_summary` already read it — but `_web_search_response_items` never copied it across, so the read was a branch that could never fire.

The effect: `EXA_CONTENTS`, `TAVILY_INCLUDE_RAW_CONTENT`, `FIRECRAWL_SCRAPE_FORMAT` are switchable in the admin UI, billed by the provider, captured by analytics, **rendered in the request detail modal** — and invisible to the model. The dashboard displayed page text Claude never got.

Content now reaches the digest and is preferred over the snippet, under its own `WEBSEARCH_DIGEST_CONTENT_CHARS` cap (default 2000) so opting in isn't trimmed back to the 600-char snippet length.

## 2. Domain filters never left the API layer

`registry.search()`, every adapter, and the analytics input payload already accepted `allowed_domains`/`blocked_domains`. Nothing read them off the client's tool definition — leaving `SUPPORTS_DOMAINS` dead in production on five providers, and the recorded input payload hardcoded to `[]`.

Anthropic declares these on the *tool*, not the tool call, so they arrive as extras on `Tool` (which permits them). They're now read and forwarded, and each attempt records the real values. `max_uses` is honoured as far as this single-shot path allows.

A request carrying both lists resolves to the allow list rather than silently intersecting — Anthropic rejects that combination outright, so guessing an intersection would invent behaviour.

## 3. Every failure reported `unavailable`

Anthropic documents six `error_code` values and a client acts on the difference: `too_many_requests` is worth retrying later, an invalid input never is. We classify errors precisely and then discarded that at the final step.

| Failure | Code |
|---|---|
| `WebSearchRateLimitError`, `WebSearchQuotaError` | `too_many_requests` |
| `WebSearchInvalidRequestError` | `invalid_tool_input` |
| exhausted `max_uses` budget | `max_uses_exceeded` |
| anything else | `unavailable` |

Deliberately no guessing at `query_too_long` or `request_too_large` — nothing classifies those confidently, so they stay `unavailable`.

## Verification

New tests: content passthrough and digest preference; tool-option parsing including the both-lists case and absent parameters; end-to-end forwarding asserted on the `search_with_logging` call; the full error-code table. Existing digest-shape expectations updated for the additive `content` key, and five test doubles updated for the new keyword args.

`ruff format`, `ruff check`, `ty check` clean; no suppressions.

Full suite passes except **14 failures that also fail on unmodified `main`** — 8 from real API keys in the local environment defeating `Settings()` isolation, 6 PowerShell installer tests. Identical set before and after this change.

## Residual risks

Content preference increases input tokens per search for anyone who has content options enabled — that is the point, but it is a real cost change, tunable via `WEBSEARCH_DIGEST_CONTENT_CHARS=0` to disable.

`user_location` is still not forwarded. It needs a country/locale translation layer across providers that spell it nine different ways (`BRAVE_COUNTRY`, `SERPER_GL`, `EXA_USER_LOCATION`, `FIRECRAWL_LOCATION`, …); that belongs in its own change rather than bolted on here.
