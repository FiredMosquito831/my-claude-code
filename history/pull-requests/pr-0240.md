## Description

## What was wrong

Adding a custom provider on the **Providers** tab produced a card that reported its models while nothing else in the process had them. `GET /v1/models`, the **Models** page, the **Model Config** pickers and `~/.fcc/codex-model-catalog.json` were all empty for that provider. The only recovery was a restart — or, by accident, a second registry mutation.

Measured on the reporting install's `~/.fcc/logs/server.log` (all +03:00):

| Time | Event |
| --- | --- |
| 01:14:06 | last process restart |
| 03:05:32 | `POST /admin/api/custom-providers` — provider created |
| 03:05:37–39 | the create's hot reload sweeps **all** providers' `/models` |
| **03:05:39.883** | `Provider model discovery skipped: provider=custom_b_ai reason=query failure: PermissionDeniedError` |
| 03:06:09 | `PATCH /admin/api/custom-providers/custom_b_ai` — a second mutation |
| **03:06:14.360** | `Provider model discovery cached: provider=custom_b_ai models=44` |

There is no `Starting Claude Code Proxy...` line after 01:14:06, so the restart the report credited the fix to never happened. The PATCH did it.

## Mechanism

The create route called two things that each went to the upstream:

1. `ProviderRuntimeManager.replace()` fires a fire-and-forget sweep of **every** provider's `/models` (`provider_manager.py:459-461`).
2. The route then awaited `test_provider`, which fetches `/models` again (`admin_custom_routes.py:227` → `application.py:275-299`).

So a host registered one second earlier was asked for its model list **twice, concurrently, with the same brand-new key**. One of the two came back `PermissionDeniedError`. That failure was only logged (`discovery.py:155-160` — no caller and no UI learned of it), and the response's `models` array came from the **test result**, not from the catalogue (`admin_custom_routes.py:226-234`) — so the card could truthfully advertise 44 models the catalogue did not hold. On top of that, `test_provider` cached un-enriched infos while discovery cached models.dev-enriched ones, and `updateCustomProviderCard` never rewrote the model-count line.

## Fix

- **One fetch per create.** `ProviderRuntimeManager.replace()` takes `background_refresh`; a registry mutation names the one provider it changed and gets the new `refresh_provider_models()` instead — one awaited, provider-scoped discovery, with **one bounded retry** for the provider that just changed (a gateway that has not finished propagating a key answers 403 once and then serves the list fine). No periodic timer was added.
- **A discovery failure is reported.** `ProviderDiscoveryFailure` carries `error_type` and a redacted message back through `ProviderModelRefreshResult`. Create / enable / add-key / remove-key responses carry a `discovery` block (`{provider_id, ok, model_count, error_type, message}`), and the card renders it red with the upstream's reason instead of settling into a healthy-looking card.
- **The response reports the catalogue.** `model_count` and `models` come from the cache the discovery just filled, not from an independent probe.
- **One cache-and-publish seam.** `cache_enriched_model_infos()` in `providers/runtime/discovery.py` is now the only place model infos are enriched from models.dev and cached — used by both background discovery and the admin refresh button, so the catalogue no longer depends on which one filled it.
- **UI.** The custom card's "Test" button reads **"Refresh models"**, matching the identical `POST /admin/api/providers/{id}/test` call on a static remote card ("Test connection" stays for `kind === "local"`), and `updateCustomProviderCard` now rewrites the model-count line in place.
- **Docs.** New `docs/USAGE.md` "Custom providers" section, a `README.md` paragraph, an `ARCHITECTURE.md` "Custom Providers" subsection, and a paragraph in the in-dashboard Guide. `docs/AGENT_SPEC_CUSTOM_PROVIDERS.md` ("Temporary spec; delete before release") is deleted, its still-true parts folded into `ARCHITECTURE.md`.

Version bumped 6.21.0 → **6.22.0** (MINOR: new response field + changed UI behaviour), `uv lock` in the same commit.

## Residual risks

- **`AdminRuntimePort.reload_providers` changed signature** (added keyword-only `refresh_provider_id`, now returns `dict[str, Any]` instead of `None`). It is an internal Protocol with one production implementation; the test double in `tests/api/test_admin_custom_providers.py` was updated. Any out-of-tree implementation would break.
- **The bounded retry costs one extra upstream call on a genuine failure** (two `/models` requests instead of one when the host is really refusing). Retry delay is 0.25 s and the retry count is 2 attempts total, both hard-coded parameters rather than settings — deliberately, to avoid adding a knob for Part A.
- **`refresh_provider_models` holds `_replace_lock` across the retry**, so a mutation that fails discovery blocks another mutation for up to ~0.25 s plus two upstream round trips. `connected_provider_changed` already had the same shape.
- **A disabled or keyless entry is not probed** (`_discovery_target` returns `None`), so those mutations fall back to the old blanket background sweep. That is the pre-existing behaviour, not a new one.
- **The jsdom harness is close to its 180 s subprocess timeout** under a fully parallel run and errored twice on this machine at ~99 % CPU; it passes cleanly when the file is run on its own (159 passed) and each harness invocation takes ~40 s standalone. This is the known 99 %-hang flake, not a new regression — my additions cost ~0.75 s per run.
- **Part B is untouched.** Custom providers still have no models.dev bucket (so limits and reasoning efforts come from the cross-provider vote), no per-key health readout, no onboarding credit, and no guard against disabling a routed provider. Those questions are undecided.
