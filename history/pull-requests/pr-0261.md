## Description

# Add HyperCharm (`hypercharm`) as a generic OpenAI-chat gateway

`v6.38.0` → **`v6.39.0`** (MINOR — new provider). Base `de483f60`.

HyperCharm (`https://hyper.charm.land/v1`) serves **32 open-weight models** —
DeepSeek, GLM, Kimi, Qwen, Llama, Gemma, `gpt-oss`, MiniMax — over OpenAI Chat
Completions. It is wired the way every other static provider is wired, through the
global mechanisms, with **no special-casing anywhere**.

## Why chat completions only

The host also answers `/v1/messages` and `/v1/responses`, and both were probed
returning 200 — but both are translation shims over the same roster. There is **no
`claude-*` id on the host at all**: `POST /v1/messages` with `claude-sonnet-4-5`
answers

```
404 {"type":"error","error":{"type":"not_found_error","message":"model not found: claude-sonnet-4-5"}}
```

so the Command Code dual-protocol split would add a branch that can never be taken,
and `/v1/messages` returns `"signature":""` on its thinking blocks — a translation,
not a native Anthropic upstream. Chat completions buys the entire universal stack:
per-model overrides, learned dialect, reject-and-remember, the learned output-cap
net, credential rotation, the exhausted-credits matcher.

## The profile is the generic one

```python
"hypercharm": OpenAIChatProfile(
    _policy(
        "HYPERCHARM",
        ReasoningReplayMode.DISABLED,
        include_extra_body=True,
        extra_body_validator=validate_extra_body_does_not_override_canonical_fields,
        default_max_tokens=ANTHROPIC_DEFAULT_MAX_OUTPUT_TOKENS,
    ),
    OPENAI_STANDARD_REASONING,
),
```

Every field is the generic default: `OPENAI_STANDARD_REASONING` is the *same object*
every generic gateway declares (pinned by identity, not equality), the model listing
is the stock `OpenAIModelListing()`, `reasoning_delta_field` stays at its
`reasoning_content` default (which is what the host actually streams), no
postprocessors, no `structured_reasoning_details`, `max_tokens` not
`max_completion_tokens`.

**No union effort enum, no bespoke encoder, no honoured-ness A/B, no per-provider
tuning.** `/v1/models` publishes no `supported_parameters`, so there is nothing to
narrow the dialect *with*; the per-model `reasoning.effort_levels` ladders it does
publish differ model by model (`gpt-oss-120b` has seven rungs, `deepseek-v4-flash`
has two, 21 of 32 declare none), which is exactly what the per-model capability gate
in front of the encoder is for. `PROVIDER_TUNING` is a single provider-agnostic
`RotationTuning`, so there is no per-provider place to put a number and none was
created. The observed `x-ratelimit-limit-hour: 200` / `-day: 1000` headers are
recorded as evidence only and hardcoded nowhere.

## Shared error-reader fix (general, not a HyperCharm branch)

HyperCharm answers a bad key with `{"error": "authentication failed"}` — a **bare
string** — while spelling every other failure as `{"error": {"message": …}}`. Any
host may do that.

`core/anthropic/upstream_errors.py::anthropic_stream_failure` read only the object
shape and threw the host's own words away, substituting the generic
`"Provider stream failed."` It now reads a bare string as the message; the kind
still falls through to the `UPSTREAM` default, because that shape carries no `type`.

The OpenAI-chat readers needed **no change** and that was verified rather than
assumed — `classify_provider_failure`, `upstream_complaint` and
`parse_output_token_cap` were each exercised against both envelope shapes and are
now pinned. HyperCharm's cap rejection, `"Invalid max_tokens input."`, **names no
number**, so the learned-cap net correctly learns nothing from it; that is pinned
too, in both envelope shapes, because the wrong outcome there is not a crash but a
*wrong* learn.

## Residual risks

- **`ReasoningReplayMode.DISABLED`, not `REASONING_CONTENT`.** Reasoning is *read*
  correctly on the return path (measured), but assistant history is not replayed back
  with its thinking. Whether this host accepts an assistant turn carrying
  `reasoning_content` was **not probed** (it would have cost a request), so the
  conservative setting — the one `nararoute`, `tokenrouter`, `chutes` and `cline` all
  use — was chosen. Upgrading it later is a one-line change plus one probe.
- **`x-ratelimit-*` behaviour under pressure is UNKNOWN.** No 429 was provoked and no
  `retry-after` header was ever seen, so the throttle path is unexercised for this
  host. Deliberately not guessed at, and deliberately not hardcoded.
- **`kimi-k2-thinking` has tier-1/2 metadata only** until models.dev adds it. It
  degrades to "not reported" rather than to a wrong number, which is the intended
  behaviour, but a route pinned to it gets no context-length bound.
- **The `/models` vendor keys are left on the floor.** `context_window`,
  `max_output_tokens` and `pricing` are richer and fresher on the host than in
  models.dev, and a bespoke extractor would beat tier 3 and would cover
  `kimi-k2-thinking`. That is a real feature and a separate PR; it is not wired here
  because a third listing dialect is exactly the special-casing this PR set out to
  avoid.
- **Pre-existing, unrelated, unchanged:** the admin's "No label associated with a form
  field" a11y issue rises 52 → 53 because a provider card is one more instance of the
  existing pattern; and the request-detail modal header chip reads "answered" even on
  an errored request. Neither is introduced here and neither was touched.
