## Description

## What was broken

Toggling one token-optimizer agent from the tray **silently reverted whatever the dashboard had changed**.

```
1. dashboard: enable codex        -> disk {claude:F, codex:T, pi:F}
2. tray:      toggle claude       -> disk {claude:T, codex:F, pi:F}
                                                    ^^^^^^^ reverted
```

`_toggle_rtk_agent` flipped one entry in a cache snapshotted at tray construction, then wrote **all three fields** reconstructed from that stale cache.

## Mechanism

The tray and the admin HTTP API are separate processes that both persist `RtkState` to `~/.fcc/rtk.json`, with no lock and no cross-process notification.

The API does it correctly — `current = await asyncio.to_thread(load_rtk_state)` before writing. The tray did not. The write itself is atomic (`os.replace`), so this was a **lost update**, not a corrupt file: the setting simply vanished with no error.

## The fix

`_toggle_rtk_agent` re-reads from disk, flips **only** the requested agent on that fresh state, and refreshes the in-memory cache from it so the checkmarks match reality.

No locking, no IPC, no file watcher — read-modify-write is the whole fix. A comment records *why*, so nobody optimises it back into a cached write later.

### Also fixed — same root cause, smaller form

`Start at Login` and `Tray Enabled` derived their new value from the stale cached field.

`config/desktop.py::_update_state` re-reads before writing, so these could **never clobber a different field** — that part of the original report was wrong and is worth stating plainly. But they could compute the **wrong direction**: if the dashboard turned `start_at_login` on after the tray started, the tray's next click wrote `True` over `True` and *appeared to do nothing*. Both now derive from persisted state.

`_set_server_mode` writes an absolute value and was never affected.

## Residual risks

**The tray still holds an in-memory cache rather than reading state per menu render**, so a checkmark can display a stale value until the next toggle. That is a display concern, not data loss — and the toggle now behaves correctly regardless of what the checkmark showed. Fixing it properly is a menu-rendering change, deliberately out of scope.

**No live desktop run.** `pystray` needs a platform backend, so this is exercised through the menu objects and the state file — the contract the tray shares with the CLI and the dashboard — not by clicking a real tray icon.
