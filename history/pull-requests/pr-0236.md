## Description

## What was wrong

A stream that has shown the reader text cannot fall back. The words are on screen and no other model can un-send them, so until 6.15.0 every failure past that point — the stall deadline, the request budget, a mid-stream 5xx, a dropped connection — reached Claude Code as an API error printed underneath a half-written answer, and the turn died. The incident that started this work streamed 1,333 characters, went quiet, and was reported as `API Error … stopped producing output`, with seven healthy fallback models recorded as `not tried: a timeout failure ends the route`.

6.15.0 (#233) gave that case an honest ending: close the open block, send a `stop_reason` meaning "cut short", stop. The turn stopped dying — but the answer was still half an answer.

## What this does

Rather than only *ending* a half-written answer, the next model on the route is handed the text already sent and asked to carry on from it, and its stream is spliced into the same message. One `message_start`, one text block, one ending. The turn survives.

### The splicer — `core/anthropic/streaming/splice.py` (new, pure)

Freezes what the reader was actually shown, then rewrites a second model's SSE so the two form one valid message. Every rule traces to a line in `stream_contracts.py`:

| Rule | Why |
|---|---|
| Drop the continuation's `message_start` | `sse_aggregation.py` keeps the *last* envelope and would clobber the one the client already has |
| Offset every block index above the highest seen | `stream_contracts.py:124-125` — indices are single-use for the whole message |
| Map the continuation's first `text` block onto the block left open at the failure | one continuous block, no seam |
| Drop a continuation's thinking entirely | `ContentBlockThinking.signature` is provider-cryptographic; a foreign model cannot produce a valid one |
| Emit exactly one `message_delta`/`message_stop`, output tokens summed | `stream_contracts.py:106-109` |

`truncation.CommittedStreamTracker` grows the read-only accessors the freeze needs (`text_prefix`, `thinking_prefix`, `next_index`, `open_blocks`, `consumed_output_tokens`) and keeps following the *outgoing* stream across the seam, so a second failure is judged against the whole message rather than only its last third.

### The one judgement that is not mechanical

Measured across thirteen live model/host pairs, the dominant failure of a continuation prompt is a **verbatim restart** — the reader would see the opening paragraph twice. So:

- nothing the continuation writes reaches the client until the restart verdict is in;
- `strict_continuation_suffix` rejects a restart outright and strips a repeated tail;
- `recovery.continuation_suffix` is **left alone** — the same-provider recovery path depends on it, and its short-candidate clause (`recovery.py:118-119`, returns the whole candidate when it is short) is exactly the hazard here.

A rejected continuation is discarded and the message ends on what the first model said. Held-but-unjudged bytes are discarded too, so a continuation that dies before it is judged has shown the reader nothing and the *next* model continues from the first model's words.

### Every exit lands on 6.15.0's truncated message, never on an error

No model left · a continuation that says nothing · a continuation that restarts · `wire_api == "responses"` · a `FALLBACK_SKIP_KINDS` failure · a `stop_reason` the model already sent (`max_tokens` exhaustion arrives this way) · the operator turning it off. The one state never continued is a half-written `tool_use`, which still errors — `sse_aggregation.py:106-112` would substitute `input={}` for JSON it cannot read and Claude Code *runs* tool calls.

That asymmetry is why this can ship on: being wrong costs length, not correctness.

### The prefill

Assistant turn carrying the text so far, then a user turn carrying `recovery.CONTINUATION_NUDGE` (promoted from `_RECOVERY_USER_PREFIX` — one wording, not two). Ending on the **user** turn is load-bearing: a request whose last message is the assistant's is a *prefill*, which Anthropic rejects with a 400 on Claude 4.6+ and which only DeepSeek, Mistral and Anthropic accept market-wide. The assistant-then-user shape needs none of it, sets no `prefix` flag, and was the only shape measured as working. Tools are deliberately kept and the nudge is deliberately tool-neutral (LiteLLM #31067 is a fallback that "continues generating prose instead of invoking tools" and returns a *completed* stream with empty `tool_calls` and no error).

### Also: the second half of the commit holdback

`STREAM_COMMIT_HOLDBACK_SECONDS` asks whether a model has had time to fail. New **`STREAM_COMMIT_HOLDBACK_CHARS`** (default `0` = today's behaviour) asks whether it has said enough to be worth keeping. Both conditions must be met, or the stream must end. A model that writes one word and dies inside the window has shown the reader nothing, so the route restarts on the next model invisibly. The 65,536-byte ceiling still releases output whatever is set, because a memory bound is not a policy.

**Naming note.** The brief called for `FALLBACK_COMMIT_HOLDBACK_SECONDS`; the shipped setting for exactly that is already `STREAM_COMMIT_HOLDBACK_SECONDS` (`constants.py`, manifest "Commit holdback", Deadlines card). Per the brief's own "do not create a second knob for the same thing", it is reused, and the new knob is named as its sibling rather than with a `FALLBACK_` prefix that would read as a different buffer.

## Design notes worth stating

**Prior art.** Anthropic's own server-side fallback (beta `server-side-fallback-2026-07-01`) is this design, vendor-sanctioned: the open block closes, only the partial output's `text` blocks are passed forward, the fallback model continues into the same `message_start`, and a decline while a `tool_use` block is open is not retried at all. No gateway does it — Portkey and TrueFoundry's "streaming fallback" features are both *commit at the first chunk*, which MCC shipped in 5.50.0; Kong, Bifrost, Helicone and Cloudflare all decide before the body. LiteLLM's Responses path is the one attempt, and its open bugs (#31067, #27967, #18229, #26015) are this PR's test list. A separate source survey found no proxy re-dispatches once visible output exists: CLIProxyAPI errors on a 200, 9Router truncates silently with no terminal frame, and OpenClaw's agent core surfaces the error (its per-chunk idle watchdog defaults are 120 s cloud / 300 s self-hosted / 0 for localhost).

**No `fallback` content block, deliberately.** Anthropic marks each model boundary with one. Not emitted here for two reasons: `stream_contracts._ALLOWED_BLOCK_START_TYPES` would have to be widened, weakening the guarantee every other stream test relies on; and it is a beta the installed client never opted into. The model change is recorded on the attempt row instead.

**`requests.provider` / `resolved_model` keep last-writer-wins** — the row names the model that *finished*, which is what "which model answered this request" means to `idx_requests_model`, the analytics model breakdown and every export. That another model started it is recoverable from `request_attempts`. No new column, so `_ROLLUP_ACKNOWLEDGED_COLUMNS` and the DDL are untouched.

**No export change in v1.** `_REQUEST_DETAIL_DERIVED` carries only ladder rollups and no export path joins attempt rows.

**Not built, deliberately:** a same-model empty/reasoning-only retry (OpenClaw re-prompts the same model up to 3×). `FALLBACK_ON_REASONING_ONLY` already moves those to the next model; adding a second mechanism was explicitly out of scope. Noted as a follow-up.

## Residual risks

1. **The message names a model that did not write all of it.** `message_start` has already gone out naming the first model, and this feature deliberately adds no visible seam (Anthropic's `fallback` content block is not emitted, for the reasons above). A client reading `message_start.model` is told the model that *started* the answer. The request detail carries the truth; the stream does not.
2. **A partial restart is not always caught.** `looks_like_a_restart` catches a verbatim restart and a jump back into the middle of what was sent. A model that *paraphrases* its opening — "The sea is blue…" after "The sea is vast…" — matches neither test and would be spliced, producing a visible restatement. That shape was observed only under the bare-prefill form, never under the nudge, but it is not impossible.
3. **Continuation quality is model-dependent and mostly poor.** Of thirteen live model/host pairs measured, three of three non-empty nudge responses were clean, but six models that answered the bare form returned nothing at all under the nudge. Most resumes will end as a truncated message, i.e. exactly 6.15.0. The feature buys the good case; it does not make the good case common.
4. **A half-written tool call still errors.** The one path that still hands the reader a dead turn. Cross-model tool-JSON repair is a follow-up, not this PR.
5. **The continuation's own prompt tokens are not billed to the message.** `message_delta.usage.output_tokens` is summed across both models; `input_tokens` stays what `message_start` announced, so `message_start` and `message_delta` agree as they do on every other stream. The second request's prompt (the original conversation plus the answer so far) is real spend that the message-level usage does not show. It is visible as a second `request_attempts` row.
6. **Latency on the rescue path.** Up to 512 characters of the continuation, or the whole of it if shorter, are held before anything is forwarded. On the live proof the continuation arrived as one delta rather than streaming. This is the price of never showing a restart.
7. **Two adjacent text blocks in states (b) and (d).** When the failure did not land inside a text block, the continuation opens a second one. That is contract-valid and both live proofs exercised it, but **what the real Claude Code TUI renders for two adjacent text blocks in one message is UNVERIFIED** — every proof here is `curl` plus the contract validator, not the installed client. The seam-free path (state (a), one open block) is the common case and was verified live.
8. **`stop_reason: max_tokens` on an unusable continuation** inherits 6.15.0's compromise: it is the protocol's only value meaning "cut short", and a client that reads it as a real token-limit hit will draw the wrong conclusion about why.
9. **UNVERIFIED — LiteLLM line numbers.** The `router.py` references in the design notes (~L2471, ~L2681) drift with `main` and are not pinned to a SHA. The behaviours and issue numbers were confirmed; the line numbers should not be quoted as exact.
10. **The `attempted`-set rotation coverage gap** flagged in the design brief (`credential_rotation.py:219 acquire()`) is still thin in the existing suite — it has no dedicated named test, only the two-key connection-error case. This PR does not touch the pool at all, so it neither closes nor widens the gap; it is recorded so it is not lost.
