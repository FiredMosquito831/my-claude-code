## Description

## The problem was structural, not cosmetic

Model Routing rendered into the generic auto-fit field grid, so a tier's primary model and its fallback chain landed in **separate, often non-adjacent cells** — "Opus Override" finished row one, "Opus Fallback Chain" started row two. The one relationship that governs every request (what this tier tries, and in what order) was invisible.

Around it: ~200px of dead space per row, nine near-identical help sentences, and the only truncated thing on the page was the model name itself (`nvidia`, `openc`) while "Remove" got full width.

## Each tier is now one card, with its models on a rail

```
┌─────────────────────────────────────────┐
│ OPUS                       Custom route │
│  ●─ nvidia_nim/nemotron-3-ultra    ▾    │
│  │                                      │
│  ①─ open_router/qwen3-coder      ▾  ×   │
│  │                                      │
│  ②─ cerebras/kimi-k2             ▾  ×   │
│  │                                      │
│  ⊕─ Add fallback                        │
└─────────────────────────────────────────┘
```

Filled dot for the primary, numbered markers for fallbacks, terminating in the add affordance. **The rail's length is the depth of that tier's safety net** — no fallbacks gives a stub, three gives a long descent. Numbering earns its place because the order genuinely is the try-order.

The rail is drawn **per node**, not as one absolute line down the card: a single line with a fixed offset only meets the markers while every row is exactly the same height, which is not a guarantee worth depending on. Markers are raised above it, since absolutely positioned segments otherwise paint over the static content they are meant to run behind.

## Copy: nine sentences to one

- `Select None to use the Default Model for X requests` ×4 → a state the card reports: **Inherits default** / **Custom route**
- `Tried in order when X cannot serve a request` ×5 → stated once, above the grid

Repeated near-identical text teaches the eye to skip the whole column. The default card gets **no** chip: it is the thing the others inherit, so calling it "custom" would be noise on every install.

## Two other decisions

**Model refs in monospace.** They are paths, not prose — mono makes the provider prefix scannable instead of making a long slug look like a mistake. Adds `--font-mono`.

**The palette is untouched.** This is one section of a shipped dashboard; repainting it would be vandalism. The boldness is spent on the rail.

**The vision adapter is deliberately not a sixth route card** — it fires on what a request *contains* rather than which model was asked for, so it gets its own shape below the grid instead of masquerading as a tier.

## Structurally this only changes arrangement

`buildFieldControl()` is factored out of `renderField()` so the generic grid and the routing view wire controls into the **same** dirty/apply machinery, and the rail carries the `field` class so every existing input style still applies. Any field the manifest adds to this section later still renders, in a plain grid below.

## Residual risks

- **This has not been rendered in a browser.** There is no browser tooling in this environment, so the visual result is reasoned about, not seen. The rail geometry, the mono sizing, and the 720px breakpoint are the parts most likely to need a second pass.
- The onboarding deep-link `[data-key="MODEL"]` now resolves to the route card rather than a field wrapper. That is the same pattern `renderField` already used (`wrapper.dataset.key`), and it scrolls to the card, which is at least as useful — but it is a behaviour change worth knowing about.
