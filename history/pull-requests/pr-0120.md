## Description

## What was wrong

The vision adapter never fired for an image that arrived **inside a tool result**, so those requests went to a model documented not to accept images, and analytics recorded an ordinary route.

Measured on the live request log (read-only):

```
total rows                       115,522
route_diversion IS NOT NULL            0
route_chain IS NOT NULL           71,654   (tracing live since 8 Aug)
route_attempt > 0                    608   (fallbacks DO get recorded)
```

The gate was open the whole time — `/admin/api/models` reports `nous_portal/tencent/hy3:free` (the configured Sonnet primary) in `blind_models`, and `MODEL_VISION` is set.

## Mechanism

`request_carries_image` walked only the top level of each message's content:

```python
return any(
    isinstance(block, ContentBlockImage)
    for message in request.messages
    if isinstance(message.content, list)
    for block in message.content
)
```

`ContentBlockToolResult.content` is `str | list[Any] | dict`, and an image returned by a tool (reading a PNG, an MCP screenshot) is nested inside it. Probed against the real model:

```
 True  top-level image block          (pasted screenshot)
False  image inside a tool_result     (Read tool / MCP screenshot)
False  document block                 (PDF)
```

## What this does

- **Detection** — `request_image_inputs` walks tool-result content at bounded depth and counts `document` blocks too: a model that cannot read an image cannot read a PDF.
- **Recording** — `input_image_count` on the row, plus a downscaled WebP thumbnail in its own content-addressed table. Claude Code re-sends the conversation each turn, so keying on the source bytes stores one screenshot once rather than once per turn (measured: 5 requests, 1 stored blob). Retention deletes links with their rows, and a picture once no surviving request points at it.
- **Settings** — `REQUEST_LOG_CAPTURE_IMAGES` and `REQUEST_LOG_IMAGE_MAX_PIXELS` (0 records the image without pixels), both bounded through `config/limits.py` and on the Limits page.
- **Dashboard** — an `image` / `N images` chip on the row, an "Image input" line and the thumbnails in the detail, and a "With image input" figure in the window stats, counted separately from the diversion because a vision-capable primary takes an image without diverting at all.

Thumbnailing runs at finalize time, never between the client and its first token, and never raises — an unreadable image is still recorded as an image that arrived.

## Verification

- **Probe of the real router**: a `tool_result` image and a PDF both divert, `plan.diversion is RouteDiversion.VISION`, and the row reads back `route_diversion='vision'`.
- **Mutation-tested guards** — each broken on purpose, each turned the suite red by name: detector stops walking tool results (3 + 1 failures), prune stops deleting orphaned images (1), per-request instead of deduped storage (6), thumbnail failure raises instead of degrading (1).
- **Full suite**: 3858 passed, 6 pre-existing PowerShell installer failures — identical to unmodified `fork/main`.
- **Real browser** on a throwaway home (port 8177): chips render, both thumbnails decode at 512×320 and 329×512, the PDF row shows "no preview stored", a text-only row hides the pane, no console errors, and the chip passes AA in all four themes (5.38–9.38:1).
- The live WSL server on `:8082` answered 200 afterwards and was never touched.

## Residual risks

- **Existing rows cannot gain images they never stored.** The count and thumbnails start from this version.
- **URL image sources are counted but have no pixels to keep** — the proxy does not fetch them.
- Storage grows by one thumbnail per distinct image (tens of KB), bounded by row retention and by `REQUEST_LOG_IMAGE_MAX_PIXELS=0` for anyone who wants counts only.
- `pillow` is a new runtime dependency, locked in `uv.lock` with the version bump.
