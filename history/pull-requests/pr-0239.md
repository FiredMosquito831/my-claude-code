## Description

## What was missing

**A route rail could only be reordered one arrow press at a time, and never across cards.** The six rails on Model Config draw a route as an ordered path, but the only way to move an entry was its up/down arrows — one press per position — and there was no way at all to move a model from the Sonnet rail to the Opus rail except reading the ref off one card and retyping it into the other. `README.md` said "entries can be reordered" and stopped there, because that was all there was to say.

**And there was no way to take one model out of a route for an hour.** The only tool was the row's `×`: deleting it loses the ordering you spent time building, and the request log stops mentioning the model at all, so you cannot see that it *was* the thing you switched off. Hiding it on the Models page does nothing — that page is documented hide-only and never touches routing (`core/model_visibility.py:18-23`), which is exactly the confusion 5.65.0 closed and this must not re-open.

## Design

### Drag: pointer events, one mutator

Pointer events rather than HTML5 drag-and-drop, for a reason rather than a preference. jsdom has neither `PointerEvent` nor a usable `DataTransfer`, so an HTML5 implementation could be written but never covered by the harness this repo tests its UI with; the product's only existing drag (`startModelsDrag`, the Models page) is already pointer-based, and two drag idioms on adjacent pages read as a bug rather than as a distinction; and HTML5 DnD has no touch story at all.

Every gesture — pointer, keyboard, and the existing arrows' promotion path — funnels into **one** `applyRouteDrop(target, ids, copy)`. That is the only function that mutates a chain, so dedupe, the primary swap and the undo snapshot happen in exactly one place. It reuses `ModelChainEditor.swapPrimaryAndFirst()` and `setPrimaryValue()` rather than reimplementing the ordering rules those already own.

Row identity is a stable id (`route:MODEL_OPUS`, `chain:MODEL_OPUS_FALLBACKS#7`), never the model ref — a ref may legitimately sit on two rails and a fresh row holds none. The selection lives in `state.routeSelection`, never in the DOM, the same rule `test_admin_models_view.py` pins for the neighbouring page. The gap that made cross-rail drag impossible was that **no registry of chain editors existed** — every editor was reachable only through the closure that built it — so `state.routeRails` (chainKey → editor) is new.

The decided semantics, all of them: Ctrl/Cmd-click toggles, Shift-click ranges within one rail, Shift+Space and Shift+Arrow reach the same ranges from a focused grip; a group lands in **rail** order, not click order; a same-rail drop is a move, a cross-rail drop is a copy and Shift at *drop* time makes it a move; a copy onto a chain that already holds the ref **moves the existing row** rather than adding a duplicate the reader would watch vanish on Apply; a copy onto a chain whose primary is that ref is refused with *"Opus already routes to … first"*; a Shift-move may empty a source chain (legal — `BLANK_MEANS_UNSET_FIELDS`) but a primary is never moved out of its own rail, because an empty `MODEL` fails validation and the server refuses to start. Dragging a primary onto its own fallback 1 is the swap its down arrow already performs. The arrows are untouched — they are the WCAG 2.2 single-pointer alternative. Touch drags from the grip only, and `touch-action: none` is scoped to the grip alone (the file's first and only such rule) so a finger still scrolls the card.

Ctrl+Z is depth-1, routing view only, ignored while `document.activeElement` is a text field so it never fights native undo inside a combobox. One drag is one entry — including a nine-row group drop and including both keys a primary swap touches. There is no Discard button; that is its own PR with its own contract test.

### Pause: the benching seam, not the router

The two requirements pull apart in `resolve_chain`: a ref filtered out there never reaches `plan.model_refs()` and therefore gets **no attempt row at all**, so "never executed" and "still visible in the request log" cannot both hold at that line. They can at the 6.14.0 benching seam, so that is where the filter lives:

* `RouteHealthRegistry.usable_indexes(..., paused=...)` drops paused indexes. `_prepare_from` iterates `order`, not `attempts`, so a paused index is never executed and no budget is spent.
* `_AttemptLedger.mark_paused()` beside `mark_benched()`, and it runs **second** — a model that is both benched and paused reads as paused, because the bench is this build's guess and the pause is the operator's decision.
* Pause is **excluded from the "nothing survived" bypass** (`MODEL EJECTION BYPASSED`). Restoring a model somebody paused would be the opposite of what the button says, so an all-paused route returns an empty order and the executor raises a named error instead of quietly re-routing.
* Pause applies even with `FALLBACK_BENCH_ENABLED` off: that switch governs automatic ejection, not one a human flipped.

Everything downstream needed no change — `outcome="skipped"` is already legal, `error_kind` is a free `str | None`, and the detail modal renders the kind verbatim as a chip. `"paused"` appears in the request log with zero JS changes.

Six keys, one per rail: `MODEL_PAUSED`, `MODEL_FABLE_PAUSED`, `MODEL_OPUS_PAUSED`, `MODEL_SONNET_PAUSED`, `MODEL_HAIKU_PAUSED`, `MODEL_VISION_PAUSED`. Pause covers a route's primary *and* its chain, so it is not a property of the chain — hence `MODEL_OPUS_PAUSED` rather than `MODEL_OPUS_FALLBACKS_PAUSED`. They are never rendered as controls (they are claimed by the routing view so they do not fall into the "anything the manifest adds later" grid as six bare text boxes) and are pruned on write when a ref leaves the route it was paused on — scoped to routes the save actually edited, so an install whose routes live in a repo `.env` does not lose its pauses on an unrelated save.

The write goes through `apply_admin_config_with`, the #223-locked read-derive-write, never a client-side read plus a full replacement — that is precisely the bug #223 fixed. It clears the settings cache and republishes the provider generation, so no restart and no page refetch. `limit_hint()` hardcoded `"Limits & Resilience"`; it is a section→page map now, so a routing error says **Model Config → Model Routing** rather than sending the reader to a page with no such control on it.

One `role=status` panel serves the whole page — drag announcements and pause announcements both — declared statically in `index.html`, whole sentences, `hidden` toggled rather than `style.display`, with Undo and Dismiss.

## Residual risks

* **The dirty-drag / immediate-write interaction** is the sharpest edge here. It is covered on both sides — the browser proves one POST with one route entry beside a dirty drag, and `test_a_pause_write_touches_no_other_setting` proves the env diff is a single added line — but it is the one place where two save models meet on one page.
* **Touch drag is proven in jsdom and in Chrome with a synthetic touch pointer, never on real hardware.** The guard and `touch-action` scoping are right; finger feel is unverified.
* **Six new env keys widen the config surface.** They are in `.env.example`, `docs/USAGE.md` and `README.md`, but no test asserts either file covers every key — the manifest contract is membership-based, never cardinality.
* **`Application._config_lock` is process-local `asyncio`.** Two overlapping pause writes in one server now have a driven test; a second server process editing the same `~/.fcc/.env` is still unserialised, exactly as before this PR.
* **Escape is two steps**: the first abandons a live drag, the second clears the selection. Deliberate — one Escape undoes one intent — but worth knowing.
* Admin screenshots (`/admin/img/admin-model-config.png`) are a manual capture step per `docs/RELEASE-CHECKLIST.md`; the rails look different now and the shipped image is stale. Follow-up, not automated against `:8082`.
