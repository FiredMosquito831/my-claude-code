## Description

## What was wrong

Auto-refresh re-ran the two most expensive endpoints every 15 seconds regardless of whether anything had happened. On an idle dashboard that is percentiles, three `GROUP BY` breakdowns and a series bucket — forever, for no new data.

## The change

**A heartbeat endpoint.** `GET /admin/api/requests/pulse` answers one `COUNT`/`MAX` under the same filters. Auto-refresh polls that and only falls through to the full reload when the row count or newest timestamp actually moved. **11 ms against ~800 ms** for `stats()` on a 50k-row log.

The tab also stops polling entirely while hidden (and catches up on becoming visible), and the interval is selectable — 5/15/30/60s instead of fixed 15.

**The baseline is established by the first pulse, not by the preceding full load.** The list query is paged, so its newest visible row is not `MAX(ts_epoch)` once you are past page one; seeding from it would make every later tick look changed and reload the whole view — exactly the cost this removes. It is also keyed by the filter signature, since a different window has different counts and comparing across a filter change reports movement that only happened because the question changed.

**Three server-side fixes in `stats()`:**

- Percentiles no longer pull every `duration_ms` into Python to sort — the cursor is streamed and abandoned once the highest needed rank has gone past.
- The stats cache was an **unbounded dict** keyed by the full filter tuple, leaking a full payload per distinct filter combination for the life of the process. Now a 64-entry LRU that also drops entries on expiry.
- Each breakdown is capped at 50 rows by volume with a `*_truncated` flag **surfaced in the UI**. A gateway with hundreds of models returned hundreds of rows on every poll. The cap is never silent.

## What did not work, recorded so it is not repeated

An index leading on `duration_ms` makes the percentile lookup **68x faster in isolation** and made the whole of `stats()` **2.2x slower**:

```
with    idx_requests_duration_v1:  stats() 1525 ms
without idx_requests_duration_v1:  stats()  701 ms
```

Same database, same process, differing only by the index existing. With no `ANALYZE` statistics SQLite starts preferring it for the totals and breakdown aggregates, which it does not cover — turning one clean scan of `idx_requests_stats_v3` into an index seek plus a table lookup per row. It would also have meant building an index over a 1.2 GB `requests.db` on first start. **Not added.**

## Residual risks

- **The visibility pause, the interval selector and the truncation note have not been driven in a browser.** Logic verified by reading and by the live endpoint responses above.
- The breakdown cap slightly reduces filter autocomplete suggestions, which are built from those same breakdowns. Visible via the truncation note.
- Benchmarks are on a synthetic 50k-row database, not the real 1.2 GB log. Absolute numbers there will be larger; the relative comparison is what these support.
- `pulse()` cannot detect a change where one row is pruned and another added between ticks such that both count and max timestamp land identically. Vanishingly unlikely, and the next real request corrects it.
