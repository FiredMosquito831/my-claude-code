## Description

Last of four from the fallback audit.

## 1. `error_kind` spoke two languages

An `ApplicationError` carries a `FailureKind` as a class attribute — but only `ExecutionFailure` was ever read. So the request log recorded `timeout` and `rate_limit` alongside `InvalidRequestError` and `ApplicationUnavailableError`: the same failure spelled two ways, splitting any grouping by that column. On 21 days of live traffic that was **102 of 1,081 errors**.

`failure_kind()` / `failure_kind_name()` now read all three shapes in `core/failures.py`, and both the request row and the attempt log use them. The private copy added in #165 is gone.

## 2. A malformed request walked the whole chain

A 400 is the caller's, not the model's — the same body fails identically everywhere, so a three-model chain bought three round trips to the same error and three log rows all saying the request was invalid.

`FALLBACK_SKIP_KINDS` lists the kinds that end a route instead of moving on. Default `invalid_request`; **empty means fall back on absolutely everything**, which is the literal reading of what you asked for and is one setting away.

**A deny-list, not an allow-list, on purpose.** A failure kind added later falls back by default — the safe direction. An allow-list would silently stop covering it.

The skipped models say *why*:

```
0  failed    groq/llama-3.3-70b     invalid_request  messages: field required
1  not tried openrouter/glm-5       route_ended      not tried: a invalid_request
                                                     failure ends the route
```

That's the difference between "your chain did not help" and "your chain was correctly not used" — legible only because of #165.

**An unknown kind is refused at startup**, not ignored. A typo would fail *open*: the name never matches, the route falls back on everything, and the setting looks applied while doing nothing.

## Architecture note

`config` is a leaf package by declared policy — it imports nothing, not even `core` — so settings validation cannot reach `FailureKind`. My first attempt imported it anyway and `test_package_dependencies_follow_declarative_policy` caught it. The names are mirrored in `config/constants.py` and **pinned equal in both directions** by a contract test, because a list that mirrors another file drifts and only one of the two drift directions is loud.

The field went to the **routing** section rather than Limits: every Limits field must be a bounded numeric (an existing guard caught the misplacement), and it belongs beside the chains it governs anyway.

## Residual risks

- **Nothing backfills old rows.** `error_kind` stays as recorded for requests that predate this, so grouping across the boundary still needs both spellings.
- **A 400 from a gateway that misclassifies** would now end the route where it previously moved on. If a provider returns 400 for something a different model could serve, `FALLBACK_SKIP_KINDS=` (empty) restores the old behaviour.
- Not exercised end-to-end against a live upstream that returns a genuine 400 — covered by unit tests with a provider double.
