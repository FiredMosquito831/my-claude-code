## Description

A green test run must leave the machine it ran on exactly as it found it. This one did not. Twice in a single day the suite deleted the developer's real `HKCU\Software\Microsoft\Windows\CurrentVersion\Run\MyClaudeCodeDesktop` autostart value, and it had been rewriting real files inside `~/.fcc` for longer than that.

Both classes come from one shape of mistake: a test redirects *part* of the machine and the code under test reaches the rest of it. `tests/cli/test_desktop_rtk.py` redirected `HOME`, which isolated the state file and left the registry live. Nine tests in `tests/runtime/test_catalogue_fanout.py` gave one harness a `tmp_path` and let the other eleven resolve into the real config directory. Review does not reliably catch a missing fixture argument, and neither does a per-run `-p` plugin — one was in place for the second incident and the file it did not `--ignore` still got through.

So the guard is now `tests/support/hermetic.py`, installed for the whole session from `pytest_configure` and re-exported by `tests/conftest.py`. No test opts in. A test can only opt *out*, explicitly, with a marker.

**Test-only.** `src/` is untouched; no runtime, CLI, setting, wire format or config-schema change.

## Design notes worth reading before review

**`MCC_CONFIG_DIR` is deliberately unset, not pointed at a shared directory.** It outranks `HOME` in `resolve_config_dir`, so the ~112 tests that redirect `HOME` themselves would assert on `tmp_path/.mcc/.env` while the application wrote somewhere else; and one directory shared across xdist workers races on `os.replace(".env.tmp" -> ".env")`, which on Windows surfaces as `PermissionError`. Per-test and `tmp_path`-derived is what makes both impossible.

**Matching is by prefix, not equality.** The 6.41.1 guard compared the config *directory* for equality, so everything one level inside it was unguarded — which is precisely the set that got damaged. The protected root is now the whole user profile rather than a list of config directories: this project's subject matter *is* other tools' configuration (`~/.codex`, `~/.claude.json`, `~/.crush`, `~/.gemini`), and an enumeration goes stale the next time a harness is added. The temporary directories and the checkout are carved back out, both captured before any redirect.

**Registry reads succeed; only writes fail.** 720 tests reach the registry indirectly through `urllib.request.getproxies_registry` and `platform`. Failing those would be pure noise, so the fake answers reads from an in-memory store. An opted-in write still lands in that store — nothing in the suite reaches the real registry, marker or not.

**`HermeticityViolation` derives from `BaseException` on purpose.** `HarnessCatalogueFanoutPublisher._publish_one` catches `Exception` around the very write that damaged `~/.fcc` and turns it into a `logger.warning`, so an `AssertionError` guard was swallowed and the test stayed green while the file was written. Deriving from `BaseException` means the guard propagates through every `except Exception` in the application — which is why this PR needs no `src/` change to make the failure stick.

**The guard's own tests run a child pytest.** `tests/contracts/test_hermetic_guard.py` writes a deliberately leaking test, runs it under a child `pytest` with this plugin, and asserts that the child run *fails* and names the artefact. Asserting in-process would only test an interceptor's return value, not its effect on a test report — which is exactly how the old config-dir assertion stayed dead for three releases. The child is handed a stand-in profile under `tmp_path`, so even the tests of the guard touch nothing real.

`tests/README.md` states the contract and the three opt-out markers; `AGENTS.md` and `CONTRIBUTING.md` point at it.
