## Description

Reported: *"for certain providers adding keys and configuring them doesn't work, nothing happens or it says application error, opencode go is an example"* — plus a request to add Azure and check every other provider.

Both symptoms were real and separate, and the sweep found a third.

## 1. OpenCode Go could not be configured at all

`opencode` and `opencode_go` share `OPENCODE_API_KEY`. `_credential_field_specs` emits **one field per credential**, not per provider, so the second one was deduplicated away. What was left on the card, confirmed in a browser before changing anything:

```json
{"provider":"opencode_go","fields":["OPENCODE_GO_PROXY"],"keyManagers":0}
```

One advanced proxy input. No key field, no rotation, nothing to press. It was the only non-local provider in that state.

The dedupe is correct — two inputs bound to one variable is two ways to write one value. The key pool is addressed by *variable*, not by provider, so the borrowing card now renders the same add/remove manager, and the owning card keeps the single rotation select. `provider_config_status` gained `credential_owner_id`, `credential_owner_name` and `credential_shared_with` so each card can say where its key actually lives.

## 2. "Application error" was the exception class name

`test_provider` returned `type(exc).__name__` and threw the message away:

```
before  {"ok":false,"error_type":"ApplicationUnavailableError"}
after   {"ok":false,"error_type":"ApplicationUnavailableError",
         "message":"GEMINI_API_KEY is not set. Add it to your .env file.
                    Get a key at https://aistudio.google.com/apikey"}
```

The sentence that says what to do was already being raised. It now goes through `redact_sensitive_error_text` — the same redactor the logs use — and is rendered on the card.

## 3. DeepSeek could not be proxied

The only remote provider with no `proxy_attr`. Added `DEEPSEEK_PROXY`, plus a contract test so the next provider cannot omit one silently.

Card order also now follows catalog order rather than first-field-seen, which had put OpenCode Go last on the page — nowhere near the account it shares.

## 4. Azure OpenAI

Added against the **v1 API surface**. `default_base_url` is deliberately `None`: the host carries the customer's own resource name, so any default would be wrong for everyone. The missing-URL error names `AZURE_OPENAI_BASE_URL` instead.

`reasoning_effort` is **not** sent. The model is a customer-chosen deployment name, so nothing in the request reveals whether it is a reasoning model — omitting the field costs thinking on one that is, sending it to one that is not 400s every request. `extra_body` passes through. Same trade-off and same resolution as the existing Alibaba profiles.

## Verification

Every provider swept through `/admin/api/providers/{id}/test` on the reporter's own server. The chain works; `kimi` returns a genuine `AuthenticationError` — an expired credential, not a code defect.

Re-checked in a browser after the fix: adding a key **from the OpenCode Go card** stores it and flips both cards to Configured.

```json
{"storedKeys":["sk-ope…3456"],"count":1,
 "zenPill":"Configured","zenMeta":"1 key",
 "goPill":"Configured","goMeta":"1 key"}
```

No `data-key` occurs more than the pre-existing wrapper+input pair, and there are no duplicate element ids — so `changedValues()` is unaffected.

No Azure key was available, so the wire shape was proved against a fake upstream:

```
POST /openai/v1/chat/completions
  authorization: Bearer azure-secret-key
  model: my-gpt-5-deployment
  max_tokens: None
  max_completion_tokens: 256
  reasoning_effort: <absent>
  message roles: ['system', 'user']
streamed text: 'Hello from Azure.'
```

Correct path, Bearer auth, deployment name as `model`, `max_completion_tokens` rather than `max_tokens` (the o-series and gpt-5 reject the older field), no `api-version` parameter, and text round-tripped end to end.
