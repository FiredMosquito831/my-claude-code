## Description

**4.21.2 staged the install correctly but never completed it.** PATCH `4.21.2` → `4.21.3`.

## What was wrong with my own fix

Under `$ErrorActionPreference = 'Stop'`, a native command writing to **stderr** raises a terminating `NativeCommandError` in PowerShell — and `uv` writes its progress there.

The helper died on uv's first `Resolved 79 packages in 367ms` line: before installing anything, and before writing its result file. So the update silently never happened, and the dashboard had nothing to report either.

```
uv.EXE : Resolved 79 packages in 367ms
    + CategoryInfo          : NotSpecified: (...) [], RemoteException
    + FullyQualifiedErrorId : NativeCommandError
```

The native call now runs with `Continue` in effect and is judged by **exit code alone**, restoring `Stop` afterwards for the cmdlets that follow.

## Verified against a real install

Reproduced in an isolated `UV_TOOL_DIR`, so nothing on the host was touched.

**Original bug confirmed** — running `uv tool install --force` from inside the target environment:
```
error: failed to remove directory `...\tools\free-claude-code\Scripts`: Access is denied. (os error 5)
```
and the aftermath — uv had already deleted `site-packages` before failing:
```
PackageNotFoundError: No package metadata was found for free-claude-code
ModuleNotFoundError: No module named 'free_claude_code'
```
That is exactly the reported corruption.

**With this change**, same scenario: stages, exits cleanly with the old version still working, and the helper then installs for real:
```json
{ "ok": true, "exit_code": 0, "message": "Deferred install completed." }
```
`4.21.1 → 4.21.2`, environment intact and `fcc-server --version` working.

## Important limitation

**This cannot help an install still running 4.21.1 or earlier.** The upgrade is performed by the code already loaded, so a user below 4.21.3 who presses the button still runs the old in-place path and still gets the corruption. They must update once from the install script; after that the button is safe.

That's inherent to self-updating and worth stating plainly in the release notes rather than leaving people to discover it.

## Verification

New regression test asserts the native call runs under `Continue` and that success is taken from `$LASTEXITCODE` — the precise trap that broke it. Full suite passes except the 14 failures that also fail on unmodified `main`.

## Residual risks

The captured `output` still contains the `NativeCommandError` text as a non-terminating error record, because `2>&1` merges stderr into the stream. Cosmetic — the install completes and the exit code is authoritative — but it makes the stored log noisier than it needs to be.
