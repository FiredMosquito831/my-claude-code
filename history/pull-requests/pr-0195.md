## Description

## What

Replaces the consecutive-count fallback eject (3 failures / 30s) with a rate-based policy that requires a sustained failure rate over a window before benching, and adds a per-route retry-once toggle for the primary. Both behaviors are configurable; a legacy mode preserves the old consecutive-count shape.

## Why

The old consecutive-count rule was prone to false positives: a model that 2-3 transient 500s in a row got benched for 30s even when it was otherwise healthy, and the chain moved on before the real upstream error reached the client. The rate-based shape (50% over 10 requests, 8-sample floor, 3s bench) absorbs one-off blips on low-traffic models while still tripping fast on sustained failures, matching the mature-router pattern (LiteLLM / Portkey / OpenRouter). The retry-once toggle gives a one-shot chance to recover from genuinely transient errors (timeout, 5xx, 429, upstream) before falling through, which is what the user already had in spirit.

## How

- `core/credential_rotation.py`'s `RouteHealthRegistry` now supports `mode="consecutive" | "rate_based"`. Rate-based uses a rolling window of outcomes (True=success, False=failure); a model benches when failures/window >= rate AND window >= min_samples. The `route_health_registry` factory's cache key expands from a 2-tuple to a 6-tuple of all six knobs, so changing any one starts a fresh registry.
- `RouteExecutor.__init__` gains `retry_first` and `provider_lookup` params. The chain loop retries the primary once on a transient error when `retry_first="retry_once"`, gated on position 0 and `_error_is_retryable()` (transient kinds only). The provider rate-limit skip reads `ProviderRateLimiter.remaining_wait()` via the executor's `provider_lookup` lambda, so a rate-limited provider is skipped at plan-build time without paying the wait.
- `settings.py` adds 5 new `Field` entries (`fallback_behavior`, `fallback_eject_window`, `fallback_eject_failure_rate`, `fallback_eject_min_samples`, `fallback_retry_first`) with the documented defaults. `FALLBACK_EJECT_AFTER_FAILURES` is no longer read by the new eject logic; it remains valid as a deprecated alias for `FALLBACK_EJECT_AFTER_FAILURES` (the consecutive-mode knob) and emits a one-time warning if set.
- `manifest.py` adds 5 new `ConfigFieldSpec` entries (2 selects, 3 numbers) so the new env vars are editable in the admin UI with the right types and descriptions. `FALLBACK_BEHAVIOR` and `FALLBACK_RETRY_FIRST` are selects with `legacy` / `rate_based` and `skip` / `retry_once` options respectively.
- `.env.example` documents the 5 new vars with comments and updates the existing eject block to note that the consecutive settings are legacy-mode only.
- `messages.py` and `responses.py` handlers thread the new params through to the executor, with a `_throttle_lookup` helper that resolves a provider and returns its `throttle_remaining()` (or None if unknown).
- `docs/USAGE.md` updates the fallback settings table with the two new rows (Eject mode, Retry primary once) and one-paragraph explanations of each.

## Residual risks

None known in the shipped code. The retry-once loop behavior is exercised by the `_error_is_retryable` unit test (classification) plus an end-to-end test planned separately; the chain-loop retry path itself is not mocked at the unit level because it requires a streaming provider mock. The provider rate-limit skip is wired but not asserted against a live 429 in this PR; will be covered by a stub-upstream e2e in a follow-up if you want it.
