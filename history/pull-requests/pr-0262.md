## What this is

The documentation release for the 6.22.0 → 6.39.0 arc.

Going in, the assumption was that all four surfaces had fallen behind. They had
not. `README.md`, `docs/USAGE.md` and `ARCHITECTURE.md` were updated release by
release across the arc and are, on inspection, accurate and current — USAGE
already documents the `quota` billing phrases with a measured example, the
Qwen/Pi user-agent collision, `--skip-trust`, `--no-gitignore` and every
harness. **The in-dashboard Guide is what had fallen behind**, and the Guide is
where a user is standing when they need help. So this PR is weighted there, and
it deliberately does not rewrite prose that was already right.

## The drift guard

`tests/contracts/test_docs_reference_drift.py`, with
`tests/contracts/docs_reference_allowlist.txt` for names the docs mention on
purpose. It checks that every environment variable, `mcc-*`/`fcc-*` command,
HTTP route and dashboard page name used in code voice in README, USAGE and the
Guide actually resolves — against `Settings.model_fields`, the websearch
catalogue, the harness/launcher/catalogue modules, `[project.scripts]` **and**
`[project.gui-scripts]`, the route decorators plus the `wire_surfaces`
constants, and `VIEW_GROUPS`.

**What it caught on the first run.**

Two real drifts in `README.md`, both of which would have made a reader's edit
do nothing:

1. "match the API key to `AUTH_TOKEN`" — the setting is
   **`ANTHROPIC_AUTH_TOKEN`**.
2. "`MAX_CONCURRENCY` moved here" — the field is
   **`PROVIDER_MAX_CONCURRENCY`**.

Four blind spots in the guard itself, each fixed rather than excused:

3. `mcc-desktop` reported missing — it lives in `[project.gui-scripts]`, which
   the first version did not read.
4. `mcc-backup`, `fcc-backup`, `mcc-harness` reported as missing launchers —
   they are the `.mcc-backup` file suffix and the `x-mcc-harness` header. The
   command pattern now refuses a match preceded by `.` or `-`.
5. `BRAVE_COUNTRY` and ~20 siblings reported as nonexistent — search settings
   live in the websearch catalogue, not `Settings`. `GOOSE_DISABLE_KEYRING`,
   `KIMI_CODE_HOME` and friends likewise live in the launchers and catalogue
   serialisers, not `config/harnesses.py`.
6. `docs/USAGE.md` "from the **Limits** tab in 5.48.0" flagged as a missing
   page. It is a true sentence about a page since renamed **Limits &
   Resilience**; the guard now only fails *instructions*, not history.

A companion test fails if an allow-list entry becomes real, so the file cannot
quietly rot — it immediately retired seven entries once the scan widened.

Everything else the guard flagged was triaged against source and is a
deliberate mention: other tools' variables (`CLOUD_CODE_URL`,
`GEMINI_CLI_TRUST_WORKSPACE`, `COMMAND_CODE_API_KEY`, `NIM_ENABLE_KV_CACHE_REUSE`,
`UV_TOOL_BIN_DIR`, Qwen's own `DEFAULT_TOKEN_LIMIT`), two settings documented as
**removed** (`CREDENTIAL_CIRCUIT_THRESHOLD`, `MIN_CREDENTIAL_FIRST_TOKEN_SECONDS`),
a variable USAGE names precisely to say it does **not** exist (`KIMI_CODE_HOME`),
and upstream error phrases quoted so a log line can be matched (`LOCKED_OUT`,
`NOT_ENOUGH_BALANCE`).

**Secret scan, and what it caught.** The rule for this release is that no
published screenshot may show an `sk-` prefix *at all*, masked or not, because
a masked label still carries a real key's first and last characters.

Two separate violations were found and fixed, both by looking at the images
rather than trusting the capture:

1. The **previous, committed** `admin-request-detail.png` rendered a key label
   reading `sk-n…oKuN`. It had shipped that way. Its replacement shows
   `user…ubCk`.
2. The **first re-capture** of `admin-key-performance.png` rendered five real
   masked labels — `sk-n…0awp`, `sk-n…oKuN`, `sk-8…Kofx`, `sk-o…7e52`,
   `sk-2…otqn`. Faking the keys in the scratch `.env` was not enough: the
   copied request log still carried `key_label` values captured from real
   traffic. Fixed at the source by rewriting every `sk-…` label in the scratch
   database — five distinct labels, mapped 1:1 across `requests`,
   `request_attempts` and the three rollup tables so the aggregates still add
   up — and re-capturing.

No `sk-` byte sequence appears in any of the 56 PNGs, and the scratch data they
were rendered from now serves zero `sk-` key labels. No screenshot shows a
request or response body; the one body-adjacent panel captured is MCC's own
"REQUEST BODY SENT (NO PROMPT TEXT)", which renders structural fields and
character counts only.

## Residual risks

- **Prose accuracy is still unguarded.** The new test proves every identifier
  resolves; it cannot prove a sentence is true. The four new Guide sections
  were each written against the source (`core/tier_refs.py`,
  `config/harness_tiers.py`, `core/client_fingerprint.py`,
  `providers/anthropic_oauth/entrypoint.py`, `core/failures.py`,
  `config/settings.py`) rather than from release notes.
- **Screenshots carry scratch-instance cosmetics.** The sticky action bar shows
  a `C:\tmp\claude\…` config path in some full-page captures, and one full-page
  shot is very tall. Cosmetic only; no secret and no user content.
- **`admin-update-banner.png` remains pre-6.x.** Documented, not hidden — the
  banner only renders when a newer release exists, which an instance running
  the version under development cannot produce.
- **New Guide image filenames 404 on an already-running server.**
  `_bundled_image_names()` (`api/admin_routes.py:364`) is `@lru_cache(maxsize=1)`,
  so the servable-PNG allowlist is snapshotted once per process. Verified: the
  two newly named images 404'd on the running scratch server and all eight
  returned 200 after a restart. This is a **dev-time gotcha only** — an install
  of this release starts a fresh process — so the cache is deliberately left
  alone in a documentation PR, and is recorded here rather than fixed.
- **The drift guard only reads code voice** — backticks and fenced blocks. A
  variable named in plain prose is not checked, deliberately, because
  instructions are formatted and prose mentions are where the false positives
  live.
- The one PowerShell-installer and websearch baseline failures are unrelated
  and pre-existing; this PR touches neither installer scripts nor websearch.
