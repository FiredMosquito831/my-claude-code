## Description

## What was wrong

Three defects, all pre-existing, made the cache figures unusable.

### 1. The stored input count was our own estimate

The ledger emits `message_start` with a pre-flight estimate — upstream hasn't reported anything yet — and the provider's real `prompt_tokens` arrives later on `message_delta`. `request_capture` read `input_tokens` **only from `message_start`**, so every row kept the guess and discarded the truth.

Paired with a provider-reported cache figure, that produced 608 rows in the live log where cached tokens exceeded the whole input — impossible from a single usage payload:

```
nvidia_nim  595 rows   tokens_in max 460,340   cache_read max 481,536
open_router  13 rows   tokens_in max  79,118   cache_read max  82,176
```

### 2. Cached tokens were counted twice

An OpenAI-family `prompt_tokens` **includes** tokens served from cache. Anthropic's `input_tokens` **excludes** them, expecting the caller to add `cache_read_input_tokens` back for the total. We emitted the first under the second's name.

A real logged row: 267,968-token prompt, 261,120 of it cached, reported as **529,088** — to our analytics and to Claude Code's own context and cost display. The streaming path now subtracts the read count first, so `input + cache_read` reconstructs `prompt_tokens` exactly.

DeepSeek falls out of the same rule: it splits `prompt_tokens` into `prompt_cache_hit_tokens + prompt_cache_miss_tokens`, so reporting the hit count alone is enough — the subtraction lands on the miss count. It had also mapped misses to `cache_creation_input_tokens`, counting that slice again. A miss is a token the cache did not serve, not a token written at a premium, which is what Anthropic's field means.

### 3. Cache writes were never read

OpenRouter reports the write side as `cache_write_tokens` inside `prompt_tokens_details`. Nothing read it, so `cache_write_tokens` is null in **all 39,000 rows** of the live log.

### Dashboard

It had drifted into two conventions at once — older helpers divided by `tokens_in` (OpenAI shape), the per-request figure added cache reads on top (Anthropic shape). Same data, two answers. Everything now uses one definition of total input, shown alongside the uncached part in both the cards and the request detail. The tokens-by-model chart also uses total input, or a heavily cached model reads as idle.

## Verification

18 new tests: the read/write mapping, zero-versus-absent reporting (`0` means no hit, absent means the provider never said), the subtraction against real logged numbers, DeepSeek's hit/miss split, underflow, and the capture path preferring the provider's count while still keeping the estimate when upstream stays silent.

One existing DeepSeek test asserted the bug — `input 30 + read 10 + creation 20` for a **30-token prompt**. It now asserts `20 + 10` and checks the sum reconstructs 30.

```

```

Same 14 failures as the unmodified base (8 need real API keys, 6 are the PowerShell installer tests).

## Residual risks

- **Reported input-token numbers will drop** for every provider that reports caching, in both the dashboard and Claude Code. That is the correction, but historical rows keep the old inflated values, so trends will show a step change at this version.
- **Historical rows keep the estimate** in `tokens_in`. Only new requests store the provider's real count, so old and new rows are not directly comparable.
- The write-side subtraction is deliberately **not** applied: `cached_tokens` is documented as read-from-cache and unambiguously part of `prompt_tokens`, whereas whether `cache_write_tokens` is also included is not documented. Subtracting it could understate input, so writes are reported without being subtracted.
- `cache_control` is still dropped in conversion to the OpenAI wire format. Harmless where caching is automatic, but caching cannot engage for Anthropic, Qwen or Gemini models routed through OpenRouter, which require explicit breakpoints. Separate change, wider blast radius.
