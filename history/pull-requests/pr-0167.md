## Description

Third of four from the fallback audit. Two defects in the same subsystem, both of which made a configured chain unreachable.

## 1. One shared budget, drained by the first model

`FALLBACK_TOTAL_TIMEOUT` was a single pool for the whole request, so a silent primary could spend all of it and every model behind it was skipped for lack of time — `MODEL CHAIN EXHAUSTED: request budget spent before trying …`.

Measured on 21 days of live traffic: **393 requests ran the full 600s budget having produced only scaffolding**, with a chain sitting unused.

Each attempt now gets an equal share of what's left, counting itself and every model still behind it. Unused time flows forward, so a chain of fast failures leaves the last model nearly the whole budget rather than a third of it.

```
before   [ attempt 0 ................ 600s ] X   chain never reached
after    [ attempt 0 .. 200s ] X
         [ attempt 1 .. 200s ] -> answers
```

**The share bounds time-to-first-content only.** Once a stream is producing, the attempt owns the rest of the budget — cutting a working answer to preserve a fallback that may not be working is the wrong trade. #166 is what makes "producing" mean *content* rather than any frame, which is why these two landed in this order.

## 2. A bench that never happened

`RouteHealthRegistry` ejects a model after N consecutive failures. The comment on its own factory warned that *"a registry rebuilt per request would never reach its failure threshold and would eject nothing"* — which is exactly what was happening, because `MessagesHandler` and everything it owns, including the executor and its registry, is constructed **per request** in `routes.py`.

Registries now live at module scope, keyed by the two settings that define ejection, so changing either starts a clean registry rather than inheriting benches made under a different policy. An autouse fixture clears them between tests, since this is process state.

## Correction to #165

That PR reported *"confirmed live: four consecutive failures produced zero `MODEL CHAIN: skipping` lines"*. **That grep read the uvicorn log, which never contains those lines — the probe was broken.** The conclusion was right, as the before/after above now shows properly, but the evidence cited for it was not.

Also worth recording: `MODEL CHAIN: skipping` stays at zero even with ejection working, when *every* model on the route is benched. Ejecting all of them is deliberately bypassed — skipping a bad model is an optimisation, refusing to try anything is an outage.

## Residual risks

- **A single-model route is unaffected** (share == whole budget), but a long chain now gives each model a smaller silence budget than before. A model that legitimately takes 250s to emit its first token, on a 3-model chain with a 600s total, will now be abandoned at 200s where it previously had 600. `FALLBACK_TOTAL_TIMEOUT` is the knob if that bites.
- **Registries are keyed by ejection settings, not by provider generation.** A config reload that changes neither ejection value keeps existing benches — deliberate, since model health is still valid, and bounded by `FALLBACK_EJECT_SECONDS`.
- The `skipped/ejected` rows added in #165 will now actually appear in the request detail.
