## What this adds

`mcc-commandcode` — the seventh coding agent MCC can launch, speaking Anthropic
Messages against `POST /v1/messages`. Registry entry, launcher, catalogue
serialiser, console script, both installers and both uninstallers, `mcc-help`,
the Coding agents card, README / `docs/USAGE.md` / `ARCHITECTURE.md` / Guide /
Get Started — all generated from the one `HarnessSpec`.

## Why it needed a new mechanism

Command Code is the first CLI MCC can serve **only** by writing into a file the
user owns. Read out of the installed binary's own bundle (`command-code`
1.39.0, `dist/cli.mjs`):

```js
function homeDir15(e){return e.env().HOME??e.env().USERPROFILE}
function getUserProvidersConfigPath(e){const t=homeDir15(e.runtime);
  return t?`${t}/.commandcode/providers.json`:void 0}
```

and `loadProvidersConfig` reads that path and nothing else — no `--config`
flag, no config environment variable, no project-local file. Every other
harness has an escape (two env vars for Claude Code, ephemeral `-c` for Codex,
a process-local registration for Pi, `OPENCODE_CONFIG` / `KILO_CONFIG` for the
OpenCode family). This one does not, so PR spec Q14's merge path applies.

`config/harness_config_merge.py` is the only module in the codebase allowed to
write a document MCC did not create, and it makes four guarantees, each pinned
by a test:

| Guarantee | Test |
| --- | --- |
| One key — only `provider.mcc` is written; everything else is carried through | `test_every_key_mcc_did_not_write_survives_byte_for_byte` |
| One backup, taken before the first edit and never refreshed | `test_the_backup_is_the_users_file_not_yesterdays_mcc_output` |
| Idempotent, measured on MCC's key rather than the file's bytes | `test_an_unchanged_refresh_writes_nothing_and_backs_nothing_up`, `test_a_users_own_indentation_is_not_reformatted_on_an_unchanged_refresh` |
| Reversible — `mcc-commandcode --disconnect` | `test_disconnect_removes_only_mccs_key` |

The comparison is on the owned subtree and not on the file's bytes on purpose:
the atomic writer emits one canonical two-space shape, so a byte comparison
would reformat the whole document of anyone who indents differently, on every
single launch.

The background fan-out is stricter still — it keys off the **presence of MCC's
own key**, never the file's existence. A Command Code user who has never run
`mcc-commandcode` already has a `providers.json`, and finding a `provider.mcc`
block appear in it because a provider key rotated on a server they left running
is exactly what the never-write-for-an-unlaunched-harness rule exists to stop
(`test_a_users_own_config_is_not_written_into_until_mcc_is_invited`).

Home is resolved the way the *CLI* resolves it (`HOME` first, `USERPROFILE`
second), not the way `Path.home()` does on Windows. A developer with `HOME` set
— every Git-for-Windows install — would otherwise have MCC merge into one file
while the CLI read another, with a picker that silently never shows MCC's
models as the only symptom.

## The token still never lands on disk

`providers.json` refuses a literal key ("raw secrets don't belong in
providers.json") and expands `"$VAR"` from the process environment instead, so
the merged block carries `"$MCC_COMMANDCODE_API_KEY"` and the launcher sets it
in the child process only. `baseURL` *is* written literally: Command Code
validates that field with `new URL(...)` and substitutes nothing into it. The
serialiser is a pure function of the model records and cannot know this
install's port, so it emits `COMMANDCODE_BASE_URL_SENTINEL` and the caller —
launcher or publisher, both of which know the proxy root — replaces it before
the block reaches disk.

## One change outside the harness layer: the auth header

`require_proxy_auth` read `Authorization: Bearer` only. Command Code's
`authHeadersFor` sends `{"x-api-key": key}` and **nothing else** for a provider
declared `api: "anthropic-messages"`, and its static `headers` map takes no
substitution — so the trick PR #244 used for OpenCode (write an explicit bearer
header) would have put the proxy token into the user's own file. Both headers
are how a real Anthropic Messages client authenticates, so MCC now reads both,
with `Authorization` still winning when both are present and
`anthropic-auth-token` still unread.

## Serialiser mapping

`application/catalogues/commandcode.py`, every field read out of `parseModel` /
`parseProvider` / `parseCost` in Command Code's own bundle:

| Ladder | Command Code |
| --- | --- |
| `context_length` | `contextWindow` |
| `max_output_tokens` | `maxOutput` |
| `reasoning.can_reason` | `reasoning` |
| `reasoning.supported_efforts` | `reasoningEfforts[]`, intersected with `low\|medium\|high\|xhigh\|max` and never extended |
| `input_price` / `output_price` | `cost.input` / `cost.output` (models.dev units, which is where both come from) |
| `default_parameters` | `options` |

Unknown stays unknown: every key is optional, so a `None` omits it and the
omission is recorded under `_mcc_defaulted` — folded **inside** `provider.mcc`,
so removing MCC's key removes every trace of MCC — printed on the launcher's
stderr and counted on the dashboard card. What Command Code does instead of an
absent key (`maxOutput` falls back to `max(1024, contextWindow/2)`) is recorded
in `CLI_DOCUMENTED_DEFAULTS`, read out of its bundle rather than guessed, and
`test_no_serialiser_hard_codes_a_limit` AST-scans the module.

## Harness id vs provider id

The harness is `commandcode_cli`, not `commandcode`. The latter is already an
**upstream gateway provider** in `config/provider_catalog.py`, and both halves
ship in this release: one is where MCC can buy tokens, the other is a CLI MCC
serves. `opencode` and `kilo` are allowed to overlap and the README says why;
Command Code is the one case where the same string would resolve a harness and
a provider in the same release, so the suffix removes the collision
(`test_the_command_code_harness_id_never_collides_with_the_gateway_provider`).
The distinction is written out in the same boxed paragraph PR #244 added, in
both `README.md` and `docs/USAGE.md` §6.

## Residual risks

- **The merge is a merge.** MCC now writes into a file the user owns. The
  guarantees above are tested, but a document with a *non-object* `provider`
  value is replaced rather than merged into (Command Code would reject it
  anyway), and a real content change rewrites the whole document in the atomic
  writer's two-space shape — the backup is the mitigation, and the unchanged
  case no longer touches the file at all.
- **Accepting `x-api-key` widens the accepted auth surface** by one header.
  It still requires the exact configured token, compared with
  `secrets.compare_digest`, and `Authorization` still wins when both are
  present — but it is a behaviour change to a security-relevant path and two
  tests that asserted the old rejection were deliberately rewritten.
- **`contextWindow` and `cost` were `null` in the scratch run**, because a
  custom provider can only reach the cross-provider reference rung and this
  machine had no live models.dev feed. That is the ladder's existing behaviour,
  not the serialiser's — the mapping for those two keys is covered by unit
  test rather than by the live run.
- **`reasoningEfforts` was never populated in the live run** for the same
  reason. Its clamping is covered by four unit tests, not by a real model.
- **Command Code auto-updates itself.** The launcher passes nothing to stop
  that; a user's `command-code` may change schema under a generated block. The
  serialiser was read against 1.39.0 and the version is stated in every
  docstring so the next reader knows what to re-check.
- **`--disconnect` is MCC's flag, not Command Code's.** If a future Command
  Code release adds a flag of that name, the launcher would shadow it. Checked
  against 1.39.0's full `--help`: no collision today.
