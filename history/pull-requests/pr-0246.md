## Description

## What this adds

One harness: **Kimi Code**, Moonshot's `kimi` CLI. Registry id `kimi_code`, binary `kimi` (alias `kimi-cli`), launcher `mcc-kimi`, protocol Anthropic Messages, catalogue format `kimi`, `rtk_agent=False`. Version **6.28.0** (MINOR), `uv lock` in the same commit.

It is a **Python tool on PyPI**, not an npm package: `uv tool install kimi-cli`, or `pipx install kimi-cli`. MCC installs neither — the registry's hint is printed and the launcher exits 127.

## What the spec said, and what the installed package actually does

Everything below was read out of the installed package's own source at **1.50.0**, not out of the vendor's docs. Four of the spec's assumptions do not hold, and each one changed the design.

| The spec / the docs | Kimi Code 1.50.0, in its own source |
| --- | --- |
| `KIMI_CODE_HOME` overrides the config directory | **No such variable.** The string does not occur in the package. `kimi_cli/share.py:get_share_dir()` is `$KIMI_SHARE_DIR` or `~/.kimi`; the config is `<share dir>/config.toml` (`kimi_cli/config.py:get_config_file`). `~/.kimi-code/` is an older layout — this machine still has one, last written 2026-07-20, and it was not touched. |
| `~/.kimi-code/config.toml` | `~/.kimi/config.toml` |
| `[models."…"]` carries `max_output_size` | **No such field.** `LLMModel` is `provider`, `model`, `max_context_size`, `capabilities`, `display_name`. Kimi derives the completion cap itself in `kimi_cli/llm.py:compute_max_completion_tokens`. |
| `capabilities` ← vision / tools / reasoning | `ModelCapability = Literal["image_in", "video_in", "thinking", "always_thinking"]`. **No tools capability, and no per-model reasoning-effort field anywhere in the schema.** |
| `[providers.*]` vs `KIMI_MODEL_*` precedence is contradictory — UNCONFIRMED | **Settled.** `kimi_cli/llm.py:augment_provider_with_env_vars` overrides `base_url`/`api_key`/model fields only for provider types `kimi`, `openai_legacy`, `openai_responses`. An `anthropic` provider — the only type that reaches MCC — falls through its `case _: pass`. For the type MCC uses there is no precedence, because there is no override. |

Also confirmed from source: `create_llm`'s `case "anthropic"` builds `kosong.contrib.chat_provider.anthropic.Anthropic`, which is the **official `anthropic` SDK**, so the header on the wire is `x-api-key` — the one `require_proxy_auth` learned to read in #245.

## Config delivery: `--config-file`, not a merge, not the share dir

Kimi publishes `kimi --config-file PATH`. So MCC writes `~/.fcc/kimi-code-config.toml` and passes that path. **`~/.kimi/config.toml` is never read, written or backed up** — no TOML merge writer was needed at all.

`KIMI_SHARE_DIR` existed and was **deliberately not used**: that directory also holds the user's sessions, OAuth credentials, plugins and background-worker state, so redirecting it to serve one config file would hide every session they have. The flag moves the config alone.

The flag goes **ahead** of the user's arguments, because it binds to Kimi's root Typer callback: `kimi term --config-file X` would be read as an argument to `term`.

**The trade is stated, not hidden** — in `README`, `docs/USAGE.md`, `ARCHITECTURE.md` and on the card: `--config-file` *replaces* the config document rather than overlaying it (`cli/__init__.py` picks one of `--config`, `--config-file`, the default path; `load_config` reads that one file). So an `mcc-kimi` session takes Kimi's own defaults for `theme`, `hooks` and `loop_control`. Sessions, skills and MCP servers come from the share dir and from Kimi's own MCP defaults and are unaffected.

## The one deviation from the brief: the token is in MCC's own file

The brief said to keep the proxy token off disk, and to stop rather than write it if the CLI supports no reference form. **Kimi supports none**, and the evidence is in the table above: `api_key` is a plain `SecretStr` with no `"$VAR"` / `"{env:VAR}"` / `"!command"` form, and the environment overrides do not reach an `anthropic` provider. There is no out-of-band channel; the choice was a literal value or no Kimi Code support.

It writes the literal, into a file **MCC owns** under `~/.fcc`, `chmod 0600` (best-effort; close to a no-op on Windows), in the same directory as the `~/.fcc/.env` that already stores the identical `ANTHROPIC_AUTH_TOKEN` in clear. Nothing is disclosed that was not disclosed already, and **nothing is written into a document the user owns**. With proxy auth off the value is the existing `fcc-no-auth` marker, which is not a credential. Flagged under Residual risks.

## Serialiser

`application/catalogues/kimi.py`, pure `Iterable[CatalogueModel] -> (document, DefaultedFields)`:

| Ladder | Kimi |
| --- | --- |
| `context_length` | `max_context_size` |
| `max_output_tokens` | *(no field — Kimi derives it)*, and **not** recorded as defaulted: a field the CLI does not have is not a field the CLI guessed |
| `supports_vision` | `capabilities: ["image_in"]` |
| `supports_tool_calls` | *(no field)* |
| `reasoning.can_reason` | `capabilities: ["thinking"]` |
| `reasoning.mandatory` | `capabilities: ["always_thinking"]` |
| effort rungs | *(no field — `clamp_efforts` is deliberately not called)* |
| prices, pinned params | *(no fields)* |

`MODEL_ENTRY_PATHS["kimi"] = ("models",)` — a third shape, a mapping at the document root, because that is what `Config.models` is.

**Unknown stays unknown, argued rather than asserted.** `max_context_size` is a *required* int, so an unknown one cannot be omitted — and MCC still refuses to invent a window. It writes `0`, which is Kimi's own marker: `compute_max_completion_tokens` branches on `max_context_size <= 0` and falls back to its own 32,000-token budget. The AST guard covers `kimi.py` (glob) and passes; `test_a_fully_unknown_model_never_produces_a_zero_limit` now derives its zero exemption from each format's declared `CLI_DOCUMENTED_DEFAULTS` rather than from a hard-coded list, so a stray zero anywhere else in any format still fails.

## New: an atomic TOML writer

Kimi's `config.toml` is the first generated catalogue that is not JSON, so `config/harness_toml.py` gives it the same atomic write-if-changed contract `config/atomic_json.py` gives the others, over a deterministic emitter narrow enough to **raise** on anything it cannot encode. `tomllib` reads TOML and does not write it; a silently mis-encoded config is a model picker that is empty for reasons nobody can see. `HarnessCatalogue.document_format` selects the writer in the launcher and in the fan-out publisher; `admin_harness_routes._read_catalogue` selects the parser.

## One bug this found, by launching rather than by reasoning

The first real launch logged `POST /v1/v1/messages 404`. Kimi's client is the **official** Anthropic SDK, whose route is already `/v1/messages`; the OpenCode family and Command Code go through Vercel's `@ai-sdk/anthropic`, which appends a bare `/messages` and does want the `/v1`. So the correct base URL for Kimi is the exact opposite of the correct base URL for them. `kimi_base_url` now strips a trailing `/v1` instead of appending one, and the second commit says why in the place a reader would otherwise "fix" it back.

`max_context_tokens=200000` is the ladder's own number reaching Kimi's status display — Kimi Code publishes **no model-list subcommand**, so this is the only surface it offers for that check.

**Auth**, with `ANTHROPIC_AUTH_TOKEN=scratch-proxy-token` on the scratch proxy:

```

```

## Residual risks

- **The proxy token is on disk in `~/.fcc/kimi-code-config.toml`.** Justified above and documented in three places, but it *is* a second copy of a value that previously lived only in `~/.fcc/.env`. `chmod 0600` is close to a no-op on Windows. If Kimi ever adds a reference form, this should move to it.
- **`--config-file` replaces rather than overlays**, so `theme`, `hooks` and `loop_control` from the user's own `config.toml` do not apply to an `mcc-kimi` session. Documented; there is no overlay mechanism in 1.50.0 to use instead.
- **No default model.** `Config.default_model` is left empty because MCC publishes no "primary" model and picking one would be inventing a preference. A bare `mcc-kimi` therefore needs `-m` or `/model`. The card, `mcc-help` and the docs all say so.
- **Read against 1.50.0 only.** The five source facts this design rests on are version-pinned observations. `augment_provider_with_env_vars`' `case _: pass` in particular could gain an `anthropic` branch in a later release, which would make the token-on-disk trade unnecessary.
- **`~/.kimi-code/` still exists on machines that used an older build.** MCC neither reads nor migrates it; a user who has one and no `~/.kimi` sees Kimi create the new layout on first run, which is Kimi's behaviour and not MCC's.
- **`video_in` is never emitted.** The ladder resolves no video signal, so every model would be an unknown and recording one per model would bury the two capabilities that matter. If a video signal is added upstream this needs revisiting.
- The end-to-end run used a **fake** gateway on 8299 and a custom provider. The inbound half (`POST /v1/messages`, auth, catalogue, config) is real; the upstream half is not a real vendor.
