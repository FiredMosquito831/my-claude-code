## Description

## The remaining blocker (found by the live test)

The rename-then-reinstall handled the tool dir (Windows lets you rename a dir a process runs from), but `uv tool install` then failed copying the **launcher shims** in `~/.local/bin`:
```
failed to copy ...\my-claude-code\Scripts\fcc-claude.exe to ...\.local\bin\fcc-claude.exe:
The process cannot access the file because it is being used by another process. (os error 32)
```
A running launcher holds its own `.exe` shim **without `FILE_SHARE_DELETE`**, so it cannot be overwritten or renamed (verified: 5 attempts, all os error 32). "Running in memory" doesn't bypass this — the lock is on the open handle's share mode.

## Why it's solvable

The shim is **version-agnostic**: its embedded `__main__.py` shebangs to the absolute tool-dir python path and imports the entrypoint. It does NOT embed a version. So a locked shim does not need updating — a new launch of it already resolves the fresh tool dir after the rename+reinstall.

## The fix (community-canonical)

The uv maintainers (uv#14520) and real updaters (Microsoft conductor, hermes-agent) use: **"move the running executables into a temporary directory" before installing.** This PR does exactly that:

1. Rename the tool dir aside (already in place).
2. **Rename every launcher shim aside** (best-effort — the ~17 free ones succeed; the ~3 locked ones held by active windows fail and stay, which is fine).
3. `uv tool install` writes a fresh tool env + fresh shims at the canonical paths.
4. Open windows keep old code; new windows/servers get the new version.
