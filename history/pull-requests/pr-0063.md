## Description

Step 1 of the storage work: **6× more retention for the same disk**, measured by replaying real traffic.

## Why bodies, and why a dictionary

Measured on the reporter's live database — this reframes the problem:

| | per row | share |
| --- | --- | --- |
| Metadata (34 columns) | 332 bytes | 1% |
| Bodies (`input_text`, `output_text`, `thinking_text`, `tool_calls`) | **30.7 KB** | **99%** |

So bodies move to their own table — [SQLite's own guidance](https://sqlite.org/forum/info/3aa7b489ded45a23): a row larger than a page spills into a chain of overflow pages that every table scan walks, and any update rewrites the whole cell.

And they compress far better than they look, because consecutive requests repeat a near-identical system prompt and conversation history — redundancy per-row compression cannot see. On a **held-out** split (train on older rows, test on newer, the direction a live server works in):

```
no dictionary                       2.78x
dictionary trained on  300 rows     8.18x
dictionary trained on 2000 rows     8.22x
trained on the test set itself      8.94x   <- overfitted; ignore
```

More training data does not help, so training once at a few hundred rows is enough. zstd is in the **3.14 standard library** ([PEP 784](https://peps.python.org/pep-0784/)), so this adds no dependency.

## End-to-end, on 4,000 real requests

| | rows | database | per row |
| --- | --- | --- | --- |
| Inline (today) | 4,000 | 168.5 MB | 41.1 KB |
| Compressed | 4,000 | **28.2 MB** | **6.9 KB** |

**6.0× smaller**, ~8× on the text itself with the rest being metadata, indexes and page overhead. `dbstat` confirms the split held: bodies 91.5%, metadata 2.7%, indexes 4%. All 4,000 rows verified present and round-tripping byte-identically. Reading a body costs ~24 µs; writing costs ~4 ms a row on the background writer, off the request path.

## Correctness

- **Blobs record their own `dict_id`**, so retraining can never orphan an older row — tested explicitly across dictionary generations.
- **Nothing migrates.** Rows written before the upgrade keep their inline text and are read from there until retention drains them. Search spans both forms via a SQL function over the compressed payload, which costs no storage where an FTS index would give back much of the saving.
- **`prune` and `clear` own the child table**, or blobs outlive their rows and the file grows forever.
- Corrupt blob degrades to null text instead of raising.
- `REQUEST_LOG_COMPRESS_BODIES=false` restores the old behaviour.

## A data-loss bug found while measuring

The first replay reported a suspiciously good 24×. It was wrong: only **1,050 of 4,000 rows had been written**. `close()` waited a fixed 5 s for the writer, and compressing a deep queue takes longer, so the rest were dropped silently. The wait now scales with the backlog and logs anything genuinely abandoned. Covered by a regression test that replays enough volume to reproduce it.

That bug predates this branch — compression just made it easy to hit.
