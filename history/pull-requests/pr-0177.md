## Description

## The claim that was wrong

`tool_result_trimming.py` said:

> *"The transform is deterministic. The same result trims to the same bytes on every turn, so a conversation prefix stays stable and Anthropic prompt caching keeps hitting after the one turn on which a result first crosses the threshold."*

**Per-request determinism is not cross-request prefix stability.** A result changes on **two** occasions: when it first crosses the threshold, and again when it **ages out of `protect_recent_results`**. The second rewrites bytes in the *middle* of an already-established prefix. The docstring didn't mention it.

## Measured

Real `Settings` → real `MessagesHandler` trim path → real OpenAI-chat provider → loopback to a stub modelling prefix caching. 24 turns.

**Controls first.** Positive control reproduced **91.8% → 94.9%** cache hit (the shape of real traffic, with per-turn prefix match at 100.00% from turn 5 on). Negative control with a deliberately mutated prefix collapsed to **0.0%**. Same sign at cache-block granularity 1, 128 and 1024 — the conclusion is not an artifact of the cache model.

| protect_recent | fresh tokens | cache hit | chars removed |
|---:|---:|---:|---:|
| **0** | **72,897** | **91.9%** | 15,024,408 |
| 1 | 486,278 | 62.5% | 13,781,644 |
| **2 (shipped)** | 521,860 | 69.1% | 12,561,418 |
| 4 | 955,949 | 59.8% | 10,409,077 |
| *trimming off* | *470,648* | *91.8%* | *0* |

**The shipped default costs 10.9% more fresh input tokens than not trimming at all.** Enabling it mid-conversation costs one near-total cache miss — **3.8% hit, 107,797 fresh tokens on a single turn**. Break-even is a baseline hit rate around **90.9%**: below it trimming wins, above it trimming loses. On a log where five providers sit at 84–98%, that is the losing side.

## The cost is the recency guard, not trimming

At `protect_recent=0` the per-turn prefix match is **100.00% on every turn**, the hit rate is unchanged (91.9% vs 91.8%), fresh tokens fall **84.5%**, and it removes *more* content than the default — because a result is then trimmed the moment it appears and never mutates again.

## Why the default is unchanged anyway

`protect_recent=0` means the model never sees the full text of the read it just issued. **That answer-quality cost is unmeasured.** A measured cache win does not justify an unmeasured quality loss, and the feature ships off regardless. Owner's call, asked and answered.

## What this PR actually does

Docs only. The docstring and the `.env.example` block now carry the table and the break-even figure, so nobody enables this without meeting the number first.

**No behaviour change, no default change, no new setting.**

## Residual risks

- The experiment models **OpenAI-compatible automatic prefix caching**. For a provider using Anthropic-style *explicit* `cache_control` breakpoints the result would be **strictly worse** for trimming — a mid-prefix change invalidates breakpoints *and* incurs cache-write cost at 1.25×, which this model prices at zero.
- Token counts use cl100k, not each provider's real tokenizer. Not load-bearing: the conclusion held at three granularities.
- One conversation shape and one file-size cycle. The *frequency* of cache loss depends on how many reads exceed the threshold; its per-event character does not.
- There is a countervailing number: trimming cuts **total** prompt tokens 70.5%, so on a provider that bills cache reads above ~1.26% of a fresh token, trimming is cheaper in money while being more expensive in fresh tokens. Whether that applies depends on cache-read pricing that was not looked up.
