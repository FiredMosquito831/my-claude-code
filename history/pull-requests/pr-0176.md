## Description

## Why this exists

Claude Code re-sends its whole conversation every turn, tool results included. RTK compresses **Bash** output via a PreToolUse hook and **structurally cannot see `Read`, `Grep` or `Glob`** — they never touch a shell. MCC is on the wire and sees all of them. That gap is the entire justification for this feature.

**It is also the most dangerous thing in this arc**, because it changes what the model sees. Everything below follows from that.

## Safety design

**Off by default at every level.** A fresh install behaves exactly as 5.46.0 does: a master switch plus three per-tool rules, all off, with `is_inert()` checked before a single message is walked. Mutating either default to `on` fails three named tests — verified independently:

```
anchor count = 1
CAUGHT   D1 master switch defaults ON
    FAILED test_every_rule_is_off_by_default[Read]
    FAILED test_every_rule_is_off_by_default[Grep]
    FAILED test_every_rule_is_off_by_default[Glob]
```

**Three states per rule: off / observe / on.** Observe does the whole transform and discards the write, so you can watch what a rule would do to your real traffic before letting it act. That is the safety story, not a footnote.

**A trim announces itself.** Silently cutting a `Read` result is worse than spending the tokens — the model believes it saw the whole file and states conclusions about content it never received. The marker names the actor, because the natural inference from a short result is that *the file* is short:

```
[[ my-claude-code TRIMMED THIS TOOL RESULT: 51868 of 59982 characters were removed
from the middle of this Read result (lines 53 to 717). The elision was made by the
my-claude-code proxy, NOT by the Read tool, and NOT by the file being short. You
have NOT seen the removed content: do not describe, summarise, quote, or draw any
conclusion about it. Re-run Read over the omitted range if you need it. ]]
```

Line numbers are **read out of the kept text**, not recomputed — recomputing would be wrong whenever `Read` was called with an `offset`.

**Attribution is conservative by construction.** A `tool_use_id → name` map is built from *every* `tool_use` block, and an id is kept only if exactly one name was ever seen for it and that name is exactly `Read`/`Grep`/`Glob`. Recording all names is what makes an id claimed by both `Read` and `Bash` recognisably **ambiguous** rather than silently resolving to `Read`. Anything unattributable — unmatched id, conflicting id, no id, MCP-namespaced tool, `is_error` result, image block, non-string text — is left byte-for-byte alone.

## The threshold is measured, not invented

Rendering all 970 source and doc files in this repo the way `Read` renders them (`%6d\t` + line):

```
p50 3,012 · p75 8,534 · p90 20,735 · p95 32,954 · p99 93,433 · max 374,612
```

Default = that **p90**: ~89% of whole-file reads are never touched, while the ~11% above it hold **59.6% of all bytes**. Head/tail keeps default to 4,000 each — above the measured p50, so a trimmed result still carries more than a median whole file at each end.

The four numeric settings are in `LIMIT_RANGES`, so the admin form publishes the same bounds it clamps to. The three mode fields **reject** an unknown value rather than clamp — a typo like `aggressive` must be loud in both directions.

## Cost

```
disabled, 561,600 chars of tool results   0.001 ms
observe,  561,600 chars                   0.180 ms
on,       561,600 chars                   0.203 ms
```

Disabled is a single `is_inert()` call before anything is looked at.

## Where this can still hurt — read this before enabling anything

- **A marker is not the content.** The model is told to re-read and may not.
- **The middle of a file is often where the answer is.** Head-and-tail is right for navigability, not relevance.
- **An extra recovery turn can cost more than the trim saved.** Net savings are positive only across a long conversation where a result is re-sent many times. Observe mode measures the gross saving and cannot measure this.
- **Prompt cache invalidation is the most likely way this loses money, and it is NOT measured.** Trimming changes bytes mid-prefix. The transform is deterministic and tested as a fixed point, but the recency guard means a result becomes trimmable as it *ages out* of the protected window, so a change is introduced on the turn that happens. **On providers running at 96–98% cache hit rates this can exceed the saving.**
- **`/v1/messages/count_tokens` is untouched**, so it reports counts for the *untrimmed* request and the client's own context accounting will disagree with what MCC sends.
- **Anthropic server-side context editing is not interlocked.** If both are active, neither one's numbers are attributable.

## Deliberately not done

- **No Bash** — RTK's territory, and overlapping makes savings unattributable.
- No tool inputs, system prompt, or assistant messages.
- No dashboard aggregate; savings live in trace rows until the page lands.
- No token counting inside the layer — characters are exact and free.
