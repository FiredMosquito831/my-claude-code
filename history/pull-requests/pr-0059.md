## Description

## A vision diversion left no trace at all

`_apply_vision_policy` replaces the head of the chain, so a diverted request was logged as `provider=chatgpt_oauth, resolved_model=gpt-5.6-luna, route_attempt=0` — **byte-identical to a route that simply points at that model.** Three releases of vision routing were completely unobservable.

Worse: nothing in the test suite asserted that `route_attempt` or `route_primary_model` ever reached storage. That is why the whole area could be wrong without anything going red.

## The plan now carries its own decision

`RoutedMessagesPlan` gains `diverted_from` and `diversion` (a `RouteDiversion` enum, today only `VISION`), set when an applied policy changes the head of the chain. `RequestCapture` gains `set_plan()`, called once before execution by both the Messages and Responses handlers.

Three columns, migrated on open like every column since 4.22.0:

| column | meaning |
| --- | --- |
| `route_chain` | every model the request was prepared to try, in order |
| `route_diverted_from` | the route's own model, when a policy replaced it |
| `route_diversion` | which policy did it |

`route_chain` is stored **even when the primary answers**: "a chain existed and was not needed" and "there was no chain" are different facts about a route, and only the first one tells you your fallbacks are configured.

`_apply_message_routing_policies` rebuilt the plan positionally, which would have silently dropped both new fields for every safety-classifier request. It uses `dataclasses.replace` now.

## Surfaced in three places

- **Request detail** draws the chain as a path, each hop marked *answered* / *failed* / *not needed* — in words as well as colour — with a sentence naming what the request was diverted from and why.
- **A Vision adapter panel** beside Failover, same `from → to` shape.
- **A `vision` badge** on the model cell, next to the existing fallback badge.

`stats()` gains `diverted` and `diverted_routes` alongside the fallback pair.

## gpt-5.6 is a family name, not a servable id

Only `-luna`, `-sol` and `-terra` exist on this plan; the bare id 404s. 4.41.0 removed an explicit exclusion for it on the grounds that it contradicted the provider's own `>5.4` heuristic — **the heuristic was the thing that was wrong, and the original author knew.** It is back in the disallow set, with the three real variants in the static list.

## Verification

**A real 3-hop chain, live.** Two broken NVIDIA models then `opencode/deepseek-v4-flash-free`:

```
provider         opencode
resolved_model   deepseek-v4-flash-free
route_attempt    2
route_chain      nvidia_nim/deliberately/not-a-real-model,
                 nvidia_nim/also/not-real,
                 opencode/deepseek-v4-flash-free
```

`route_chain[route_attempt] == provider/resolved_model` — the invariant the dashboard highlights on, now guarded by a test.

**A real image request, live.** `nous_portal/tencent/hy3:free` publishes `input_modalities: ["text"]`, so the request diverted:

```
route_diverted_from  nous_portal/tencent/hy3:free
route_diversion      vision
stats(): diverted=1, diverted_routes=[{"diverted_from": "nous_portal/tencent/hy3:free", ...}]
```

The upstream then 400'd, because the adapter model I picked for the test cannot read images either. That is the diversion being *visible*, not the diversion failing — and it is precisely the thing that was impossible to see before.

**The dashboard renderers driven through jsdom** against real row shapes — 20 checks covering hop marking, the untried tail, the diversion note, the empty panel, both badges, and rows written before route tracing existed. One of those checks caught a self-inconsistent fixture of mine rather than a bug, which is the guard doing its job.

## Residual risks

- **No browser.** The chain block's spacing and colour are reasoned about, not seen. jsdom proves structure only.
- Three columns on a 1.7 GB table. They are `ALTER TABLE ... ADD COLUMN`, which SQLite does without rewriting rows, and the migration is covered by a test that drops the columns from a seeded database and reopens it.
- `route_chain` adds roughly the length of the configured chain per row. Rows without a chain store one model ref.
- Historical rows have `route_chain IS NULL` and the panel hides rather than inventing a single-hop chain from `resolved_model` — those rows never recorded whether fallbacks existed.
