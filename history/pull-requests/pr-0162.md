## Description

## A column with no producer, finally wired

The `headers` column has existed since the original request-logging commit in **July** — schema, dataclass field, INSERT, and a JSON decode on every detail read — and has been **NULL on every one of 142,718 rows**, because nothing ever set it.

This supplies the missing producer. The column, field type, INSERT and read path are untouched; they were already correct.

## The filter is positive, and that is the whole design

Headers carry `authorization` and `x-api-key` on **every single request**. So the allow-list lives in a neutral module that is the only place deciding which header values may be persisted:

```
user-agent · x-app · anthropic-version · anthropic-beta · accept · content-type
```

A deny-list was rejected outright: it is wrong the moment a client sends a header nobody anticipated — and discovering what clients actually send is the point of this data.

**Unlisted headers get their NAMES recorded and their values never read**, under a single reserved entry:

```json
"(unlisted)": "authorization,cookie,proxy-authorization,x-api-key"
```

Parentheses are **illegal in an RFC 9110 field name**, so that key cannot collide with a real header. Names are sanitised to the token character set, which structurally strips colons, whitespace and quotes — so value text cannot ride along inside the list *even if the code above it changed*. You can see that a client sent `x-api-key` without the key ever touching the database.

## Where the headers come from

**Explicitly, from the FastAPI endpoints** — they already take `Request` for `get_request_id`, so `request.headers` was one parameter away, threaded down the same chain that already carries the request id. No ContextVar, no middleware change, no new global state. Every new parameter defaults to `None`, so existing call sites and tests compile unchanged. Four files, +33/−6.

## Caps

| Cap | Value | Why |
| --- | --- | --- |
| value chars | 1024 | a real user-agent plus a full `anthropic-beta` list is well under 1 KiB |
| unlisted names | 32 | overflow appends `+N-more`, so a count is never silently lost |
| name chars | 64 | longest real field names are ~30 |
| total chars | 4096 | overflow drops the discretionary `(unlisted)` entry first, then sheds **whole** entries — every surviving value is a faithful copy, not a truncated one |

## Residual risks

**~28 MB across a 142k-row log** at roughly 200 bytes per row. Small against the current 800 MB, but it is new steady-state growth on a table that has had a whole arc spent shrinking it.

**Old rows stay NULL.** No backfill is possible — the headers were never captured.

**The allow-list is a judgement call.** It captures client identity and protocol version, nothing else. If a header turns out to matter later it must be added deliberately, which is the intended cost of a positive list.
