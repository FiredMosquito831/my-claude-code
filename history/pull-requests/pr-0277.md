## Description

## What this is

The Python half of the desktop app. `desktop-shell/` (#272) builds a ~1.5 MB Tauri window; `shell-release.yml` (#273–#276) attaches it to every release. Nothing yet *used* it. This is spec S4 — "pin, fetch and verify (Path A)" — so every existing user gets the app on their next `mcc-desktop` launch, with no installer.

`uv tool install` cannot deliver a compiled binary. `config/rtk.py` has worked around that for a pinned third-party Rust binary across five targets since before 6.40.0, so this is that machinery pointed at our own release rather than anything new.

## Design

| Concern | Decision | Where |
| --- | --- | --- |
| **Pin** | One release tag (`DESKTOP_SHELL_RELEASE_TAG = "v6.43.0"`) plus four in-source SHA-256 digests. Asset names carry no version (Q5), so the pin names *which release's* shell, not a shell version. | `config/desktop_shell.py` |
| **Trust** | Two sources that must agree. The release's `SHA256SUMS-desktop-shell.txt` is downloaded **first** and compared to the in-source digests; a disagreement refuses before the archive is touched. Then the archive itself is verified against the same digest. A source-only pin gives no signal when a release asset is replaced; a file-only check trusts whoever can write to the release. | `_confirm_published_digest` |
| **Extract** | Exactly one executable. Any member with an absolute path, a drive letter or a `..` component, and any symlink or hardlink, refuses the whole archive rather than being skipped — that archive is not the one our workflow produced. | `_extract_zip` / `_extract_tar` |
| **Install** | `os.replace` into `~/.local/bin/MyClaudeCode[.exe]`. On Windows the target may be a *running* executable, so a sharing violation renames it aside (`MyClaudeCode.old-<epoch>.exe`, swept on a later launch) and retries — the installer's shim rename-aside pattern, for the same reason. Overridable with `MCC_DESKTOP_SHELL_DIR`. | `_install_atomically` |
| **Receipt** | `MyClaudeCode.receipt.json` beside the binary names the tag and digest. It is what `ensure_desktop_shell()` checks first, so an unchanged pin costs one JSON read and no network; a moved pin always re-fetches; a binary with no receipt is not trusted. | `read_receipt` / `is_desktop_shell_installed` |
| **Fallback** | Every failure — offline, proxy, unbuilt architecture, read-only home, `DESKTOP_SHELL=off` — is a `logger.warning` naming the reason and a `None` from `ShellWindow.create()`. The launch is never blocked. | `ShellWindow.create` |
| **Opt out** | `DESKTOP_SHELL=off`, or `--window app-mode`. | docs |

## The window chain, per OS

`auto` walks `shell → app-mode → pywebview → browser`. An **explicit** `--window` still degrades through `PROVIDER_CHAIN` only, so a pin never lands on the shell as a consolation prize.

| OS | `auto` picks | Tray icon | Notes |
| --- | --- | --- | --- |
| Windows | shell, else app-mode (Edge/Chrome/Brave) | **Python (pystray)**; the shell's is off | Unsigned: SmartScreen may warn; Smart App Control may hard-block, and `DESKTOP_SHELL=off` + app-mode is the answer there |
| macOS | shell, else app-mode | **Python (pystray)**; the shell's is off | Unsigned too, but a file `urllib` downloaded is **not** quarantined — quarantine is applied by browsers — so Path A never meets Gatekeeper's download gate. This is exactly why there is no `.dmg` (Q7) |
| Linux (display + shell) | shell | **the shell's** — there is no Python tray, `pystray` is win32/darwin only | `headless_refusal_reason()` lifts here; needs webkit2gtk-4.1 (Ubuntu 22.04+/Debian 12+/Fedora 40+) |
| Linux (display, no shell) | app-mode | none | Still refuses, and the message now names *why* the app was unavailable |
| Linux/WSL (no display) | — | — | Still refuses. The shell cannot conjure a display |

**One tray icon (risk "two tray icons", decision Q2).** `mcc-desktop` sets `MCC_DESKTOP_SHELL_TRAY=0|1` in the shell child's environment; `desktop_status()` honours it, so the `--print-status` the shell reads reports `tray_enabled: false` **to that child alone**, while a human running `--print-status` still sees the persisted preference. A new `shell_tray` key says the same thing unambiguously for a future shell that reads it explicitly. Recommendation implemented: **Python keeps the icon this release**; the shell's tray takes over later and the Python tray retires.

**Raising the window is a second launch, not a doorbell.** The shell holds `tauri-plugin-single-instance`, whose second-instance callback focuses the open window and exits — the same trick `AppModeWindow` plays with a Chromium profile. Ringing `desktop.activate` from Python instead would feed the tray's *own* activation watcher, which polls that file, and the two would raise each other in a loop. So the tray's *Open Admin* → `show_window()` → `focus()` → one more launch → one window.

## The double-window bug S2 found

`mcc-server` opens the dashboard in the default browser when it becomes healthy (`Settings.open_admin_browser`, on by default, `MCC_OPEN_BROWSER`). `DesktopController._spawn_server` passed no environment, so **one `mcc-desktop` launch produced two dashboards**: the app-mode window and a browser tab. That predates the shell and is much worse with it.

Fixed at the one place the desktop app starts a server: the child now inherits `os.environ` plus `MCC_OPEN_BROWSER=0`. The desktop state is the authority on windows here, not the server's default — including `window_open=False`, where the user asked for no window and a browser tab is still a window. `test_the_variable_is_the_one_settings_actually_reads` reads the name off `Settings.model_fields` so a typo cannot silently restore the bug.

## Other changes

- `cli/tool_paths.py` — `uv tool dir --bin` then `PATH` (Q5), extracted from the controller so the shell child is handed the *installed* `mcc-desktop` in `MCC_SHELL_DESKTOP_COMMAND`. A GUI launch does not inherit a login shell's `PATH`.
- `--print-status` gains `shell_tray`, `shell_binary`, `shell_release_tag`, `shell_ready`. Additive; `schema` stays `1`.
- `WindowOnlyHost` — a tray-shaped stand-in so `launch_desktop` runs on Linux, where there is no `pystray` to import and the shell draws the icon.
- `tests/conftest.py` grows an autouse `_isolate_desktop_shell`: the fetcher is real, and without this any test that built an `auto` window downloaded 1.5 MB from GitHub. Install dir under `tmp_path`, shell off by default.
- ADR 0003, superseding ADR 0002's *Alternatives rejected* on the compiled-window question, and recording that "`uv tool install` cannot deliver a compiled binary" was already false when it was written.

## Not proven here

A real macOS or Linux launch. First-run SmartScreen/Gatekeeper behaviour — reputation is per file hash and accrues from real downloads, so a locally fetched binary says nothing. The pin stays at **v6.43.0**: the digests for v6.44.0 cannot exist until `shell-release.yml` has built it, so moving the pin is a follow-up PATCH, and `docs/RELEASE-CHECKLIST.md` §8 is now the written procedure for it.
