## Description

## What was wrong

Every fallback on the routing page has ↑/↓ arrows. The primary model above them did not — so the arrows stopped exactly at the entry that actually serves the traffic. Promoting a fallback meant retyping two fields by hand and hoping they agreed.

A route *is* one ordered path: `MODEL` plus the comma-joined chain beside it. It just happens to be stored as two settings.

## What this does

The rail reorders as the single list it looks like. The primary gets the same two buttons every row under it has, wired to the `ModelChainEditor` next to it — that class already owns the ordering rules, so nothing new decides what "up" means.

All six rails share one builder (`appendRouteRail`): the four tier overrides, the default route, and the vision adapter. A rail that reorders differently from the one beside it reads as a bug, not as a distinction.

```
1  nvidia_nim/nemotron-3   [↑ off] [↓ on ]        <- primary (MODEL)
2  groq/llama-3.3-70b      [↑ on ] [↓ on ] [x]
3  cerebras/qwen-3-480b    [↑ on ] [↓ off] [x]

press ↓ on row 1 ->

1  groq/llama-3.3-70b      <- MODEL
2  nvidia_nim/nemotron-3   <- MODEL_FALLBACKS[0]
3  cerebras/qwen-3-480b
```

## Why it is a swap and never an insert

No button press can leave a route without a primary. Both halves of that matter and they fail differently:

- **An empty `MODEL` fails validation**, so the server refuses to start. Loud, recoverable by hand.
- **An empty tier override is quiet and worse.** Routing reads a route's own fallbacks only when that route has its own primary, so clearing `MODEL_OPUS` silently orphans `MODEL_OPUS_FALLBACKS` — the tier drops back to the root model *and* the root chain, with nothing in the log to say the chain next to it stopped being consulted.

So demotion is gated on there being a fallback to swap with, and re-gates live as the primary is typed in. **Promotion deliberately is not gated that way**: promoting into an unset override is exactly how a route stops inheriting the default, and there the row is removed rather than left holding an empty value.

That orphan behaviour is now **pinned in `test_routing_chains.py`** rather than left as a comment, so nobody "fixes" the button gate into a bug.

## Residual risks

- **The "Custom route" / "Inherits default" chip does not update live.** It is computed at render, so filling a previously unset override by promotion leaves the chip reading "Inherits default" until the next load. Pre-existing — typing in the field does the same — and deliberately out of scope.
- **Not seen in a real browser.** jsdom has no layout engine, so the button alignment is reasoned from the DOM (a hidden copy of the remove button holds the column) and from the CSS, not measured. That is the one thing worth a second pass.
- Unrelated, found while measuring and **not touched**: `BRAVE_EXTRA_SNIPPETS` is a boolean whose payload `value` is `""` while its checkbox reads `false`, so it sits in `changedValues()` on a freshly loaded page — on `main` too. It rides along on the next unrelated Apply.
