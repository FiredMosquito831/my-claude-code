## Description

## The bug you reported

v5.3.0 hardcoded `ENABLE_WEB_SERVER_TOOLS=true` on the `mcc-claude` / `fcc-claude` child env. That was **half a switch**:

- The client told Claude Code to offer `web_search`/`web_fetch` tools.
- But the **proxy's own** `enable_web_server_tools` (which gates local execution) was still **off by default** in the settings model.

So via `mcc-claude` a web_search call hit *"local web server tools are disabled (ENABLE_WEB_SERVER_TOOLS=false)"* — the exact error you saw. Your manual `settings.json` path worked because that environment's `.env` had the var on.

## The fix

1. **`launch()` now passes `settings.enable_web_server_tools`** into the env builder, which sets `ENABLE_WEB_SERVER_TOOLS=true` on the session **only when the proxy will actually execute the tools**. The dashboard **Web Tools** toggle now controls both layers with one switch.
2. **Settings default flipped `false` → `true`.** The code default contradicted `.env.example`, the dashboard manifest, and `mcc-init`'s env template (all `true`). The `false` was only a wrong fallback when no `.env` existed.

## Verification

- `build_minimal_claude_proxy_env` omits the var by default, adds exactly it when `enable_web_server_tools=True`.
- New launcher test: setting off → no env var, only proxy vars changed.
- Two default-contract tests updated to expect `true`; the "rejects forced server tool when disabled" API test now explicitly disables the setting.
- 368 tests pass; the 2 `test_web_server_tools.py` failures are pre-existing on unmodified `fork/main` (confirmed earlier).
- ruff format/check and ty clean.
