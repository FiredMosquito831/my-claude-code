## Description

## What was wrong

Every catalogue MCC generated for a coding agent contained the same invented numbers for every model.

`cli/launchers/codex_model_catalog.py:151-183` built **the same dict for every model**, varying only `slug`, `display_name` and `priority`:

```python
"context_window": 200000,
"max_context_window": 200000,
"effective_context_window_percent": 95,
"experimental_supported_tools": [],
"input_modalities": ["text"],
```

and applied the same fixed four reasoning rungs to everything (`SUPPORTED_REASONING_LEVELS`, `:16-27`). Pi's bundled extension had the same shape of problem one level down — `pi_extension.ts:6-7` hard-coded `DEFAULT_CONTEXT_WINDOW = 128000` and `DEFAULT_MAX_TOKENS = 16384`, and `:65` emitted `cost: {input: 0, output: 0, cacheRead: 0, cacheWrite: 0}` for every model.

Neither could have done better. Both were built from `GET /v1/models`, whose `ModelResponse` (`api/model_catalog.py:32-39`) carries an id, a display name, a timestamp and **no capability fields at all**. The launchers run in their own processes with no `RequestRuntimePort`, so the resolution ladder — which already resolves per-model context length, output ceiling, vision, tool support and effort vocabulary, and renders all of it on the Models page — was unreachable from the code that had to publish it.

Measured on a scratch server with four models whose real limits differ by two orders of magnitude:

```
BEFORE custom_acme/openai/gpt-5-nano                    context_window= 200000 rungs= ['low','medium','high','xhigh'] modalities= ['text']
BEFORE custom_acme/google/gemini-3.1-flash-tts-preview  context_window= 200000 rungs= ['low','medium','high','xhigh'] modalities= ['text']
BEFORE custom_acme/anthropic/claude-opus-4-7            context_window= 200000 rungs= ['low','medium','high','xhigh'] modalities= ['text']
```

An 8k model and a 1M model were advertised to Codex's picker as identical.

Separately, three ids — `claude`, `codex`, `pi` — were written out by hand in `pyproject.toml`, both installers (three lists each), `mcc-help`, `RtkState`, `_ALL_AGENTS`, the tray menu and the dashboard. Eight places to forget one.

## What this changes

**One registry.** `config/harnesses.py` declares each coding-agent CLI once: id, display name, binary, protocol, install hint (with a Windows override), console-script commands, catalogue format and filename, passthrough subcommands, binary-identity markers, and RTK capability with its enable/uninstall arguments. `mcc-help`, the RTK state file's keys, the RTK CLI, the tray menu, the dashboard and both installers' three lists are generated from or checked against it. It holds data only and lives under `config/` because `api/` may not import `cli/` (`tests/contracts/test_import_boundaries.py`); `cli/harnesses/registry.py` binds a spec to launcher behaviour and is the one place the never-install rule is enforced.

**One neutral record.** `application/catalogue_model.py` builds a `CatalogueModel` per routable model from the ladder — context length, output ceiling, vision, tool support (derived from the gateway's published `supported_parameters`, never assumed), the full `ModelReasoningCapability`, prices, and per-field provenance. Every capability field is `X | None`, and `None` means *no source stated this*. It reuses `build_models_list_response`'s visibility filter, ref enumeration and two-variant projection, so a model cannot appear in one and not the other.

**Thin per-CLI serialisers.** `application/catalogues/{codex,pi}.py`, one pure function each. Effort vocabularies are *intersected* with the CLI's own rungs, never extended. Where a CLI's schema makes a field optional, an unknown omits the key; where it requires a value, the serialiser uses **that CLI's** documented default from a module-level `CLI_DOCUMENTED_DEFAULTS` and records the substitution — visible in the file's `_mcc_defaulted` block, on the launcher's stderr, and on the dashboard card.

**A capability-bearing route.** `GET /admin/api/catalogue-models` (loopback-only) returns the neutral records plus each harness's already-serialised document. `mcc-codex` and the Pi extension fetch that instead of `/v1/models` and write the bytes they are handed, so the launch-time path and the background refresh cannot drift. `/v1/models` is untouched — it is an Anthropic-compatible payload Claude Code itself consumes.

**A fan-out publisher.** `runtime/harness_catalogues.py` replaces `CodexModelCatalogPublisher` on the identical `cache_model_infos` → `_publish_model_catalog` trigger. Because it builds from the ladder, **a capability change with no change to the model list now re-emits every catalogue**, which was not true before. It refreshes only files that already exist; the one exception is `~/.fcc/codex-model-catalog.json`, created at startup because the Codex App reads it from a persistent `config.toml` and has no launcher.

## What to expect

Codex's `/model` picker now shows each model's real window and only the reasoning rungs that model actually publishes. Same server, same four models, after:

**Models whose real window is under 200000 will stop claiming 200000 in Codex's picker.** That is the fix, not a regression.

## Deviations from the spec

- **Serialisers live in `application/catalogues/`, not `cli/harnesses/catalogues/`.** `cli` may only import `config` and `core`, so a serialiser there could not have imported `CatalogueModel`. The AST guard scans the package where they actually are.
- **`config/harnesses.py`, not `cli/harnesses/registry.py`, holds the specs.** `api` may not import `cli`, and the dashboard has to list harnesses. `cli/harnesses/registry.py` exists and holds the launcher-side binding.
- **The route returns each CLI's serialised document as well as the neutral records.** Same reason: a launcher cannot import the serialisers, so the server runs them and the launcher writes bytes. This also removes any chance of the two paths drifting.
- **`ensure_exists` still creates `~/.fcc/codex-model-catalog.json` at startup**, behind an explicit `created_at_startup` flag on the spec. Q8's rule is otherwise implemented as written; the exception exists because the Codex *App* reads that file from a persistent `config.toml` and has no launcher, so the documented behaviour would have regressed.
- **`write_json_document_atomically` now writes bytes instead of text.** `Path.write_text` translates `\n` to CRLF on Windows, which would have made the same document differ from itself across platforms and defeated the content-compare skip. This also preserves the old Codex writer's LF output.

## Residual risks

- **The Pi extension's runtime path is unverified.** `projectMccCatalogueModels` is exercised only by the route's own contents and the Python-side unit tests; no Pi session was launched, because the only `pi` on this machine's `PATH` is an unrelated npm package that the identity probe correctly rejects. The extension keeps a `/v1/models` fallback with a `console.warn`, so an older proxy or a route failure degrades to the previous behaviour rather than failing to load.
- **`supports_parallel_tool_calls` is recorded as defaulted for most models**, because only OpenRouter-dialect gateways publish `supported_parameters`. It is honest but noisy in the `_mcc_defaulted` block.
- **Codex's tolerance of the extra `_mcc_defaulted` top-level key is verified against 0.151.0 only.** If a future Codex rejects unknown keys, the block has to move out of the file (the dashboard and stderr copies are independent of it).
- **The tray menu's Codex entry is now labelled "Codex CLI"** rather than "Codex", because labels come from the registry's display names. Cosmetic and deliberate.
- **`test_toggle_survives_concurrent_external_write` flaked once under full-suite load.** It passes in isolation and on three consecutive directory runs; the pystray teardown warning it sits beside is pre-existing.
