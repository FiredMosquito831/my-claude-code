## Description

## What was broken

The dashboard showed the client's numbers and called them MCC's.

`api/request_capture.py::extract_request_params(request: MessagesRequest)` reads `max_tokens` and `len(tools)` off the **inbound** Anthropic request. `build_capture` calls it once at construction, and `api/handlers/messages.py` calls `build_capture` *before* `resolve_messages_plan` and before any budget work. `application/routing.py::apply_output_token_budget` then writes the resolved value onto a `model_copy` of the routed attempt — which the capture, holding the original object, never sees.

Net effect on the live server: the dashboard says `64000` while `16384` goes to `nvidia_nim/thinkingmachines/inkling` (model limit) and `42992` goes to `opencode/hy3-free` (context headroom). A night was spent debugging a request builder that was working correctly.

Related: `reasoning_adaptation` records what gating **decided**, never whether the encoder acted on it. `commandcode` uses the `NoReasoning` encoder, whose `encode()` body is a bare `return`, so ~23,000 requests logged plausible reasoning adaptations for a policy that was then discarded. That column misled four separate investigations into thinking gating had regressed.

## Mechanism

`core/wire_capture.py` follows the pattern `credential_attribution` and `install_recovery_trace` already use: the API boundary installs one mutable `WireTrace` in a ContextVar for the life of a request, and the provider writes into it from the commit boundary. A mutable slot stays visible through any number of context copies; a ContextVar holding an immutable value would not.

**The commit boundary** is the last statement before the body crosses into the SDK:

- `openai_chat/provider.py::_create_stream`, immediately after `create_body = self._prepare_create_body(body)`. This is downstream of base conversion, common policy, provider postprocessors, the v5.66.0 override postprocessor, tool-name encoding, `_apply_learned_output_cap` and every create-level retry rewrite — and it is the only `chat.completions.create` call site in the tree, so it covers the whole OpenAI-compatible family. `stream=True` is passed to the SDK as a keyword, so it is recorded alongside the dict rather than read back out of it.
- `anthropic_messages/provider.py` and `chatgpt_oauth/provider.py`, before their `_send_stream_request`. Headers are not recorded — they carry the bearer token.

Last write wins per attempt index, so a body rewritten by a create-level retry is recorded as the body that produced the outcome, not the one that was rejected.

## What it does

**1. Per-attempt wire parameters.** `request_attempts.params` — NULL on all 65,214 rows, written only by recovery events — now also carries the resolved facts under a `wire` key: model, `max_tokens` (reading `max_completion_tokens` / `max_output_tokens` too), tool count, the sampling parameters actually present, and the reasoning fields actually emitted, whatever dialect spells them. The flat recovery counters keep their existing shape beside it.

**2. The full request body, minus the input text.** New `request_attempts.wire_body` holds the whole JSON body with message, system and prompt *content* replaced by structure — roles, block types, character counts, image media types — and everything else intact: model, `max_tokens`, sampling, tools (names + parameter names, prose dropped), stream flags, `extra_body`, reasoning fields. Text is not duplicated; it is already captured behind the Prompt pane, and doubling it would inflate a 163 MB database.

Redaction runs on the whole tree in two passes, because either alone leaks: by key **name** (`api_key`, `apiKey`, `nvidia-api-key`, `authorization`, `cookie`, exact `token`/`key`/`auth`), and by value **shape** through the project's existing `redact_sensitive_error_text` (`sk-`, `nvapi-`, `gsk_`, `hf_`, `AIza`, `Bearer x`). `max_tokens` is deliberately not caught by the exact-`token` rule.

Capped at 8,000 characters; over that the row stores an explicit `{_truncated, _original_chars, _limit, _preview}` envelope and the dashboard says so.

**3. Was reasoning actually emitted.** New `request_attempts.reasoning_emitted` (INTEGER, nullable) records whether the outbound body carried a reasoning instruction at all — checking `reasoning`, `reasoning_effort`, `thinking`, `enable_thinking`, `include_reasoning`, `chat_template_kwargs` and their `extra_body` equivalents, and treating `{"type": "disabled"}` / `"none"` / `False` as not emitted. NULL stays "not measured" and never reads as "no reasoning sent".

## Storage

`CREATE TABLE IF NOT EXISTS` is a no-op on the user's existing database, so both new columns go through `_ATTEMPT_ADDED_COLUMNS` and a generalized `_ensure_attempt_columns`, each ALTER guarded by its own `PRAGMA table_info` and tolerant of a lost migration race. The existing single-column `_ensure_attempt_params_column` is folded into it. No index is added — these columns are read by request id, which the primary key already serves, so there is no stale-index-definition hazard. The INSERT column list and its placeholder string are generated from one tuple so they cannot drift, and the row width is checked against it at write time (§48: a 43-column INSERT with 42 markers once broke every write). The migration is two `ALTER TABLE ... ADD COLUMN` statements, which SQLite performs in constant time regardless of row count, on the writer thread.

## Dashboard

A collapsed **Request body sent (no prompt text)** panel in the existing request-detail modal, beside the route-attempts panel it follows in structure and CSS. Each attempt shows its model, `max_tokens`, tool count and a reasoning-sent badge; opening it shows the pretty-printed body. A **Reasoning sent** row now sits directly under **Reasoning adaptation** in the meta list, so intent and action are readable side by side.

## Residual risks

- **Not every provider has an instrumented commit boundary.** `vertex/client.py` calls `execute_with_retry` with a request object rather than a body dict and is not instrumented, so Vertex attempts record NULL. That reads correctly as "not measured" rather than as a wrong value, but it is a coverage gap.
- **Redaction cannot cover a credential that is neither auth-named nor recognizably shaped.** A provider that accepted an opaque token under, say, `client_ref` would store it. Redaction is conservative — key-name matching is substring-based and errs toward over-redacting — but it is pattern-based, not proof.
- **The 8,000-character cap is a judgement call.** A very large tool schema set can truncate; the truncation is explicit in the stored row and in the UI, so it fails loudly rather than silently.
- **`request_attempts.params` now carries two kinds of fact** (recovery counters, flat; wire parameters, nested under `wire`). Any future reader of that column must know both shapes. Putting the wire summary in a separate column was the alternative; nesting keeps the existing shape untouched for existing readers.

## Deliberately not done

Nothing about what is *sent* changed. The cross-provider matcher, the commandcode encoder, the NIM retry strip, the context-headroom floor and credential health are untouched and remain separately queued.
