| For | Ubuntu 22.04+, Debian 12+ | Fedora 40+, Arch, openSUSE, or no root at all |

packaging format to keep green.

## Why the `.deb` is hand-rolled, and not `cargo tauri build --bundles deb`

Tauri's bundler can build a `.deb` and can pin `depends`. Four reasons it was
still the wrong tool *here*, all of them about this repository rather than
about the bundler:

1. it needs `tauri-cli`, which `shell-release.yml` deliberately does not
   compile on four runners — the workflow's own comment documents
   `cargo build --release --features custom-protocol` as the exact equivalent
   of `cargo tauri build --no-bundle`;
2. it names the file `<productName>_<version>_<arch>.deb`, i.e.
   `My Claude Code_0.1.0_amd64.deb` — a space *and* a version, both of which
   decision Q5 forbids in an asset name, so it would be renamed anyway;
3. its version comes from `tauri.conf.json` (`0.1.0`), not from the release
   tag. Two places to bump is one too many;
4. it appends its own entries to `depends`, which is the single field this
   package exists to control.

`installer/linux/build-deb.sh` is one `dpkg-deb --build`, with the reasoning
written at the top of the file.

## The package layout

| Path | Mode |
| --- | --- |
| `/usr/bin/MyClaudeCode` | 0755 |
| `/usr/share/applications/my-claude-code-desktop.desktop` | 0644 |
| `/usr/share/icons/hicolor/{512x512,256x256,128x128,32x32}/apps/my-claude-code-desktop.png` | 0644 |
| `/usr/share/doc/my-claude-code-desktop/copyright` | 0644 |
| `/usr/share/doc/my-claude-code-desktop/changelog.gz` | 0644 |
| `DEBIAN/{control,postinst,postrm,md5sums}` | 0644 / 0755 / 0755 / 0644 |

```
Package: my-claude-code-desktop
Version: <tag without the v>          Architecture: amd64
Section: utils                        Priority: optional
Depends: libwebkit2gtk-4.1-0, libgtk-3-0t64 | libgtk-3-0, libayatana-appindicator3-1 | libappindicator3-1
```

Every alternative is load-bearing: Ubuntu 24.04 and Debian 13 renamed
`libgtk-3-0` → `libgtk-3-0t64` and `libappindicator3-1` →
`libayatana-appindicator3-1` in the 64-bit `time_t` transition, so naming one
spelling makes the package uninstallable on half the supported distributions.

**Deliberate deviation from the spec:** §3.2 had the tray library as a
`Recommends`. It is a `Depends` here, because `apt install
--no-install-recommends` is common and a tray that silently is not there is the
failure this whole arc exists to remove.

**No 48x48 icon.** There is no 48px source in the tree, and resampling one in
CI would put a slightly different image in every build. hicolor scales between
the four sizes that do exist.

`postinst`/`postrm` do exactly one thing each — `update-desktop-database` and
`gtk-update-icon-cache`, both `|| true` — so a machine without
`desktop-file-utils` still configures the package. A contract test asserts
nothing else in either script mutates anything.

## The tarball's `install-desktop.sh`

POSIX `sh`, per-user, no root, reversible. Writes `~/.local/bin/MyClaudeCode`,
a receipt beside it, `~/.local/share/applications/my-claude-code-desktop.desktop`
and icons under `~/.local/share/icons/hicolor`; `--uninstall` removes exactly
those and is idempotent.

The entry's `Exec=` is rewritten to the **absolute** installed path: a GUI
launcher does not inherit a login shell's `PATH`, and on Debian/Ubuntu
`~/.profile` only adds `~/.local/bin` when the directory already existed at
login — so a relative `Exec=` works from a terminal and fails from the menu.

**Delivery path A is unaffected.** `config/desktop_shell.py` never required a
single-member archive; it requires *exactly one member whose basename is
`MyClaudeCode`*, and no links. The extra members are simply not candidates.
That is now pinned from both sides — a new Python test extracts from an archive
carrying the installer, the entry and two icons (binary listed **last**, so
order cannot matter), and `smoke/linux-tarball.sh` asserts the archive's shape.
A second new test pins the other direction: two members named `MyClaudeCode`
are still refused.

`DESKTOP_SHELL_RELEASE_TAG` is untouched (still `v6.43.0`). It moves in a
follow-up, once a release carrying the new tarball exists to pin against.

## The `.desktop` reconciliation — one icon, not two

The server's `install.sh --desktop` writes
`~/.local/share/applications/my-claude-code.desktop` (`Name=My Claude Code`,
`Exec=mcc-desktop`). The app writes `my-claude-code-desktop.desktop`
(`Name=My Claude Code (desktop app)`, `Exec=MyClaudeCode`). **The app's entry
wins**, because it is the better launcher: it opens the dashboard in its own
window and installs My Claude Code itself if it is missing.

Three separations, because each alone is escapable:

1. **different filenames**, so neither installer overwrites the other's file;
2. **different `Name=`**, so a machine that ends up with both shows which is
   which rather than two identical tiles;
3. **different icon names** — a per-user icon *shadows* a system one of the
   same name, so sharing `my-claude-code` would mean the `.deb`'s icon silently
   never rendering.

And the common case never gets there: `create_linux_desktop_entry`
(`scripts/install.sh`) now checks `/usr/share/applications` and
`~/.local/share/applications` for the app's entry and steps aside if it finds
one, printing why. It steps aside *only* — removing either entry belongs to
`scripts/uninstall.sh`.

`StartupWMClass=MyClaudeCode` matches the shipped binary's basename, which is
what GTK derives `WM_CLASS` from, so the window groups with its launcher icon.
A contract test pins it against `[[bin]] name` in the shell's `Cargo.toml`.

## Uninstall parity — three lanes

| Command | Removes |
| --- | --- |
| `sudo apt remove my-claude-code-desktop` | everything the `.deb` put under `/usr`. |
| `./install-desktop.sh --uninstall` | everything the tarball put under `~/.local`. |
| `scripts/uninstall.sh` | My Claude Code itself **and** the per-user desktop app: `~/.local/bin/MyClaudeCode`, the path-A receipt, the tarball receipt, the entry and all four icons. |

**`uninstall.sh` closes a gap that predates this PR:** delivery path A has been
putting `MyClaudeCode` and `MyClaudeCode.receipt.json` in `~/.local/bin` since
S4, and nothing removed them — `uv tool uninstall` cannot see them and purging
`~/.mcc` does not reach them.

**It never removes the `.deb`.** It detects the package with `dpkg-query` and
prints `sudo apt remove my-claude-code-desktop`, because deleting a dpkg-owned
file behind dpkg's back leaves the package database claiming a file that is
gone. A contract test asserts `uninstall.sh` names no `/usr` path and runs no
`dpkg -r`.

`tests/contracts/test_uninstaller_parity.py` gains **six ARTEFACTS rows** (each
naming a creator, with markers, and the remover that must match) and **eleven
new assertions** covering the package layout, the `Depends` alternatives, the
maintainer scripts, the two-entry collision, the `install.sh` step-aside, and
the tarball installer's write/remove symmetry.

## CI: the proof, not a claim

New steps on the `ubuntu-22.04` leg, in order — the same
snapshot/install/assert/uninstall/diff shape as
`smoke/windows-installer.ps1`, with `dpkg -i` under
`DEBIAN_FRONTEND=noninteractive` playing the part `/VERYSILENT` plays there:

1. **Package (tar, Linux)** — stage the binary, `install-desktop.sh`, the entry
   and four icons; members named explicitly and in a fixed order;
2. **Build the .deb** — version from the release tag, `0.0.0` for a
   non-version dispatch (matching the Windows installer's rule);
3. **lintian (advisory)** — full output in the log, four suppressions for tags
   true by design. It does **not** gate: lintian ships new tags with new
   versions, and a policy checker turning a working package red should not
   block a release when the real gate is the next two steps;
4. **Smoke the .deb** — control fields including both renamed alternatives;
   `dpkg -i` with no prompt; **every** path `dpkg-deb --contents` declares
   present on disk **with its declared mode**; `desktop-file-validate`;
   `StartupWMClass` against the installed binary's name; then
   `smoke/linux.sh` re-run against the **installed** `/usr/bin/MyClaudeCode`
   under Xvfb (foreign-status stub → conflict page, starts nothing), so a
   package that ships a correct file list but a broken program still fails;
   then `dpkg -r`, every path asserted gone, and a **filesystem diff that must
   be empty**;
5. **Smoke the tarball** — archive shape (exactly one `MyClaudeCode`, no links,
   no unsafe paths), extract, `install-desktop.sh` against a **scratch `HOME`**,
   assert binary/entry/receipt/icons and that `Exec=` is absolute, nothing
   written outside `~/.local`, `--uninstall`, run it twice, and a file-level
   diff that must be empty.

`icon-theme.cache` and `mimeinfo.cache` are excluded from both diffs, and the
exclusion is the interesting part: the maintainer scripts regenerate them
*after* removal, so on a machine that had neither they legitimately exist
afterwards. They are derived entirely from the entries around them, which is
what the diff actually checks.

The checksum file goes from five lines to six, with a `grep` asserting the
`.deb` is in it; the shape regex already allowed the name. Seven shell assets
on the release page now.

## Not verified, and worth saying

- **No human has seen this on a Linux desktop.** The applications-menu tile,
  the icon at each size and the tray in a real status area are all unproven —
  a virtual framebuffer has no StatusNotifier host.
- **Fedora is untested.** `install-desktop.sh` writes only to XDG paths and
  runs under `dash`, but no Fedora machine ran it.
- `StartupWMClass` is asserted against the binary name, not against a live
  `WM_CLASS`. A mismatch would only detach the window from its launcher icon in
  the taskbar; installing `xdotool` in CI to prove it was judged not worth the
  flake.
- `lintian` is advisory, on purpose (see above).
