## The escaping fix, and what only a browser found

Escaping raw HTML is right for safety and wrong for *display*: the README opens with a centred `<div>` banner that would render as five lines of `&lt;div&gt;`. Lines that are nothing but tags are dropped **before** parsing, so nothing is ever promoted from text to markup.

Two cases that rule got wrong, **both found by opening the page, not by a test**:

- **Image captions are `<p><em>…</em></p>`** — tags wrapped around prose, so *not* HTML-only. They survived, got escaped, and put literal markup above the fold. A line that both opens with a tag and closes with one is now unwrapped to its text.
- **`<https://example.com>` is an autolink, not a tag** — but it opens with a letter, so the HTML-only rule matched the whole line and the URL vanished with no trace. No curated doc has one today; a future one would have lost content silently.

Verified through the live API after the fix: **0 literal `&lt;p&gt;`, 0 literal `&lt;em&gt;`**, caption text present.

## Why this one ships visible

The standing rule that new things ship off is about features that **change behaviour**. This is read-only local content — no network, no writes — and it was explicitly requested. Gating documentation behind a switch nobody turns on is a page nobody reads.

## Deliberately not done

- **Relative images are not bundled.** The six docs reference only remote badges, so nothing local breaks; a future doc with a screenshot would point at GitHub rather than ship 3.1 MB of PNGs.
- Internal docs (RELEASE-CHECKLIST, BRAND, AGENT_SPEC_*, ADRs, `research/`, `smoke/README`) excluded, with a wheel test asserting they stay out.

## Residual risks

- `_strip_html_only_lines` is the one place document content is altered, and it is line-based: a future doc placing a lone semantic tag on its own line could lose it. Fences are protected; nothing else is.
- `_bundle_dir()`'s checkout fallback is what makes the wheel test load-bearing. Delete that test and a broken install goes quiet again.
