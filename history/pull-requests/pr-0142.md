## Description

## What this changes

`mcc-desktop` was a tray icon whose only way to show the dashboard was `webbrowser.open()` — a tab dropped into whatever browser is default, among every other tab already open. There was no window belonging to this product. Now there is.

## Why not "just embed a webview"

That phrase is three answers wearing one name — WebView2 on Windows, WKWebView on macOS, WebKitGTK on Linux — and they are not interchangeable. `pywebview` on Linux additionally needs apt-installed system packages that our wheel-only `uv tool install` cannot provide.

An audit of `admin.js` settled the ordering. Three things the dashboard depends on break inside an embedded webview:

| Feature | Call site | Embedded |
| --- | --- | --- |
| **Both OAuth logins** | `admin.js:2302`, `:2364` — `window.open(_blank)` | silently no-ops → **login unreachable** |
| Analytics export | `admin.js:7649` — `<a download>` | disabled by default, engine-specific |
| Copy buttons | `admin.js:3601`, `:7906` — `navigator.clipboard` | varies by engine |

The first is disqualifying on its own. A window where login silently does nothing is worse than a browser tab.

So the window is a **seam with an ordered chain** — app-mode → pywebview → browser tab — preferring Chromium app-mode because it *is* a browser and therefore has zero functional regressions. The preference persists as `window` in `desktop.json` and is pinnable via `mcc-desktop --window`; an unavailable pin degrades with a warning rather than raising (Part IV §3: a guardrail must degrade, not become an outage).

**pywebview ships unavailable by default** — it is not a dependency and cannot guarantee the download / external-link settings it would need — so the delivered chain is app-mode → tab. ADR 0002 records the full reasoning, including Tauri's rejection on three independent grounds (Rust toolchain + 3-OS matrix + second release pipeline; `uv tool install` cannot deliver a binary; and it's *still* WebKitGTK on Linux, so it doesn't even buy uniformity).

## The six lifecycle cases

- **A second launch focuses the running instance** instead of opening another browser tab. Backed by a file rather than a socket, deliberately: binding a listener raises the Windows firewall prompt on first run, and a port can be taken by the very program the app is already fighting over. The lock owner clears the file before watching, so a signal from a dead instance is discarded.
- **The port probe distinguishes three states, not two.** `preflight_proxy`'s "no" covered both *nothing is listening* and *something that is not us is*; spawning into the second produced a bind failure with no explanation. The message now names the process and pid holding the port.
- **A dead server notifies only after three consecutive failed probes**, so a self-update replacing its own process is not read as death.
- **Headless refuses with the working alternative**, not the missing display — and quotes the **configured** admin URL. A message naming `:8082` on a machine serving `:9000` sends the reader somewhere empty.
- **Closing the window no longer stops the server.** `minimize_to_tray` has been persisted and echoed by `--status` since 5.19.0 and consumed by nothing; it works for the first time here.
- **The tray reads `tray_icon_bytes()`.** v5.26.0 shipped that tighter render for exactly this surface and nothing called it.

One fix outside the obvious blast radius: `admin_routes`' `update_desktop` reconstructs `DesktopState` from the payload, so without carrying `window` through, **every unrelated dashboard save silently reset the preference** (§97 — a writer that regenerates a file owns everything in it).

## Residual risks

- **No live window was displayed.** App-mode command construction is unit-tested, not executed against a real browser; the macOS and Linux binary searches are monkeypatched only.
- The `PywebviewWindow` provider is entirely unexercised code. That is precisely why it ships gated off rather than merely untested.
- `focus()` for app-mode is best effort — it re-invokes the app command and relies on Chromium's profile process to raise the existing window.
- The dashboard cannot yet *set* `window`; the endpoint preserves it but exposes no control. That is PR 3.
