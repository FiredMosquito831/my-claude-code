## Description

## What was broken

A malformed request benched the credential that happened to carry it.

On the user's live NVIDIA NIM pool (3 keys, `round_robin`) every request was
returning `400 Validation: top_p is immutable for this model and must be 0.95`
(a separate defect, fixed in 5.61.0). Each of those 400s escalated one key's
cooldown ladder and, three in a row, tripped its circuit breaker — until the
pool had nothing left to serve:

```
per-key:  nvap…L_9v  ok=6 err=13     nvap…bUuX  ok=5 err=14     nvap…epz9  ok=8 err=15
plus 61 requests with key_label = NULL, ALL errors, almost all moonshotai/kimi-k3:
  "All API keys for this provider are in cooldown. Retry..."
```

Round-robin selection itself was measured healthy (19/16/16 on this pool,
48%/48% on a 2-key Nous pool) and is untouched. The pool was not mis-selecting;
it had been emptied.

**This is long-standing, not a regression.** v5.56.0 did the same thing:
`health.failure_count += 1` then an `else` branch benching on any non-auth,
non-429 status, with no gate on whether rotation was warranted.

## Mechanism

`providers/credential_rotation.py::report_failure` computed two things and
honoured only one:

```python
rotate = error_justifies_rotation(error)        # correctly False for a 400
failure_class = _failure_class(_status_from_error(error))
async with self._lock:
    self._engine.fail(index, failure_class)     # UNCONDITIONAL
```

`error_justifies_rotation` already states the right idea in its own docstring —
*"A plain 400 invalid request will fail identically with every key, so it is not
rotated"* — and `_failure_class` maps anything that is not 401/403/429 onto
`"transient"`, i.e. the generic cooldown ladder plus circuit-breaker progress.

## What this does

Adds an explicit predicate `failure_implicates_credential(error)` and gates the
health update on it. When a failure does not implicate the credential,
`report_failure` returns the (unchanged) `rotate` value without touching health
at all.

**Why a separate predicate rather than reusing `error_justifies_rotation`:** the
two questions differ at the edges. "Would another key help?" is False for
several errors that genuinely *do* implicate this one — an unclassified
transport-layer exception, for instance. Gating health on the rotation
predicate would have silently stopped counting those, weakening exactly the
failover that multi-key rotation exists for (WORKING-NOTES §12 records that
missing the auth path once made multi-key failover silently dead). The new
predicate is deliberately narrow: it returns False only for failures positively
identified as request-shaped, so anything unrecognized keeps counting as before.

**Request-shaped** = an `ExecutionFailure` whose kind is `INVALID_REQUEST` or
`CONTEXT_LENGTH` (a body the model rejects, or one past its context window —
both properties of the request, identical on every key), or a bare 400 from any
error shape that classification does not read as a throttle or an upstream fault
wearing a 400.

| Failure class | Health before | Health now |
| --- | --- | --- |
| 400 invalid_request | cooldown ladder + circuit progress | **untouched** |
| CONTEXT_LENGTH (400) | cooldown ladder + circuit progress | **untouched** |
| 401 / 403 auth | LOCKED_OUT, 5min→1h→24h ladder | unchanged |
| 429 rate limit | cooldown tier escalates, **no** circuit progress | unchanged |
| upstream 5xx / overload | cooldown ladder, breaker at 3 | unchanged |
| timeout / transport | cooldown ladder, breaker at 3 | unchanged |
| unrecognized exception | cooldown ladder, breaker at 3 | unchanged |

`rotate` is still `error_justifies_rotation(error)` in every case, so a 400 still
means "do not try another key" and the chain falls through exactly as it did.

**Observability:** a skipped failure logs at DEBUG naming the credential index,
the status and the model, so "why didn't this key get benched" is answerable.
`RotatingProvider` passes `request.model` through. No new DB column.

## Websearch path — checked, does not share the defect

`websearch/base.py::_search_with_rotation` re-raises
`WebSearchInvalidRequestError` and `WebSearchConfigError` **before** any
`report_failure` call, so request-shaped faults never reach the shared
`core/credential_rotation.py` engine on that side. No change needed. The
existing `test_invalid_request_raises_without_rotating` was strengthened to
assert the whole health record (state, `failures`, `consecutive_failures`)
rather than only `failures == 0`, so a future refactor that routes it through
the pool fails loudly.

## Residual risks

- **A 400 that really is the key's fault now goes uncounted.** Some gateways
  return 400 for a disabled or over-quota key instead of 401/403. The predicate
  mitigates this only for 400s that classification reads as a throttle or
  upstream fault; a vendor that invents a novel 400 for "your key is dead" would
  no longer bench it. Rotation behaviour is unaffected (`rotate` is unchanged),
  so such a request still fails the same way — it just no longer cools the key
  down. Judged the right trade: the opposite error empties a healthy pool.
- **Skipped failures are invisible in the dashboard.** Deliberate — no new DB
  column was added, so the only record is the DEBUG log line. `request_log`
  still records the request and its error as it always did; only per-credential
  health is left alone.
- **`RotatingProvider` is the only caller passing `model`.** Any future caller
  of `report_failure` that omits it gets `model=unknown` in the log line, not an
  error.
