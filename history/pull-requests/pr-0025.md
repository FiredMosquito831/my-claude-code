## Description

**Reported:** press Update on Windows, stop the server with Ctrl+C, nothing happens — the version never changes. PATCH `4.21.4` → `4.21.5`.

## Root cause: process id reuse

The helper waited with `Get-Process -Id $parent`. Windows recycles pids quickly, and that is exactly what happened — measured live:

```
PID 38012 IS VISIBLE -> python started 08/01/2026 01:47:00
```

The server was stopped at 01:46; an unrelated `python` inherited pid 38012 a minute later. The helper kept waiting on a stranger and never installed. Nondeterministic by nature — which is why this flow sometimes worked and sometimes silently did nothing.

## Fix

The parent is now pinned by **id + creation time**, read via `GetProcessTimes` and compared against `Process.StartTime.ToFileTimeUtc()`. Same id, different start time ⇒ our parent is gone.

Two details that matter:

- When the creation time can't be read, the check falls back to the id alone and treats *unknown* as **still alive**. Assuming "gone" would install underneath a running server — the exact corruption this whole path exists to prevent.
- `GetProcessTimes` needs explicit `argtypes` or the handle is truncated on 64-bit and silently returns 0. That bit me during development; it's now asserted by a test comparing the value against PowerShell's.

## Also: retry the install

Handle release isn't instantaneous — an antivirus scan or a slow shutdown can hold the environment briefly. Losing that race left uv having already deleted part of the environment, which is a broken install.

The install now retries with backoff (0/5/10/20/30s). A later attempt succeeds because the earlier one removed whatever it could, so a transient lock degrades into a *slower* update rather than a broken one. Attempt count is recorded in the result.

## Verification

**Pid reuse, reproduced deliberately** — an unrelated process occupying the pid:

New tests cover the start-time pinning, the fallback direction, the retry loop, and the `GetProcessTimes`/PowerShell agreement (skipped off Windows). Script rendering is Linux-safe so CI still exercises it.

## Residual risks

The retry ladder tops out at ~65s of waiting. Something holding the environment longer than that (a stuck process, aggressive endpoint protection) still fails — but it now fails *reporting* a failure with the attempt count, rather than appearing to do nothing.
