## Description

Adds two harnesses to the registry — **Qwen Code** (`mcc-qwen`) and **Crush** (`mcc-crush`) — both speaking Anthropic Messages, both served from a document MCC owns, neither editing a file the user wrote. Version **6.29.0** (MINOR).

This is PR 7 of `specs/PR-CLI-HARNESSES-SPEC.md` §D4, on top of #241 / #244 / #245 / #246.

## The spec was wrong about both CLIs, in MCC's favour

Every claim below was read out of the installed CLI's own source and then confirmed on the wire.

### Qwen Code 0.15.11 (`@qwen-code/qwen-code`, installed here)

| What the spec said | What `cli.js` actually does |
| --- | --- |
| Env-only: `ANTHROPIC_BASE_URL` + `ANTHROPIC_API_KEY` + `ANTHROPIC_MODEL` | It works, but `getAuthTypeFromEnv()` is the **lowest**-precedence source. `loadCliConfig` resolves `argv.authType \|\| settings.security.auth.selectedType \|\| getAuthTypeFromEnv()`, so an auth type a user once picked in Qwen's UI silently outranks MCC's environment. |
| `security.auth.selectedType = "anthropic"` "may require a settings write" | It does not. `--auth-type` is a real yargs option whose `choices` include `anthropic`, and `argv.authType` outranks both the settings key and the environment. **MCC writes no `security.auth` key at all.** |
| "Qwen carries little metadata"; one `ANTHROPIC_MODEL` | `settings.modelProviders.anthropic` is an **array** of `{id, name, baseUrl, envKey, generationConfig}` records — the exact shape Qwen's own provider wizard emits (`getPreviewJson`) — with `generationConfig.contextWindowSize`, `.modalities` and `.reasoning`. So MCC publishes the whole ladder, not one model. |

There is no `QWEN_CODE_HOME`; `QWEN_DIR` is the hard-coded `.qwen`. But `getSystemSettingsPath()` reads **`QWEN_CODE_SYSTEM_SETTINGS_PATH`**, so MCC writes `~/.fcc/qwen-code-settings.json` and names it in the launched process only.

### Crush v0.92.0 (`@charmland/crush`, **not** installed here — installed into a scratch npm prefix)

| What the spec said | What v0.92.0 actually does |
| --- | --- |
| `crushrc` (Bash) is current; `crush.json` deprecated | Both load and merge (`crushrc` wins in the same directory). `crush schema` — undocumented, not in `--help` — still publishes the full JSON schema. |
| `crush provider add --type anthropic --base-url …` | There is no `provider` command in `--help`. |
| No override, so MCC must merge into the user's file | **`CRUSH_GLOBAL_CONFIG`** replaces the global config *directory*. MCC owns `~/.fcc/crush/` and writes one `crush.json`. No merge, no backup file. |
| `--discover-models` is "buggy for openai-compat" | Worse than buggy for us: measured, `discover_models: true` issues **`GET <base_url>/models`** — not `/v1/models`. Against a root base URL it finds nothing, and the `/v1` base URL that would reach it breaks `POST /v1/messages`. MCC sets `discover_models: false`. |

## Config mechanism, with evidence

| | Qwen Code | Crush |
| --- | --- | --- |
| Delivery | `file` via `QWEN_CODE_SYSTEM_SETTINGS_PATH` | `file` via `CRUSH_GLOBAL_CONFIG` |
| MCC's document | `~/.fcc/qwen-code-settings.json` | `~/.fcc/crush/crush.json` |
| Variable value | the file path | the file's **parent directory** (Crush looks for `crush.json` inside) |
| User file touched | none (`~/.qwen/settings.json` never read for MCC, never written, never backed up) | none (`~/.config/crush` never read for a provider, never written, never backed up) |
| Auth type selected by | `--auth-type anthropic` on argv | `providers.mcc.type: "anthropic"` |
| Secret reference | `"envKey": "MCC_QWEN_API_KEY"` → `process.env[envKey]` at request time | `"api_key": "$MCC_CRUSH_API_KEY"` (Crush's own schema example is `"$OPENAI_API_KEY"`) |
| Auth header on the wire | `Authorization: Bearer …` (`useProxyIdentity` for a non-`*.anthropic.com` host) | `x-api-key: …` |
| SDK | `@anthropic-ai/sdk` | `anthropic-sdk-go` |
| Base URL shape | **proxy root, no `/v1`** | **proxy root, no `/v1`** |

Both SDKs append `/v1/messages` themselves — the opposite of Command Code's `@ai-sdk/anthropic`, which is the PR 6 bug this PR was told to watch for. `config/harness_base_url.py` is the new shared resolver: a serialiser writes a sentinel, `with_root_base_url` replaces it with `root_base_url(proxy_root_url)` (which strips a caller-supplied `/v1`) in both the launcher and the fan-out publisher, selected by the new `HarnessCatalogue.base_url_sentinel` field.

`~/.qwen/settings.json` was read **only** for schema discovery and nothing in it was written; no secret was read out of it.

## Serialiser mappings

`application/catalogues/qwen.py` → `modelProviders.anthropic[]`:

| Ladder | Qwen |
| --- | --- |
| `context_length` | `generationConfig.contextWindowSize` (omitted + recorded when unknown) |
| `supports_vision is True` | `generationConfig.modalities.image` (omitted for known-absent **and** unknown; only unknown is recorded, because Qwen's modalities are opt-in booleans) |
| `reasoning.can_reason is False` | `generationConfig.reasoning: false` |
| `reasoning.supported_efforts` | `generationConfig.reasoning.effort` = the **strongest** supported rung, clamped to `low/medium/high` (Qwen has no per-model effort *list*, only the one a session starts at; `resolveEffectiveEffort` clamps `max`→`high` for every non-DeepSeek host anyway) |
| known-to-reason, no knob | `reasoning: {}` |
| `max_output_tokens`, tool support, prices, pinned params | *Qwen has no field* |

`application/catalogues/crush.py` → `providers.mcc.models[]`:

| Ladder | Crush |
| --- | --- |
| `context_length` | `context_window` **(required)** |
| `max_output_tokens` | `default_max_tokens` **(required)** |
| `supports_vision` | `supports_attachments` **(required)** |
| `input_price` / `output_price` | `cost_per_1m_in` / `cost_per_1m_out` **(required)**; the two cache rates are always Crush's, recorded |
| `reasoning.can_reason` | `can_reason` **(required)** |
| `reasoning.supported_efforts` | `reasoning_levels[]` clamped to `low/medium/high`, plus `default_reasoning_effort` (middle rung, or the strongest when `mandatory`) |
| `default_parameters` | `options`, with anything outside Crush's five named knobs going to `options.provider_options` |

`_mcc_defaulted` at the document root is tolerated by both CLIs at runtime — verified by loading a document carrying it and seeing the models still listed, despite Crush's schema saying `additionalProperties: false` (advisory for editors; the Go decoder ignores unknown keys).

**Crush's `CLI_DOCUMENTED_DEFAULTS` were measured, not assumed.** With `default_max_tokens: 0` the agent request goes out with `max_tokens: 4096` while the title request goes out with `0`, so MCC writes **4096**. `context_window: 0` loads, runs, and reaches no request body, so it is written as is.

## Residual risks

- **Qwen's `modelProviders` REPLACE semantics.** Confirmed from the schema (`mergeStrategy: "replace"`) and from the merge order (`systemDefaults → user → workspace → system`), but not exercised against a user who has their own `modelProviders` entries. The consequence is scoped to the session and stated on the card and in both docs.
- **`CRUSH_GLOBAL_CONFIG` moves the whole global layer.** A user with global LSP/MCP/permission config in `~/.config/crush` gets Crush's defaults for those during an `mcc-crush` session. `crushrc` was not tested as MCC's own document — MCC writes only `crush.json`, and if a user has a project-local `crushrc` in the working directory it wins over MCC's global `crush.json` for any key it sets, including `providers`. Not tested.
- **Crush is not installed on this machine.** Everything above was run from a scratch npm prefix (`@charmland/crush@0.92.0`, Go binary v0.92.0). A different platform's binary was not exercised.
- **Qwen rewrites a settings document whose `$version` is stale.** Observed once during investigation, before `"$version": 4` was added to the generated document. If Qwen bumps `SETTINGS_VERSION` past 4, MCC's file will be migrated in place on first read until `QWEN_SETTINGS_VERSION` is updated; the write is idempotent afterwards, so the failure mode is a rewritten-then-restored file rather than a broken one.
- **Crush's `models.small` is the same model as `models.large`.** MCC states no ordering beyond `GET /v1/models`', and picking a "small" model by name-matching would be a guess. A user who wants a cheaper summariser has to set it in a project-local config.
- **`~/AppData/Local/crush` now exists on this machine** — Crush's own *data* directory, created by the direct schema/wire probes during investigation (before `LOCALAPPDATA` was redirected for the `mcc-crush` runs). It holds Crush's cached provider catalogue and an empty project list; no MCC file and no credential. Nothing under `~/.config/crush`, `~/.qwen` or `~/.fcc` was written.
- The 8082 install was not restarted or updated; the fan-out behaviour there only changes on its next upgrade.
