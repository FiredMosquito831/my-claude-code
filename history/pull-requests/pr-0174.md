## Description

## What was wrong

RTK measures every command it wraps and **we threw all of it away.** The dashboard showed three checkboxes and an "installed `<version>`" line; the question a user actually has — *"is this saving me anything?"* — was unanswerable.

## What this adds

`read_rtk_gain()` runs `rtk gain --all --format json` and exposes it at `GET /admin/api/rtk/gain`, loopback-guarded and on a worker thread (a subprocess call on the event loop would starve every other request).

**The schema was established from upstream source, not docs prose** — `src/analytics/gain.rs` (`ExportData`/`ExportSummary`) plus `src/core/tracking.rs`. That mattered: the published configuration page says **nothing** about `gain` output, and there is **no per-command breakdown in the JSON export** — that exists only in the human renderer. A docs-driven implementation would have shipped a parser for fields that don't exist.

```
summary  { total_commands, total_input, total_output, total_saved,
           avg_savings_pct, total_time_ms, avg_time_ms }
daily / weekly / monthly
         [ {date, commands, input_tokens, output_tokens,
            saved_tokens, savings_pct, total_time_ms} ]
```

**Failure is a first-class result, never an exception and never a 500:**

```
{available, reason, detail, binary_path, summary, periods, raw}
reason ∈ {not_installed, run_failed, empty_output,
          invalid_json, unexpected_schema, timeout}
```

A number RTK did not report stays `None`, **never `0`** — "RTK saved you nothing" and "we could not read RTK's numbers" are different facts and the page must distinguish them. Booleans are explicitly rejected where a number is expected, since `bool` is an `int` in Python and would otherwise sail through.

## Version pin: 0.44.2 → 0.45.0, plus drift detection

A hand-maintained mirror of somebody else's release **will** go stale — this repo already lost four releases to that exact shape once.

- `rtk_status()` now reports `pinned_version`, `installed_version`, `version_matches_pin` at **zero network cost**, so a drifted local binary is visible on the dashboard.
- A network-gated test (`MCC_NETWORK_TESTS=1`) asserts the pin still equals the latest upstream tag *and* that all five digests still match. It goes red the day 0.46.0 ships.
- "Latest upstream" is deliberately **not** in the status payload — that would put a GitHub round trip on every dashboard load and break offline use.

**How the digests were obtained, and why they're trustworthy.** From the GitHub API's server-computed per-asset `digest`, cross-checked against the release's own `checksums.txt`. The method was then *validated* by running it against `v0.44.2` and reproducing all five currently-pinned digests byte for byte:

```
rtk-x86_64-unknown-linux-musl.tar.gz   d94cc2a3…7e33   ← matches current pin
rtk-aarch64-unknown-linux-gnu.tar.gz   5cd3f7fa…e8a9   ← matches current pin
rtk-x86_64-apple-darwin.tar.gz         636f808d…20d81  ← matches current pin
rtk-aarch64-apple-darwin.tar.gz        b7c2218e…f6393  ← matches current pin
rtk-x86_64-pc-windows-msvc.zip         3a1e114e…9d47c  ← matches current pin
```

So the new pins come from the same pipeline as the trusted ones. **Auto-download of anything newer than the pinned, digest-verified release was not added and must not be.**

## RTK telemetry: the docs are wrong, in the user's favour

I briefed this agent that `[telemetry] enabled` defaults to **true** and that we might be silently opting users in. **That was wrong**, and it proved so from source rather than building on my premise:

```rust
#[derive(Debug, Default, Serialize, Deserialize)]
pub struct TelemetryConfig {
    pub enabled: bool,              // Rust Default for bool = false
    pub consent_given: Option<bool>,
```

plus an upstream `test_telemetry_default_disabled`. `maybe_ping()` additionally requires a compiled-in URL, an unset `RTK_TELEMETRY_DISABLED`, **and** `consent_given == Some(true)` — written only by an interactive `y/N` prompt that short-circuits when `RTK_TELEMETRY_DISABLED` is set, which `_run_rtk` always sets. **Enabling RTK through MCC cannot opt anyone in.**

No status field was added, because the truth doesn't support one. A source-cited comment records why.

## Also: direct tests for `count_text_tokens`

Published in 5.42.0 and until now asserted only *indirectly* through the handlers that call it. Two properties no handler test can see:

- **The empty string costs 0.** `get_token_count` bills per-message framing and scores `""` at 4; a handler reports this as `usage.output_tokens`, so the framing would be invented tokens.
- **`disallowed_special=()` is load-bearing on the request path.** tiktoken's default **raises** on text containing a special-token literal, and `count_text_tokens` runs on every request via `get_token_count` — so a prompt quoting `<|endoftext|>` would crash rather than count.

```
CAUGHT  M1 special tokens rejected again (tiktoken default raises)
CAUGHT  M2 count_text_tokens gains per-message framing
CAUGHT  M3 _DISALLOWED_SPECIAL repopulated with a real special token
survivors: none
```

## Deliberately not done

- **No dashboard UI** — the page PR owns that. This is the data and the API.
- **No `config.toml` writes.** Reading is in scope; editing is a later PR.
- **No CLI surface** on `mcc-rtk`; nothing needed one yet.

## Residual risks

- **The 0.45.0 binary is unexercised.** Installing RTK was out of scope, so the digest pin guarantees *integrity*, not CLI compatibility. `--all --format json` is present in the master source that **is** 0.45.0. Reverting the six version literals leaves all drift detection working if that trade is unwanted.
- **`tests/config/test_rtk.py` still hand-copies the `_RELEASES` table**, so a future bump must touch two places. Pre-existing design, not widened here.
- `raw` is returned unbounded, though bounded in practice by `history_days` (~90 + ~13 + ~4 rows). The UI PR can drop it.
