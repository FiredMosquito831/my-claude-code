## Description

## What was wrong

`req_cf646eed209a4c7f95064201d4a2a339`, 14:10:35Z, read read-only from the request log:

| Fact | Value |
|---|---|
| Tries on attempt 0 (`nvidia_nim/moonshotai/kimi-k3`) | **15** (3 keys × 5) |
| Statuses | `429`×14, `502`×1 |
| Time actually inside the provider | **6.1 s** |
| Time asleep in MCC's own backoff | **51.0 s** |
| Attempt 0 wall time | **57.3 s** |
| Whole request | 81.4 s |
| Who answered | `commandcode/z-ai/glm-5.3-flash`, attempt 1, 24.0 s |

**89 % of the 57 seconds the client waited was MCC sleeping**, on a model whose 429 arrives in
0.2 s, with `nvidia/nemotron-3-ultra-550b-a55b` — same provider, same three keys — sitting seven
slots down the same chain, never asked. Three minutes later that model answered `200` on key 0
with nothing changed but the clock.

## Mechanism

Three separate things each charged for the same 429, and the third is the one that hid the
sibling:

1. **`execute_with_retry` retried a 429 on the same key** with exponential backoff — 5 tries per
   key × 3 keys is the 15 tries and the 51 seconds.
2. **`failure_policy` installed a provider-wide reactive block** for the operator's whole 60 s
   cooldown, *in addition to* the rotation engine's own 60 s bench. The same cooldown, spent
   twice: once as a bench a router can step over, once as a sleep inside the credential that no
   router can see.
3. **A 5xx set that block too** (`status is not None`), so one bad gateway response throttled a
   credential provider-wide.

Reproduced live on an isolated server (see Verification): attempt 1, the healthy sibling on the
same provider, is recorded `skipped - cooldown` — killed by (2) — and the request fell through to
an entirely different provider 75 seconds in.

## The fix

**A 429 is answered by routing, not by waiting.** With `RATE_LIMIT_ROUTES_AROUND_MODEL` on (the
new default):

- The limiter re-raises on the first try — no sleep, no retry, no reactive block. The try is still
  recorded on the ladder, before any decision, exactly where it was.
- The pool benches the **(key, model)** pair, leaves the credential `HEALTHY`, and does **not**
  rotate. It raises `ModelRateLimited`, carrying the provider, the model, the key and the
  provider's own `rate_limit` `ExecutionFailure`.
- The executor prefers the next chain model on **that same provider** — a reordering of the
  positions `_prepare_from` already walks, not a second code path, so the cooldown step-over, the
  announcement and the preflight are untouched.
- With no such model on the chain, one **diagnostic probe** (16 output tokens, no tools, no
  system, on a model the operator already configured on that provider, on the key that just
  refused, bounded by a 5 s `asyncio.timeout` in the executor) decides:
  `200` → keep the scoped bench and continue the chain; `429` → promote to a whole-key bench and
  rotate, as 6.19.0 did; anything else → 6.19.0.
- The probe candidate comes from the operator's own routes only — `MODEL_HAIKU` → `MODEL_SONNET` →
  `MODEL` → `MODEL_FABLE` → `MODEL_OPUS` and their fallbacks — never the provider's `/models`
  catalogue, which is where hidden models and paid-tier surprises live. No configured route on
  that provider means no probe.

**Independent of the toggle:** 5xx and transport faults keep their same-key ladder (that is the
one failure a second knock can fix), with shipped `PROVIDER_RETRY_ATTEMPTS` **5 → 3**; a 5xx never
sets a reactive block; and the 60 s cooldown is applied once, as the pool's bench.

**Deadlines now measure time an upstream was actually listening.** New `core/waiting_clock.py`:
providers credit seconds they have *already* spent asleep, and `_next_chunk` re-arms its wait by
exactly that much. It is a **mutable holder** in a `ContextVar`, and that is load-bearing rather
than stylistic — the executor waits in a task of its own, a task gets a *copy* of the context, and
a bare float would be credited into the copy and never seen by the waiter. The whole-request
budget is **not** re-armed and clamps the re-arm, so nothing can outlive `FALLBACK_TOTAL_TIMEOUT`.
Direction is one-way, providers → executor: nothing tells a pool how long it may take, and
`core.attempt_budget` stays unimportable.

`.env.example` shipped `PROVIDER_RETRY_BACKOFF_MAX_SECONDS=60` while the constants, the manifest,
the README, `docs/USAGE.md` and `test_limit_bounds.py` all said `10` — a six-times-longer ladder
for anyone who started from the file the install instructions hand them. Fixed to `10`, with the
contract test that was missing.

## Pinned tests that changed

The three 429 retry-count tests are **parametrized** over the toggle, so the off-case keeps every
existing assertion verbatim as the documented off-switch. The manifest default and
`PROVIDER_RETRY_ATTEMPTS_DEFAULT` move together, with no new entry in
`DEFAULTS_THAT_DIFFER_FROM_THE_CODE`. Two changes the spec's survey did not anticipate, both
direct consequences of "a 5xx never sets a reactive block":

- `test_nvidia_nim_degraded_retry.py` ×2 asserted `extend_reactive_block` **is** called on a 529
  (a 5xx). Now `assert_not_called()` / `call_count == 0` — the stronger form of the new `T1`.
- `test_provider_runtime.py::test_create_provider_instantiates_each_builtin` pins the exact
  `ProviderRateLimiter(...)` call, which gained one keyword.

## Residual risks

- **The last-resort ladder has no backoff between its tries.** With one key and one configured
  model the executor spends `PROVIDER_RETRY_ATTEMPTS` tries so the case does not regress, but back
  to back: that client sees the same `rate_limit` error in 1.2 s instead of ~7 s. Against a
  60-second limit the sleep was never going to clear it, but it is a real difference.
- **`RouteExecutionPolicy` gained `rate_limit_attempts`**, fed from the existing
  `PROVIDER_RETRY_ATTEMPTS` (and forced to 1 when the toggle is off, so the ladder is not spent
  twice). No new setting, but the executor now reads a provider-shaped number.
- **The probe costs ~10 input + ≤16 output tokens**, at most once per chain position per request,
  and only when a rate-limited provider has no sibling on the chain. It is not cached: a verdict
  is a fact about one instant, and caching it re-invents the stale-bench problem this fixes.
- **`§5` is inert on a stock install.** All five `FALLBACK_*` deadlines still ship at `0`, so
  `_chunk_timeout` returns `None` and `_next_chunk` takes its fast path. It matters for the
  operator who sets a first-token deadline, and it is what makes recommending one honest again.
- **No dashboard screenshot.** The probe row's rendering is covered by a jsdom test against the
  real `admin.js` (`test_a_single_try_with_a_probe_still_shows_its_ladder`), not by an eye.
