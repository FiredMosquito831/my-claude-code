## Description

## What was wrong

4.33.0 replaced the full-scan percentile with a streamed cursor that stops once the highest needed rank has gone past. Measured properly, that is **1.5x (unfiltered) to 1.74x (provider-filtered)** the cost of the plain `fetchall()` it replaced — on identical results:

```
unfiltered                     streaming 265.3 ms   fetchall 175.2 ms   -> 1.51x
provider filter (~12.5k rows)  streaming 123.1 ms   fetchall  70.7 ms   -> 1.74x
```

Two reasons, both knowable in advance:

- **`p95` needs a rank near the end of the row count whatever the filter is**, so "stop early" has almost nothing to stop early from — the saving is on the last 5%.
- **`fetchall()` is one bulk C-level fetch** inside the `sqlite3` module; iterating the cursor pays a Python-level `__next__` per row. At 12.5k rows that overhead is the entire difference. The query plan is identical either way — only the Python-side consumption changed.

## The fix

`_percentiles` is now the same single query and single fetch the `_percentile` helper used, with p50 and p95 sharing one sorted list instead of two module-level calls. **It is not faster than 4.32.0**, and the docstring now says so along with why the two cleverer mechanisms lost, so nobody re-attempts them.

The rest of 4.33.0 stands and is where the actual wins are: the LRU-bounded stats cache, the capped breakdowns, and `pulse()` — the one that matters, because it stops the expensive query running at all when nothing changed.

## How this shipped, since the process failure is the interesting part

The end-to-end A/B I gated the release on **could not see it**. `stats()` takes 700–1400 ms on this machine with run-to-run swings of 2–4x; the regression is ~90 ms. It sat under the noise floor, and three alternating rounds showed the branch level-or-faster.

What found it was measuring **the disputed function alone, both implementations in one process, alternating order, asserting both return identical results first**. That comparison is unambiguous in 15 reps.

The whole-call benchmark is still necessary — it is what caught the `duration_ms` index that made `stats()` 2.2x slower by poisoning other queries' plans, which no microbenchmark would ever show. Neither replaces the other.

**Credit:** this was reported by the subagent that wrote the original change, after I had already merged and released it. I had dismissed the same concern on my own noisier numbers.
