## Description

First of four PRs from the fallback-chain audit. This one is the **instrument** — it makes the other three measurable rather than argued.

## The gap

The request log holds one row per request, so it can only ever name the model that **answered**. `route_attempt` is the index that won; `error_kind` is the *final* outcome. A request rescued by a fallback was therefore recorded as `status=success` with no trace of what it was rescued from.

Measured against 21 days of live traffic — **150,846 requests**:

```
attempt=1 from=commandcode/deepseek/deepseek-v4-pro   n=319  rows carrying any reason: 0
attempt=1 from=commandcode/meta/muse-spark-1.2        n=261  rows carrying any reason: 2
```

1,144 fallbacks succeeded. For the largest cohort the reason was recoverable from the database in **exactly zero** of them.

## What this adds

A `request_attempts` side table — one row per model the chain reached *or deliberately did not reach*:

```
attempt  outcome    model_ref                        kind            duration
0        failed     groq/definitely-not-a-real-model authentication  125 ms
1        failed     cerebras/also-not-real           authentication  214 ms
2        failed     groq/third-not-real              authentication   48 ms
```

**`skipped` is the row that pays for itself.** A three-model chain that only ever ran one was indistinguishable from a one-model route — so "the fallback did not help" and "the fallback was never asked" could not be told apart. Both reasons a model goes unreached are now named: benched by recent failures, or the budget was spent before its turn.

Surfaced in the request detail as a **ROUTE ATTEMPTS** panel: verdict, model, duration, error-kind badge, full reason.

## Design

- **A side table, not more columns.** The number of attempts is a property of the chain, not of the schema — and "attempt 2 never ran because the budget was gone" is a fact about an attempt that has no row on the request.
- **Verdicts are published once, when the chain settles.** An attempt verdict is never worth a database round trip while a client is waiting for tokens.
- **A new table, so `CREATE TABLE IF NOT EXISTS` is sufficient** — it is *columns on an existing table* that need an `ALTER`, and there are none here. Nothing to migrate.
- **Retention reaches it.** Attempts are deleted with the request they belong to, and by `clear`.
- Failures are named by their `FailureKind` where they carry one, so the attempt log has one vocabulary. The request row's own mixed `error_kind` is left alone here — that's PR 4.

## Verification

End to end against a **real server and real upstreams** (throwaway HOME, three deliberately-invalid models), read back through the admin API — three attempts, each with its own provider, model, duration, kind and message. Before this change that row carried `error_kind=authentication, route_attempt=2` and nothing else.

Guards mutation-tested, each failing **by name**:

| mutation | caught by |
| --- | --- |
| M1 a mid-stream failure recorded as success | `stream_that_dies_after_preflight` |
| M2 benched model indistinguishable from never-reached | `model_benched_by_recent_failures` |
| M3 only the winning attempt published | all five attempt tests |
| M4 `ExecutionFailure` named by class not kind | `execution_failure_is_named_by_its_kind` |
| M5 attempts never written to the database | `rescued_request_keeps_the_reason` |
| M6 retention leaves orphaned attempts | `attempts_are_deleted_with_the_request` |
| M7 attempt timing dropped | `stream_that_dies_after_preflight` |

**M1 and M7 initially survived**, and the tests were fixed rather than the finding dropped. M1: the rescued-request test fails at *preflight*, a different code path from a stream that dies *after* preflight, so the branch was uncovered. M7: the assertion was `(x or 0) >= 0`, which is true of `None`.

Local CI: `ruff format --check`, `ruff check`, `ty` clean; pytest **4,804 passed** with the documented 6 `test_install_ps1_*` baseline failures.

## Residual risks

- **`skipped/ejected` will read zero until the health registry outlives a request.** `MessagesHandler` — and with it the executor and its `RouteHealthRegistry` — is constructed per request in `routes.py`, so the 3-consecutive-failure threshold resets every time and nothing is ever benched. Confirmed live: four consecutive failures of the same model produced zero `MODEL CHAIN: skipping` lines. The source comment on `route_health_registry` predicts this exact failure. The recording here is correct and starts working the moment the lifetime is fixed; that fix belongs with the deadline work in PR 2.
- **Storage cost is unmeasured on a large database.** Rows are small (~120 bytes) and only written for multi-model routes, but I have not run it against the 903 MB live copy.
- The panel is hidden for single-attempt requests, so nothing changes for a route without a chain.
