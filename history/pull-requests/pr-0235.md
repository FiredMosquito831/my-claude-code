## Description

Analytics aggregates were computed by scanning `requests` (and `request_attempts`) once per figure. On the maintainer's 244,425-request / 766,124-attempt log an all-time call with local answers hidden measured **38.5 seconds**. This adds a pre-aggregated rollup, maintained on insert inside the writer's existing transaction, and serves the same payload from it.

## [Logic Altered]

**Three new tables, nine dimensions, one UTC hour of grain.** `request_stats_rollup` (21 additive counters), `request_stats_latency` (a 64-bucket log-spaced histogram) and `request_stats_detail` (the four "grouped list, LIMIT 10" facts, distinguished by `kind`). Keyed on `hour_epoch, is_local, provider, resolved_model, requested_model, status, endpoint, key_label, optimization` — every dimension `_where` can filter on, so no filter the dashboard can produce is unservable. SQL NULL is stored as the empty string. On the measured log that is ~33k rows against 244k, about 5 MB on a 2.28 GB file.

`requested_model` and `optimization` are dimensions because `_where` needs them: a model filter matches `resolved_model` **or** `requested_model`, and a `local:<rule>` provider key resolves to `provider IS NULL AND optimization = ?`. `status` stays a dimension of the *detail* table too — the spec dropped it, but a status filter genuinely restricts the fallback, diversion and upstream lists (only the error list implies its own status), and dropping it would make those three wrong under a status filter.

**Both attempt-level aggregates are rolled up.** `recovery` and `upstream_statuses` were 65% of the cost (19.9 s of 31.0 s in the design measurement) and read `request_attempts`, not `requests` — a rollup over `requests` alone could not have reached the acceptance bar. The recovery counters and the upstream status census are summed from the `RequestRecord`'s own attempt list in `_flush`'s in-memory batch, the same objects `_store_attempts` is writing in the same transaction; the attempts table is never re-read on insert.

`upstream.requests` is a distinct-request count that stays exact under `SUM` without a `DISTINCT`: a request lives in exactly one dimension bucket and contributes 1 per distinct upstream status it saw, so summing over buckets reproduces `COUNT(DISTINCT request_id)` grouped by status. That is the only non-obvious additivity claim in the design and it is commented at the site.

**Why maintenance-on-insert is sound.** One background writer thread owns one connection for its lifetime; requests only `enqueue`. `requests` rows are **never UPDATEd after insert on the live path** — the single `UPDATE requests` in `src/` is inside `compact_request_log`, which NULLs `input_text`/`output_text` after moving them to `request_bodies` and touches no rolled-up column. So no UPDATE hook is needed. The `_flush` insert is `INSERT OR REPLACE`, so `_existing_ids` already filters re-flushed records for `_accumulate_totals`; the rollup reuses **the same list**, hoisted to one local so the two aggregates provably see the same set. The rollup writes join `_flush`'s existing `with conn:`, so a failed batch rolls them back with the rows and the aggregate cannot drift ahead of the table it summarises.

**`is_local` is now a stored column, and the covering index is `_v4`.** `local=hide` was *slower* than `local=all` on every scan, because `NOT (provider IS NULL AND optimization IS NOT NULL)` references `optimization`, which `idx_requests_stats_v3` did not carry — SQLite abandoned the covering index and read the base table, and therefore the body overflow pages. `LOCAL_ANSWER_SQL` remains the single definition of the rule (it computes the column on insert and drives the chunked backfill); `_where` reads `LOCAL_ANSWER_COLUMN_SQL`. `idx_requests_stats_v4` leads on `is_local` and adds `optimization`; `_v3` is explicitly dropped, per the versioned-index rule.

**Known regression, disclosed:** `fallback_routes` on *raw rows* went 867 → 1047 ms in the design measurement, because `route_primary_model` is not covered by `_v4`. Accepted: that list is served from the rollup now, and the raw path only runs under `q=`, where the search predicate dominates anyway. `_v4` is deliberately **not** widened with the route columns — the `_percentiles` docstring records that an index leading on `duration_ms` made `stats()` 2.2× slower by confusing a planner with no `ANALYZE`.

**Percentiles are bucketed.** 64 log-spaced buckets from 1 ms to 30 min. This was chosen by measurement against 48 and 80 buckets: 64 holds all-time p50/p95/p99 error to ≤ 2.3% at 26k stored rows. The backfill uses `LN`, not `LOG` — SQLite's `LOG` is base 10, and using it against a natural-log step produced 94–99% percentile error in the design's first measurement pass. If a user's SQLite lacks `SQLITE_ENABLE_MATH_FUNCTIONS` the backfill falls back to a Python-side chunked pass and logs it, rather than silently mis-bucketing. `_percentiles` is kept unchanged and reachable — it is the live `q=` path, the live pre-backfill path, and the oracle the histogram is measured against.

**`served_from`.** The payload gains `"served_from": "rollup" | "rows"`. This is why the bump is MINOR. The dashboard reads nothing new. Free-text `q` is the only filter that forces the raw scan today — it is a correlated `EXISTS` over compressed bodies and is not a rollup dimension — along with any window before the one-time backfill marker lands.

**Window snapping.** One UTC hour is the finest grain, so a window that is not hour-aligned is rounded **outward** and the payload reports both bounds (`window.snapped_since` / `snapped_until`). The difference is real — on the measured log a 24 h p95 moves 20% between the requested and the snapped window — so it is stated rather than smoothed over. *Rejected alternative:* serving sub-hour windows from raw rows. Short windows are already fast (168 ms for 24 h before this change, and 24 h is the shortest window the UI offers), but a split rule would make `served_from` depend on the clock.

**Retention.** `prune` does **not** touch the rollup, exactly as it does not touch `request_totals` or `server_sessions`. That is what lets "all time" stay true on a capped table — and it means the rollup and a raw scan legitimately disagree once retention has bitten. Two existing tests encoded the old behaviour and were updated to assert both halves: the raw path still collapses to the surviving rows, the rollup keeps the pre-prune figure. `clear()` **does** wipe all three tables, because "clear log" is an explicit erase.

**Migration order** (all on the writer thread, none in `__init__`, none on a request path): `_ensure_stats_index` (drop `_v3`, create `_v4`) → `_ensure_is_local_backfill` (chunked, 5 000 rows per commit) → `_ensure_rollup_backfill` (chunked by 24 UTC hours, resumable) → `_ensure_totals_backfill` → `_ensure_auto_vacuum` → first flush. The rollup backfill records the hour it reached under `rollup_backfilled_through` and writes `rollup_backfilled_at` only on completion; a chunk is either wholly committed or wholly absent, so the resume marker is the *only* idempotence mechanism and a re-run with the completion marker present is a no-op. `stats()` serves from raw rows until that marker exists, so a half-built rollup is never read. Because the backfill runs before the first flush, there is no overlap with the live accumulator at all.

**The `requests` INSERT now has the 42/43 guard.** `_REQUEST_INSERT_COLUMNS` generates the column list, the placeholder list and a runtime width assertion, exactly as `_ATTEMPT_INSERT_COLUMNS` has done since a 43-column INSERT with 42 markers broke every write. The hand-written 44-column list and hand-written 44-`?` VALUES clause are gone.

## [Verification Method]

Everything below was measured on a **clone** of a `VACUUM INTO` copy of a real log — **244,425 requests / 766,124 attempts, 2.28 GB, 31 UTC days**. The live database was never opened except read-only; the clone was deleted afterwards.

### Acceptance: all-time `local=hide`

| | store `stats()` | endpoint `GET /admin/api/requests/stats?local=hide` on an isolated server |
|---|---|---|
| **before** (6.16.0) | **38,540.7 ms** | **36,789.9 ms** |
| **after** (this PR) | **134.8 ms** | **88.7 ms** cold / **16.0 ms** warm |
| | **286×** | **415×** |

Both runs answered `total = 240864`. **Acceptance bar was < 300 ms; measured 134.8 ms at the store and 88.7 ms end-to-end.**

Same isolated server (port **8199**, `HOME` redirected onto the clone, loopback `curl`); `netstat` checked before each start; port 8082 and `~/.fcc` never touched. Running 6.16.0 against the migrated clone re-created `idx_requests_stats_v3`; restarting 6.17.0 dropped it again and left only `_v4`, which is the versioning rule working on a real file.

## [Residual Risks]

1. **p50/p95 stop being exact.** Measured 0.87–1.26% on every all-time percentile of the real log, 3.0–4.2% on hour-aligned 24 h windows, and **11.5%** on the worst slice measured (`local=only`, 24 h, 1,183 sub-millisecond samples). It is worse on small samples by construction: with few observations there is nothing inside a 26%-wide log bucket to interpolate against. The exact path is kept and still pinned by `test_percentiles_match_old_interpolation_unfiltered_and_filtered`, repointed at `_stats_from_rows`; three other existing tests that asserted an exact percentile off `stats()` were repointed the same way rather than given a loose tolerance. README, USAGE and the in-dashboard Guide all say the cards are approximate.

2. **A window that is not hour-aligned is widened.** It can include up to 59 minutes of older traffic than asked for. Both bounds are in the payload, but nothing in the dashboard renders the difference yet. One existing test asserted that `since = now + 1000` returns nothing; under the snap it returns the current hour, and the test was moved to `now + 7200` with the reason written down. If exactness for short windows matters more than the snap, the alternative is on the table: serve anything under 48 h from raw rows and mark it `served_from: "rows"` — measured 444 ms in the design pass, above the 300 ms bar but only for short windows.

3. **The rollup and a raw scan legitimately disagree once retention has bitten.** That is the point — it is how "all time" stays true on a capped table — but it is a real behaviour change, and it changed two existing tests. A reader comparing the Analytics cards against a hand-written `SELECT` over `requests` on a pruned database will find the cards higher, and correctly so.

4. **Rollup drift when a column is added to `requests`.** The `_ROLLUP_ACKNOWLEDGED_COLUMNS` contract test is the mitigation and is the single most important test in this PR: any `PRAGMA table_info(requests)` change fails the suite until the author classifies the new column. Second line of defence is the equality contract, which compares every payload key. Neither catches a new *counter* added to the `totals` query that reads an already-acknowledged column — that one relies on the equality test noticing the mismatch, which it will, but only if the new key is in the payload both paths build.

5. **`SQLITE_ENABLE_MATH_FUNCTIONS` may be off** in a user's SQLite, so `LN` in the backfill can raise. Guarded: `_has_ln_function` probes it once and the backfill falls back to a Python-side chunked pass, with a log line. **UNVERIFIED** — the fallback path is exercised by no test and was not run against a real build without math functions; the interpreter in this checkout has `LN`, so only the fast path was measured. Reproducing it needs a SQLite built without the flag.

6. **`is_local` before its backfill finishes.** `DEFAULT 0` means a pre-existing local-answered row reads as upstream until the chunked UPDATE lands (measured 1.3 s for 3,561 rows here, but it scales with the local-answer count). During that window `local=hide` shows a few rows it should not. The migration order puts this backfill before the rollup backfill so the rollup is never built on wrong values.

7. **Two processes on one file.** Both new backfills catch `sqlite3.Error` and skip, treating a second process's marker as "already done" — the rule `_ensure_totals_backfill` already follows. The rollup backfill additionally resumes from `rollup_backfilled_through`, so a lost race costs at most a re-walk of one uncommitted chunk. Not exercised by a test; the failure mode if it were wrong is a doubled bucket, which the equality contract would catch on the affected window.

8. **Free-text stats is still slow, and now visibly so.** `q=` over a 24 h window measured 6.85 s end-to-end, and over the whole log it did not finish inside ten minutes — it re-runs the body-decompression scan once per aggregate, including inside the `request_id IN (SELECT id FROM requests <where>)` subqueries. This PR does not make it worse (the raw path is the old code, and `_v4` helps everything except `fallback_routes`), and per the decision on scope nothing was slowed to serve it. FTS5 is the real answer and is a separate change.

9. **Float summation order.** `avg_duration_ms` is now `SUM(duration_sum) / SUM(duration_count)` over buckets rather than a single `AVG(duration_ms)`, so the two sum in a different order. They matched exactly on all six real-database comparisons and across 102 synthetic filter combinations, but a value landing exactly on a 2-decimal rounding boundary could in principle round differently.

10. **`served_from` is a new public API field.** Additive, and the dashboard ignores unknown keys — the jsdom suite passes unchanged — but it is why this is MINOR rather than PATCH.

11. **The rollup never shrinks.** By design, like `request_totals`. At the measured traffic level that is roughly 1,000 rows a day across the three tables, a few MB a year, against a body store measured in gigabytes. Said plainly in the README so nobody is surprised by a table that only grows.
