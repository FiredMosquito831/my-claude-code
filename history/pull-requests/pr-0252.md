## Description

Two safety nets have quietly been OpenAI-chat-only since 6.5.0. Every provider that subclasses `BaseProvider` directly bypassed both, so the same 400 a *custom* provider recovered from was a hard failure on a first-party Anthropic key.

- **Reject-and-remember** (PR #221): a 400 that names the reasoning field → retry once without it, remember `(provider, model)`, relabel the Models page.
- **Learned output cap**: a 400 that states the host's own maximum → clamp, retry, and clamp proactively from then on.

`src/my_claude_code/providers/recovery/` is now the one implementation, and it knows no protocol.

## The ladder, per dialect

Rung order is unchanged: narrowest-and-most-certain first, generic reasoning strip **last** (a provider's own reasoning recovery is strictly the better one), unrecognised 400 → raise.

| # | Rung | OpenAI Chat Completions | Anthropic Messages | OpenAI Responses |
| --- | --- | --- | --- | --- |
| 1 | `output_cap` (may fire more than once) | `max_completion_tokens must be less than or equal to 40960` | `max_tokens: 100000 > 64000, which is the maximum allowed number of output tokens for claude-sonnet-4-5-20250929` | `max_output_tokens must be at most 100000` |
| 2 | `stream_usage` | SDK names `stream_options.include_usage` | — | — |
| 3 | `provider_specific` | NIM chat-template pair, DeepSeek `tool_choice`, Mistral reasoning | — | — |
| 4 | `reasoning_field` | any `is_reasoning_key` key the complaint names (`reasoning_effort`, `reasoning`, `chat_template_kwargs`, …) | `thinking: Extra inputs are not permitted`, `thinking.budget_tokens: Input should be greater than or equal to 1024` | `reasoning: Extra inputs are not permitted` |
| — | give up | `top_p is immutable for this model` → raised, thinking kept | `Invalid input` → raised | same |

Body keys are arguments, not branches: `max_completion_tokens`/`max_tokens` here, `max_tokens` there, `max_output_tokens` for Responses. The comparator phrasings are shared across all three, because a gateway may answer in any of them regardless of protocol.

## Echo safety, extended to the two siblings

A pydantic validation error echoes the whole submitted request back under `input`/`body`/`ctx`. Anything found there names a field *we sent*. `complaint.py` has pruned those keys since 6.12.0; `mistral/reasoning.py` and `deepseek/tool_choice.py` did not, so a forced-tool request was its own evidence and an echoed `reasoning_effort` read as a rejection. Both now take their words through the shared matcher, and `is_echo_key` is public so Mistral's own structured walk (it reads a pydantic `loc` path) prunes identically. **The rejection-phrase requirement that kept them from firing on shape is unchanged.**

## Persistence: deliberately not in this PR

Both memories stay **per process and per provider instance**. Nothing is written to `~/.fcc`. This is the documented behaviour, not an oversight: a host that was briefly misconfigured heals by itself on the next reload instead of staying blacklisted, at the cost of one 400 per model after a restart. Persisting it is not a one-file change — it needs a setting, an admin field, the two settings contract tests, a staleness policy and an eviction rule for a model whose deployment moved — so it stays a PART XII item rather than being smuggled in here. `docs/USAGE.md` now states the trade-off in the user's own words.

## Residual risks

- **A client-supplied `thinking` block still pays the 400 every time.** `MessagesRequest.thinking` reaches `build_anthropic_messages_body` through `model_dump`, so a learned refusal narrows *gating* but cannot stop a body the client itself asked for. The net recovers it on every request (two tries instead of one) rather than once. Pre-existing encoder behaviour, out of scope here; visible in the second-request log above.
- **Command Code's Anthropic half is unproven against a real cap 400.** This plan has no Claude model, so only the `Invalid input` shape was captured. Its cap wording is assumed to be Anthropic's, and the parser accepts every comparator phrasing to hedge that.
- **The Responses dialect has no output-cap rung.** Its encoder emits no output-token field, so the rung could not fire; adding it now would be dead code. `RESPONSES_OUTPUT_FIELDS` is exported and tested so wiring it is one line the day the encoder emits one.
- `is_bad_request` now also accepts `422` inside `parse_output_token_cap` (it previously took `400` only there). A 422 naming an output field with a stated maximum is a request-shape rejection by any reading; no existing test asserted otherwise.
- Memories are per provider *instance*, so a rotating pool learns once per credential rather than once per gateway. This preserves 6.5.0 behaviour exactly and avoids one key's misconfiguration teaching the others.
