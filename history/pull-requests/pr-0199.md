## Description

## What was broken

`src/my_claude_code/providers/chatgpt_oauth/` ignored the reasoning policy completely. A client sending `thinking: {type: "disabled"}`, or a route configured `reasoning=off`, still got reasoning at effort `"medium"` — on **100% of chatgpt_oauth traffic**. This provider serves `MODEL_VISION` and the first `MODEL_FALLBACK`, so it was live on every vision request.

## Mechanism

`build_chatgpt_oauth_request_body` had **no reasoning parameter at all**:

```python
def build_chatgpt_oauth_request_body(
    request: MessagesRequest,
    *,
    default_max_tokens: int | None = None,
) -> dict[str, Any]:
```

and both call sites in `provider.py` (`preflight_stream` ~183, `stream_response` ~232) dropped the fully-gated `ReasoningPolicy` they were handed:

```python
build_chatgpt_oauth_request_body(request)
```

so the reasoning block was a constant, emitted whenever a private helper matched the model id by string prefix:

```python
def _supports_reasoning(model: str) -> bool:
    name = model.lower()
    return name.startswith("gpt-5") or name.startswith("codex") or name.startswith("o")
```

`startswith("o")` matches **any** id beginning with the letter "o", and model-name branching for reasoning capability is explicitly forbidden by the project's architecture principles.

## What the fix does

- Adds a **required keyword-only `reasoning: ReasoningPolicy`** to `build_chatgpt_oauth_request_body`, and passes the real policy from **both** call sites.
- Encodes the policy in the Responses API dialect:
  - `ReasoningControl.OFF` → **no** `reasoning` block and **no** `include` key. Omission is the safe encoding; `effort: "none"` is not documented for every model this backend serves.
  - A named effort → `{"effort": <mapped>, "summary": "auto"}`.
  - Provider-default / unspecified → `effort: "medium"`, preserving today's behaviour so no user's default silently changes.
  - Whenever a block is emitted, `include: ["reasoning.encrypted_content"]` is kept — it is what makes stateless multi-turn reasoning work under `store: false`.
- Deletes `_supports_reasoning` and its call.

### Capability decision: rely on upstream gating (option b)

Not a models.dev lookup inside the encoder. The policy reaching a provider has **already** passed through `application/reasoning_gating.py::adapt_reasoning_policy`, which suppresses reasoning for models known not to support it and clamps efforts to the model's published vocabulary. Re-testing capability in the encoder would duplicate that decision and create a second source of truth. This also matches the project's layering: capability gating belongs to the application layer, wire encoding to the provider. No new name-prefix test was introduced.

### Effort mapping

| `ReasoningEffort` | sent as | note |
| --- | --- | --- |
| `minimal` | `minimal` | verbatim |
| `low` | `low` | verbatim |
| `medium` | `medium` | verbatim |
| `high` | `high` | verbatim |
| `xhigh` | `high` | **mapped down** — the Responses endpoint documents no named effort above `high` |
| `max` | `high` | **mapped down**, same reason |
| *(no effort named)* | `medium` | preserved default |
| `control=OFF` | *(block omitted)* | no `reasoning`, no `include` |

The narrowing mirrors `_LOW_MEDIUM_HIGH` in `providers/openai_chat/profiles.py`, which solves the same problem for chat-completions providers with a shorter vocabulary.

### Deliberately unchanged

`default_max_tokens` still sends no explicit output limit to the Codex/Responses endpoint — that is a separate concern and out of scope here.

## Residual risks

- **`xhigh`/`max` narrowing is a judgement call.** They are mapped to `high` rather than sent verbatim, checked against the published Responses API effort vocabulary, **not against a live ChatGPT/Codex OAuth key**. If the backend later accepts a higher named effort, this table is the one place to widen.
- **A provider-default policy still sends `effort: "medium"`.** That is deliberate (preserving current behaviour), but it means a hypothetical non-reasoning model that upstream gating did not catch — capability `None`, i.e. no models.dev row — would still receive a reasoning block. In practice the provider's own allowlist admits only GPT-5.4+/Codex models, all of which reason.
