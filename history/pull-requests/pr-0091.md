## Description

## What was broken

The deferred install path (Windows, when the app is already running) stages a verified wheel and spawns a detached helper to finish the install after the launchers exit. The helper invoked uv by placing a **command string** at statement position:

```powershell
$argumentsLiteral 2>&1 | Out-String | Out-Null
```

`$argumentsLiteral` was the string `` & 'C:\...\uv.exe' @('tool','install',...) ``. In PowerShell a statement-position string is treated as a **command name**, never executed — so uv never ran. The staged update silently installed nothing and the `mcc-*` commands were never created. The user saw "Update staged for after restart" with no error, then `mcc-claude` was "not recognized".

## The fix

The helper now emits the uv path and the argument array as real PowerShell values and calls uv through the call operator:

```powershell
$uvPath = '<...>'
$installArgs = @('tool','install','--force',...)
& $uvPath @$installArgs 2>&1 | Out-String | Out-Null
```

So once the launchers exit, the detached helper actually runs `uv tool install --force ... my-claude-code @ file:///...` and the `mcc-*` command family is created — the same outcome as the WSL/Linux direct path.

## Verification

- Reproduced the PowerShell bug: a string at statement position does not execute its inner command (the literal string was written, the command never ran).
- Ran the real `Start-DeferredInstall` against a stub `uv` with a live process: the detached helper invoked `uv tool install --force ... my-claude-code @ file:///...` after the process exited.
- Added an end-to-end regression test (`test_install_ps1_deferred_helper_runs_uv`) that loads the real function, points it at a stub uv, and asserts uv is invoked; plus a static guard asserting the helper uses `& $uvPath @$installArgs`. Both pass.
- Full installer test file: 3 new tests pass; the 6 pre-existing PS harness failures are identical on this branch and on unmodified `fork/main` (a checksum-fixture issue, out of scope).
