## Description

## What was broken

Every request left this proxy asking for the same **81,920** output tokens, whatever model it was routed to.

`core/anthropic/conversion.py` built the body with `max_tokens or default_max_tokens`, and the only `default_max_tokens` any profile ever passed was `ANTHROPIC_DEFAULT_MAX_OUTPUT_TOKENS = 81920` — a compile-time literal with no env var and no relation to any model. Nothing anywhere compared the client's `max_tokens` to what the routed model can actually emit: `ProviderManager.model_output_limit()`, built in #200, had exactly one consumer, and it was sizing the *reasoning* budget.

On this user's live routes that is wrong in both directions:

| routed model | real output limit | what was sent |
| --- | ---: | ---: |
| `nvidia_nim/minimaxai/minimax-m3` | 16,384 | 81,920 |
| `nvidia_nim/thinkingmachines/inkling` | 16,384 | 81,920 |
| `nous_portal/tencent/hy3:free` | 128,000 | 81,920 |
| `nous_portal/meituan/longcat-2.0:free` | 131,072 | 81,920 |
| `nous_portal/z-ai/glm-5.2:free` | 230,400 | 81,920 |

The first two get rejected or truncated by the provider. The last three had capacity thrown away for nothing. `max_tokens or default` also treated a client-sent `0` as unset.

## Mechanism

The rule is **WORKING-NOTES §54**:

```
requested <= model maximum  ->  send what was requested
requested >  model maximum  ->  send the MODEL'S MAXIMUM
unknown                     ->  fall back, and say so
```

New `application/output_tokens.py` makes the decision as four separately-named, separately-tested steps — clamp to the published limit, fall back when nothing published one, apply the operator's optional ceiling, bound by remaining context. They are deliberately *not* fused into one `min()`: that is how a fallback silently becomes a cap.

`core/` cannot look any of this up, so the plumbing follows the precedent v5.60.0 set for `reasoning_adaptation`:

1. `ModelRouter` resolves the inputs (published limit, context window, the three settings) into an `OutputTokenLimits` record carried on `RoutedMessagesRequest`.
2. `ProviderExecutor` finishes the job once the prompt has been counted — the context-headroom half needs that count — rebinding **every attempt**, not just the primary, to its own model's capacity. A fallback on a 16k model must not inherit a budget sized for the 262k model above it.
3. The value reaches `build_base_request_body` as the routed request's own `max_tokens`, so it works for every provider dialect at once. `OpenAIChatRequestPolicy.default_max_tokens` stays as the last-resort default for paths that never went through routing.

`core/anthropic/conversion.py` gains no lookup and no new dependency — only the `or` → `is None` fix.

## Non-obvious choices

- **`MAX_OUTPUT_TOKENS_CEILING` ships unset.** A ceiling that binds below a model's declared capability is the anti-pattern §54 forbids — it is what OpenCode does, and it silently caps a 262k model at 32k. It exists only as an opt-in runaway guard.
- **`MAX_OUTPUT_TOKENS_UNKNOWN_DEFAULT` never lowers an explicit client value.** A number nobody published has no standing to shrink an explicit request. The same reasoning already unset `NIM_MAX_TOKENS`.
- **Context headroom is not optional.** 1,117 of 7,440 models.dev entries report `limit.output == limit.context`; on those, asking for the full output leaves no room for the prompt. `MAX_OUTPUT_TOKENS_CONTEXT_MARGIN = 1024` covers the gap between FCC's own token count and the upstream tokenizer plus the provider's chat template, and is small against the smallest real window in the catalogue (4,096).
- **Headroom ≤ 0 leaves the request untouched.** Sending a zero or negative `max_tokens` turns "your prompt is too long" into "your request is malformed". The provider's own error names the real window better than a guess here can (LiteLLM does the same, deliberately).
- **Context length comes only from the provider's `/models`, never models.dev.** A resold deployment's window is routinely smaller than the originating vendor's, and overstating it produces a budget that does not fit.
- **The reactive cap learned from a 400 still wins.** `_apply_learned_output_cap` runs last and only ever lowers, so ground truth about *this deployment* beats a published claim about the model. It never raises a smaller catalogue value: "at most N" does not contradict a value below N.
- **Token counting stays after preflight.** An existing test pins that ordering, and a request that cannot be converted at all should not pay for tokenization first.

## Clamping precedence

```
1. limit    = provider /models  ->  models.dev  ->  cross-provider modal  (from #200)
2. clamp    client max_tokens (IS NOT NONE, not falsy) down to limit      -> WARNING
3. fallback MAX_OUTPUT_TOKENS_UNKNOWN_DEFAULT, only when both are absent
4. ceiling  MAX_OUTPUT_TOKENS_CEILING, if the operator set one           -> WARNING
5. context  min(budget, context_length - input_tokens - margin), if > 0  -> WARNING
6. learned  provider's own 400 cap, applied in the provider, lowers only
```

## Residual risks

- `context_length` is only as good as what a gateway publishes on `/models`. A provider that overstates it will produce a budget that still does not fit; the request then fails at the provider with its own error, which is what happened before this PR too.
- The 1,024-token margin is a judgement call. It is generous for a small prompt and thin if an upstream chat template is unusually large; it is env-configurable (`MAX_OUTPUT_TOKENS_CONTEXT_MARGIN`) precisely because no single number is right everywhere.
- The learned output cap is still per-process and lost on restart, so the first request after a restart to a provider that under-reports its limit still pays one 400. Noted, deliberately out of scope.
- `max_tokens: 0` is now forwarded verbatim instead of being replaced. That is the correct reading of the client's intent, but a client that sent `0` by accident will now see the provider's error rather than a silent 81,920.

## Deliberately not done

- No reasoning/thinking budget change. PR3 owns the budget-vs-answer reconciliation; subtracting an answer floor here would collide with it.
- `chatgpt_oauth` still sends no `max_tokens` (documented behaviour, left alone).
- Making the learned output cap durable across restarts.
