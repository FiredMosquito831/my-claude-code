### What was invisible

1. **A host answering with the deprecated `delta.function_call` shape.** The
   Chat door's chunk reader has always decoded the field (`chunks.py`'s
   `_DELTA_FIELDS` declares it) and no provider code has ever read it, so a
   call arriving that way would reach the client as nothing at all and the
   reply would look exactly like a model that stopped by itself. The
   investigation's blind spot U3 was not "a counter fired zero" — it was "no
   counter existed".
2. **"It said it would keep reading and stopped."** Measurable until now only
   by joining the client's transcripts to the log by hand: 9.3 % of
   main-thread in-loop turns on `opencode_go/muse-spark-1.3-contributor`
   against 1.1 % on `opencode_go/deepseek-v4.1-flash` — same door, same day,
   same client.

### The derivation, in full

**In-loop** = the request immediately preceding this one in the same thread
ended with at least one tool call. The thread is `session_id` plus `agent_id`:
a subagent speaks in its own transcript and its turns interleave with the main
thread's while it runs, so both are required. `session_id` arrived in 7.42.0,
so no older row is in any thread here; a client that states no session id is
outside the population entirely.

**Ended with text only** = the turn called no tool (`tool_call_count` is
written NULL, never 0, when a turn called no tool) and delivered visible text
(`output_chars > 0`). The predicate reads both spellings of "none" so a future
writer that starts storing the zero cannot silently zero the count.

Only successes are counted; failed and cancelled requests stay in the sequence
their neighbours are read against, because treating one as absent would make
the turn after it follow a tool call two turns back. Turns whose text length
was never recorded are counted apart (`unmeasured_turns`): unknown is neither
"text" nor "no text".

Two approximations, stated rather than hidden, both of which read low: a
thread's first turn inside the window has no predecessor inside it; and a
client that interleaves requests of its own in one thread puts one between a
tool call and the turn that consumed it.

### Why the Models page payload does not move

The brief preferred the design that leaves the pinned equality baseline alone,
and `/admin/api/requests/latency` set that precedent in 7.5.0. The count
changes with every logged request and is fetched beside the page instead.
`test_7_115_1_adds_a_route_beside_the_page` names every entry a page change
would have moved and finds each byte-identical; the browser scenario reads the
model-row keys out of the payload the page actually received to prove no
in-loop field is in it.
