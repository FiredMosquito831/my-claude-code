## What was actually broken

`ReasoningPolicy.on()` — control ON with the effort discarded — is not an edge case. It is exactly what gating's `_drop_controls` and its toggle-only branch both return, so it is the policy that reaches the encoder on every route whose models.dev row publishes no effort control. **Command Code's encoder had no path for it**, so gating logged *"REASONING LEVEL DROPPED: ... enabling thinking"* while the body that left carried no reasoning instruction at all.

**1. `NamedEffortReasoning` with no `enabled_value` has nothing to emit.** Command Code was wired that way in 5.69.0, deliberately: the note said a bare request already reasons the most, so naming a rung would *reduce* reasoning. A live A/B refutes it (identical prompt, `max_tokens: 3000`, real User-Agent, HTTP status checked):

```
commandcode  deepseek/deepseek-v4-flash  bare  200  reasoning_tokens=132
commandcode  deepseek/deepseek-v4-flash  max   200  reasoning_tokens=1046
commandcode  xiaomi/mimo-v2.5            bare  200  reasoning_tokens=7
commandcode  xiaomi/mimo-v2.5            max   200  reasoning_tokens=17
```

Eight times the thinking, not less. Fixed: `enabled_value="max"`.

**2. `ReasoningControl.ADAPTIVE` was investigated and is NOT a defect — hypothesis refuted.** Outside `anthropic_messages` it has no encoder anywhere, and adaptive therefore encodes byte-identically to "no opinion" on 20 of 41 profiles and on NVIDIA NIM. That is a *stated product decision*, not an oversight: adaptive names no effort and no budget, so there is nothing honest for a level-only encoder to send, and `tests/application/test_adaptive_reasoning.py` pins it (`test_non_anthropic_providers_emit_no_new_field_for_adaptive`, `test_adaptive_is_never_translated_into_a_fabricated_control`). The `_mandatory_off_rewrite` path that substitutes adaptive is correct for the same reason — a model that *cannot* run with thinking disabled reasons by default, so sending nothing is exactly what makes the request succeed where the OFF would have 400'd. An earlier revision of this PR made every enable-channel encoder emit for adaptive; it broke 9 of those tests and was reverted. Reported here rather than silently dropped, because the original brief flagged it as a likely bug.

Also note the client path: Claude Code's `thinking: {type: "adaptive"}` never reaches `ReasoningControl.ADAPTIVE` at all — `application/reasoning.py` maps it to `ReasoningControl.ON`. So the operator's `client=adaptive` requests were always control ON, and defect 1 above is the whole of what they hit.

**3. OpenCode is the exact inverse of Command Code, and must not be "fixed" the same way.** Same probe:

```
opencode  hy3-free        bare     200  reasoning_tokens=3000
opencode  hy3-free        max      200  reasoning_tokens=903
opencode  hy3-free        minimal  200  reasoning_tokens=836
opencode  hy3-free        none     200  reasoning_tokens=0
opencode  mimo-v2.5-free  bare     200  reasoning_chars=317
opencode  mimo-v2.5-free  max      400  Upstream request failed: [400] Invalid request parameters
opencode  mimo-v2.5-free  minimal  400  Upstream request failed: [400] Invalid request parameters
```

Naming any rung reduces reasoning, **and the gateway validates the enum but forwards the field to the model**, which rejects it outright on `mimo-v2.5-free` while a bare request returns 200 and reasons. So OpenCode's `reasoning_effort` is safe *only* behind the per-model capability gate that already stands in front of it, and it deliberately gains no `enabled_value`. Recorded next to the encoder with the numbers, and pinned by a test.

## Scope: the metadata-driven encoder selector is NOT in this PR

The addendum asks for encoder selection derived from a metadata ladder (`supported_parameters` -> models.dev `reasoning_options` -> the profile's declared encoder) across all ~56 providers. **That is the right design and this PR does not build it.** Landing it safely needs a seam that does not exist yet, and half-building it would leave dead configuration that reads as live — the exact failure mode 5.70.0's audit exists to prevent.

Proposed split, with the seam already located:

- **This PR (5.71.0):** the diagnosis above, the one wire defect it proves, and registry-wide tests that make the *class* of bug fail loudly for any profile added later.
- **Next PR, the selector.** `OpenAIChatProfile.apply_reasoning` already receives the `MessagesRequest` (whose `.model` is the provider model id by then) and `build_openai_chat_request_body` already receives `provider_id`, so the encode call site can consult a per-`(provider, model)` dialect **without touching the `Provider` protocol**. Inject a `reasoning_dialect_lookup` callable from `provider_manager` alongside the existing `reasoning_capability_lookup`, resolving:
  1. provider `/models` `supported_parameters` (already on `ProviderModelInfo` since #200) — `reasoning_effort` -> named-effort, `reasoning` -> reasoning-object, a thinking/budget field -> its encoder;
  2. models.dev `reasoning_options` type (`effort` / `toggle` / `budget_tokens`), via the same tiered read `resolve_model_reasoning_capability` already performs;
  3. the profile's declared encoder, unchanged, whenever both are silent — which keeps every body byte-identical where metadata says nothing;

  and surfacing the chosen dialect **and its source tier** on the Models page the way 5.68.1 surfaced limit tiers.

  Two findings from this PR the selector must respect, and that argue for doing it separately rather than quickly: **capability and dialect are different questions** (`opencode/mimo-v2.5-free` is a model models.dev says reasons, on a host that 400s the reasoning parameter), and **more control is not more reasoning** — on OpenCode, emitting the parameter the metadata authorises *costs* 70% of the thinking. A selector that only asked "does this host accept the field" would ship that regression across the roster.

## Residual risks

- **`commandcode`'s `enabled_value="max"` is a behaviour change on real traffic.** Every Command Code model whose models.dev row publishes no effort control now receives `reasoning_effort: "max"` where it previously received nothing. Probed 200-with-more-reasoning on `xiaomi/mimo-v2.5` and `deepseek/deepseek-v4-flash`; the gateway validates the enum itself (`invalid_request_error` on `param: reasoning_effort`) rather than forwarding it upstream, which is what makes this safe where the same change would be unsafe on OpenCode. `minimax/minimax-m3-free` could not be re-probed (upstream 503 at the time); it has no reasoning channel under any dialect regardless.
- `opencode/mimo-v2.5-free` still sends no reasoning instruction. That is the correct outcome, not a gap.
- `commandcode/minimax/minimax-m3-free` now sends `reasoning_effort: "max"` and **will still not reason** — verified live across five dialects and every rung in 5.69.0. It is the model, not the wiring.
