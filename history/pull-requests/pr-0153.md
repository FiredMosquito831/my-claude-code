## Description

## What was broken

Every admin save rewrote `~/.fcc/.env` with **54 empty `FCC_SMOKE_*` keys** under a `# Smoke Tests` header — 13% of a 414-line file.

Measured by executing the writer, not by reading it:

```
total KEY=VALUE lines written : 414
FCC_SMOKE_* lines written     :  54
share of file that is smoke   : 13.0%
```

Confirmed present in a real user's live 420-line `.env`, header at line 366.

## Mechanism

The manifest registered a `smoke` section with 54 `ConfigFieldSpec` entries, and `render_env_file` iterates **all** `FIELDS` unconditionally. No view in `admin.js` claims that section (`grep -i smoke admin.js` → **0 hits**), so the fields rendered nowhere while still being written to disk on every save. Nothing in `src/` reads them either — only `smoke/` tooling does, straight from `os.environ`.

## Why this is two changes, not one

Retiring them from the manifest **alone would have made things worse**.

`unmanaged_env_values()` preserves an unmanaged key only when `key in settings_env_aliases()`. These are not Settings fields — that is the whole finding. So a user who had actually set `FCC_SMOKE_MODEL_OPENAI=gpt-4o-mini` to run smoke tests would have had that value **silently deleted** on their next save. Same "a form must not delete what it cannot see" bug class this project already fixed once.

So:

1. **Remove** the `smoke` section and its 54 fields from the admin manifest. The smoke tooling is untouched and keeps reading `os.environ`.
2. **Widen** `unmanaged_env_values()`: also preserve keys under the project's own `FCC_` prefix when they hold a **non-empty** value, even though no Settings alias reads them. Empty values still drop, so existing files self-clean. Non-`FCC_` keys keep the strict rule, so genuinely retired options still retire.

The now-dead `"smoke"` entry in `KNOWN_UNRENDERED` is removed too — leaving it would keep a permanent blind spot in the guard that exists to catch exactly this.

`.env.example` **keeps** its smoke block deliberately: those are still real, settable env vars, just no longer admin-managed.

## Residual risks

**Existing files self-clean on the next save, not on upgrade.** Users keep their 54 empty lines until they next press Apply in the dashboard. That is deliberate — rewriting someone's `.env` on upgrade is a bigger and riskier action than this fix warrants.

The widened preserve rule is scoped to the `FCC_` prefix, so it cannot resurrect unrelated third-party env vars. A populated `FCC_` key that is genuinely retired in future will now survive where it previously would have been dropped — an accepted trade for not destroying user configuration.
